# Detection check: cases

One entry per (introducing PR -> fix PR) pair. How the sample was built and what the counts mean is in
[report.md](report.md); the full candidate list is in [candidates.md](candidates.md).

Each entry answers four questions about the introducing PR, judged from the record as it stood then:

- **A. Did a rule already cover it?** Guides read at the introducing PR's first parent. `covered-loaded` = a guide
  ClawSweeper loads (root `AGENTS.md` plus every ancestor `AGENTS.md` of a changed path) states the rule, directly
  or by making a named doc section binding. `covered-unloaded` = only a guide ClawSweeper does not load states it.
  `rule-added-after` = a later commit added a rule that describes it. `no-rule` = nothing specific; broad
  principles that match are listed as "generic only" and do not count.
- **B. What did ClawSweeper say?** Every version of its review comment, recovered from GitHub's edit history.
  "Flagged" needs the same trigger and the same wrong outcome as the later fix.
- **C. Could the rule be checked from the diff?** Only for cases with a rule. "Guard" = whether a `scripts/check-*`
  script at the parent already targets that rule.
- **D. Regression test.** Whether the fix PR says its new test fails before the fix (the PR's claim, not verified).

**Group.** `core` = a confirmed regression that a user could have hit. `set aside` = the pairing is doubtful, or no
user could have seen a failure; these are kept for transparency but not counted in the report's headline split.

Classification was done by reading source and the public GitHub record. No code, tests or builds were run.
Permalinks to rules are pinned to the parent commit. ClawSweeper review links point to one comment that the bot
edits in place, so the entry names the version time that holds the quoted text.
