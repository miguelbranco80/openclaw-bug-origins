## The bug (from the fix-origins reader)
- Origin: regression (confidence medium)
- Fix: fix(ui): keep selected slash argument when selecting text (#194087)
- What the user saw: After highlighting a slash-command argument such as `ultra` and selecting text with the keyboard, the highlight jumped back to the first entry and Tab completed `default` instead.
- What the fix does: The slash argument menu now remembers the highlighted argument while the same argument draft stays active, instead of resetting to index 0 when a refresh reopens it.
- What in the causing PR was wrong: In handleSelect it added `updateSlashMenu(target.value, state, slashMenuHost, requestUpdate);`, so every native textarea select event re-ran the args branch, which sets `state.slashMenuIndex = 0`.
- Reasoning: The reset-to-0 in the args branch predates the graft (it is in chat-composer-slash-menu.ts at b14a2cae4bf6), but before 2026-08-26 the composer's select handler only refreshed the skill menu, so text selection never re-ran the slash args branch. GraphQL blame at the graft attributes the `updateSlashMenu` call in handleSelect to f8550bc11d4d (#122425), whose diff adds that line; from then on native select events reset the highlighted argument. Medium because I did not confirm the pre-August keyboard path end to end; the sibling command-mode fix #193758 the day before shows the same select-event reset.
