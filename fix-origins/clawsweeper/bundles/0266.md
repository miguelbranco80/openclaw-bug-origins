## The bug (from the fix-origins reader)
- Origin: never-worked (confidence low)
- Fix: fix: keep the mobile chat keyboard open on the first tap (#201163)
- What the user saw: On mobile web chat, tapping the message box opened the keyboard and immediately dismissed it, so it took several taps to start typing.
- What the fix does: Adds a capture-phase mousedown guard that prevents the default focus transfer when a tap that started on the editor is retargeted to another element after the keyboard moves the composer.
- What in the causing PR was wrong: b77c6de added `pointerOrigin.focus({ preventScroll: true });` in the composer's pointerdown handler so the keyboard opens mid-tap, but guarded only the later click (from #176498), not Chrome's compatibility mousedown that lands on the moved composer and blurs the editor.
- Reasoning: The click-only retarget guard was introduced with the mobile composer gesture handling in 1bc029e (#176498), and b77c6de (#181021) began focusing the editor during pointerdown so the keyboard opens before touchend, which is what moves the composer under the finger before Chrome's compatibility mousedown. Before b77c6de the first tap did not open the keyboard at all (that PR's own report), so the one-tap flow never worked end to end on this path; I could not verify Chrome Android behavior at each step, hence low confidence. ee465500 only generalized the textarea checks to the new editor and did not change the mechanism.
