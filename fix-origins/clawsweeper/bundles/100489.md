- What the user saw: A long-running agent turn could stop after another temporary rate limit despite making progress between failures, and the final error could show only the provider's short retry hint.
- What the fix does: The fix gives the agent a fresh retry budget after each completed model response, bounds retries without progress, and reports retry exhaustion in the final reply.

- Reasoning: I checked the parent of #134281 and confirmed that the ChatGPT transport retried HTTP 429s with a fresh counter for each request, so earlier recoveries did not spend the next request's budget. #134281 moved that accounting into the embedded run and removed the consecutive rate-limit counter reset. #151610 later reset the outage timer on completed responses while explicitly retaining the accumulated retry count.

- 2026-09-01T04:28:21Z obviyus: ## Compatibility decision: `retry.provider.maxRetries`

ClawSweeper asked for an intentional compatibility contract on the one remaining merge risk. Recording it here as the maintainer decision, matching the recommended option (**accept centralized budget semantics**).

**The contract:** `retry.provider.maxRetries` keeps its name, type, and meaning — the attempt budget for transient same-model retries. What changes is the owner: the budget is now spent by the failover retry controller (`src/agents/embedded-agent-runner/run/failover-retry-controller.ts:153`) instead of by per-request SDK retries. Saved values are retained as-is; there is no migration, no doctor repair, and no config-shape change.

**What an operator observes:** the budget is bounded by the existing 90-second transient-retry window with exponential backoff capped at 30s (`src/agents/embedded-agent-runner/run/helpers.ts:44-47`). A saved value larger than what fits in that window — `7`, for example — degrades to however many attempts fit, rather than an unbounded wait. That is the intended outcome: one bounded budget shared across rate-limit, overload, server-error, and timeout reasons, ending in a visible failure instead of a long silent stall.

**Why this rather than preserving the old semantics:** the pre-change behavior had no single owner. Each reason retried independently at the SDK layer, so total wall-clock time was unbounded and unobservable, and the same transient failure could be retried several times 
- 2026-09-01T04:53:32Z obviyus: ## Retry-window decision

The 90s transient-retry window stays flat. `retry.provider.maxRetries` is now the transient-retry attempt budget owned by `createEmbeddedRunFailoverRetryController`.

The window bounds time-to-failover, not attempt count. When `maybeRetryTransient` returns false, `src/agents/embedded-agent-runner/run/assistant-failover.ts:137-153` falls through to profile rotation, model fallback, or a visible error. That is better recovery than extending same-model retries against a slow provider. At the default budget of 3, backoff totals roughly 3.5–10.5s (1s base, 0.5–1.5x jitter, 30s cap), so the window binds only when requests are slow. Scaling it with the budget would delay failover and worsen the worst case.

The real defect was silent truncation. Commit `7d7d6a5e8a2` now records the retry count and budget at the controller producer. `src/agents/embedded-agent-runner/run/failover-retry-controller.test.ts` covers `records the truncation when the window ends a budget that still has attempts`.

This is not a breaking change. A saved `retry.provider.maxRetries` keeps a coherent role: it was the per-SDK-request retry count, and it is now the transient-retry attempt budget for one controller. Before this PR, the value reached only the provider SDK and multiplied against a separate hardcoded controller retry of 3; it never reached OpenClaw's own retry owner.
