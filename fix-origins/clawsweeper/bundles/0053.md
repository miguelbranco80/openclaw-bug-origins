# Rank 53: fix #191538 <- cause #159891

## The bug (from the fix-origins reader)
- Origin: regression (confidence high)
- Fix: fix(ui): Android agent browser says tab unavailable after a cold start (#191538)
- What the user saw: Opening the agent browser focus page cold (e.g. from the Android app) showed 'Couldn't load browser: This tab is no longer available' instead of the live startup tab.
- What the fix does: BrowserDocument now passes its fixed tab as a referenced tab (sessionTabs) so the session-scoped tab list includes an untracked reused startup tab.
- What in the causing PR was wrong: browser-panel-operation-ownership.ts began binding every non-dashboard panel with a sessionKey to `() => ({ sessionKey, referencedTabs: this.host.sessionTabs ?? [] })`, so GET /tabs became session-filtered, while only the chat pane was updated to pass `.sessionTabs` and the focus page (sessionKey + fixedTab, no sessionTabs) sent an empty reference list.
- Reasoning: The focus-page browser panel predates #159891 (ec00e5842d3b moved it out of app-root.ts with `.sessionKey` and `.fixedTab` but no sessionTabs), and before #159891 GET /tabs was unscoped so the fixed tab was always listed. #159891 (b9c242dd) added Gateway-side session tab filtering for any panel with a sessionKey, with referenced tabs only supplied by the chat pane, which drops an untracked startup tab from the focus page's list; the fix PR itself names #159891 as the scoping change.

## Human comments and reviews between the first ClawSweeper review and the merge
- 2026-09-27T21:33:43Z steipete: Maintainer response to the ClawSweeper review:

**[P1] Tabs opened from a panel before session tracking** — accepted as intended behavior, not adding recovery. The point of this change is that a session's panel lists only tabs with a known relationship to that session (opened by its agent or its panel, or used by its conversation). Tabs a panel opened before this change carry no recorded owner, so the Gateway cannot tell which session they belonged to; guessing would re-leak tabs across sessions, which is the bug being fixed. Nothing is closed or lost: those tabs stay open, the agent can still list and use them with the browser tool, and they appear in the Browser dock outside chat sessions. Agent-opened tabs were already tracked before this change and keep showing in their session's panel after updating. The docs now state this upgrade behavior (`docs/tools/browser/profiles.md`), and the PR body's User Impact section calls it out.

**[P2] Cleanup contract in the configuration guide** — fixed: `docs/tools/browser/configuration.md` now says session cleanup covers browser-tool opens and tabs opened from that session's Browser panel.

The failing `checks-ui-e2e` assertions expected the pre-change `/tabs/open` envelope without `tabScope`; the follow-up commit updates those expectations to the exact scoped envelope.
