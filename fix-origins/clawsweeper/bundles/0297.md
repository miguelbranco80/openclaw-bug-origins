# Rank 297: fix #200433 <- cause #198245

## The bug (from the fix-origins reader)
- Origin: never-worked (confidence medium)
- Fix: fix(queue): end queued input only on a recorded cause (#200433)
- What the user saw: With an access-policy plugin, a message queued during a brief policy outage was dropped as withheld (earlier silently cancelled) and never ran after the policy recovered.
- What the fix does: Authority owners now abort their signal when assertCurrent finds a real revocation, and queue/mailbox/steer readers end custody only on recorded abort, retirement, cancellation or consumption instead of on any failed check, deleting isFollowupOperatorAuthorityCurrent.
- What in the causing PR was wrong: It made policy outages non-terminal only inside the authority owners (`if (!isOperatorAuthorityUnavailable(error)) { revoked = true; ... }` while still `throw error`), leaving the queue readers that treat any `assertCurrent()` throw as lost authority unchanged.
- Reasoning: The followup runner's catch-all (`try { assertCurrent() } catch { operatorAuthorityLost = true }`, present since at least the Oct 18 controller refactor) was correct while every assertCurrent failure meant revocation; #198245 introduced the non-revoking 'policy unavailable' error and taught only the owners about it, so outage survival for queued input never worked from that commit (#198729 later patched some steer/mailbox readers but not the followup runner or drain). It could also be read as latent with #198245 as trigger, hence medium confidence.
