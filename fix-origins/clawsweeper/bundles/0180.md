## The bug (from the fix-origins reader)
- Origin: never-worked (confidence medium)
- Fix: fix(anthropic): cancelled Claude login checks orphan Claude Code's refresh lock (#197032)
- What the user saw: The first Claude CLI turn after an idle period stalled about 10 seconds or failed with 'another Claude Code process is refreshing it or exited mid-refresh'.
- What the fix does: The Claude CLI auth probe no longer forwards the caller's abort signal to the child process; a cancelled caller waits for `claude auth status` to exit on its own, so Claude Code's OAuth refresh lock is released.
- What in the causing PR was wrong: #137071 made probeClaudeCliAuthStatus async and cancellable, passing `signal: params?.signal` with `killProcessTree: true` to runUtf8CommandWithTimeout, so a cancelled caller SIGTERM/SIGKILLs `claude auth status` mid-refresh.
- Reasoning: The removed line `signal: params?.signal` blames to 2640154 (#137071), whose diff shows it replacing a synchronous spawnSync probe (no caller cancellation, SIGTERM-only timeout) with the async cancellable runner, so the cancel-kill path shipped with the defect. Medium rather than high because the failure also depends on Claude Code's `auth status` refreshing tokens under a lock, which I could not confirm existed at that time (if it came later this would lean latent).
