## The bug (from the fix-origins reader)
- Origin: regression (confidence high)
- Fix: fix(cron): retain cleanup work after cancellation (#170264)
- What the user saw: An operator could see an `Async work scope is closed` warning after cancelling a cron run whose cleanup was still pending.
- What the fix does: The fix registers the core-and-webhook promise with `trackAsyncWork` so delayed cleanup can finish after cancellation returns.
- What in the causing PR was wrong: The added `const running = runWithGatewayDetachedWorkContinuation(` wrapped `launchCronRun` in a scope that could drain as soon as the launch returned a cancellation result, while the untracked core-and-webhook promise was still pending.
- Reasoning: The parent already supported early cancellation, and its scheduled tick ran through `runInDetachedAsyncContext`, so returning from the run did not close a per-launch async-work scope beneath cleanup. I checked that the host-launcher diff placed that same cancellation race inside a fresh scope whose owner drains when tracked work finishes. The fix's inverse test reproduced the failure when delayed cleanup tried to register work after the scope closed.
