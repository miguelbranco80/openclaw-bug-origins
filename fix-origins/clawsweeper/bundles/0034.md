# Rank 34: fix #192017 <- cause #169214

## The bug (from the fix-origins reader)
- Origin: never-worked (confidence medium)
- Fix: fix(workboard): recover after database connection loss (#192017)
- What the user saw: With the experimental PostgreSQL engine, after one lost database connection every later Workboard request kept failing with 'PostgreSQL connection lost; transaction rolled back'.
- What the fix does: Adds an assertSettled check to the Workboard kernel (transaction usable, connection open, no open transaction) and exposes it through the worker backend's existing settlement hook so a dead connection is retired and reopened on the next request.
- What in the causing PR was wrong: The PostgreSQL engine's loseConnection marks the connection `isOpen = false` and throws 'PostgreSQL connection lost; transaction rolled back', while the same commit's Workboard worker wraps execution in `kernel.withWriteTransaction(() => execute(command))` and its catch only returns `{ ok: false, failure: encodeWorkboardSqliteFailure(error) }`, never reporting the dead connection to the worker runtime.
- Reasoning: The connection-lost error and the Workboard PostgreSQL path both arrived in 5e78ec6 (#169214); the generic worker settlement hook (backend.assertSettled) already existed since #149901 but Workboard's backend never supplied it, and its catch swallowed the failure into a structured reply. The fix's regression replay fails on the base and nothing shows the PG recovery ever worked, so this shipped with the engine; medium because intervening worker refactors (#170138, #172615) were not read line by line.
