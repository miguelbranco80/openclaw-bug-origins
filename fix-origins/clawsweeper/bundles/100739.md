# Rank 100739: fix #171805 <- cause #170467

## The bug (from the fix-origins reader)
- Origin: never-worked (confidence high)
- Fix: fix: Gateway repeatedly rebuilds directory watches above 256 agents (#171805)
- What the user saw: Operators with more than 256 distinct agent directories saw a less responsive Gateway as repeated scans tore down and rebuilt filesystem watches.
- What the fix does: The fix sizes the prepared-path cache to the registered fleet, avoids full observer scans on routine watch changes, and limits per-agent startup directory preparation to the selected owner.
- What in the causing PR was wrong: The initial watch cache used `if (preparedPaths.size <= 256)` as its eviction stop condition, then called `oldest.close()` on evicted entries, so a fleet with more than 256 distinct directories could never retain all its watches between walks.
- Reasoning: The parent resolved directory identities directly, and PR #170467 introduced watch-backed reuse with the 256-entry FIFO cap in the same diff, so reuse across larger fleets was broken from its first release. I also checked that PR #171318 later added full observer scans when rescheduling recovery, which amplified the cost of the existing watch churn. The fix's test covers repeat walks at 64, 256, and 810 agents and checks for zero watch creation, watch closure, and realpath calls on the repeat walk.
