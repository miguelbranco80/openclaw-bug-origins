## The bug (from the fix-origins reader)
- Origin: regression (confidence high)
- Fix: fix(cron): prevent overlapping retries after execution timeouts (#189469)
- What the user saw: A cron job could start a retry while its timed-out execution was still running.
- What the fix does: The fix records the timeout once, keeps the receipt active until the original execution settles, and then allows the scheduled retry to proceed.
- What in the causing PR was wrong: The refactor removed `if (!policy.deferredReceiptIds.includes(terminal.handle.receiptId))` and called `finishCronRunReceiptInDatabase` for every accepted outcome with a receipt, releasing the retry guard as soon as the timeout was recorded.
- Reasoning: The parent already supported timeout retries, and its finalizer deferred closing receipts while the underlying execution was pending. A test in the parent asserted that a timed-out run kept its receipt active and blocked a second execution until settlement. The refactor removed settlement tracking and closed the receipt when it recorded the timeout, removing the admission guard before the runner had settled.
