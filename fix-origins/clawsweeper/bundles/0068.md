- What the user saw: Leftover SQLite snapshot copies from Doctor and triage piled up in new ~/Library/Caches/openclaw/sqlite-<hash>/ directories (49 GB on one host) and were never reclaimed.
- What the fix does: resolveSnapshotStagingRoot reuses the enclosing sqlite-<24 hex> namespace when the resolved state directory lies inside one, so Doctor/triage snapshot copies stay in the installation's swept namespace.
- What in the causing PR was wrong: c16858baa256 added `const installation = createHash("sha256").update(resolveStateDir(env))...` and `path.join(admittedRoot, `sqlite-${installation}`)`, so snapshots taken while Doctor points OPENCLAW_STATE_DIR at its throwaway private copy land in a fresh per-run namespace the Gateway sweep never visits.
- Reasoning: Per-installation namespaces and their automatic reclamation were introduced together in c16858baa256 (#192368, two days before the fix); before it no namespace existed and staging was operator-owned. That commit hashed resolveStateDir(env), which in the Doctor lint context is the private copy's path, so the reclamation feature never covered snapshots taken there and each run created a new namespace; the defect shipped with the feature.
