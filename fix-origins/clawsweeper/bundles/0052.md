- What the user saw: `openclaw config set` reported success while replacing malformed UTF-8 in a config file and saving the altered bytes in its recovery backup.
- What the fix does: The fix validates UTF-8 in the root config and its includes before ordinary writes stage backups or replace a file.
- What in the causing PR was wrong: The commit replaced byte-for-byte backups with `await handle.writeFile(params.previousRaw, "utf8");`, which saves the already-decoded replacement characters in place of the original malformed bytes.
- Reasoning: I checked the causing diff against its parent and confirmed that root backups previously used `copyFile` and include backups used `readBytes`, so both preserved the original bytes even when a save rewrote malformed text. The commit switched both writers to staging backups from decoded strings, which made the original malformed bytes unrecoverable from the new backup.
