- Origin: regression (confidence medium)
- Fix: fix(update): ride out a briefly locked state database during updates (#168210)
- What the user saw: An update could abort during runtime preparation if another process held the shared SQLite write lock while the updater tried to record progress.
- What the fix does: The fix makes update history bookkeeping warn and continue on SQLite contention, gives required CLI writes more time to acquire the lock, and invalidates cached schema admission after Doctor runs.
- What in the causing PR was wrong: The new `progress.onStepStart?.(retentionStep);` call immediately before `await retainRuntime(...)` made runtime preparation depend on a diagnostic history write that could throw when SQLite was busy.
- Reasoning: The parent already retained the running updater runtime without writing a receipt at that point. The added progress callback wrote synchronously to the ledger and rethrew failures after the default SQLite lock wait, so the same failure path existed before the move to worker-backed writes. I checked that #168409 changed history retention and exposed a classification bug in the in-flight fix, while the original lock failure follows from the earlier callback and ledger code.
