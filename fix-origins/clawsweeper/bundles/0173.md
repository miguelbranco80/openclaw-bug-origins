## The bug (from the fix-origins reader)
- Origin: regression (confidence high)
- Fix: fix(msteams): allowlisted Teams senders and channels are ignored after an unrelated config reload (#186334)
- What the user saw: After an unrelated config hot reload, allowlisted Teams DM and group senders (and name-keyed team/channel entries) stopped getting replies until the Teams channel restarted.
- What the fix does: The Teams handler config reader now keeps startup-resolved allowFrom, groupAllowFrom and teams across reloads while those raw allowlist inputs are unchanged.
- What in the causing PR was wrong: The new createMSTeamsHandlerConfigReader reads from the raw `deps.accountPolicyCfg` and, for the default account, returns `(lastProjection = current)` on any reload, replacing the startup-resolved allowlists that the handler previously kept via `createRuntimeConfigReader(cfg)` on the resolved config.
- Reasoning: Before 19ac11902cdc the message handler used `createRuntimeConfigReader(cfg)` on the startup-resolved config, which does not follow the runtime snapshot when it differs, so resolved allowlists lived for the channel's lifetime. 19ac11902cdc (multi-account support) switched to a reader over the raw accountPolicyCfg that returns raw `current` after a reload for the default account, dropping resolved identities; the PR's main-vs-2026.10.8 runs confirm the earlier release worked.
