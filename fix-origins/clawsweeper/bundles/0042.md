# Rank 42: fix #201011 <- cause #165608

## The bug (from the fix-origins reader)
- Origin: never-worked (confidence medium)
- Fix: fix(gateway): separate chat-send run time from preparation (#201011)
- What the user saw: Operators saw slow chat send logs such as `preparation=476386ms` for a steered send that was acknowledged in 51 ms, when the time was actually a full agent turn.
- What the fix does: Adds a `run` phase to chat-send diagnostics and switches the dispatch scope to it while reply.run_prepared_reply runs, so prepared-reply execution is no longer reported as preparation.
- What in the causing PR was wrong: The new dispatch timing scope marks `phase?.mark("preparation")` in onSessionPrepared and only ends diagnostics in onAgentRunStart or after the whole dispatch settles, so a steered send that runs a prepared reply without the start callback books the run as preparation.
- Reasoning: The phase accounting, the onSessionPrepared preparation mark and the onAgentRunStart cutoff all arrive in #165608, while the steered queued-followup path predates it, so steered sends misattributed run time from the moment the timing shipped; #169006 only relabeled the stage as `steer`. Confidence is medium because I did not confirm that the reply.run_prepared_reply span was emitted on that path at #165608 time.
