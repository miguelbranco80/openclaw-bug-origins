## The bug (from the fix-origins reader)
- Origin: regression (confidence medium)
- Fix: fix(macos): prevent first-launch Gateway failures after upgrades (#191436)
- What the user saw: After upgrading, the macOS app's first launch could fail to start the Gateway because it launched the old seeded Gateway against state already migrated past that Gateway's supported schema.
- What the fix does: The native `doctor --client-credentials` path now also runs the daemon runtime-pin migration (even when credentials are already ready), so runtime intent is no longer left migrationPending after the schema advances.
- What in the causing PR was wrong: It made the bundled macOS app run `ClientCredentialStartup.prepare(...)` (the narrow `doctor --client-credentials`) before Gateway startup, and that path calls `prepareOpenClawStateDatabaseSchema({ env }, "doctor")` to advance shared schema without completing the daemon runtime-pin migration.
- Reasoning: The Swift side preserving the old seed while the runtime pin is migrationPending dates from b87a1abdad5 (#172703, 2026-10-15); the later 5f40d22a366 (#178998, 2026-10-21) added pre-start native credential preparation that migrates the shared schema via doctor without the pin handoff, so the preserved old Gateway now meets a too-new schema. Medium because I confirmed the schema-advancing call and the new app startup hook in 5f40d22a's diff but did not independently verify that upgraded first launches succeeded before it; it could also be read as never-worked of the auto credential migration feature.
