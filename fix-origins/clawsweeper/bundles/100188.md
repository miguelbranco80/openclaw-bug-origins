- Fix: fix(update): allow database rollback after WAL checkpoints (#162599)
- What the user saw: After an interrupted Windows update, OpenClaw could report “Databases changed after snapshot capture” and refuse both database and package rollback even though no newer data had been committed.
- What the fix does: The fix compares committed SQLite pages and retained WAL commit evidence so checkpoint-only changes no longer block rollback.
- What in the causing PR was wrong: The diff added `await prepareOpenClawStateDatabaseRemoval(databasePath, assertCurrent)` before the generation check, and that probe's Windows branch calls `close()`, which can checkpoint the WAL and invalidate the physical fingerprint.
- Reasoning: I checked the original rollback implementation and the coordination change: the earlier path used separate coordinator databases, so a pending WAL that stayed stable through admission passed the existing generation check. The later diff made Windows rollback open and close the live database before that check, and the fix PR identifies that close as the checkpoint in the failing sequence. The original comparison was already sensitive to ordinary checkpoints, and the earlier Windows behavior was verified by source inspection only.
