# Rank 273: fix #200787 <- cause #196662

## The bug (from the fix-origins reader)
- Origin: regression (confidence medium)
- Fix: fix(sandbox): reduce filesystem stalls after commands (#200787)
- What the user saw: On a btrfs host running sandboxed agents in large workspaces, the Gateway stalled: SQLite waits of 9 to 19.6 seconds and RPC p99 of about 52 seconds while command checkpoints created and deleted filesystem snapshots.
- What the fix does: Changed sandbox command checkpoints now pause the guest and capture directly into an immutable Git result, removing the per-checkpoint btrfs snapshot creation and retirement and the size/duration snapshot selector.
- What in the causing PR was wrong: #196662 replaced 'Changed checkpoints still pause through capture and publication' with btrfs checkpoints that 'take a filesystem snapshot, then resume', adding `prepareLocalWorkspaceCheckpointCapture`/`removeLocalWorkspaceCheckpointCapture` to every changed command checkpoint in runLocalWorkspaceProjection.
- Reasoning: Before 10d67445fbe, changed checkpoints paused and captured directly, which is the state this fix restores. That commit introduced a btrfs snapshot plus recursive removal for every changed checkpoint, and per the fix PR each snapshot forces a filesystem-wide btrfs transaction commit that stalled Gateway SQLite in production. d7f90ec35cf (#196727, retire captures, select snapshots only for large or slow trees) and 8ff37a6828b (#198128, skip the freeze) tuned the same path but kept snapshots for exactly the large workspaces that stalled. Medium confidence: the stall mechanism depends on btrfs kernel behavior and production timings I could not verify, and the fix is framed as an owner-accepted trade-off (about 290 ms of extra guest pause) rather than a pure bug fix.
