- [ ] **Allow retry after a completed refresh produces no card update (P2)** - If a standalone refresh finishes normally without calling `progress_card`, chat dispatch caches `status: "ok"` while the saved revision remains unchanged. After the UI times out, Retry reuses the same idempotency key; chat admission replays that cached result, and this adapter converts it to `accepted` again. No new work starts, so the advertised retry cannot recover while that result remains cached. Distinguish confirmed terminal no-update outcomes from running requests and permit a new intent only after terminal ownership is established; an accepted steer alone must not be treated as finished.

Retrying only replays the existing refresh request and reconciles the stale cached card here; it issues no new read, and the deduplicated request emits no replacement change event. The UI therefore keeps timing out despite the successful saved update. Make explicit retry reconcile through a fresh authoritative read while preserving request deduplication.
