## The bug (from the fix-origins reader)
- Origin: regression (confidence low)
- Fix: fix: resume persisted requests when transcript metadata advances (#201477)
- What the user saw: A persisted user request sometimes failed to start because another writer appended transcript metadata at the same moment, and the user had to resend the unchanged message.
- What the fix does: Moved the one-shot refresh-and-readmit retry from the final consumption path into the shared readCurrentTurn, so initial persisted-turn preparation also recovers from a benign concurrent transcript append while keeping the original entry ID and generation.
- What in the causing PR was wrong: #165367 rewrote the initial readCurrentTurn to admit through readSessionTranscriptAnchorsAsync with `...(prepared ? { contextValidation: { version: prepared.version } } : {})` and `throw new Error("Persisted user turn changed before replay admission")`, where before the initial read only reloaded and selected the turn without a version check.
- Reasoning: In #165367's diff the old initial read (`reloadPersistedTranscriptAsync` and then prepare) had no transcript-version validation; the new one validates the prepared version inside the reader snapshot, which opens the selection-to-admission race. #181473 later added a retry only to the final consumption path. Confidence is low because many later commits (#166804, #167238, #167662, #197510) reworked these readers, and the fix names the current failure as a SessionTranscriptReadFenceError, which I did not trace to a single commit.
