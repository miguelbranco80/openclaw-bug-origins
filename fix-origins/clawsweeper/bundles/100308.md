# Rank 100308: fix #153910 <- cause #131370

## The bug (from the fix-origins reader)
- Origin: never-worked (confidence high)
- Fix: fix(goals): recover unconfirmed controls after reconnects (#153910)
- What the user saw: After a lost reply, operators could be left unsure whether a Goal change took effect, and a committed Clear could remove the control they needed to check.
- What the fix does: The fix preserves unconfirmed Goal requests across reconnects and reloads, adds a Check outcome action, and keeps committed changes successful when notifications fail.
- What in the causing PR was wrong: The new controller declared `const goalOperations = new WeakMap<ChatHost, GoalOperation>();` and wired Clear to `actions.onGoalAction?.(goal.id, "clear")`, so reloading discarded the retry identity and a committed Clear could remove the control needed to retry.
- Reasoning: I checked the introducing diff and the subsequent history of the Goal controller and Gateway handler. The original direct controls kept retry identity only in memory and tied retry to the original action, so a reload or disappearance of that action could strand recovery from launch. The original Gateway handler also called `emitSessionsChanged` after committing and before replying, allowing a notification exception to turn committed success into a reported failure before the later event-worker refactor.
