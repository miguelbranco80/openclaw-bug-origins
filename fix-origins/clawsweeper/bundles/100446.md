## The bug (from the fix-origins reader)
- Origin: regression (confidence high)
- Fix: fix(auto-reply): message-tool replies from Slack threads post at the channel root on CLI runtimes (#160751)
- What the user saw: When a CLI agent used the message tool without specifying a thread ID, its reply appeared at the Slack channel root instead of in the thread where the turn began.
- What the fix does: The fix makes CLI message-tool sends use the channel adapter’s thread target and reply mode when the adapter requires replies to stay in the originating thread.
- What in the causing PR was wrong: The CLI runner added `replyToMode: turn.followupRun.originatingReplyToMode ?? turn.sessionCtx.ReplyToMode`, passing Slack’s raw `off` through the MCP grant and overriding the message tool’s thread-aware default.
- Reasoning: In the causing commit’s parent, the CLI path already carried the originating Slack thread ID through the MCP grant, and the message tool defaulted to `all` when it had a thread ID and no supplied reply mode. The causing diff forwarded the raw `off` value end to end, bypassing that fallback and causing Slack’s same-channel auto-thread resolver to omit the thread ID.
