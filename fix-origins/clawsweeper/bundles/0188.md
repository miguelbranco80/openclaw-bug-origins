## The bug (from the fix-origins reader)
- Origin: regression (confidence medium)
- Fix: fix(cron): scheduled session failures lose their cause (#195901)
- What the user saw: A failed scheduled session-target cron job showed only 'Session event execution failed' in run history and lastError, with the real cause (for example a missing account binding and its repair command) only in the Gateway log.
- What the fix does: The generic 'Session event execution failed' text is now only a placeholder, and the failed operation's recorded cause wins for the run record and job lastError.
- What in the causing PR was wrong: #178764 moved scheduled session agent turns off the cron isolated-agent runner onto session admission, whose onTerminal sets `failure ??= deliveryEvidence?.meta?.error?.message || ... || `Session event execution ${outcome}``, so a thrown failure with no delivery evidence records the generic text before the operation's real cause can.
- Reasoning: The generic-first fallback pattern came from 753a7a57be1 (#167113, immediate notifications), but scheduled session-target cron jobs only reached it when #178764 (3d2f7ca06b2) routed them through session admission and removed their isolated-agent run path, which records the real cause (the fix says isolated jobs 'already do'). I read the #178764 onTerminal diff and the fix-parent handoff code; I did not confirm that pre-#178764 session-target jobs recorded the cause for this exact thrown-refusal case, so medium rather than high.
