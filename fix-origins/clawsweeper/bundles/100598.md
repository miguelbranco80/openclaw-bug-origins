- What the user saw: An operator could open update confirmation for one Gateway, switch Gateways, and confirm an update that ran on the replacement Gateway.
- What the fix does: The fix binds update confirmations and native-decline fallbacks to their original Gateway and profile, and rechecks administrator access before native dispatch.
- What in the causing PR was wrong: The introducing diff wired the confirmation to `startGatewayUpdate: () => void this.context.overlays.runUpdate()`, which selected the connected Gateway when the operator confirmed.
- Reasoning: I checked the original confirmation diff and its overlay implementation: the dialog displayed update details captured at opening, while `runUpdate()` selected `gateway.snapshot.client` at dispatch. Gateway switching already existed, and the prior Updates action dispatched immediately, so the stale-confirmation window shipped with the dialog. I also checked the later Inbox change, which introduced a separate path for the same wrong-target outcome by moving native-decline fallback to an application-wide handler that used the current Gateway.
