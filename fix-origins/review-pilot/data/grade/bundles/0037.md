# Case 37

## The bug that later had to be fixed
- What the user saw: On btrfs, `openclaw doctor --fix` refused to rewrite agent stores with 'store files are open (pids: <Doctor's own PID>)', and rerunning hit the same refusal.
- What the later fix did: Doctor's NOCOW repair now asks every worker pool to close retained agent-store readers for the stores it is about to rewrite, reporting a close failure as a warning.
- What in the reviewed change was wrong: The memory search worker switched from `opened.database.close()` after each request to `retainOpenClawAgentDatabaseReadOnly(target)` with `opened.claim.release()` ('the database owner retains the idle reader'), leaving agent-store descriptors open in Doctor's process.
- Why: The offline NOCOW repair for agent stores worked after #161501 (ed25898341c), when the memory search worker opened and closed its read-only connection per request. #170183 (3c9ece47b31) changed the worker to retain an idle reader per agent store and only release the borrow, so Doctor's own memory-status checks left descriptors that fuser attributes to Doctor and the main-thread drain cannot close; the fix's native trace names exactly those retained readers.

### Reviewer C (2 findings)
1. **Retained search reader skips persisted corruption quarantine on every request after the first** — `extensions/memory-core/src/memory/manager-search.worker.ts`:137 (confidence low)
   Previously every keyword/curated/index-state/vector request opened a fresh connection through openOpenClawAgentDatabaseReadOnly, which runs revalidateAgentDatabaseTerminalOpen and readOpenClawDatabaseQuarantineFailure and throws when the database has been quarantined as corrupt. With retainOpenClawAgentDatabaseReadOnly the cached scope reuses its idle reader and only calls assertAgentDatabaseTerminalOpenAllowed, whose latch is a per-thread global singleton that the search worker thread does not register. Once the Gateway (another thread) quarantines a damaged memory/agent database, the search worker keeps serving recall and search results from the quarantined file instead of failing with the quarantine error; because each recall turn refreshes the idle timer, under steady traffic this can last indefinitely.
2. **Failed search keeps its broken connection for later requests** — `extensions/memory-core/src/memory/manager-search.worker.ts`:216 (confidence low)
   The finally block always just releases the borrow, even when the request threw (e.g. SqliteSchemaMismatchError 'schema admission changed; retry the request', SQLITE_CORRUPT, or an I/O error). The cached scope's own read() path discards the connection on error for exactly this reason, but retain() has no such handling, so the next search request on that worker reuses the same connection and can fail the same way, whereas the old per-request open recovered on the next request.

### Reviewer F (1 findings)
1. **Warmed memory readers bypass newly recorded quarantine** — `extensions/memory-core/src/memory/manager-search.worker.ts`:137 (confidence high)
   If a search worker has already opened an agent database and the Gateway verifier then quarantines that same file, a queued curated recall request can still return snippets from it. The verifier closes handles and sets the terminal latch in the Gateway isolate. The worker keeps its own handle and checks only the file identity and its worker-local latch when borrowing it again. If the corruption is outside the memory tables, the curated query can succeed and supply snippets to automatic recall even after quarantine has been recorded. The previous fresh-open path checked the persisted quarantine before running the query.
