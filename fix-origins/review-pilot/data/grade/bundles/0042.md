# Case 42

## The bug that later had to be fixed
- What the user saw: Operators saw slow chat send logs such as `preparation=476386ms` for a steered send that was acknowledged in 51 ms, when the time was actually a full agent turn.
- What the later fix did: Adds a `run` phase to chat-send diagnostics and switches the dispatch scope to it while reply.run_prepared_reply runs, so prepared-reply execution is no longer reported as preparation.
- What in the reviewed change was wrong: The new dispatch timing scope marks `phase?.mark("preparation")` in onSessionPrepared and only ends diagnostics in onAgentRunStart or after the whole dispatch settles, so a steered send that runs a prepared reply without the start callback books the run as preparation.
- Why: The phase accounting, the onSessionPrepared preparation mark and the onAgentRunStart cutoff all arrive in #165608, while the steered queued-followup path predates it, so steered sends misattributed run time from the moment the timing shipped; #169006 only relabeled the stage as `steer`. Confidence is medium because I did not confirm that the reply.run_prepared_reply span was emitted on that path at #165608 time.

### Reviewer C (1 findings)
1. **Cancellation cannot interrupt deferred skill preparation** — `src/gateway/server-methods/chat-send-agent-dispatch.ts`:302 (confidence high)
   If skill-library session creation or authoring stalls after the send is acknowledged, `chat.abort` marks the run canceled but cannot interrupt either await. The canceled run retains its reply-admission ticket until preparation eventually returns, so later sends to the session can receive `status: "started"` yet remain blocked indefinitely behind work the user already canceled.

### Reviewer D (5 findings)
1. **A cancelled steer can keep influencing the backing run** — `src/gateway/server-methods/chat-send-agent-dispatch.ts`:253 (confidence high)
   An active runtime accepts a steer, the Gateway acknowledges it, and the user aborts the steer before its transcript commit is confirmed. If the runtime has already consumed the steer and cannot withdraw it, it returns an accepted but unconfirmed outcome. The new work-admission check throws on the source abort before injection finalization can stop the backing run. The user sees the steer as cancelled while the backing run can continue using its text.
2. **Skill preparation can lose an acknowledged first message** — `src/gateway/server-methods/chat-send-agent-dispatch.ts`:302 (confidence high)
   When an attributed user sends the first ordinary message to a session key with no stored row, the Gateway can return `status: started` without staging the input or committing a transcript receipt. If skill selection then fails, for example because a concurrent library edit invalidates the read, dispatch never reaches session initialization. The error fallback requires an existing session row or a prepared initial row, so the user gets a run error and their acknowledged message is missing from history. Previously this selection failure rejected the request before acknowledgement.
3. **An accepted steer blocks later follow-up admission** — `src/gateway/server-methods/chat-send-handler.ts`:581 (confidence high)
   The handler reserves a FIFO ticket even after the active runtime has accepted a steer. If that runtime is still inside a long tool call, it can take up to two minutes to confirm the steer in the transcript. A subsequent `queueMode: followup` send can receive `status: started` but remain blocked outside the follow-up queue until the steer settles. Before the change, accepted steers did not take a reply-admission ticket, so the follow-up could be queued while the active run was still working.
4. **Aborting skill preparation leaves later sends blocked** — `src/gateway/server-methods/chat-send-agent-dispatch.ts`:700 (confidence high)
   If a skill-library read stalls after acknowledgement and the user aborts that run, the Gateway publishes the abort but the read has no run abort signal and the FIFO ticket is released only when dispatch unwinds. A subsequent send to the same session can be acknowledged and finish its own preparation, yet still wait for the cancelled run's read to return or time out.
5. **Slow-send diagnostics miss WebSocket work before the handler** — `src/gateway/server-methods.ts`:282 (confidence high)
   WebSocket requests resolve `expectedProfileId` and may wait for transport admission before calling `handleGatewayRequest`. The new timer starts inside that call. If either earlier step takes several seconds and the handler responds in under a second, the operator sees a slow acknowledgement with no `slow chat send` request record, and the new phase metrics omit the delay.

### Reviewer E (1 findings)
1. **Cancelled preparation keeps later sends blocked** — `src/gateway/server-methods/chat-send-agent-dispatch.ts`:700 (confidence high)
   If skill selection or authoring preparation stalls, the user can successfully abort the acknowledged run, but its admission ticket remains held until preparation returns. Neither preparation await observes the abort signal, and the ticket is released only when dispatch settles. A subsequent message in the same session therefore waits behind the cancelled run, even if its own preparation completes. Stop cannot unblock the conversation while the original preparation remains stalled.
