# Case 229

## The bug that later had to be fixed
- What the user saw: On a Windows npm-global install, every managed update rolled back during candidate Doctor with 'Plugin dependency is outside the temporary update copy' for the staged package's own typebox dependency.
- What the later fix did: Lets candidate Doctor accept dependency targets of private plugin copies that resolve into the canonical staged candidate package (in addition to the private rehearsal root), while plugin entries and repair writes stay private-only.
- What in the reviewed change was wrong: The new rehearsal check added `if (isPathInside(privateRoot, reference.source) && isPrivateLookup(reference.specifier)) { assertPrivate(reference.target); }`, where assertPrivate accepts only targets inside the private rehearsal root, so dependencies reached through host links into the staged candidate package are rejected.
- Why: Blame of every removed assertPrivate line points to 3c34fff (#146616), which created update-candidate-plugin-repair.ts and the private-only target assertion; at that commit update-candidate-plugin-tree.ts already projected host links to the candidate root (`relocations.push({ sourceRoot: host, destinationRoot: candidateRoot })`, `hostLinks`), so the conflict existed from the start. Medium because I did not confirm that the dependency inspection at 3c34fff traversed host-link files the same way as at the fix parent (it was later made async in #188787).

## Reviewers' findings
### Reviewer A (2 findings)
1. **Missing bare imports are omitted from repair discovery** — `src/plugins/plugin-generation-source-inspection.ts`:78 (confidence high)
   When a published-driver snapshot lacks a hoisted package imported by name, captureModule returns undefined because that package cannot be found in the private tree. Since local is false, the inspector records no unresolved reference. completeUpdateCandidatePluginRehearsal consequently skips recovery even when the original package remains available, and candidate validation still fails with MODULE_NOT_FOUND. This occurs with custom plugins using an ancestor's node_modules dependency without declaring it in their own manifest.
2. **Sibling modules lose their explicitly referenced assets** — `src/plugins/plugin-generation-source-inspection.ts`:53 (confidence high)
   If a plugin imports ../shared/helper.js and that helper reads new URL('./data.json', import.meta.url), the inspector captures helper.js but discards its asset reference. External helpers are captured selectively, so data.json never enters the copy plan. The private snapshot then fails with ENOENT when the helper reads the asset, despite both files being available in the original tree.

### Reviewer B (1 findings)
1. **Realpathing file locators loses the configured plugin ID** — `src/infra/update-candidate-plugins.ts`:352 (confidence high)
   For a manifestless file plugin loaded through an in-directory symlink such as `my-id.ts -> implementation.ts`, with `plugins.allow: ["my-id"]`, discovery normally identifies the plugin as `my-id`. This code instead discovers the real target, identifies it as `implementation`, and treats it as disabled, so its sibling imports outside the containing directory are omitted from the snapshot. Candidate Doctor/runtime then fails with a module-not-found error even though the enabled source plugin works.

### Reviewer C (1 findings)
1. **Missing bare-package imports never trigger snapshot repair** — `src/plugins/plugin-generation-source-inspection.ts`:78 (confidence high)
   A custom plugin can import a hoisted workspace package that is installed in an ancestor node_modules directory but not declared in the plugin's own manifest. The published updater omits that dependency. In the copied snapshot, captureModule returns undefined for the missing bare-package import, but this condition records only relative or absolute imports as unresolved. completeUpdateCandidatePluginRehearsal therefore treats the snapshot as complete and skips recovery, even when the original package is available and unchanged. Candidate Doctor or the canary subsequently fails with MODULE_NOT_FOUND.

### Reviewer D (5 findings)
1. **Plugin inspection fills the temporary volume before capacity selection** — `src/infra/update-candidate-plugins.ts`:349 (confidence high)
   If an operator sets TMPDIR to a small volume and an enabled plugin imports a dependency with a large data payload, inventory now materializes that dependency on the temporary volume before reporting its size. The worker can fail with ENOSPC before the updater gets a chance to select the state volume, even when that volume has ample space for the rehearsal.
2. **An unusable Doctor contract can now block the entire update** — `src/infra/update-candidate-plugin-repair.ts`:116 (confidence high)
   A disabled custom plugin can still have a declared Doctor contract. If that contract imports a package alias whose imports target is invalid, such as a target starting with ../, the new inspection propagates ERR_INVALID_PACKAGE_TARGET and aborts candidate Doctor. Previously Doctor caught the contract load failure and continued, so the disabled plugin could remain installed during an update.
3. **Repair rejects imports through the staged OpenClaw host link** — `src/infra/update-candidate-plugin-repair.ts`:121 (confidence high)
   A plugin that imports a host module by a relative path through its node_modules/openclaw link worked in a published-driver snapshot because the copier points that link at the staged candidate. Repair resolves the import to the staged host outside the private state directory and rejects it as an escape, blocking the update even when the snapshot is complete.
4. **Relative imports break when they cross the managed state projection** — `src/infra/update-candidate-plugins.ts`:360 (confidence high)
   If a plugin at STATE/extensions/demo imports ../../shared/value.mjs from STATE/shared, inventory finds the helper but places it under candidate-plugins while the plugin is copied to REHEARSAL/extensions/demo. The unchanged import looks in REHEARSAL/shared, so the plugin still fails to load despite the helper being copied.
5. **Sibling imports lose symlink names outside the plugin directory** — `src/plugins/plugin-generation-source-inspection.ts`:73 (confidence high)
   If a plugin imports ../shared/value.mjs and that path is a symlink to ../lib/value.mjs, inspection returns the canonical file without the sibling symlink. Neither the fresh copy nor published-snapshot repair creates shared/value.mjs in the rehearsal, so the original module specifier still fails to resolve.

### Reviewer F (2 findings)
1. **Update preparation now aborts when any plugin's source cannot be statically inspected** — `src/infra/update-candidate-plugins.ts`:349 (confidence medium)
   prepareUpdateCandidatePlugins now runs inspectPluginSourceDependencies over every enabled plugin entry, setup entry and every declared Doctor contract module (including those of disabled plugins), and nothing catches its errors. inspectPluginSourceDependencies rethrows anything outside a short list of module-not-found codes: parse/lexer failures from visitPluginSourceReferences, 'Plugin source link leaves its package', non-regular build inputs, and so on. The repair path in the same change expects such failures from original sources and turns them into warnings, but this path has no such handling. A user whose custom or npm plugin, or a disabled plugin's doctor-contract file, contains syntax the inspector rejects or a link it refuses could update before this change, because the tree copier just copied the directory. Now the whole update rehearsal fails with an inspection error that is unrelated to the update.
2. **Candidate Doctor preflight throws on unparseable copied plugin source even when the snapshot is complete** — `src/infra/update-candidate-plugin-repair.ts`:116 (confidence low)
   completeUpdateCandidatePluginRehearsal inspects every selected entry in the private copy, including Doctor contract modules of disabled plugins, with an unguarded inspectPluginSourceDependencies([entry]). Only the later inspection of the original source is wrapped in try/catch. Errors propagate through createDoctorRehearsalSnapshotPreparation into readDoctorConfigPreflightSnapshot, so they fail candidate Doctor preflight. Example: an enabled plugin, or a disabled plugin's doctor-contract module, has a source file the static inspector cannot parse or capture, even though it needs no repair. Every update driven by a published updater then fails in candidate Doctor, where before the plugin was at most reported by Doctor or plugin loading. The 'invalid source' handling only covers the original tree, and the malformed-plugin tests only cover the runtime entries of disabled plugins.
