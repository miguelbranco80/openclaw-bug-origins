# Case 247

## The bug that later had to be fixed
- What the user saw: After a reboot renumbered the disk mid-update, every later `openclaw update` or Control UI update failed with update-recovery-pending ('device number changed only') until the user ran `openclaw update repair`.
- What the later fix did: Computes the remount-mapped previous/candidate identities before the automatic settlement gate so the pre-admission settlement handles device-renumbered journals like `update repair` does.
- What in the reviewed change was wrong: c66da3d added the remount-mapped `previousIdentity = identities?.currentIdentity(initial.descriptor.previous.identity) ?? ...` only after the automatic (`onlyStaleLease`) gate, which kept comparing the raw recorded `[initial.descriptor.previous.identity, initial.descriptor.candidate.identity]` and so declined after a device renumbering.
- Why: The raw-identity automatic gate came from ff6f58a (#169038), before remount settlement existed; c66da3d (#170046) introduced the verified remount mapping for settlement but applied it only below that gate, so automatic settlement never handled a remounted journal (the PR's regression tests fail on base). 0679b18 (#181307) later widened automatic settlement to interrupted updates but kept the same gate; I attribute to c66da3d as the PR does, with medium confidence because c66da3d deliberately routed remount recovery through repair and which automatic path the reporter hit is not fully confirmed.

## Reviewers' findings
### Reviewer A (1 findings)
1. **Remounted repair bypasses the 'recovery still required' guard and archives unfinished publications unverified** — `src/infra/package-update-activation.ts`:341 (confidence medium)
   The guard that keeps a pending operation for its recovery owner (assertNoPendingPackageActivation when the live package is still the recorded previous or candidate) compares replacementIdentity against the raw historical descriptor identities, while the rest of the function now uses the device-mapped previousIdentity/candidateIdentity. After a reboot/remount changes device numbers, the live package's identity never equals a raw historical identity, so the guard is skipped. Example: a 'publishing' (or 'publication-complete', or a 'prepared' operation with an armed rollback) journal interrupted while the original package is still installed (replacement == mapped previous): manualReplacement and externalPublication are both false, so `openclaw update repair` falls into the generic settlePackageActivationCustody path and archives the operation as 'recovery-lease-missing'/'superseded-by-manual-install' without restoration or any tree/launcher verification. The settlement-only journal permits this write because the intent is 'settled'. Without remount the same state is refused as needing recovery; with remount, partially rewritten launchers pointing at the (now archived) candidate are left behind and the operator is told the old operation was settled.

### Reviewer B (4 findings)
1. **Repair closes remapped operations without verifying the previous installation** — `src/infra/package-update-activation.ts`:341 (confidence high)
   If an update stops in prepared or before displacement in publishing, a remount leaves the previous package installed under its projected identity. The fallback guard compares the live identity with the unprojected identities and falls through. Neither verification branch runs, so repair archives the unfinished operation and clears the update block without checking the previous tree or its launchers. If the lease is unchanged, it also reports a manual replacement that never happened.
2. **Repair rejects hot SQLite journals before replay can run** — `src/infra/package-update-activation-journal.ts`:365 (confidence high)
   If the updater dies during a SQLite commit, readForRecovery can recover the committed record from a snapshot while leaving the live rollback journal for replay under the executor fence. The new inspectRemount call rereads the live database before that replay. SQLite returns SQLITE_READONLY_ROLLBACK, so public repair aborts and leaves the journal blocking recovery, even when the filesystem device numbers are unchanged.
3. **Repair rejects launchers published by the updater** — `src/infra/package-update-activation-settlement.ts`:73 (confidence high)
   When publication copies a launcher into place, the installed launcher gets a different inode from the staged launcher. The updater records that inode in publications, or in the launcher intent if it is interrupted before acknowledgement. After a remount, repair ignores both records and compares the installed inode with the previous or staged inode. It rejects an intact installed candidate with an inode-mapping error and leaves the journal active.
4. **Repair rejects newer releases after some supported update targets** — `src/infra/package-update-activation.ts`:455 (confidence high)
   An interrupted update can record an explicit target such as 2026.9.4-dev.1. If the operator then manually installs 2026.10.1 after a remount, the release comparator returns null because it excludes dev prereleases. Repair reports that it requires a newer manual installation and leaves the journal active without verifying the newer package.

### Reviewer D (3 findings)
1. **Remapped previous package bypasses inconsistent-publication refusal** — `src/infra/package-update-activation.ts`:341 (confidence high)
   After device numbers change, consider a `publication-complete` journal whose live installation is the recorded previous package and whose recovery lease is still current. `replacementIdentity` equals the projected `previousIdentity`, but cannot equal either raw historical identity. The final `includes(replacementIdentity)` guard is therefore false, so repair skips the refusal and archives the operation as `superseded-by-manual-install` without verifying a newer installation. The operator is told recovery is closed and subsequent updates are admitted even though the supposedly published candidate disappeared while its original owner remained valid.
2. **In-place manual upgrades are mistaken for the old candidate** — `src/infra/package-update-activation.ts`:316 (confidence high)
   If an operator installs a newer OpenClaw version by replacing files inside the existing package directory, the directory retains the remount-projected candidate inode. Repair classifies it as `externalPublication` solely from that identity, then verifies it against the old candidate's full digest. The legitimate newer contents fail with `Package settlement full candidate fingerprint changed`, so the advertised manual-upgrade recovery remains blocked unless the installer happened to replace the package directory inode.
3. **Newer installations are checked against the obsolete launcher** — `src/infra/package-update-activation.ts`:459 (confidence medium)
   For a remounted journal replaced by a newer manual installation, this calls `verifyPackagePublicationSettlement` with the old descriptor's `launchers`. That verifier compares each live launcher to `entry.candidate`, which describes the interrupted older candidate, not the newer package's manifest/bin target. A valid newer release or package-manager installation that changes its launcher target or wrapper is rejected with `Package settlement launcher changed`, despite its manifest and inventories being valid.

### Reviewer E (2 findings)
1. **[P2] Honor recorded launcher identities when settling remounted publications** — `src/infra/package-update-activation-settlement.ts`:44 (confidence high)
   The expanded inspection now accepts publication-complete records and partially acknowledged publications, but its launcher loop still checks only previousIdentity or candidateIdentity. When publication replaces a launcher, copyPackagePathEntry creates a new inode, recorded in record.publications or the pending launcher intent; candidateIdentity identifies the retained source instead. After a reboot remaps devices, repair therefore rejects this valid installed candidate with 'Package settlement inode or device mapping changed' and leaves updates blocked. Settlement must use the recorded published launcher identity for these newly supported states.
2. **Remounted repair rejects normally published launchers** — `src/infra/package-update-activation.ts`:436 (confidence high)
   If publication finishes but the process stops before retirement, then a reboot changes device numbers, repair reaches this remount inspection with a publication-complete journal. Normal publication copies each launcher into a new inode recorded in initial.publications. The inspector instead checks against the original launcher inode or the staged launcher asset's inode, ignoring those publication records. It throws "Package settlement inode or device mapping changed" even when the installed candidate and launchers are intact, leaving repair and subsequent updates blocked.

### Reviewer F (1 findings)
1. **Published launcher inodes are rejected during remount settlement** — `src/infra/package-update-activation.ts`:438 (confidence high)
   If publication replaced a launcher before the reboot, the newly supported publishing/publication-complete settlement path rejects the intact installation. Publication copies the launcher into a fresh inode and records that identity in publications (or the pending launcher intent). inspectRemountedPackagePublication instead compares against the previous launcher inode or the staged candidate launcher inode, ignoring those recorded publication identities. Repair therefore throws "Package settlement inode or device mapping changed" and leaves subsequent updates blocked despite an unchanged, successfully published candidate.
