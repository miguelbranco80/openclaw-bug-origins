# Case 163

## The bug that later had to be fixed
- What the user saw: The Skill Workshop off panel was mis-laid out, showed raw Gateway error text, lost keyboard focus while turning on, and could stay stuck on "Turning on…" if the plugins.changed broadcast was dropped.
- What the later fix did: Fixed the Skill Workshop off-state panel layout, summarized enable/check errors behind Show details, kept the busy button focusable and moved focus to the loaded Workshop, and added a one-time recheck with a Reload fallback after a successful enable.
- What in the reviewed change was wrong: #192766 added the off panel as `<div class="sw-empty sw-plugin-off oc-settings-group settings-group">` (whose settings-group block display overrides `.sw-empty { display: grid }`), a `disabled={current().enabling}` button that drops focus, and `<ErrorBanner message={error()} />` showing raw Gateway text.
- Why: All the fixed problems are in the off-state panel that 3e114e23c33c (#192766) introduced the same day; its view.tsx diff adds the conflicting settings-group classes, the disabled busy button, the raw-error banner and the enable flow with no fallback if the broadcast never arrives. The fix PR itself describes this as a UX audit of the state from #192766, so the defects shipped with the feature.

## Reviewers' findings
### Reviewer A (2 findings)
1. **Unmarked configs with a deliberate exclusive plugins.allow get skill-workshop added and are never stamped** — `src/config/skill-workshop-plugin-migration.ts`:72 (confidence medium)
   The allowlist rule treats any unmarked config whose previous and next plugins.allow both omit skill-workshop as 'built-in era'. Configs that are hand-written or created by a first write (stampConfigWriteMetadata skips stamping when previousConfig is undefined) never get the marker; worse, stampSkillWorkshopPluginMigration now refuses to stamp on every later ordinary write because this rule always reports a change. So an operator on a current release who intentionally sets plugins.allow: ["telegram"] to harden the install sees a persistent 'needs migration' legacy warning, and openclaw doctor --fix / startup migration silently appends skill-workshop to their allowlist, turning on a plugin that loads learned skills into prompts and runs autonomous learning against their explicit policy. Before this change such a write stamped the marker and left the allowlist alone.
2. **Enable button stays stuck on 'Turning on…' when the enable succeeds but Workshop methods never appear** — `ui/src/pages/skill-workshop/plugin-availability.ts`:55 (confidence medium)
   On a successful plugins.setEnabled the owner leaves state at {status:'off', enabling:true} and relies solely on the method catalog gaining skills.workshop.list. If the response reports restartRequired, or the plugin is enabled but fails to load/register its methods, the catalog never changes, sync() is never re-run with a new client, and the page shows a permanently disabled 'Turning on…' button with no error, no retry and no hint that a restart is needed; the result of the request (restartRequired/warnings) is discarded.

### Reviewer B (2 findings)
1. **New explicit Workshop disables can be erased by Doctor** — `src/config/skill-workshop-plugin-migration.ts`:72 (confidence high)
   With an unmarked config containing plugins.allow: ["diffs"] and no Workshop entry, an ordinary config write adding plugins.entries.skill-workshop.enabled: false now produces an allowlist migration change. Consequently, stampSkillWorkshopPluginMigration leaves the config unmarked. The write-refusal guard allows this write because the previous config has no ignored entry or deny rule. On the next Doctor repair, the newly authored disable is treated as historical policy and deleted, and Workshop is added to the allowlist. Workshop then runs despite the operator's explicit disable. Previously this write recorded the marker and preserved the disable.
2. **Respect read-only plugin inventory before offering enablement** — `ui/src/pages/skill-workshop/plugin-availability.ts`:67 (confidence high)
   When Workshop is disabled on a Gateway using OPENCLAW_CONFIG_READONLY=1 or OPENCLAW_NIX_MODE=1, plugins.list returns mutationAllowed: false. This code discards that flag, so an admin still sees an active Turn on Skill Workshop button. Every click is rejected by the plugin mutation service; the page offers an operation that cannot work instead of explaining that configuration must be changed through its external owner.

### Reviewer D (4 findings)
1. **Preserve newly written Workshop policy while allowlist migration is pending** — `src/config/skill-workshop-plugin-migration.ts`:72 (confidence high)
   With an unmarked config containing plugins.allow: ["diffs"] and no Workshop entry, an operator can save plugins.entries.skill-workshop.enabled: false. The write-refusal helper permits this, but the new allowlist change makes stampSkillWorkshopPluginMigration withhold the migration marker. Runtime reads consequently ignore the newly saved entry, and a later doctor --fix deletes it as stale and adds Workshop to the allowlist, turning Workshop on despite the explicit disable. 2. **Refresh availability when plugin state changes on the same connection** — `ui/src/pages/skill-workshop/plugin-availability.ts`:29 (confidence high)
   Open Workshop while its plugin is enabled but failed to load, then disable the plugin from another client. Both method catalogs lack skills.workshop.list, so sync receives the same client and skips the inventory check. The page keeps saying the plugin failed to load and never offers Turn on Skill Workshop until the page is reopened or the connection changes.
3. **Respect the catalog's mutationAllowed flag** — `ui/src/pages/skill-workshop/plugin-availability.ts`:67 (confidence high)
   On a Gateway running with OPENCLAW_CONFIG_READONLY=1 or OPENCLAW_NIX_MODE=1 and Workshop disabled, plugins.list returns mutationAllowed:false. This code discards that flag and exposes the enable button to admins. Every click fails because the backend forbids configuration writes, leaving operators with an action that cannot work instead of explaining that changes are disabled.
4. **Respect read-only configuration before offering plugin enablement** — `ui/src/pages/skill-workshop/view.tsx`:169 (confidence high)
   With Workshop disabled and OPENCLAW_CONFIG_READONLY=1 or OPENCLAW_NIX_MODE=1, an admin still sees an active “Turn on Skill Workshop” button because this condition checks only method availability and admin scope. plugins.list explicitly reports mutationAllowed=false in these setups, and plugins.setEnabled always rejects the operation. The page therefore offers a recovery action that cannot succeed instead of explaining that the externally managed configuration must be changed.

### Reviewer E (5 findings)
1. **Doctor overrides intentionally restrictive allowlists** — `src/config/skill-workshop-plugin-migration.ts`:72 (confidence high)
   An operator who hand-writes a config for the plugin-based release with `plugins.allow: ["memory-core"]` to keep Workshop off will have Workshop enabled the next time they run `openclaw doctor --fix`. The migration treats every unmarked restrictive allowlist as built-in-era policy, so it adds `skill-workshop` even when the operator deliberately excluded it after the plugin returned.
2. **Normal Gateway startup skips the allowlist migration** — `src/commands/doctor/shared/legacy-config-migrations.runtime.skills.ts`:21 (confidence high)
   An operator who upgrades outside `openclaw update` and starts the Gateway with an otherwise valid built-in-era config such as `plugins.allow: ["memory-core"]` still loses Workshop. The startup preflight accepts the valid config without running this Doctor migration, so Workshop stays off and learned skills disappear from agent prompts until the operator repairs the config.
3. **Workshop offers an enable button that policy always rejects** — `ui/src/pages/skill-workshop/view.tsx`:169 (confidence high)
   An admin sees Turn on Skill Workshop even when `plugins.enabled` is false, a current `plugins.deny` includes `skill-workshop`, or `OPENCLAW_CONFIG_READONLY=1` makes the config immutable. In each case the Gateway refuses the request and the page re-enables the same button, so every click fails until the underlying policy changes.
4. **Availability stays stale when Workshop methods remain absent** — `ui/src/pages/skill-workshop/plugin-availability.ts`:29 (confidence high)
   If Workshop is enabled but failed to load, the open page displays the load-failure state. Disabling the plugin from another client publishes a new plugin generation, but the Workshop method is absent both before and after that change. The page keeps the same client and skips rereading `plugins.list`, so it still says Workshop is turned on and gives the admin no enable button until they reopen the page.
5. **A failed capability refresh leaves the enable button stuck** — `ui/src/pages/skill-workshop/plugin-availability.ts`:55 (confidence high)
   If `plugins.setEnabled` succeeds but the event-triggered `plugins.uiDescriptors` request times out, the Gateway has enabled Workshop while the page still has the old method catalog. The success path leaves the button disabled on “Turning on…” and offers no retry, so the Workshop never loads on that connection unless a later capability refresh succeeds.

### Reviewer F (3 findings)
1. **Previously marked allowlists are never repaired** — `src/config/skill-workshop-plugin-migration.ts`:72 (confidence high)
   If an earlier version already recorded meta.migrations.skillWorkshopPlugin=true while leaving plugins.allow without skill-workshop—as the previous migration or an ordinary config write could do—Doctor returns at the marker guard before reaching this new allowlist repair. Upgrading and running doctor --fix therefore leaves Workshop disabled for exactly those previously migrated operators.
2. **The enable button is offered when policy makes enabling impossible** — `ui/src/pages/skill-workshop/plugin-availability.ts`:71 (confidence high)
   With plugins.enabled:false or plugins.deny containing skill-workshop, plugins.list reports the installed plugin as disabled, so the page classifies it as "off" and offers Turn on Skill Workshop. plugins.setEnabled refuses these configurations as "plugins disabled" or "blocked by denylist", leaving the operator with a button that can never turn Workshop on.
3. **A failed plugin activation leaves the page permanently enabling** — `ui/src/pages/skill-workshop/plugin-availability.ts`:29 (confidence high)
   When enabling persists successfully but the plugin fails to load (for example because a runtime dependency is missing), plugins.setEnabled can resolve while the refreshed method catalog still lacks skills.workshop.list. The ensuing same-client capability update calls sync with the existing client, which returns without re-reading plugins.list, so the UI remains stuck on the disabled "Turning on…" button instead of switching to the enabled-but-failed message.
