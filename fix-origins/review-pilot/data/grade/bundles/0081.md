# Case 81

## The bug that later had to be fixed
- What the user saw: After a Gateway restart, a root chat whose work ran through a visible spawned coordinator and hidden workers stalled and did nothing until a human sent a message.
- What the later fix did: Root discovery for restart resume now follows recorded native spawn ownership (spawnedBy / createdVia spawn) through visible and hidden spawned children up to the ordinary root.
- What in the reviewed change was wrong: restartResumeSkipReason changed to `if (isSubagentSessionKey(sessionKey) || entry?.createdVia === "spawn") { return "subagent"; }`, so a visible spawned coordinator's own restart marker was rejected while root resolution (narrowed to `while (isSubagentSessionKey(root.sessionKey))` by #188402) never walked past it to the real root.
- Why: #185730 (9344233) walked requester links unconditionally, so visible children reached the root; #188402 (e051130) narrowed the walk to subagent-keyed sessions, but the visible coordinator then still got its own marker and resumed. #195661 (bbf0d73) added the createdVia === "spawn" skip ('keep spawned dashboard children with their requester') without extending the walk, so neither the visible child nor the real root was marked, which is exactly the failure the fix describes.

## Reviewers' findings
### Reviewer A (3 findings)
1. **createdVia spawn skip drops restart resume for dashboard-key spawned sessions whose requester is never marked** — `src/config/sessions/session-run-lifecycle-projection.ts`:114 (confidence medium)
   restartResumeSkipReason now returns "subagent" for any entry with createdVia "spawn". resolveRootSubagentRequester only walks parents for isSubagentSessionKey keys, so a running dashboard-key spawned session (for example an independent visible session from sessions-spawn-visible, or a child spawned without a yield batch) is enumerated as its own root at shutdown. It passes the key-only check, then gets skipped as "subagent" once the entry is read at marker write time, and again in the startup orphan and skip checks. Its requester is not marked either, because it is not running and has no requesterYieldBatch wake. After a restart or crash, nobody receives the resume input: the user's interrupted turn in that session stays stopped with no notice, where it previously got its own resume input.
2. **Quiet or intentional non-delivery settlements are recorded as child-result delivery failures** — `src/agents/subagents/registry/subagent-registry-requester-wake-mutation.ts`:226 (confidence medium)
   The new failure branch fires whenever outcome?.delivered !== true, which includes outcome === undefined. requester-settle-wake.ts calls completeBatch with no outcome for quiet settlements: cancellation already owns the result (isBatchDeliveryClosed, e.g. kill reconciliation or suppressCompletionDelivery), no remaining completion rows, no child owing a completion message, and requester turnover. It also calls it for intentional non-delivery such as store replaced or private requester replaced. For a yield batch, each of these now writes an error terminal with "The child result couldn't be delivered..." onto a requester that is still parked. It does this through the exact-run path, which can, for example, beat the kill path's terminal. For stable batches without requesterRunId, it appends a visible run-failed notice to the conversation even after the user has moved on or stopped it. Users see a spurious failure for work that was cancelled or intentionally not delivered.
3. **Sweeper now settles retired yielded runs as errors when child authority is not 'verified'** — `src/agents/subagents/registry/subagent-registry-read.ts`:166 (confidence low)
   The sweeper no longer gates on (!executionRetired || waitForMessage), and every run restored after a restart is retired, so every restored yielded run reaches settleUnreachableYieldedSubagentRun. That function now converts 'continuable' into 'unreachable' whenever resolveSubagentYieldWaitSource returns undefined. That happens when getRecordedSubagentChildAuthority is not 'verified', for example a legacy-unverified record whose childSessionIdentity lacks lifecycleRevision. It also happens when a grandchild's completionRequesterLifecycleRevision or requesterRunId does not line up with the parent run. A nested child that is still waiting for its own descendants is then force-completed with "Descendant completion can no longer continue this yielded requester." Before this change it stayed parked. Startup resolveSessionYieldWait likewise marks it 'unreachable' and records a failure terminal.

### Reviewer B (5 findings)
1. **Restart drops user turns in previously spawned dashboard chats** — `src/config/sessions/session-run-lifecycle-projection.ts`:114 (confidence high)
   After a visible spawned task finishes, a user can reopen its dashboard chat and start a new turn. If the Gateway restarts during that turn, the session's original `createdVia: "spawn"` stamp prevents shutdown from saving a recovery marker and startup from recovering the turn. The user's follow-up no longer resumes as it did before the change.
2. **Upgrade closes legacy paused tasks that still accept continuations** — `src/agents/subagents/registry/subagent-registry-sweep-settle.ts`:52 (confidence high)
   A paused native child saved by an older release can have neither a `waitForMessage` flag nor descendants. Its controlling requester could previously resume that exact task with `sessions_send`. After upgrade, the first sweep classifies the restored row as unreachable and settles it, so the requester loses the ability to continue the original task even when the requester is still present.
3. **Failed nested handoff leaves the enclosing requester waiting** — `src/agents/subagents/registry/subagent-registry-requester-wake-mutation.ts`:234 (confidence high)
   If a root yields for child A and A yields for child B, a permanent rejection of B's handoff marks A's session failed but leaves A's registry run paused. The lifecycle write updates the session row without settling the native task, and the sweeper's descendant-loss check applies only to retired runs. The root can still see A as waiting and never receive A's terminal result.
4. **Retry loses the failure notice after the lifecycle commits** — `src/agents/subagents/registry/subagent-registry-requester-wake-mutation.ts`:241 (confidence high)
   If the requester lifecycle commits as failed but the separate transcript append hits a transient write error, settlement retries the lifecycle event. The `requireYielded` check now rejects it because the run is already failed, so the retry completes without appending the classified guidance. The user sees the failed state without the notice explaining how to recover the child work.
5. **A failed restart notice strands accepted queued messages** — `src/gateway/session-restart-resume.ts`:641 (confidence high)
   When a yielded session has lost its child source and its restart marker contains accepted queued inputs, startup clears the marker before recording the yield failure. If recording that failure throws, startup skips the queued-input continuation. The messages are left unprocessed, and a later startup has no marker identifying them as inputs to resume.

### Reviewer C (3 findings)
1. **[P2] Preserve the notice receipt when lifecycle settlement partially succeeds** — `src/agents/subagents/registry/subagent-registry-requester-wake-mutation.ts`:234 (confidence high)
   After a permanently rejected child handoff, persistGatewaySessionLifecycleEvent commits the requester's failed status before separately appending the failure notice. If that append encounters a transient storage failure, settlement retries this call, but requireYielded now rejects the already-failed session. The retry returns successfully and releases the batch without ever recording the notice. The user loses the explanation and instructions for recovering saved child work. Retain and retry the notice append independently once the lifecycle write commits.
2. **[P2] Route spawned dashboard children to their requester before skipping them** — `src/config/sessions/session-run-lifecycle-projection.ts`:114 (confidence high)
   When an executing child has a dashboard key and createdVia:"spawn", shutdown now skips it. However, resolveRootSubagentRequester only follows ancestry for subagent-shaped keys, so neither the active-run enumeration nor listLiveSubagentRootSessions redirects this child to its requester. If the requester has already finished its turn and has no yield batch, it receives no restart marker. Restart stops the child, and neither conversation receives recovery input, leaving the delegated work abandoned.
3. **[P2] Continue queued inputs when recording a lost-source failure fails** — `src/gateway/session-restart-resume.ts`:641 (confidence high)
   For an unreachable yield with accepted queued messages, resumeAfterRestart is cleared before recordRestartYieldFailure runs. If that call throws, for example because the failure notice cannot be appended, control jumps to the outer catch and skips continueSessionQueuedInputs. The accepted messages remain stranded, and the next startup cancels them as orphaned inputs because their preserving marker has already been removed. The ordinary resume-failure path catches notice errors specifically so those messages can still continue.

### Reviewer D (1 findings)
1. **Failure-notice retries are rejected after the lifecycle write succeeds** — `src/agents/subagents/registry/subagent-registry-requester-wake-mutation.ts`:234 (confidence high)
   For a batch with requesterRunId, a permanent handoff failure first commits the requester's failed lifecycle, then appends its transcript notice in persistGatewaySessionLifecycleEvent. If that append fails transiently, settlement retries this call with requireYielded: true. The requester now has status "failed", so the lifecycle projection rejects the retry and never retries the notice append. Settlement then releases the batch, leaving the conversation without the promised delivery-failure explanation and recovery guidance.

### Reviewer E (1 findings)
1. **Failure-notice retries silently lose the notice after terminal settlement** — `src/agents/subagents/registry/subagent-registry-requester-wake-mutation.ts`:234 (confidence high)
   When a completion handoff permanently fails, persistGatewaySessionLifecycleEvent first commits the requester's failed lifecycle, then separately appends the transcript failure notice. If that append fails temporarily, settlement retains a retry. However, the retry repeats the lifecycle event with requireYielded:true; the already-failed session now fails that predicate, so the helper returns without retrying the notice. Settlement then clears its pending receipt. The user permanently loses the classified delivery-failure notice and its recovery guidance, even after storage recovers.

### Reviewer F (1 findings)
1. **Spawned dashboard runs lose restart recovery** — `src/config/sessions/session-run-lifecycle-projection.ts`:114 (confidence high)
   When an interactive dashboard session originally created via `sessions_spawn` is executing a later user/operator turn during shutdown, its key is not a subagent-shaped key, so `resolveRootSubagentRequester` does not redirect it to its requester. This new `createdVia === "spawn"` check then excludes the session itself from restart marking. Shutdown aborts the turn, but neither the child nor its requester receives a restart-resume input, leaving the interrupted work unreconciled after startup.
