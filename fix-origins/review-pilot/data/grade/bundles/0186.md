# Case 186

## The bug that later had to be fixed
- What the user saw: Codex, Agents API and Muse sessions with reasoning, screenshots or large tool output silently lost their oldest turns on each attempt (and the provider prompt cache missed) long before compaction.
- What the later fix did: resolveAgentHarnessHistoryLimits now returns the embedded runner's fixed 16 MiB / 10,000-event guard instead of a contextTokenBudget x 8 byte cap, and bundled Codex, Agents API and Muse callers stop passing a budget.
- What in the reviewed change was wrong: #149520 added `limits: { maxBytes: Math.min(64 * 1024 * 1024, Math.max(1024, Math.floor((contextTokenBudget ?? 128_000) * 8))), ... }` to the previously unbounded Codex mirrored-history read, so history past 8 bytes per budget token lost its oldest turns.
- Why: The budget x 8 cap was first added to the Codex harness history read by 83f948498fd (#149520, a memory fix that also introduced the bounded-read mechanism); before it the Codex read passed no limits, so history was not cut. #159375 (42e53a49df3) only moved the same expression into the shared resolveAgentHarnessHistoryLimits helper and reused it for Agents API (Muse later adopted it). Medium rather than high because the cap was a deliberate memory tradeoff and I did not confirm the pre-#149520 read had no other default bound; one could also read it as never-worked for the bounded-read feature.

## Reviewers' findings
### Reviewer A (3 findings)
1. **Model-context reads now rethrow every error, not just bounded-limit rejections** — `extensions/codex/src/app-server/session-history.ts`:134 (confidence medium)
   The catch now rethrows any error for view "model-context", not only the new RangeError from the limit. Before this change, ordinary read failures such as SessionTranscriptReadFenceError ("Session transcript changed during context read" when an unadmitted async read races an append), a CodexHistoryRejection for a malformed header, or the 60 s worker timeout returned undefined. Callers then logged a warning and continued with empty or previous history (attempt-context.ts warn branch, run-attempt-context `?? []` and `?? historyState.messages`). Those transient failures now abort the whole Codex attempt during prompt preparation, so the user sees a failed turn where the run used to continue.
2. **Compaction hook reads switched to the bounded, throwing model-context view inside event handlers** — `extensions/codex/src/app-server/event-projector-tool-transcript.ts`:602 (confidence medium)
   readMirroredSessionMessages used the native-evidence view, which returned [] on failure. It now uses "model-context", which rethrows. It runs inside handleItemStarted and handleItemCompleted for contextCompaction items, without an admission receipt, while the same run is still checkpointing tool messages into the transcript. A concurrent append makes validateSessionTranscriptContextVersion throw. A newest tool frame larger than the byte budget, which is likely right when Codex compacts a full context, makes the limit throw. Either way the notification handler throws: before/after compaction hooks do not run, and persistCodexContextCompactionActivity and the compaction end event are skipped. Hooks that do run also lose tool-result details and private metadata they used to receive from the native-evidence view.
3. **Byte budget counts raw payload bytes such as base64 images against tokens*8, so one large recent message truncates or fails the read** — `src/config/sessions/session-accessor.sqlite-model-context.ts`:172 (confidence medium)
   maxBytes is contextTokenBudget*8 (about 1 MB at 128k tokens), measured as octet_length of the projected event JSON. Inline image data and large tool outputs count byte for byte, although they cost few tokens or are sanitized later. The tail scan breaks at the first entry that does not fit instead of skipping it. So one recent 2-4 MB photo or screenshot tool result drops all older history from before_prompt_build hooks and context-engine input, even though the history would easily fit the model's context. If that entry is in the newest message or tool frame, the read throws "cannot fit the model-context limit" and the turn or compaction handling fails until the user runs /reset.

### Reviewer C (3 findings)
1. **An older ambiguous tool result blocks a valid recent context** — `src/config/sessions/session-accessor.sqlite-model-context.ts`:230 (confidence high)
   If two older calls share an ID and a displaced result matches both, a size limit can cut away just one of those calls. The reader then rejects the entire context because the result would gain an owner. It rejects even when a shorter suffix containing a newer complete tool frame and the latest user message fits. Codex consequently fails before submitting the next turn.
2. **A history read failure suppresses successful compaction reporting** — `extensions/codex/src/app-server/event-projector-tool-transcript.ts`:602 (confidence high)
   If Codex completes native compaction after the current turn adds a mirrored message or tool frame that exceeds the history budget, the completion handler's history read throws. The notification controller only logs the exception at debug level. The handler skips the after-compaction hook, the transcript activity entry, and the compaction-end event, so the session can omit a compaction that actually completed.
3. **An empty branch summary can erase the bounded context** — `src/config/sessions/session-accessor.sqlite-model-context.ts`:264 (confidence high)
   A caller can append a short user message followed by a branch summary with an empty summary string. With maxEvents set to 1 and enough bytes for either entry, the bounded reader spends the only slot on the summary. The context builder skips empty branch summaries, so the caller receives an empty message list even though the latest visible message fits.

### Reviewer D (1 findings)
1. **State metadata bypasses bounded-context limits** — `src/config/sessions/session-accessor.sqlite-model-context.ts`:282 (confidence high)
   A transcript can contain an older `model_change` or `thinking_level_change` with an arbitrarily large string (the public append methods impose no maximum), followed by a small latest message. A bounded `openModelContext` read selects the message within `maxBytes`, then reinserts the unmeasured metadata entry here. The returned context—and an async worker transfer—can therefore exceed `maxBytes` by an arbitrary amount, defeating the memory bound the new API and Codex hook path rely on.

### Reviewer E (1 findings)
1. **History read failures suppress native compaction completion** — `extensions/codex/src/app-server/event-projector-tool-transcript.ts`:602 (confidence high)
   Switching to model-context makes history read errors propagate. For example, a transcript checkpoint appended while the asynchronous read is in progress causes snapshot validation to reject. During a contextCompaction completion notification, this exits handleItemCompleted before persisting the compaction activity or emitting the compaction end event. The notification controller only logs the exception at debug level, so a successful native compaction silently loses its history marker and can leave consumers waiting for the end event.
