# Case 85

## The bug that later had to be fixed
- What the user saw: On a Btrfs host with a large, fragmented live SQLite database, Gateway database writes stalled while a read-only inspection snapshot was being taken.
- What the later fix did: Artifact-preserving SQLite inspection copies (sync and async) now use byte copies with clone: "never" instead of reflink/copy-offload, while offline snapshot publication keeps clone-first.
- What in the reviewed change was wrong: copySourceFile replaced the plain `copyFileDescriptorSync(source.descriptor, target)` byte copy with `copyRootFileSync({ ..., clone: "auto", ... })`, so artifact-preserving inspection snapshots started reflinking (FICLONE) the live database inode.
- Why: Before #172763 the synchronous inspection copy was a plain descriptor byte copy, which does not hold the source inode in Btrfs clone metadata reservation; #172763 switched it to clone "auto", and the fix's regression test (sync inspection returned a clone/offload transfer) targets exactly that line. The async inspection path got clone "auto" earlier in #162466 (9a0146355c02), and the incident's exact caller and latency attribution are not established in the PR, so confidence is medium.

### Reviewer B (2 findings)
1. **Windows short-path caches can block SQLite snapshots** — `src/infra/sqlite-readonly-location.ts`:180 (confidence medium)
   When LOCALAPPDATA or an explicit staging root uses a Windows 8.3 path such as C:\Users\RUNNER~1\AppData\Local, the staging directory keeps that spelling. The guarded copier compares ordinary and native realpaths, which can interpret the short spelling and its expanded spelling as a moved root. Strict update or Doctor inspection then fails even though the database is stable and the cache is writable.
2. **Normal rollback-journal deletion can abort inspection** — `src/infra/sqlite-readonly-location.ts`:178 (confidence high)
   If a SQLite writer commits and deletes its rollback journal after the snapshot pins and resolves the journal but before the guarded helper reopens it, the helper throws a terminal error. The previous copier could read the pinned descriptor and then retry after detecting that the journal had disappeared. Strict inspection now fails even when the database has already settled and a fresh attempt could inspect it.

### Reviewer D (1 findings)
1. **Snapshot copies reject aliased staging roots** — `src/infra/sqlite-readonly-location.ts`:180 (confidence high)
   When the snapshot staging path has a non-native spelling—such as a Windows LOCALAPPDATA/XDG_CACHE_HOME using an 8.3 path, or a POSIX staging root beneath a symlink ancestor—the code passes that spelling directly as copyRootFileSync's destination root. fs-safe requires roots to match their native realpath (the repository already rebases such roots in plugin-source-file.ts), so the guarded copy throws a path-mismatch error. Doctor/update state inspection then aborts even though the configured cache directory is writable; the previous descriptor-based copier accepted these paths.

### Reviewer E (1 findings)
1. **Canonicalize the destination root before guarded copying** — `src/infra/sqlite-readonly-location.ts`:180 (confidence medium)
   On Windows, a stagingRoot containing an 8.3 directory alias creates targetPath with that alias still present. copyRootFileSync compares ordinary and native root spellings and rejects this as a moved root—the same limitation handled by resolveNativeCopySource in src/plugins/plugin-source-file.ts. Consequently, synchronous artifact-preserving inspection fails with a path-mismatch error on an otherwise writable staging directory, whereas the previous descriptor copier succeeded. The destination directory and target path need rebasing onto the native realpath before admission.

### Reviewer F (1 findings)
1. **Sidecar churn during guarded copy now aborts the snapshot instead of retrying** — `src/infra/sqlite-readonly-location.ts`:179 (confidence medium)
   copySourceFile pins the source fd, resolves realpath, then lets copyRootFileSync re-open the path by name and compare identity. If the file is deleted or replaced between the pin and the helper's open, the helper throws an FsSafeError (not-found or identity mismatch) rather than SqliteSourceChangedError. prepareArtifactPreservingCopy only retries SqliteSourceChangedError, so the snapshot fails on the first try. The previous code copied from the pinned fd and turned drift into a retryable SqliteSourceChangedError, and the async sibling (copyPreparedLocation) still does this through its finally-block identity check. The common trigger is a database in rollback (DELETE) journal mode being written during the snapshot: SQLite deletes and recreates <db>-journal on every commit. The WAL file can also be removed when the last connection closes. A commit landing in that window makes update candidate-state inspection, update generation hashing (readCommittedContent), state ownership checks, or artifact-preserving state reads fail with a raw fs-safe error, where they used to retry and settle. The worker's contention classifier also no longer labels the failure retryable.
