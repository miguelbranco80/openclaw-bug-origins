# Case 204

## The bug that later had to be fixed
- What the user saw: `openclaw doctor --fix` on installs with an unmigrated legacy memory index warned every run that original state capture was unavailable: "Update recovery manifest is missing a root entry."
- What the later fix did: Doctor's original-state capture now omits declared roots that are SQLite sidecars of a captured database, and the capture-reuse comparer skips the same declarations so an unchanged install can reuse the sealed baseline.
- What in the reviewed change was wrong: Memory Core's new `collectBackupResources` declared every `memory/<agent>.sqlite` suffix in `LEGACY_MEMORY_SIDECAR_SUFFIXES` ("-wal", "-shm", "-journal") as `kind: "file"` resources, while the capture at that commit seeded `roots = new Set(resources.keys())` and dropped only sidecar entries, leaving sidecar roots without entries.
- Why: At 7187a9afa71 the capture code (read via git show) adds all declared resources as roots and filters only entries via `!sidecars.has(entry.sourcePath)`, and that same commit introduced Memory Core's declaration of the base file plus its -wal/-shm/-journal paths, so the manifest's root-completeness check could never pass for installs with a real legacy memory SQLite file. The blame candidate d417b52 only added the rehearsal filter to the unchanged roots line. Medium because the exact header-based database recognition of the base file at that commit was inferred from its comment and the capture structure, not run.

## Reviewers' findings
### Reviewer A (2 findings)
1. **Canvas inventory throws on an unreadable legacy root and aborts the whole recovery capture** — `extensions/canvas/doctor-contract-api.ts`:41 (confidence medium)
   collectBackupResources calls listLegacyCanvasDocumentIds, which throws for any non-ENOENT error (EACCES, ENOTDIR) on plugins.entries.canvas.config.host.root/documents. preparePluginDoctorMigrationResources does not catch collector errors, so captureUpdateRecoveryBaseline (and rehearsal plan collection in state-migrations.plugin-doctor.ts) fails outright. Before this change the same config only produced the undeclared-resources warning and detectLegacyState's failure was caught as a 'Failed detecting' warning; now an operator with a stale or permission-restricted retired Canvas root cannot update at all until they fix that directory.
2. **Already-migrated host-event archives are declared forever, permanently deferring Memory Core in rehearsal** — `extensions/memory-core/src/migration/doctor-host-events.ts`:547 (confidence low)
   collectLegacyMemoryHostEventSources returns every events.jsonl.migrated[.N] archive as a ready 'archive' source even after its checkpoint matches and no migration is needed, and the collector declares it unconditionally. Those archives are never deleted, so every later update capture copies them again, and in an update rehearsal whose agent workspace lies outside the rehearsal root (a configured absolute workspace) the path is read-only, so preparePluginDoctorMigrationResources defers the whole memory-core plugin on every update from then on, skipping its sidecar and other migrations in rehearsal with only a 'deferred' notice.

### Reviewer C (2 findings)
1. **Canonical legacy path aborts the entire recovery capture** — `extensions/memory-core/src/migration/doctor-memory-sidecar.ts`:499 (confidence high)
   If an agent's legacy memory-search store path is the canonical per-agent database path itself, collectLegacyMemorySidecarSources retains it because isCanonicalAgentDatabaseSymlink only excludes symlinks. The collector then declares that same absolute path first as `sqlite` here and again as `file` at line 504. preparePluginDoctorMigrationResources rejects the conflicting kinds, so the updater logs that original-state capture is unavailable and continues without any recovery copy; standalone Doctor likewise continues after the capture failure. Thus all migrations in that run, including Canvas and host-event moves, proceed without the recovery evidence this change is intended to guarantee.
2. **Late SQLite companions are moved without being inventoried** — `extensions/memory-core/src/migration/doctor-memory-sidecar.ts`:500 (confidence medium)
   The collector declares legacy `-wal`, `-shm`, and `-journal` paths and their archive destinations only when they exist during collection. If a companion is created after the recovery capture is sealed but before migration—such as by the still-running legacy SQLite user, or a `-shm` created when the importer attaches a WAL database—archiveLegacyMemorySidecar later re-enumerates it and renames it to `<path>.migrated`. Neither that companion nor its destination is present in the recovery manifest, so rollback cannot restore its bytes or remove the newly created archive. All possible suffix paths and destinations need missing entries just as the retry destinations do.

### Reviewer E (2 findings)
1. **A valid default legacy memory index prevents recovery capture from sealing** — `extensions/memory-core/src/migration/doctor-memory-sidecar.ts`:515 (confidence high)
   When a valid legacy index exists at stateDir/memory/main.sqlite, the retry inventory also declares main.sqlite-wal, main.sqlite-shm, and main.sqlite-journal as recovery roots, even when those files are absent. The backup consolidates the SQLite database and strips companion entries from the manifest while retaining their roots. Manifest validation rejects the entire capture with “Update recovery manifest is missing a root entry.” Doctor or the updater can then proceed without a pre-migration recovery copy.
2. **An empty legacy .sqlite placeholder aborts the entire recovery capture** — `extensions/memory-core/src/migration/doctor-memory-sidecar.ts`:504 (confidence high)
   When a configured legacy memory index points to a zero-byte file named main.sqlite, declaring it as kind file still sends it through the SQLite snapshot path because the backup classifier recognizes the .sqlite suffix before checking the header. The snapshot requires a nonempty source and aborts the entire capture. Doctor can then continue and delete the placeholder without a sealed recovery copy of the rest of the pre-repair state.

### Reviewer F (1 findings)
1. **[P1] Empty legacy .sqlite placeholders abort recovery capture** — `extensions/memory-core/src/migration/doctor-memory-sidecar.ts`:504 (confidence high)
   When a configured external legacy sidecar ends in `.sqlite` and is empty or malformed, declaring it as `file` still sends it through SQLite snapshotting: `isSqliteSnapshotFile` unconditionally accepts the `.sqlite` suffix. Recovery capture then calls `createVerifiedSqliteSnapshot` with `requireNonEmptySource: true`, which rejects an empty placeholder (and malformed databases also fail). Consequently, an update requiring recovery capture aborts before the migration can remove the harmless empty placeholder. The collector's intended header-based classification does not occur for these filenames.
