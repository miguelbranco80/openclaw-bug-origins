# Case 273

## The bug that later had to be fixed
- What the user saw: On a btrfs host running sandboxed agents in large workspaces, the Gateway stalled: SQLite waits of 9 to 19.6 seconds and RPC p99 of about 52 seconds while command checkpoints created and deleted filesystem snapshots.
- What the later fix did: Changed sandbox command checkpoints now pause the guest and capture directly into an immutable Git result, removing the per-checkpoint btrfs snapshot creation and retirement and the size/duration snapshot selector.
- What in the reviewed change was wrong: #196662 replaced 'Changed checkpoints still pause through capture and publication' with btrfs checkpoints that 'take a filesystem snapshot, then resume', adding `prepareLocalWorkspaceCheckpointCapture`/`removeLocalWorkspaceCheckpointCapture` to every changed command checkpoint in runLocalWorkspaceProjection.
- Why: Before 10d67445fbe, changed checkpoints paused and captured directly, which is the state this fix restores. That commit introduced a btrfs snapshot plus recursive removal for every changed checkpoint, and per the fix PR each snapshot forces a filesystem-wide btrfs transaction commit that stalled Gateway SQLite in production. d7f90ec35cf (#196727, retire captures, select snapshots only for large or slow trees) and 8ff37a6828b (#198128, skip the freeze) tuned the same path but kept snapshots for exactly the large workspaces that stalled. Medium confidence: the stall mechanism depends on btrfs kernel behavior and production timings I could not verify, and the fix is framed as an owner-accepted trade-off (about 290 ms of extra guest pause) rather than a pure bug fix.

## Reviewers' findings
### Reviewer A (2 findings)
1. **Preserve Podman's environment when selecting the native fixture store** — `scripts/perf/local-workspace-checkpoint-measure.ts`:1149 (confidence high)
   When an operator supplies the required private Podman store through CONTAINERS_STORAGE_CONF, the earlier createGatewayBenchEnv assignment removes that variable from process.env. These new Podman calls consequently use a different store: image inspection fails even though the specified image exists in the private store, and the benchmark exits before measuring anything. Preserve the Podman environment consistently for fixture creation, checkpoint engine calls, and cleanup.
2. **Detect mounted directories before accepting a btrfs snapshot** — `src/gateway/worker-environments/local-workspace-checkpoint.ts`:67 (confidence medium)
   If an operator mounts another filesystem or bind-mounts a directory beneath the btrfs workspace, the snapshot contains the underlying mountpoint directory rather than the mounted contents. That directory has an ordinary inode, so the inode-2 completeness check does not trigger fallback. Checkpointing can therefore succeed while omitting new files or propagating deletions of previously accepted files beneath the mount into the canonical workspace. The previous live-tree capture included those files.

### Reviewer C (2 findings)
1. **Capture cleanup failure turns accepted checkpoints into errors and blocks every later checkpoint** — `src/gateway/worker-environments/local-workspace-projection-operation.ts`:1667 (confidence medium)
   removeLocalWorkspaceCheckpointCapture runs unguarded in the finally block after the guest has resumed and canonical acceptance has finished. It also runs before pausing in prepareLocalWorkspaceCheckpointCapture, and on the unchanged-probe path in checkpointLocalWorkspace. If removing the snapshot fails, the error replaces the checkpoint's result. Examples: rmSync fails with a code other than EACCES/EPERM/ENOTEMPTY; chmod fails with EPERM on a guest-created directory owned by another UID; the native helper times out or is killed on a very large tree. The command is reported as failed even though its bytes were accepted, and a typed error from run (rejection or conflict) is masked. The leftover checkpoint-capture then makes the leftover removal throw again at the start of every later checkpoint, including unchanged ones. The sandbox cannot checkpoint again until someone removes the directory by hand.
2. **Snapshot copy failures no longer fall back to the paused Git capture path** — `src/gateway/worker-environments/local-workspace-checkpoint.ts`:1251 (confidence low)
   On a btrfs subvolume projection, every changed checkpoint now depends on the native copy subprocess. Only errors coded CLONE_UNAVAILABLE, EXDEV or ENOSYS fall back to run(). Other failures make the whole checkpoint throw instead of using the existing paused Git capture, which would have succeeded. Examples are the generic "Native worktree copy failed: <termination>" errors from write() (timeout, killed, process-tree-extinction failure), EPERM/EACCES from snapshot creation, and ENOSPC. Each mutating command's finalization then fails, and keeps failing while the condition lasts. Before this change these checkpoints did not depend on the native helper at all.

### Reviewer D (3 findings)
1. **Snapshots can delete canonical files backed by host mounts** — `src/gateway/worker-environments/local-workspace-manifest-scan.ts`:545 (confidence high)
   Bind-mount a directory containing an already accepted file over an ordinary empty directory inside the btrfs projection, then edit a different file. The live scan can see the mounted file, but the btrfs snapshot contains the underlying empty directory. That directory has no inode-2 marker, so checkpointing treats the missing file as a guest deletion and removes it from the canonical worktree even though it remains visible in the guest.
2. **Foreign-owned snapshot directories can block all later checkpoints** — `src/infra/fs-safe-copy.worker.ts`:39 (confidence high)
   A non-root Gateway can read a guest-created directory owned by another UID, such as a root-owned 0755 directory created through a writable rootful Docker sandbox. The snapshot preserves that ownership. Cleanup cannot unlink files inside the directory, and the repair skips chmod because the owner's mode bits already include 0700. The command reports a checkpoint failure after its edits have reached canonical storage. Subsequent checkpoints fail while removing the same leftover snapshot, even if the directory is removed from the live guest.
3. **Native benchmark loses its report on a standard cgroup v2 host** — `scripts/perf/local-workspace-checkpoint-measure.ts`:2285 (confidence high)
   Run the native benchmark directly on a Linux host where /sys/fs/cgroup exposes the actual cgroup v2 root. Its cpu.stat exists, so the script enables CPU accounting, but root cgroups have no cpu.max. After the measured commands complete, the report builder throws ENOENT and the operator gets no benchmark report.

### Reviewer E (1 findings)
1. **Snapshot cleanup blocks checkpoints on guest-owned directories** — `src/gateway/worker-environments/local-workspace-projection-operation.ts`:115 (confidence high)
   With a non-root Gateway and a Docker sandbox configured to run as root with capabilities, the guest can create root-owned 0755 directories containing files, including excluded node_modules outputs. The btrfs snapshot preserves that ownership. Canonical capture succeeds, but the Gateway cannot unlink files inside those snapshot directories, and the permission-repair helper cannot grant itself ownership rights. This awaited cleanup therefore fails the completed command with EACCES. The leftover capture also blocks subsequent checkpoints because preparation requires deleting it first. Previously, excluded outputs did not need to be recursively deleted during checkpointing.
