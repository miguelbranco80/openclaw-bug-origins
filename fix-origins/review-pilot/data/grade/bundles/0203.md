# Case 203

## The bug that later had to be fixed
- What the user saw: A guest viewing another person's Activity saw the permission error flicker into loading placeholders (and a fresh denied request) whenever an unrelated session changed.
- What the later fix did: The Activity session owner now remembers a settled FORBIDDEN denial and ignores unrelated invalidations and bucket rollovers, while explicit retry, changed filters and authority changes (sharing/profile-identity events, new hello) still reload.
- What in the reviewed change was wrong: The guest-privacy change added the `error.gatewayCode === "FORBIDDEN"` branch that clears `currentResult` and rows but records no settled-denial state, so the existing `invalidate()` path reloads the denied query (loading placeholders) on every unrelated session change.
- Why: `git log -S FORBIDDEN` on session-activity-owner.ts shows the denial handling first arrived in 5d3e157 (#191978), which made person activity deny guests and cleared rows on denial without any guard in invalidate/load, so the flicker shipped with the denial feature. The blame candidate 10c95d1a is the earlier Solid refactor that created the generic invalidate-and-reload path, which was fine before denials existed; medium because the reload path is older and the defect is the interaction.

## Reviewers' findings
### Reviewer A (1 findings)
1. **Agent owner and creator filters are rejected as foreign people** — `src/gateway/session-profile-activity-policy.ts`:57 (confidence medium)
   For a session-only guest, sessions.list with ownerId or creatorId set to a configured agent ID (for example, "research") now throws FORBIDDEN because that ID differs from the guest's profile ID. These are actor filters that also support agents, so guests can no longer filter otherwise readable shared sessions by their agent owner or creator; they instead receive the misleading "Other people's activity is private" error.

### Reviewer B (1 findings)
1. **Preserve agent owner and creator filters for guests** — `src/gateway/session-profile-activity-policy.ts`:57 (confidence high)
   For a session-only guest, sessions.list with ownerId set to a configured agent such as "main" now returns FORBIDDEN, even when the matching sessions are shared with that guest. creatorId has the same problem for agent-created sessions. These filters accept actor IDs, including agents, but the new check treats every value as a human profile ID and requires it to equal the viewer's profile. This breaks filtering otherwise readable sessions by their agent owner or creator.

### Reviewer E (4 findings)
1. **Foreign-filter response reveals whether an agent has hidden sessions** — `src/gateway/session-utils-list.ts`:98 (confidence high)
   On the cached WebSocket list path, a session-only guest who supplies a foreign ownerId and an agentId gets a successful empty result when the configured agent has no sessions. Once another user creates a draft on that agent, the same request returns FORBIDDEN even though the draft is invisible to the guest. Empty partitions skip authorization, while nonempty partitions run it before checking row visibility.
2. **Person privacy check blocks filters for agent-owned sessions** — `src/gateway/session-profile-activity-policy.ts`:58 (confidence high)
   A session-only guest can see a shared session whose assigned owner is the agent main, but filtering the list by ownerId main now returns FORBIDDEN with a message about other people's activity. The existing owner filter accepts agent identities, and the new guard treats every owner ID as a human profile ID.
3. **Saved owner filter leaves the sidebar on a denied query after demotion** — `ui/src/components/session-owner-filter.ts`:149 (confidence high)
   A member who saves another person's sidebar owner filter keeps that preference after becoming a guest. In the agent-chip sidebar, the restored filter now produces FORBIDDEN, and the automatic reset requires a successful result from that same query. The sidebar stays on the failed filter across reloads until the user manually chooses a different owner filter.
4. **Everyone shows the guest's personal session count** — `src/gateway/session-list-filters.ts`:562 (confidence high)
   If a guest can see two shared sessions and is associated with only one, the Activity people picker shows 1 next to Everyone even though choosing Everyone shows both sessions. The picker uses peopleSessionCount for the full time window, but the new calculation counts only sessions associated with the guest.

### Reviewer F (2 findings)
1. **Agent owner/creator filters are rejected as 'other people's activity' for session-only callers** — `src/gateway/session-profile-activity-policy.ts`:450 (confidence medium)
   ownerId and creatorId are actor-id filters that also match agents (ownerId is the 'assignable owner identity', documented as a configured agent ID for agent owners; creators can be agents). For any caller with a viewer ID (session-only guest, or an agent run started by one), the policy runs every creatorId/ownerId through resolveSessionProfileId and compares it with the viewer's profile ID. An agent ID such as 'main' never matches, so a guest filtering the sidebar by an agent owner, or the sessions_list agent tool called with ownerId/creatorId set to an agent, now gets FORBIDDEN 'Other people's activity is private' even though no person's activity is involved. The owner-facet change (effectiveOwner.identity.id === activityViewerId) also drops agent owners from the facet, so the guest's agent-owner filter options disappear.
2. **Guest's saved sidebar owner filter for another person now makes every sidebar list request fail** — `src/gateway/session-profile-activity-policy.ts`:461 (confidence low)
   Before this change guests could pick another person as the sidebar owner filter, and the UI persists that choice in localStorage as 'owner:<id>' (loadStoredSidebarSessionOwnerFilter) and sends it as ownerId on every sidebar sessions.list. After upgrade the Gateway throws FORBIDDEN for that ownerId, so the guest's sidebar session list fails on every load and refresh instead of falling back. The owner facet that would let the UI show and reset the selection comes from the same failing response, and only the Activity page controller was taught to handle the new FORBIDDEN; the sidebar still holds the stale filter.
