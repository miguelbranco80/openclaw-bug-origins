# Case 153

## The bug that later had to be fixed
- What the user saw: A guest conversation continuing an existing PR reported its base as current after the target branch advanced, leaving the newer target files out of the workspace.
- What the later fix did: Prepared-PR refresh_base (and preparation when the accepted base disagrees with PR metadata) now reads the live target branch SHA via readGitHubPublicationBaseSha instead of trusting lagging PR-detail base SHA.
- What in the reviewed change was wrong: The commit that added refresh_base for prepared PRs set the binding's `base: pendingBase ? previous.base : structuredClone(pullRequest.base)` from GitHub PR details and integrated `commit: binding.base.commit`, never reading the live branch ref.
- Why: Refreshing a prepared PR's target branch was introduced hours earlier by 5cac93c15f2 (#190223), whose title says prepared PRs could not refresh before; it took the base commit from inspectOwnGitHubPullRequest PR details, which lag the branch ref. No other commit touched the preparation file between that commit and the fix, so the stale-base defect shipped with the feature.

### Reviewer D (1 findings)
1. **prepare_pr guidance still tells the model an explicit refresh imports the newer PR head and is acknowledged with expectedHeadCommit, contradicting the now-enabled bound refresh_base** — `src/agents/tools/github-publish-tool.ts`:143 (confidence low)
   In a prepared-PR session with refresh_base available, the prepare_pr paragraph (unchanged) says 'An explicit refresh of the bound PR integrates its newer head' and 'repeat with conflictsResolved: true and expectedHeadCommit set to the returned headCommit', while refresh_base now accepts bound PRs but never imports the head and only acknowledges via baseCommit. A model following the prepare_pr text calls refresh_base to pick up another writer's commits (nothing imported; next publish fails push_rejected) or acknowledges refresh_base conflicts with expectedHeadCommit and no baseCommit, which throws 'The pending source integration changed; call refresh_base again'.

### Reviewer E (1 findings)
1. **Interrupted refresh can discard its accepted base** — `src/gateway/github-pr-workspace-preparation.ts`:372 (confidence high)
   The binding is updated by accept() before MERGE_HEAD is written. If the operation is interrupted in that window and the PR is then retargeted to an unrelated branch, the retry sees no pending MERGE_HEAD and replaces previous.base with the new GitHub target. It therefore integrates the new target and never finishes the already accepted base, contrary to the documented recovery behavior.

### Reviewer F (4 findings)
1. **Base refresh can apply private files after the requester loses repository access** — `src/gateway/github-pr-workspace-preparation.ts`:397 (confidence high)
   A linked guest starts refreshing their prepared PR in a private repository. If their GitHub repository access is revoked during the base fetch while the managed publisher retains access, the final check still passes. It rechecks the publisher's write eligibility and the guest's local account link, then applies the fetched private target files to the guest's workspace.
2. **Base refresh overwrites a staged deletion when a working copy exists** — `src/gateway/github-publication-base-refresh.ts`:143 (confidence high)
   In a prepared workspace, a guest uses git rm --cached on a tracked file and keeps an edited working copy. Git reports the staged deletion and the untracked copy as separate records, so the partial-staging guard lets refresh proceed. The final git add -A stages the working copy and replaces the guest's staged deletion.
3. **Merging the PR on GitHub strands pending local base conflicts** — `src/gateway/github-pr-workspace-preparation.ts`:141 (confidence high)
   A base refresh conflicts with unpublished guest edits while the remote PR remains mergeable. If someone merges the PR on GitHub before the guest acknowledges the local resolution, refresh_base rejects the merged PR before it reaches recovery. The canonical workspace keeps MERGE_HEAD, so archive and eviction still reject it and tell the operator to finish the integration.
4. **Refreshing after a fork rename leaves publication targeting stale repository metadata** — `src/gateway/github-pr-workspace-preparation.ts`:370 (confidence high)
   After an external fork PR is prepared, rename its head repository without changing its branch or commit, then advance the target and run refresh_base. Refresh succeeds because the repository ID is unchanged, but it saves the new base with the old head repository name. Publication rejects the saved target, and prepare_pr takes its same-head, same-base shortcut without repairing the name.
