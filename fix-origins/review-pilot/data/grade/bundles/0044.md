# Case 44

## The bug that later had to be fixed
- What the user saw: In Firefox on desktop, the last reply's footer controls (such as Copy) sat hidden behind the chat composer at the bottom of the transcript.
- What the later fix did: Moves the desktop Details reservation from a CSS grid on the transcript scroll container to a width-reduced .chat-thread-content wrapper, so Firefox includes the bottom padding in the scroll range, and updates geometry code for the extra wrapper.
- What in the reviewed change was wrong: It pulled the composer up over the transcript with `margin-top: calc(-1 * var(--chat-composer-overlap, 0px))` and relied on `--chat-thread-padding-bottom: calc(6px + var(--chat-composer-overlap, 0px))` for clearance, padding that Firefox drops from the desktop transcript's grid scroll range.
- Why: The desktop scroll container became `display: grid` in #179059 (2026-10-21), and the fix says Firefox leaves trailing grid padding out of the scroll range. That cost only 6px until #195508 (2026-11-09) made the composer overlap the transcript and moved the last turn's clearance into that padding, so Firefox reply footers were first covered then. I read both diffs; confidence is medium because I did not reproduce the Firefox padding behavior myself, and #179059's grid is the precondition rather than the visible break.

## Reviewers' findings
### Reviewer A (2 findings)
1. **Overlapping full-width footer swallows pointer input on the transcript's bottom band, including its scrollbar** — `ui/src/styles/chat/startup-layout.css`:182 (confidence medium)
   The new negative margin-top pulls .chat-footer (position: relative, full pane width, no pointer-events: none) 28px (35px at corner scale 1.25) up over .chat-thread-viewport, and as the later positioned sibling it paints and hit-tests above the transcript. The transcript's scrollbar sits at the pane edge (scrollbar-gutter both-edges), outside the centered composer, so the bottom 28-35px of the scrollbar track, and on Windows/Linux classic scrollbars the down-arrow button, now lie under the transparent footer: clicking or dragging there hits the footer instead of the scrollbar. Likewise, while scrolled mid-conversation, links, buttons and text in messages passing through that band beside the composer's rounded corners are visible but not clickable or selectable. Wheel input is forwarded, but mouse clicks and drags are not.
2. **Full-pane history-error view gets the footer overlap without compensating bottom padding** — `ui/src/styles/chat/startup-layout.css`:182 (confidence low)
   The extra bottom padding was added only to .chat-thread-viewport/.chat-thread, but the footer's negative margin applies whatever sits above it. When history fails with an empty transcript, the fallback .chat-history-error (an overflow:auto scrollport whose stage has min-height 260px and only 24px padding) occupies that slot. The footer now covers its bottom 28-35px: in a short pane where the stage scrolls, scrolling to the end leaves the last few pixels of the Retry control under the composer, and in taller panes the centered error art/text is centered in a box that extends behind the composer, so it sits visibly lower than the space actually visible above the composer.
