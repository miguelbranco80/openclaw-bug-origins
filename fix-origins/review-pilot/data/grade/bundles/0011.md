# Case 11

## The bug that later had to be fixed
- What the user saw: When OpenClaw ran under Bun with an old Node (e.g. 20) earlier on PATH, Node-only helper processes such as Gateway post-ready maintenance crashed with a syntax error on a `using` declaration.
- What the later fix did: Made the Node helper resolver fast path and the standalone probe also require isSupportedOpenClawNodeVersion, so unsupported Node installs are skipped in favor of a supported one.
- What in the reviewed change was wrong: The new resolver accepted any non-Bun node via `!process.versions.bun && (!requiredFlag || process.allowedNodeEnvironmentFlags.has(requiredFlag))` in both the fast path and the probe, with no check against the supported Node floor.
- Why: The resolver was introduced in #145688 without any version gate, while node-version.mjs and package.json engines at that commit already required Node >=24.16, so it could select an unsupported Node from day one; later commits (#183120, #183493) only moved the same predicate into a generated probe. Medium rather than high because the visible crash also needed compiled code using newer syntax, but the missing check against an already-existing support contract is the defect.

## Reviewers' findings
### Reviewer A (4 findings)
1. **Node discovery can stall the Gateway with Tool Search disabled** — `src/agents/tool-search-config.ts`:59 (confidence high)
   On a Bun-hosted Gateway, the first ordinary agent turn with Tool Search disabled or unset still probes for Node because the default mode is code. Each candidate runs synchronously with its own five-second timeout. A stale Node shim that hangs can freeze the Gateway for five seconds, delaying unrelated requests as well as the current turn. Multiple hanging candidates compound the delay.
2. **Cached Node paths survive installation and upgrade changes** — `src/infra/node-runtime-executable.ts`:67 (confidence high)
   If a Bun Gateway probes before Node is installed, installing a compatible Node into a directory already on PATH leaves Tool Search in structured mode. If a package upgrade removes the cached executable and puts a working replacement elsewhere on the same PATH, the Gateway keeps advertising code mode and calls fail with ENOENT. Both results persist across config reloads because the cache key stays the same.
3. **Node version-manager shims lose their launch environment** — `src/infra/node-runtime-executable.ts`:80 (confidence high)
   When the only compatible Node is exposed through an asdf shim that resolves the asdf command through PATH, invoking node from the operator's shell works. The probe strips PATH and version-manager settings, so the shim cannot find asdf in a directory such as /opt/homebrew/bin. The Gateway silently falls back to structured Tool Search despite having a compatible Node available.
4. **Startup output is accepted as part of the executable path** — `src/infra/node-runtime-executable.ts`:84 (confidence high)
   If an earlier node launcher on PATH prints a startup notice to stdout before forwarding to a compatible Node, the resolver caches the notice and the reported executable path as one string. It stops searching even if a plain Node executable appears later on PATH. The Gateway advertises tool_search_code, but calls fail because the cached string is not an executable path.

### Reviewer B (3 findings)
1. **Cached Node path becomes unusable after a Homebrew upgrade** — `src/infra/node-runtime-executable.ts`:93 (confidence high)
   Under Bun, probing /opt/homebrew/bin/node returns Node's resolved process.execPath in a versioned Homebrew Cellar directory. This path is cached indefinitely. When Homebrew upgrades Node and removes that directory, PATH remains unchanged, so the resolver keeps returning the deleted executable. Tool Search continues advertising code mode, but every invocation fails with ENOENT until OpenClaw restarts.
2. **Probe drops environment needed by Node version managers** — `src/infra/node-runtime-executable.ts`:80 (confidence high)
   If a Bun-hosted installation's only compatible Node is exposed through a version-manager shim using a custom VOLTA_HOME or ASDF_DATA_DIR, the probe removes those variables and HOME. The shim cannot locate the installed Node, and the system-location fallbacks find nothing. OpenClaw then silently falls back to structured tools despite a compatible Node being installed and available through the operator's PATH.
3. **Node discovery now drops environment required by existing installations** — `src/test-utils/node-process.ts`:21 (confidence medium)
   When running tests under Bun with Node installed through an asdf installation that requires a custom ASDF_DATA_DIR, delegating to the new resolver removes that variable from the discovery subprocess. The asdf node shim can no longer find the installed Node version. If no system Node is available, resolveTestNodeExecPath throws "Unable to locate a Node executable" and subprocess-based tests fail despite a working Node on PATH. The previous probe inherited the environment and supported this setup.

### Reviewer D (1 findings)
1. **Sterile probes cannot resolve version-manager Node shims** — `src/infra/node-runtime-executable.ts`:80 (confidence high)
   When Bun runs with Node installed through asdf using a custom ASDF_DATA_DIR, and only the asdf shims directory is on PATH, the probe removes ASDF_DATA_DIR, HOME, and PATH before executing the shim. The shim cannot locate its installed Node, so the resolver rejects an otherwise compatible installation and Tool Search falls back to structured tools. The shared test resolver also now throws in this setup, whereas its previous probe inherited the environment and resolved Node successfully.

### Reviewer E (2 findings)
1. **Sterile probe env rejects version-manager Node shims (Volta, asdf, mise)** — `src/infra/node-runtime-executable.ts`:78 (confidence medium)
   Each PATH candidate is probed with buildProbeEnv(env), which keeps only SystemRoot/WINDIR/TEMP/TMP/TMPDIR and drops HOME, PATH, VOLTA_HOME, ASDF_DATA_DIR and similar. On a Bun-hosted install where Node comes from a version manager (a common setup), the `node` on PATH is a shim that needs HOME or its own env vars to pick a real Node version. Without them the shim exits non-zero (for example 'No version is set for command node' or a Volta home error), so every candidate is skipped and null is cached. isToolSearchCodeModeSupported() then returns false and Tool Search quietly drops from code mode to tools mode under Bun, even though a compatible Node is installed. resolveTestNodeExecPath (which used to probe with the full process.env) now throws 'Unable to locate a Node executable' on the same machines.
2. **Negative resolution is cached for the life of the process** — `src/infra/node-runtime-executable.ts`:92 (confidence low)
   When no candidate succeeds, null is cached under a key built only from the platform, runtime version, flag, PATH and PATHEXT. That happens if Node is installed or upgraded after the Gateway starts, or if one cold-start probe hits the 5 s timeout on a loaded machine. Every later resolveToolSearchConfig call then reports code mode unsupported and silently uses tools mode, and tool_search_code keeps failing with 'requires an installed Node runtime', until the Bun-hosted process restarts. No warning names the cause.

### Reviewer F (1 findings)
1. **Sterile probe rejects version-manager Node shims** — `src/infra/node-runtime-executable.ts`:82 (confidence high)
   When a Bun-hosted gateway has a compatible Node available only through a PATH shim or wrapper that needs HOME, PATH, ASDF_DATA_DIR, VOLTA_HOME, or similar environment state, the almost-empty probe environment makes that shim fail. The resolver then reports no compatible Node, so requested Tool Search code mode silently falls back to structured tools even though a valid Node installation is available.
