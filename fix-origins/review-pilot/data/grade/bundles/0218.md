# Case 218

## The bug that later had to be fixed
- What the user saw: An update interrupted with Ctrl-C or SIGTERM while verifying the restarted Gateway appeared to hang for up to the update deadline printing service=unknown health=ready even though the Gateway was healthy (and, separately, large-state installs fell back from candidate admission after a fixed 120 s).
- What the later fix did: Makes restart readiness polling honor the enclosing command-process scope's cancellation and sizes candidate admission's timeout from measured state bytes capped by the step deadline.
- What in the reviewed change was wrong: The commit made a signal during "activating", "restarting", "verifying" call `for (const stop of admission.forward) { stop(); }` and wrapped the Gateway restart/verification in `forward(() => ...)`, while waitForGatewayHealthyRestart kept polling with `const signal = params.deadline?.signal ?? params.signal;` and ignored the stopped scope.
- Why: The headline hang comes from the interrupted-update recovery path added in 59834998f25 (#165863): it stops forward command scopes on a signal during verifying and runs the restart/verification inside such a scope, but the readiness poller (its signal line dates from 2b125389c8b, Sept 22, before this commit) never read the scope signal, so every systemctl spawn died and polling continued until the deadline; that feature shipped with the bug. The second defect (admission using prepared.timeoutMs, unset by default, so a fixed 120 s) dates from acffa7681f0 (#155632) and is a separate never-worked sizing issue not traced further here.

## Reviewers' findings
### Reviewer A (3 findings)
1. **Cancellation also closes the Git rollback command scope** — `src/cli/update-cli/update-command-execution.ts`:671 (confidence high)
   If SIGINT, SIGTERM, or SIGHUP arrives after Git checkout mutation starts but before onTransaction registers the retained transaction, cancellation closes the scope enclosing updateGitInstall. Its immediate rollback also runs inside that scope: runGitRollbackSteps cannot spawn its git reset/checkout commands because spawnCommand rejects with "Command process scope is closed". The checkout can remain partially updated and the Gateway stopped, with no retained transaction available to finish restoration. Immediate rollback needs to execute outside the canceled forward scope.
2. **The staged package operation does not inherit cancellation** — `src/cli/update-cli/update-command-execution.ts`:623 (confidence high)
   For the default package candidate-admission path, stagePackageInstallUpdate starts runPackageInstallUpdate before this scope exists. stagedPackage.run only resolves its continuation and awaits the existing operation; AsyncLocalStorage does not move that operation into the caller's scope. Consequently, a signal during its activation Doctor does not cancel that child. If the Doctor hangs beyond the signal recovery budget, the updater exits before rollback and restart, leaving the Gateway stopped despite announcing recovery.
3. **Cancellation also disables immediate Git rollback** — `src/cli/update-cli/update-command-mutable-signals.ts`:81 (confidence high)
   The new scope wraps all of updateGitInstall, including its internal rollbackError/restoreRuntime recovery. If SIGINT, SIGTERM, or SIGHUP arrives during Git checkout, after the Gateway stops but before onTransaction publishes a retained transaction, stop() aborts this scope. The subsequent Git rollback commands inherit the aborted signal and cannot execute. The outer finalizer has no retained transaction to retry restoration, leaving the Gateway stopped and potentially leaving a partially changed checkout despite announcing recovery before exit.

### Reviewer B (1 findings)
1. **Signal recovery loses its admission at mutation start** — `src/cli/update-cli/update-command-mutable-signals.ts`:74 (confidence high)
   Every real mutable update calls `deferLedgerWrites()` at mutation start, which removes the run from `admissions`. Subsequent restart/verification scopes therefore take this no-admission path, phase updates and interruption recording also become no-ops, and compensation is not registered. If SIGTERM/SIGHUP arrives while restarting or verifying, forward work is not cancelled and the terminal report can remain successful or omit the interruption (the immediate message can also incorrectly say `activating`), rather than reporting the signal and stopping forward work as promised.

### Reviewer C (3 findings)
1. **Late signal after a verified successful activation rolls back or fails a healthy update** — `src/cli/update-cli/update-command-post-update.ts`:885 (confidence medium)
   The in-memory signal phase is only advanced by recordPhase/maybeRestartService and is never cleared once verification succeeds or the run finishes, so it stays 'verifying' for the rest of finalization. If SIGINT/SIGTERM/SIGHUP arrives after the new Gateway restarted and passed verification (e.g. during completePostUpdateMaintenance, deferred plugin convergence, or package-completion cleanup), onSignal takes the recovering path and sets admission.interruption. The final `reportResult(await runPostUpdate())` then calls captured.interruptedResult on the 'ok' result, which unconditionally rewrites it to status 'error', reason 'interrupted'; recoverFailedResult then sees an error with a packageTransaction and runs rollbackFailedUpdate, stopping the healthy new Gateway and reverting to the old package (without the DB backup, since gatewayStartAttempted is true). If the signal lands after that first call, line 907 still rewrites the verified 'ok' result to 'error/interrupted'. The operator who closed the SSH session or pressed Ctrl-C after seeing a healthy Gateway gets an unrequested rollback and an extra outage, or a history row/report saying the update failed while the new version is running, prompting an unnecessary 'openclaw update repair'.
2. **Interruption overwrites the real failure reason and failed step** — `src/cli/update-cli/update-command-mutable-signals.ts`:118 (confidence medium)
   recordMutableUpdateInterruption always replaces `reason` with 'interrupted' and `failedStep` with the synthetic signal step whenever the signal step is not already present. When an update has already failed for a real cause (e.g. candidate-verification-failed, restart-unhealthy, a rollback/restore failure) and the signal arrives later, during rollback or cleanup, the second application in finishSettledUpdate (pendingResult at post-update line 907) or the terminal wrapper rewrites the published terminal result so the report and history show 'interrupted' as the reason and the signal step as the failed step. The operator loses the actual root cause of the failed update and the triage/next-action guidance that depends on the original reason.
3. **Repeated Ctrl-C/SIGTERM ignored for up to the 30-minute recovery budget** — `src/cli/update-cli/update-command-mutable-signals.ts`:281 (confidence low)
   Once the first signal takes the recovering path, the exit gate waits for the whole terminal settlement up to activationTimeoutMs/defaultStepTimeoutMs, which falls back to DEFAULT_UPDATE_STEP_TIMEOUT_MS (30 minutes) for CLI runs. Any further SIGINT/SIGTERM/SIGHUP hits `if (shutdown) return;` and is silently dropped, and the CLI fallback handler has already detached itself. Before this change the first signal exited promptly; now an operator whose rollback or Gateway restart hangs cannot interrupt the updater by pressing Ctrl-C again and has to find and SIGKILL it, which skips the very cleanup this change is meant to guarantee. Even after the budget expires, the exit barrier still awaits in-flight compensations without a bound.

### Reviewer D (1 findings)
1. **Git rollback inherits the cancelled forward scope** — `src/cli/update-cli/update-command-execution.ts`:671 (confidence high)
   The new forward scope encloses all of updateGitInstall, including updateGitCheckout's internal rollbackError/restoreRuntime recovery. If a signal arrives after checkout mutation starts but before the retained transaction is registered, stopping this scope also cancels recovery: runGitRollbackSteps cannot launch its reset/checkout commands because spawnCommandWithInvocation rejects the aborted scope. The updater therefore leaves the checkout unrestored and the Gateway stopped even when the previous runtime is available. Internal Git rollback must execute outside the cancelled forward scope.

### Reviewer E (5 findings)
1. **Interrupting Git activation also cancels checkout rollback** — `src/cli/update-cli/update-command-execution.ts`:671 (confidence high)
   On a managed Git install, send SIGTERM after checkout changes HEAD but before the runner registers its rollback transaction, for example while it sets the new dev branch's upstream. The new scope cancels the Git runner's recovery commands along with its forward commands. The checkout can stay on the candidate commit, and without a verified source rollback or a retained transaction the updater leaves the Gateway stopped.
2. **Post-stop config validation disables signal recovery** — `src/cli/update-cli/update-command-execution-guards.ts`:110 (confidence high)
   If the config changes while the Gateway is stopping, the post-stop refresh reruns candidate validation. The ledger correctly keeps the phase at activating, but the signal tracker stores the requested validating phase. A SIGTERM during that rehearsal takes the pre-activation exit path, seals compensation, and can leave the Gateway stopped.
3. **Migrated finalization can complete successfully after interruption** — `src/cli/update-cli/update-command-mutable-signals.ts`:310 (confidence high)
   If the installed updater receives SIGTERM while the candidate worker owns finalization after a schema migration, the worker is outside the tracked forward scopes and receives no interruption. It can keep mutating state, start the candidate Gateway, and publish a success report even though the parent announced an interruption and exits with code 143.
4. **Staged updates keep running activation commands after a signal** — `src/cli/update-cli/update-command-execution.ts`:623 (confidence high)
   For an update using an explicit package artifact, the staging code starts the install pipeline before this cancellation scope exists. Calling run here resumes and awaits that existing pipeline, so a SIGTERM sent to the updater during the staged candidate's activation Doctor does not reach the Doctor process. The Gateway can remain down while recovery waits for Doctor to finish or for the signal recovery budget to expire.
5. **A signal during final history capture can produce a success report** — `src/cli/update-cli/update-command-post-update.ts`:400 (confidence high)
   After a successful restart, send SIGTERM while the updater is awaiting capture of the completed history record. The signal handler still accepts the signal as a verification interruption, but the pending result was already computed and terminal publication never checks it again. The updater can save a success report without the signal and then exit with code 143.

### Reviewer F (2 findings)
1. **Cancel the staged operation, not just its awaiting caller** — `src/cli/update-cli/update-command-execution.ts`:621 (confidence high)
   For updates using stagedPackage, stagePackageInstallUpdate already started the installation before this command scope exists. Its run() only resolves a continuation and awaits the existing promise, so subsequent installation commands retain their original AsyncLocalStorage context. SIGTERM during a long activation Doctor therefore aborts this empty scope without stopping Doctor. The updater can wait until the activation deadline with the Gateway stopped instead of promptly entering recovery.
2. **Keep immediate Git rollback outside the canceled forward scope** — `src/cli/update-cli/update-command-execution.ts`:671 (confidence high)
   The new scope encloses all of updateGitInstall, including updateGitCheckout's immediate rollbackError recovery. If a signal interrupts git-checkout or arrives after checkout but before the runtime transaction is retained, rollback runs inside the now-aborted scope. Its recovery Git commands fail with 'Command process scope is closed', preventing restoration of the previous checkout. No retained transaction is available for the later finalizer to retry that restoration, so the update leaves the checkout unrecovered and the Gateway stopped.
