# Case 241

## The bug that later had to be fixed
- What the user saw: With the Claude CLI runtime, answers from nested subagents or workflows were lost because the turn ended after the root agent's answer when a task snapshot listed a child before its parent.
- What the later fix did: Replaced the single-pass background-task hold scan with a fixed-point scan (after recording ownership for the whole snapshot) so children listed before parents still get held.
- What in the reviewed change was wrong: Inside the single for-loop over message.tasks it added the gate `(parentTaskId === undefined || input.pendingBackgroundTaskIds.has(parentTaskId) || input.pendingBackgroundTaskIds.has(id))`, so a child seen before its parent in the same snapshot found no held parent and was skipped.
- Why: Before 3d7f8fbf (#182516) nested Agents/Workflows with a parent_task_id were owner=false and never held; that commit introduced holding children of held parents, with the parent-held check evaluated in one pass in snapshot order, which is exactly the ordering defect fixed here. Intervening commits (c93890f, etc.) only renamed calls to tasks.*; the PR body confirms main's scan was single-pass.

## Reviewers' findings
### Reviewer A (1 findings)
1. **Foreground descendant can terminate the outer turn** — `extensions/anthropic/cli-runtime-tasks.ts`:48 (confidence medium)
   When a foreground Agent launches a background child, the parent finishes, and the child’s forwarded notification result arrives before the main query’s final result, the child is now owned by the current input even though it was deliberately excluded from pendingBackgroundTaskIds. Its notification is queued and its task-origin result is therefore treated as the current input’s terminal answer. The iterator closes with the child answer and the foreground parent’s actual final answer is dropped; this is the reverse completion order of the existing foreground-descendant test, which only covers the parent result arriving while the child still runs.

### Reviewer B (1 findings)
1. **Stopping the last nested task leaves the turn open** — `extensions/anthropic/cli.runtime.ts`:484 (confidence high)
   When a background parent has already returned its answer and its nested Agent or Workflow is the only remaining hold, the runtime emits the parent's answer as interim. If Claude then reports the child as stopped, this branch clears the hold, but turn settlement still requires a later result. Stopped tasks produce no follow-up result, so the turn stays active until the watchdog fires.

### Reviewer C (1 findings)
1. **Parent counted as running until its own task_notification, so a child forwarded to the main stream after the parent ended can be treated as consumed by the subagent** — `extensions/anthropic/cli-runtime-tasks.ts`:88 (confidence low)
   recordRunningDescendants removes a launcher from the running map only when that launcher's own task_notification arrives. A background_tasks_changed snapshot that no longer lists the launcher does not remove it, and the fixture shows native emits that snapshot before the launcher's notification. Suppose the nested child's task_notification arrives in that window: the launcher has ended (it has left the snapshot), but its notification has not been processed. Native routes the child's completion to the main conversation, yet parentRuns is true. acceptMessage then deletes the child from pendingBackgroundTaskIds and taskNotifications. The next main-stream result is delivered as terminal and the turn completes. The forwarded child answer arrives after the turn has settled, so the user never gets the nested agent's final answer. The remaining entries in runningDescendants can also make completeTurn abort the warm process.
