# Case 71

## The bug that later had to be fixed
- What the user saw: On PostgreSQL 16, retained one-shot cron jobs could not finish and enabling or disabling a cron job failed with `function json(unknown) does not exist`.
- What the later fix did: Added an engine-owned jsonValue helper that casts bound JSON text with ::json on PostgreSQL and uses json(...) on SQLite, and used it in the cron enabled-state update.
- What in the reviewed change was wrong: The PostgreSQL port of cron finalization kept `eb.fn<string>("json", [eb.val(enabled ? "true" : "false")])` as the jsonSetPath replacement, emitting json($1), a function PostgreSQL 16 does not have.
- Why: Before e96c704 the cron enabled update used SQLite json_set and could not run on PostgreSQL at all; e96c704 introduced the PostgreSQL path via jsonSetPath but kept the SQLite-only json(...) call for the replacement, which only resolves on PG17+ (SQL/JSON constructor), so the PG16 case shipped broken with the port. I read e96c704's diff and jsonSetPath at that commit, which passes the replacement through as `${replacement}::jsonb`, leaving json($1) in the SQL.

### Reviewer F (1 findings)
1. **PostgreSQL still cannot finalize jobs with escaped NULs in their definitions** — `src/cron/store/row-codec.ts`:660 (confidence high)
   A retained one-shot job can be created with a NUL in its agent prompt. The cron store serializes it as an escaped \u0000 in the PostgreSQL text column. When the run finishes, the new enablement update casts the entire definition to jsonb, which rejects that escape even though the update only changes the enabled flag. The finalization transaction rolls back, leaving the job marked as running and its terminal result absent from history.
