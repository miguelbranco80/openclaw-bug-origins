# Case 151

## The bug that later had to be fixed
- What the user saw: Control UI Template review and publish failed with 'Your ClawHub account needs a personal publisher handle.' for accounts whose ClawHub handle has uppercase letters.
- What the later fix did: Lowercases and trims the ClawHub /whoami handle before validating it as the personal publisher.
- What in the reviewed change was wrong: The introducing commit added `const publisher = result.user?.handle;` followed by a lowercase-only `/^[a-z0-9][a-z0-9._-]*$/` check, so a mixed-case whoami handle is rejected as clawhub_identity_required.
- Why: The whoami call and lowercase-only regex check were added together in 94867f9f884 (src/claws/draft-publish.ts), then moved verbatim by the refactors f16e8bc092e7 and d1c8d42588a (Claws to Templates rename) without behavior change. Medium rather than high because I could not confirm ClawHub's whoami always returned GitHub-cased handles when the code was written (if it changed later this would be latent).

## Reviewers' findings
### Reviewer A (3 findings)
1. **Excluded plugins survive in legacy profile paths** — `src/claws/draft-choices.ts`:129 (confidence high)
   For a valid manifest using the supported legacy `metadata.openclaw.config: profiles/custom.yaml`, unchecking a plugin removes its `packages` entry but rewrites extensions only when the file path is exactly `profiles/openclaw.yml`. The custom profile remains in the archive with that plugin extension, so installing the published Claw still installs/enables the plugin the creator excluded.
2. **Excluding a managed avatar makes the draft invalid** — `src/claws/draft-choices.ts`:102 (confidence high)
   If `agent.identity.avatar` names a destination in `workspace.files`, unchecking that source removes the workspace entry but leaves the avatar reference. Manifest validation then rejects the rebuilt package because a local avatar must match a managed destination, so the creator cannot review or publish the Claw without the optional avatar.
3. **Publication uses a Gateway-wide account rather than the acting creator** — `src/claws/draft-publish.ts`:19 (confidence medium)
   On a multi-user Gateway, an administrator publishing from their Control UI does not supply or bind a ClawHub credential to their authenticated user profile. The code loads the process-wide environment/CLI token, so if the Gateway host was logged into ClawHub as another person, the administrator's publish action uploads under that other person's account.

### Reviewer B (3 findings)
1. **[P2] Allow exclusions for every item returned by review** — `packages/gateway-protocol/src/schema/claw-drafts.ts`:44 (confidence high)
   A valid draft can declare more than 128 optional dependencies because manifest packages, MCP servers, and cron jobs have no corresponding count limit. Reviewing a draft with 129 MCP declarations succeeds and returns 129 selectable items, but excluding all of them makes both review and publish fail with INVALID_REQUEST because excluded exceeds maxItems: 128. Creators cannot apply their selections without manually editing the proposal; successive reviews do not help because exclusions are not persisted.
2. **Profile extension dependencies cannot be individually excluded** — `src/claws/draft-choices.ts`:72 (confidence high)
   A valid draft can declare plugins solely in profiles/openclaw.yml's extensions array. Only manifest.packages entries become plugin review items, so these dependencies have no checkbox, and submitting their package IDs as exclusions fails with invalid_review_choices. The creator must remove the entire profile, including unrelated agent settings, to omit one such plugin; otherwise the published Claw still requires its installation.
3. **Removing a profile leaves its explicit manifest pointer dangling** — `src/claws/draft-choices.ts`:126 (confidence high)
   For a supported draft with metadata.openclaw.config set to profiles/openclaw.yml, unchecking that file removes its contents but preserves the metadata pointer. The subsequent package build tries to read the deleted profile and fails with openclaw_profile_read_failed, preventing the creator from reviewing or publishing that selection.

### Reviewer C (7 findings)
1. **Publication uses the Gateway's ClawHub account** — `src/claws/draft-publish.ts`:19 (confidence high)
   If a creator uses a shared Gateway whose environment token or saved ClawHub login belongs to someone else, review and publish both use that host credential. The creator sees the other account as publisher and can publish an immutable version under that account.
2. **Headless administrator clients can publish** — `src/gateway/server-methods/claws-drafts.ts`:43 (confidence high)
   A headless client with a live authenticated administrator WebSocket passes the same check as the Control UI. It can request a review token and publish in sequence with no person opening the review or confirming publication in the UI.
3. **Drafts are created outside the source session's worktree** — `src/gateway/server-methods/claws-drafts.ts`:39 (confidence high)
   When the source chat runs in a local worktree, the Gateway creates the draft in the agent's configured workspace. The generated command gives the agent a relative path, which resolves inside the worktree. The agent either cannot open the draft or writes a separate copy, leaving the Gateway to review the untouched starter document.
4. **Profile extensions are missing from dependency choices** — `src/claws/draft-choices.ts`:67 (confidence high)
   A draft with a plugin declared only in the OpenClaw profile includes that dependency in the archive, and Add resolves it as a plugin. The creator gets no checkbox for that plugin and has to discard the entire profile, including unrelated settings, to remove it through review.
5. **Excluding the avatar file breaks review** — `src/claws/draft-choices.ts`:102 (confidence high)
   After a valid draft maps a file such as avatar.svg to the agent's workspace avatar, unchecking that file removes its workspace mapping but leaves the avatar reference in the manifest. The builder rejects the selection, so the creator cannot get a fresh review token without editing the proposal.
6. **Excluding the profile can leave a broken metadata reference** — `src/claws/draft-choices.ts`:125 (confidence high)
   A valid manifest can point to profiles/openclaw.yml through the supported legacy openclaw.config metadata key. Unchecking that profile removes the file but retains the pointer, so the next review fails when the builder tries to open the deleted profile.
7. **A UTF-8 BOM makes every draft save look stale** — `src/claws/draft.ts`:66 (confidence high)
   If an editor writes the draft with a UTF-8 byte-order mark, the read method strips it before calculating the revision. Save compares that revision with a hash of the original bytes, including the mark. An unchanged draft therefore produces a conflict even immediately after reloading.

### Reviewer D (2 findings)
1. **Profile extension dependencies are missing from review choices** — `src/claws/draft-choices.ts`:67 (confidence high)
   A valid proposal can declare plugins in profiles/openclaw.yml under extensions without declaring them in manifest.packages. These plugins remain in the published archive and become installation requirements when adding the Claw, but review exposes no individual plugin choices for them. Attempting to exclude their package IDs is rejected as invalid_review_choices, so the creator must remove the entire profile, including unrelated agent settings, to exclude those dependencies.
2. **Excluding an avatar file makes the selected package invalid** — `src/claws/draft-choices.ts`:102 (confidence high)
   When agent.identity.avatar references a workspace.files destination backed by an authored SVG file, the initial draft reviews successfully. Unchecking that file removes its workspace mapping but leaves agent.identity.avatar unchanged. Building the selected package then fails validation because the avatar no longer matches a workspace.files destination, preventing the creator from reviewing or publishing the Claw without that optional file.

### Reviewer E (4 findings)
1. **Empty top-level draft description discards the manifest's agent description** — `src/claws/draft-choices.ts`:97 (confidence high)
   createClawDraft seeds the draft with description: "". If the agent writes the description only in the CLAW.md frontmatter (agent.description), as the draft-format reference example does, and leaves the top-level field empty, `choices?.description ?? proposal.description ?? manifest.agent.description` stops at "" because ?? does not skip empty strings. The code then sets manifest.agent.description to undefined. The review shows an empty description, and if the creator publishes without retyping it, the package has no description.
2. **Review always overwrites the agent display name with the package slug** — `src/claws/draft-choices.ts`:100 (confidence medium)
   applyClawDraftChoices unconditionally sets manifest.agent.name = name, where name is the lowercase package slug, even when no choices are given. A draft that declares agent.name: "Portable Agent" (as in the documented format) is published with agent.name "portable-agent-slug", so installers see the slug instead of the author's chosen display name.
3. **ClawHub identity failures are reported as a draft-content problem** — `src/gateway/server-methods/claws-drafts.ts`:89 (confidence medium)
   reviewClawDraft and publishClawDraft first call /api/v1/whoami through fetchClawHubJson. An expired or revoked `clawhub login` token (401), a rate limit, or a network error throws a ClawHubRequestError, not a ClawProjectError. draftError then returns the generic "The Claw draft could not be processed. Check its contents and try again." The creator is sent to edit a valid draft instead of signing in again or retrying.
4. **Definitive publish rejections are reported as unconfirmed with no reason** — `src/claws/draft-publish.ts`:122 (confidence low)
   The catch around the POST to /api/v1/packages turns every error into publication_unconfirmed, including definite HTTP rejections such as 409 (version already exists), 400 (validation), or 403 (handle not allowed). For example, a creator who publishes 0.1.0 again is told publication "was not confirmed" and to check ClawHub, but never learns that the version already exists or which field ClawHub rejected.

### Reviewer F (2 findings)
1. **Profile plugin dependencies are absent from review selections** — `src/claws/draft-choices.ts`:67 (confidence high)
   When a proposal declares plugins in profiles/openclaw.yml's extensions array, the review lists no plugin items for those dependencies because it enumerates only manifest.packages. Their exclusion IDs are rejected as unknown, and publication retains the extensions. Consumers subsequently install those dependencies through planClawExtensions. The creator cannot remove an individual profile plugin while retaining the profile's other settings.
2. **Excluding the avatar file leaves an invalid manifest** — `src/claws/draft-choices.ts`:102 (confidence high)

The subsequent build fails manifest validation because the avatar must match a workspace.files destination. Consequently, unchecking this optional file prevents review and publication instead of producing a package without the avatar.
