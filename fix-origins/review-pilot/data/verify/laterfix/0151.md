## F1: Publication uses the Gateway's ClawHub account
- Where: `src/claws/draft-publish.ts`:19
- Claimed failure: If a creator uses a shared Gateway whose environment token or saved ClawHub login belongs to someone else, review and publish both use that host credential. The creator sees the other account as publisher and can publish an immutable version under that account.

## F2: A UTF-8 BOM makes every draft save look stale
- Where: `src/claws/draft.ts`:66
- Claimed failure: If an editor writes the draft with a UTF-8 byte-order mark, the read method strips it before calculating the revision. Save compares that revision with a hash of the original bytes, including the mark. An unchanged draft therefore produces a conflict even immediately after reloading.

- Later fixes touching this file: none

## F3: Review always overwrites the agent display name with the package slug
- Where: `src/claws/draft-choices.ts`:100
- Claimed failure: applyClawDraftChoices unconditionally sets manifest.agent.name = name, where name is the lowercase package slug, even when no choices are given. A draft that declares agent.name: "Portable Agent" (as in the documented format) is published with agent.name "portable-agent-slug", so installers see the slug instead of the author's chosen display name.

- Later fixes touching this file: none

## F4: Empty top-level draft description discards the manifest's agent description
- Where: `src/claws/draft-choices.ts`:97
- Claimed failure: createClawDraft seeds the draft with description: "". If the agent writes the description only in the CLAW.md frontmatter (agent.description), as the draft-format reference example does, and leaves the top-level field empty, `choices?.description ?? proposal.description ?? manifest.agent.description` stops at "" because ?? does not skip empty strings. The code then sets manifest.agent.description to undefined. The review shows an empty description, and if the creator publishes without retyping it, the package has no description.

- Later fixes touching this file: none

## F5: Excluding the avatar file breaks review
- Where: `src/claws/draft-choices.ts`:102
- Claimed failure: After a valid draft maps a file such as avatar.svg to the agent's workspace avatar, unchecking that file removes its workspace mapping but leaves the avatar reference in the manifest. The builder rejects the selection, so the creator cannot get a fresh review token without editing the proposal.

- Later fixes touching this file: none

## F7: Drafts are created outside the source session's worktree
- Where: `src/gateway/server-methods/claws-drafts.ts`:39

The generated command gives the agent a relative path, which resolves inside the worktree. The agent either cannot open the draft or writes a separate copy, leaving the Gateway to review the untouched starter document.

## F8: Definitive publish rejections are reported as unconfirmed with no reason
- Where: `src/claws/draft-publish.ts`:122
- Claimed failure: The catch around the POST to /api/v1/packages turns every error into publication_unconfirmed, including definite HTTP rejections such as 409 (version already exists), 400 (validation), or 403 (handle not allowed). For example, a creator who publishes 0.1.0 again is told publication "was not confirmed" and to check ClawHub, but never learns that the version already exists or which field ClawHub rejected.

## F9: ClawHub identity failures are reported as a draft-content problem
- Where: `src/gateway/server-methods/claws-drafts.ts`:89
- Claimed failure: reviewClawDraft and publishClawDraft first call /api/v1/whoami through fetchClawHubJson. An expired or revoked `clawhub login` token (401), a rate limit, or a network error throws a ClawHubRequestError, not a ClawProjectError. draftError then returns the generic "The Claw draft could not be processed. Check its contents and try again." The creator is sent to edit a valid draft instead of signing in again or retrying.

- Later `fix`/`revert` commits on main touching this file (1, oldest first):
