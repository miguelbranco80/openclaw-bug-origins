# Case 0203: findings and later fixes

The reviewed change is commit `5d3e157432a84e085eebf5a43a7ae471ff0fefbb` (2026-11-04).

## F1: Guest's saved sidebar owner filter for another person now makes every sidebar list request fail
- Where: `src/gateway/session-profile-activity-policy.ts`:461
- Claimed failure: Before this change guests could pick another person as the sidebar owner filter, and the UI persists that choice in localStorage as 'owner:<id>' (loadStoredSidebarSessionOwnerFilter) and sends it as ownerId on every sidebar sessions.list. After upgrade the Gateway throws FORBIDDEN for that ownerId, so the guest's sidebar session list fails on every load and refresh instead of falling back. The owner facet that would let the UI show and reset the selection comes from the same failing response, and only the Activity page controller was taught to handle the new FORBIDDEN; the sidebar still holds the stale filter.

- Later `fix`/`revert` commits on main touching this file (1, oldest first):
  - `4005ca2f0faa` 2026-11-10 fix: guests cannot select owners of readable sessions (#196446)

## F2: Saved owner filter leaves the sidebar on a denied query after demotion
- Where: `ui/src/components/session-owner-filter.ts`:149

In the agent-chip sidebar, the restored filter now produces FORBIDDEN, and the automatic reset requires a successful result from that same query. The sidebar stays on the failed filter across reloads until the user manually chooses a different owner filter.

## F4: Foreign-filter response reveals whether an agent has hidden sessions
- Where: `src/gateway/session-utils-list.ts`:98
- Claimed failure: On the cached WebSocket list path, a session-only guest who supplies a foreign ownerId and an agentId gets a successful empty result when the configured agent has no sessions. Once another user creates a draft on that agent, the same request returns FORBIDDEN even though the draft is invisible to the guest. Empty partitions skip authorization, while nonempty partitions run it before checking row visibility.

## F6: Agent owner/creator filters are rejected as 'other people's activity' for session-only callers
- Where: `src/gateway/session-profile-activity-policy.ts`:450
- Claimed failure: ownerId and creatorId are actor-id filters that also match agents (ownerId is the 'assignable owner identity', documented as a configured agent ID for agent owners; creators can be agents). For any caller with a viewer ID (session-only guest, or an agent run started by one), the policy runs every creatorId/ownerId through resolveSessionProfileId and compares it with the viewer's profile ID. An agent ID such as 'main' never matches, so a guest filtering the sidebar by an agent owner, or the sessions_list agent tool called with ownerId/creatorId set to an agent, now gets FORBIDDEN 'Other people's activity is private' even though no person's activity is involved. The owner-facet change (effectiveOwner.identity.id === activityViewerId) also drops agent owners from the facet, so the guest's agent-owner filter options disappear.

  - `4005ca2f0faa` 2026-11-10 fix: guests cannot select owners of readable sessions (#196446)
