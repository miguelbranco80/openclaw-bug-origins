## F2: Sidecar churn during guarded copy now aborts the snapshot instead of retrying
- Where: `src/infra/sqlite-readonly-location.ts`:179
- Claimed failure: copySourceFile pins the source fd, resolves realpath, then lets copyRootFileSync re-open the path by name and compare identity. If the file is deleted or replaced between the pin and the helper's open, the helper throws an FsSafeError (not-found or identity mismatch) rather than SqliteSourceChangedError. prepareArtifactPreservingCopy only retries SqliteSourceChangedError, so the snapshot fails on the first try. The previous code copied from the pinned fd and turned drift into a retryable SqliteSourceChangedError, and the async sibling (copyPreparedLocation) still does this through its finally-block identity check. The common trigger is a database in rollback (DELETE) journal mode being written during the snapshot: SQLite deletes and recreates <db>-journal on every commit. The WAL file can also be removed when the last connection closes. A commit landing in that window makes update candidate-state inspection, update generation hashing (readCommittedContent), state ownership checks, or artifact-preserving state reads fail with a raw fs-safe error, where they used to retry and settle. The worker's contention classifier also no longer labels the failure retryable.

## F3: Windows short-path caches can block SQLite snapshots
- Where: `src/infra/sqlite-readonly-location.ts`:180
- Claimed failure: When LOCALAPPDATA or an explicit staging root uses a Windows 8.3 path such as C:\Users\RUNNER~1\AppData\Local, the staging directory keeps that spelling. The guarded copier compares ordinary and native realpaths, which can interpret the short spelling and its expanded spelling as a moved root. Strict update or Doctor inspection then fails even though the database is stable and the cache is writable.
