## F1: Repair closes remapped operations without verifying the previous installation
- Where: `src/infra/package-update-activation.ts`:341
- Claimed failure: If an update stops in prepared or before displacement in publishing, a remount leaves the previous package installed under its projected identity. The fallback guard compares the live identity with the unprojected identities and falls through. Neither verification branch runs, so repair archives the unfinished operation and clears the update block without checking the previous tree or its launchers. If the lease is unchanged, it also reports a manual replacement that never happened.

## F2: Repair rejects launchers published by the updater
- Where: `src/infra/package-update-activation-settlement.ts`:73
- Claimed failure: When publication copies a launcher into place, the installed launcher gets a different inode from the staged launcher. The updater records that inode in publications, or in the launcher intent if it is interrupted before acknowledgement. After a remount, repair ignores both records and compares the installed inode with the previous or staged inode. It rejects an intact installed candidate with an inode-mapping error and leaves the journal active.

## F3: Repair rejects hot SQLite journals before replay can run
- Where: `src/infra/package-update-activation-journal.ts`:365
- Claimed failure: If the updater dies during a SQLite commit, readForRecovery can recover the committed record from a snapshot while leaving the live rollback journal for replay under the executor fence. The new inspectRemount call rereads the live database before that replay. SQLite returns SQLITE_READONLY_ROLLBACK, so public repair aborts and leaves the journal blocking recovery, even when the filesystem device numbers are unchanged.

## F4: Remounted repair bypasses the 'recovery still required' guard and archives unfinished publications unverified
- Where: `src/infra/package-update-activation.ts`:341
- Claimed failure: The guard that keeps a pending operation for its recovery owner (assertNoPendingPackageActivation when the live package is still the recorded previous or candidate) compares replacementIdentity against the raw historical descriptor identities, while the rest of the function now uses the device-mapped previousIdentity/candidateIdentity. After a reboot/remount changes device numbers, the live package's identity never equals a raw historical identity, so the guard is skipped. Example: a 'publishing' (or 'publication-complete', or a 'prepared' operation with an armed rollback) journal interrupted while the original package is still installed (replacement == mapped previous): manualReplacement and externalPublication are both false, so `openclaw update repair` falls into the generic settlePackageActivationCustody path and archives the operation as 'recovery-lease-missing'/'superseded-by-manual-install' without restoration or any tree/launcher verification. The settlement-only journal permits this write because the intent is 'settled'. Without remount the same state is refused as needing recovery; with remount, partially rewritten launchers pointing at the (now archived) candidate are left behind and the operator is told the old operation was settled.

## F5: Repair rejects newer releases after some supported update targets
- Where: `src/infra/package-update-activation.ts`:455
- Claimed failure: An interrupted update can record an explicit target such as 2026.9.4-dev.1. If the operator then manually installs 2026.10.1 after a remount, the release comparator returns null because it excludes dev prereleases. Repair reports that it requires a newer manual installation and leaves the journal active without verifying the newer package.
