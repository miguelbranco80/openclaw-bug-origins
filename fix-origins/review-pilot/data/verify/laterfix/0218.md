## F2: Interruption overwrites the real failure reason and failed step
- Where: `src/cli/update-cli/update-command-mutable-signals.ts`:118
- Claimed failure: recordMutableUpdateInterruption always replaces `reason` with 'interrupted' and `failedStep` with the synthetic signal step whenever the signal step is not already present. When an update has already failed for a real cause (e.g. candidate-verification-failed, restart-unhealthy, a rollback/restore failure) and the signal arrives later, during rollback or cleanup, the second application in finishSettledUpdate (pendingResult at post-update line 907) or the terminal wrapper rewrites the published terminal result so the report and history show 'interrupted' as the reason and the signal step as the failed step. The operator loses the actual root cause of the failed update and the triage/next-action guidance that depends on the original reason.

## F3: Late signal after a verified successful activation rolls back or fails a healthy update
- Where: `src/cli/update-cli/update-command-post-update.ts`:885
- Claimed failure: The in-memory signal phase is only advanced by recordPhase/maybeRestartService and is never cleared once verification succeeds or the run finishes, so it stays 'verifying' for the rest of finalization. If SIGINT/SIGTERM/SIGHUP arrives after the new Gateway restarted and passed verification (e.g. during completePostUpdateMaintenance, deferred plugin convergence, or package-completion cleanup), onSignal takes the recovering path and sets admission.interruption. The final `reportResult(await runPostUpdate())` then calls captured.interruptedResult on the 'ok' result, which unconditionally rewrites it to status 'error', reason 'interrupted'; recoverFailedResult then sees an error with a packageTransaction and runs rollbackFailedUpdate, stopping the healthy new Gateway and reverting to the old package (without the DB backup, since gatewayStartAttempted is true). If the signal lands after that first call, line 907 still rewrites the verified 'ok' result to 'error/interrupted'. The operator who closed the SSH session or pressed Ctrl-C after seeing a healthy Gateway gets an unrequested rollback and an extra outage, or a history row/report saying the update failed while the new version is running, prompting an unnecessary 'openclaw update repair'.

## F6: Repeated Ctrl-C/SIGTERM ignored for up to the 30-minute recovery budget
- Where: `src/cli/update-cli/update-command-mutable-signals.ts`:281
- Claimed failure: Once the first signal takes the recovering path, the exit gate waits for the whole terminal settlement up to activationTimeoutMs/defaultStepTimeoutMs, which falls back to DEFAULT_UPDATE_STEP_TIMEOUT_MS (30 minutes) for CLI runs. Any further SIGINT/SIGTERM/SIGHUP hits `if (shutdown) return;` and is silently dropped, and the CLI fallback handler has already detached itself. Before this change the first signal exited promptly; now an operator whose rollback or Gateway restart hangs cannot interrupt the updater by pressing Ctrl-C again and has to find and SIGKILL it, which skips the very cleanup this change is meant to guarantee. Even after the budget expires, the exit barrier still awaits in-flight compensations without a bound.

## F7: Staged updates keep running activation commands after a signal
- Where: `src/cli/update-cli/update-command-execution.ts`:623
- Claimed failure: For an update using an explicit package artifact, the staging code starts the install pipeline before this cancellation scope exists. Calling run here resumes and awaits that existing pipeline, so a SIGTERM sent to the updater during the staged candidate's activation Doctor does not reach the Doctor process. The Gateway can remain down while recovery waits for Doctor to finish or for the signal recovery budget to expire.
