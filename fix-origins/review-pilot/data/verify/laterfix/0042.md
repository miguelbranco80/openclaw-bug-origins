## F2: Skill preparation can lose an acknowledged first message
- Where: `src/gateway/server-methods/chat-send-agent-dispatch.ts`:302
- Claimed failure: When an attributed user sends the first ordinary message to a session key with no stored row, the Gateway can return `status: started` without staging the input or committing a transcript receipt. If skill selection then fails, for example because a concurrent library edit invalidates the read, dispatch never reaches session initialization. The error fallback requires an existing session row or a prepared initial row, so the user gets a run error and their acknowledged message is missing from history. Previously this selection failure rejected the request before acknowledgement.

## F4: An accepted steer blocks later follow-up admission
- Where: `src/gateway/server-methods/chat-send-handler.ts`:581
- Claimed failure: The handler reserves a FIFO ticket even after the active runtime has accepted a steer. If that runtime is still inside a long tool call, it can take up to two minutes to confirm the steer in the transcript. A subsequent `queueMode: followup` send can receive `status: started` but remain blocked outside the follow-up queue until the steer settles. Before the change, accepted steers did not take a reply-admission ticket, so the follow-up could be queued while the active run was still working.

## F5: Slow-send diagnostics miss WebSocket work before the handler
- Where: `src/gateway/server-methods.ts`:282
- Claimed failure: WebSocket requests resolve `expectedProfileId` and may wait for transport admission before calling `handleGatewayRequest`. The new timer starts inside that call. If either earlier step takes several seconds and the handler responds in under a second, the operator sees a slow acknowledgement with no `slow chat send` request record, and the new phase metrics omit the delay.
