# Case 0011: findings to check

## F1: Negative resolution is cached for the life of the process
- Where: `src/infra/node-runtime-executable.ts`:92
- Claimed failure: When no candidate succeeds, null is cached under a key built only from the platform, runtime version, flag, PATH and PATHEXT. That happens if Node is installed or upgraded after the Gateway starts, or if one cold-start probe hits the 5 s timeout on a loaded machine. Every later resolveToolSearchConfig call then reports code mode unsupported and silently uses tools mode, and tool_search_code keeps failing with 'requires an installed Node runtime', until the Bun-hosted process restarts. No warning names the cause.

## F2: Node discovery can stall the Gateway with Tool Search disabled
- Where: `src/agents/tool-search-config.ts`:59
- Claimed failure: On a Bun-hosted Gateway, the first ordinary agent turn with Tool Search disabled or unset still probes for Node because the default mode is code. Each candidate runs synchronously with its own five-second timeout. A stale Node shim that hangs can freeze the Gateway for five seconds, delaying unrelated requests as well as the current turn. Multiple hanging candidates compound the delay.

## F3: Startup output is accepted as part of the executable path
- Where: `src/infra/node-runtime-executable.ts`:84
- Claimed failure: If an earlier node launcher on PATH prints a startup notice to stdout before forwarding to a compatible Node, the resolver caches the notice and the reported executable path as one string. It stops searching even if a plain Node executable appears later on PATH. The Gateway advertises tool_search_code, but calls fail because the cached string is not an executable path.

## F4: Cached Node paths survive installation and upgrade changes
- Where: `src/infra/node-runtime-executable.ts`:67
- Claimed failure: If a Bun Gateway probes before Node is installed, installing a compatible Node into a directory already on PATH leaves Tool Search in structured mode. If a package upgrade removes the cached executable and puts a working replacement elsewhere on the same PATH, the Gateway keeps advertising code mode and calls fail with ENOENT. Both results persist across config reloads because the cache key stays the same.

## F5: Sterile probe env rejects version-manager Node shims (Volta, asdf, mise)
- Where: `src/infra/node-runtime-executable.ts`:78
- Claimed failure: Each PATH candidate is probed with buildProbeEnv(env), which keeps only SystemRoot/WINDIR/TEMP/TMP/TMPDIR and drops HOME, PATH, VOLTA_HOME, ASDF_DATA_DIR and similar. On a Bun-hosted install where Node comes from a version manager (a common setup), the `node` on PATH is a shim that needs HOME or its own env vars to pick a real Node version. Without them the shim exits non-zero (for example 'No version is set for command node' or a Volta home error), so every candidate is skipped and null is cached. isToolSearchCodeModeSupported() then returns false and Tool Search quietly drops from code mode to tools mode under Bun, even though a compatible Node is installed. resolveTestNodeExecPath (which used to probe with the full process.env) now throws 'Unable to locate a Node executable' on the same machines.

## F6: Node version-manager shims lose their launch environment
- Where: `src/infra/node-runtime-executable.ts`:80
- Claimed failure: When the only compatible Node is exposed through an asdf shim that resolves the asdf command through PATH, invoking node from the operator's shell works. The probe strips PATH and version-manager settings, so the shim cannot find asdf in a directory such as /opt/homebrew/bin. The Gateway silently falls back to structured Tool Search despite having a compatible Node available.
