# Case 0273: findings to check

## F1: Capture cleanup failure turns accepted checkpoints into errors and blocks every later checkpoint
- Where: `src/gateway/worker-environments/local-workspace-projection-operation.ts`:1667
- Claimed failure: removeLocalWorkspaceCheckpointCapture runs unguarded in the finally block after the guest has resumed and canonical acceptance has finished. It also runs before pausing in prepareLocalWorkspaceCheckpointCapture, and on the unchanged-probe path in checkpointLocalWorkspace. If removing the snapshot fails, the error replaces the checkpoint's result. Examples: rmSync fails with a code other than EACCES/EPERM/ENOTEMPTY; chmod fails with EPERM on a guest-created directory owned by another UID; the native helper times out or is killed on a very large tree. The command is reported as failed even though its bytes were accepted, and a typed error from run (rejection or conflict) is masked. The leftover checkpoint-capture then makes the leftover removal throw again at the start of every later checkpoint, including unchanged ones. The sandbox cannot checkpoint again until someone removes the directory by hand.

## F2: Snapshots can delete canonical files backed by host mounts
- Where: `src/gateway/worker-environments/local-workspace-manifest-scan.ts`:545
- Claimed failure: Bind-mount a directory containing an already accepted file over an ordinary empty directory inside the btrfs projection, then edit a different file. The live scan can see the mounted file, but the btrfs snapshot contains the underlying empty directory. That directory has no inode-2 marker, so checkpointing treats the missing file as a guest deletion and removes it from the canonical worktree even though it remains visible in the guest.

## F3: Foreign-owned snapshot directories can block all later checkpoints
- Where: `src/infra/fs-safe-copy.worker.ts`:39
- Claimed failure: A non-root Gateway can read a guest-created directory owned by another UID, such as a root-owned 0755 directory created through a writable rootful Docker sandbox. The snapshot preserves that ownership. Cleanup cannot unlink files inside the directory, and the repair skips chmod because the owner's mode bits already include 0700. The command reports a checkpoint failure after its edits have reached canonical storage. Subsequent checkpoints fail while removing the same leftover snapshot, even if the directory is removed from the live guest.

## F4: Snapshot copy failures no longer fall back to the paused Git capture path
- Where: `src/gateway/worker-environments/local-workspace-checkpoint.ts`:1251
- Claimed failure: On a btrfs subvolume projection, every changed checkpoint now depends on the native copy subprocess. Only errors coded CLONE_UNAVAILABLE, EXDEV or ENOSYS fall back to run(). Other failures make the whole checkpoint throw instead of using the existing paused Git capture, which would have succeeded. Examples are the generic "Native worktree copy failed: <termination>" errors from write() (timeout, killed, process-tree-extinction failure), EPERM/EACCES from snapshot creation, and ENOSPC. Each mutating command's finalization then fails, and keeps failing while the condition lasts. Before this change these checkpoints did not depend on the native helper at all.

## F5: Native benchmark loses its report on a standard cgroup v2 host
- Where: `scripts/perf/local-workspace-checkpoint-measure.ts`:2285
- Claimed failure: Run the native benchmark directly on a Linux host where /sys/fs/cgroup exposes the actual cgroup v2 root. Its cpu.stat exists, so the script enables CPU accounting, but root cgroups have no cpu.max. After the measured commands complete, the report builder throws ENOENT and the operator gets no benchmark report.
