# Case 0163: findings to check

## F1: Doctor overrides intentionally restrictive allowlists
- Where: `src/config/skill-workshop-plugin-migration.ts`:72
- Claimed failure: An operator who hand-writes a config for the plugin-based release with `plugins.allow: ["memory-core"]` to keep Workshop off will have Workshop enabled the next time they run `openclaw doctor --fix`. The migration treats every unmarked restrictive allowlist as built-in-era policy, so it adds `skill-workshop` even when the operator deliberately excluded it after the plugin returned.

## F2: A failed capability refresh leaves the enable button stuck
- Where: `ui/src/pages/skill-workshop/plugin-availability.ts`:55
- Claimed failure: If `plugins.setEnabled` succeeds but the event-triggered `plugins.uiDescriptors` request times out, the Gateway has enabled Workshop while the page still has the old method catalog. The success path leaves the button disabled on “Turning on…” and offers no retry, so the Workshop never loads on that connection unless a later capability refresh succeeds.

## F3: Enable button stays stuck on 'Turning on…' when the enable succeeds but Workshop methods never appear
- Where: `ui/src/pages/skill-workshop/plugin-availability.ts`:55
- Claimed failure: On a successful plugins.setEnabled the owner leaves state at {status:'off', enabling:true} and relies solely on the method catalog gaining skills.workshop.list. If the response reports restartRequired, or the plugin is enabled but fails to load/register its methods, the catalog never changes, sync() is never re-run with a new client, and the page shows a permanently disabled 'Turning on…' button with no error, no retry and no hint that a restart is needed; the result of the request (restartRequired/warnings) is discarded.

## F4: Workshop offers an enable button that policy always rejects
- Where: `ui/src/pages/skill-workshop/view.tsx`:169
- Claimed failure: An admin sees Turn on Skill Workshop even when `plugins.enabled` is false, a current `plugins.deny` includes `skill-workshop`, or `OPENCLAW_CONFIG_READONLY=1` makes the config immutable. In each case the Gateway refuses the request and the page re-enables the same button, so every click fails until the underlying policy changes.

## F5: Normal Gateway startup skips the allowlist migration
- Where: `src/commands/doctor/shared/legacy-config-migrations.runtime.skills.ts`:21
- Claimed failure: An operator who upgrades outside `openclaw update` and starts the Gateway with an otherwise valid built-in-era config such as `plugins.allow: ["memory-core"]` still loses Workshop. The startup preflight accepts the valid config without running this Doctor migration, so Workshop stays off and learned skills disappear from agent prompts until the operator repairs the config.

## F6: Availability stays stale when Workshop methods remain absent
- Where: `ui/src/pages/skill-workshop/plugin-availability.ts`:29
- Claimed failure: If Workshop is enabled but failed to load, the open page displays the load-failure state. Disabling the plugin from another client publishes a new plugin generation, but the Workshop method is absent both before and after that change. The page keeps the same client and skips rereading `plugins.list`, so it still says Workshop is turned on and gives the admin no enable button until they reopen the page.

## F7: Unmarked configs with a deliberate exclusive plugins.allow get skill-workshop added and are never stamped
- Where: `src/config/skill-workshop-plugin-migration.ts`:72
- Claimed failure: The allowlist rule treats any unmarked config whose previous and next plugins.allow both omit skill-workshop as 'built-in era'. Configs that are hand-written or created by a first write (stampConfigWriteMetadata skips stamping when previousConfig is undefined) never get the marker; worse, stampSkillWorkshopPluginMigration now refuses to stamp on every later ordinary write because this rule always reports a change. So an operator on a current release who intentionally sets plugins.allow: ["telegram"] to harden the install sees a persistent 'needs migration' legacy warning, and openclaw doctor --fix / startup migration silently appends skill-workshop to their allowlist, turning on a plugin that loads learned skills into prompts and runs autonomous learning against their explicit policy. Before this change such a write stamped the marker and left the allowlist alone.
