# Case 0186: findings to check

## F1: Model-context reads now rethrow every error, not just bounded-limit rejections
- Where: `extensions/codex/src/app-server/session-history.ts`:134
- Claimed failure: The catch now rethrows any error for view "model-context", not only the new RangeError from the limit. Before this change, ordinary read failures such as SessionTranscriptReadFenceError ("Session transcript changed during context read" when an unadmitted async read races an append), a CodexHistoryRejection for a malformed header, or the 60 s worker timeout returned undefined. Callers then logged a warning and continued with empty or previous history (attempt-context.ts warn branch, run-attempt-context `?? []` and `?? historyState.messages`). Those transient failures now abort the whole Codex attempt during prompt preparation, so the user sees a failed turn where the run used to continue.

## F2: An empty branch summary can erase the bounded context
- Where: `src/config/sessions/session-accessor.sqlite-model-context.ts`:264
- Claimed failure: A caller can append a short user message followed by a branch summary with an empty summary string. With maxEvents set to 1 and enough bytes for either entry, the bounded reader spends the only slot on the summary. The context builder skips empty branch summaries, so the caller receives an empty message list even though the latest visible message fits.

## F3: A history read failure suppresses successful compaction reporting
- Where: `extensions/codex/src/app-server/event-projector-tool-transcript.ts`:602
- Claimed failure: If Codex completes native compaction after the current turn adds a mirrored message or tool frame that exceeds the history budget, the completion handler's history read throws. The notification controller only logs the exception at debug level. The handler skips the after-compaction hook, the transcript activity entry, and the compaction-end event, so the session can omit a compaction that actually completed.

## F4: Compaction hook reads switched to the bounded, throwing model-context view inside event handlers
- Where: `extensions/codex/src/app-server/event-projector-tool-transcript.ts`:602
- Claimed failure: readMirroredSessionMessages used the native-evidence view, which returned [] on failure. It now uses "model-context", which rethrows. It runs inside handleItemStarted and handleItemCompleted for contextCompaction items, without an admission receipt, while the same run is still checkpointing tool messages into the transcript. A concurrent append makes validateSessionTranscriptContextVersion throw. A newest tool frame larger than the byte budget, which is likely right when Codex compacts a full context, makes the limit throw. Either way the notification handler throws: before/after compaction hooks do not run, and persistCodexContextCompactionActivity and the compaction end event are skipped. Hooks that do run also lose tool-result details and private metadata they used to receive from the native-evidence view.

## F5: An older ambiguous tool result blocks a valid recent context
- Where: `src/config/sessions/session-accessor.sqlite-model-context.ts`:230
- Claimed failure: If two older calls share an ID and a displaced result matches both, a size limit can cut away just one of those calls. The reader then rejects the entire context because the result would gain an owner. It rejects even when a shorter suffix containing a newer complete tool frame and the latest user message fits. Codex consequently fails before submitting the next turn.

## F6: Byte budget counts raw payload bytes such as base64 images against tokens*8, so one large recent message truncates or fails the read
- Where: `src/config/sessions/session-accessor.sqlite-model-context.ts`:172
- Claimed failure: maxBytes is contextTokenBudget*8 (about 1 MB at 128k tokens), measured as octet_length of the projected event JSON. Inline image data and large tool outputs count byte for byte, although they cost few tokens or are sanitized later. The tail scan breaks at the first entry that does not fit instead of skipping it. So one recent 2-4 MB photo or screenshot tool result drops all older history from before_prompt_build hooks and context-engine input, even though the history would easily fit the model's context. If that entry is in the newest message or tool frame, the read throws "cannot fit the model-context limit" and the turn or compaction handling fails until the user runs /reset.
