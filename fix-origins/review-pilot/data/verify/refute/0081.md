# Case 0081: findings to check

## F1: Sweeper now settles retired yielded runs as errors when child authority is not 'verified'
- Where: `src/agents/subagents/registry/subagent-registry-read.ts`:166
- Claimed failure: The sweeper no longer gates on (!executionRetired || waitForMessage), and every run restored after a restart is retired, so every restored yielded run reaches settleUnreachableYieldedSubagentRun. That function now converts 'continuable' into 'unreachable' whenever resolveSubagentYieldWaitSource returns undefined. That happens when getRecordedSubagentChildAuthority is not 'verified', for example a legacy-unverified record whose childSessionIdentity lacks lifecycleRevision. It also happens when a grandchild's completionRequesterLifecycleRevision or requesterRunId does not line up with the parent run. A nested child that is still waiting for its own descendants is then force-completed with "Descendant completion can no longer continue this yielded requester." Before this change it stayed parked. Startup resolveSessionYieldWait likewise marks it 'unreachable' and records a failure terminal.

## F2: Failed nested handoff leaves the enclosing requester waiting
- Where: `src/agents/subagents/registry/subagent-registry-requester-wake-mutation.ts`:234
- Claimed failure: If a root yields for child A and A yields for child B, a permanent rejection of B's handoff marks A's session failed but leaves A's registry run paused. The lifecycle write updates the session row without settling the native task, and the sweeper's descendant-loss check applies only to retired runs. The root can still see A as waiting and never receive A's terminal result.

## F3: Restart drops user turns in previously spawned dashboard chats
- Where: `src/config/sessions/session-run-lifecycle-projection.ts`:114
- Claimed failure: After a visible spawned task finishes, a user can reopen its dashboard chat and start a new turn. If the Gateway restarts during that turn, the session's original `createdVia: "spawn"` stamp prevents shutdown from saving a recovery marker and startup from recovering the turn. The user's follow-up no longer resumes as it did before the change.

## F4: Retry loses the failure notice after the lifecycle commits
- Where: `src/agents/subagents/registry/subagent-registry-requester-wake-mutation.ts`:241
- Claimed failure: If the requester lifecycle commits as failed but the separate transcript append hits a transient write error, settlement retries the lifecycle event. The `requireYielded` check now rejects it because the run is already failed, so the retry completes without appending the classified guidance. The user sees the failed state without the notice explaining how to recover the child work.

## F5: Upgrade closes legacy paused tasks that still accept continuations
- Where: `src/agents/subagents/registry/subagent-registry-sweep-settle.ts`:52
- Claimed failure: A paused native child saved by an older release can have neither a `waitForMessage` flag nor descendants. Its controlling requester could previously resume that exact task with `sessions_send`. After upgrade, the first sweep classifies the restored row as unreachable and settles it, so the requester loses the ability to continue the original task even when the requester is still present.

## F6: A failed restart notice strands accepted queued messages
- Where: `src/gateway/session-restart-resume.ts`:641
- Claimed failure: When a yielded session has lost its child source and its restart marker contains accepted queued inputs, startup clears the marker before recording the yield failure. If recording that failure throws, startup skips the queued-input continuation. The messages are left unprocessed, and a later startup has no marker identifying them as inputs to resume.

## F7: createdVia spawn skip drops restart resume for dashboard-key spawned sessions whose requester is never marked
- Where: `src/config/sessions/session-run-lifecycle-projection.ts`:114
- Claimed failure: restartResumeSkipReason now returns "subagent" for any entry with createdVia "spawn". resolveRootSubagentRequester only walks parents for isSubagentSessionKey keys, so a running dashboard-key spawned session (for example an independent visible session from sessions-spawn-visible, or a child spawned without a yield batch) is enumerated as its own root at shutdown. It passes the key-only check, then gets skipped as "subagent" once the entry is read at marker write time, and again in the startup orphan and skip checks. Its requester is not marked either, because it is not running and has no requesterYieldBatch wake. After a restart or crash, nobody receives the resume input: the user's interrupted turn in that session stays stopped with no notice, where it previously got its own resume input.

## F8: Quiet or intentional non-delivery settlements are recorded as child-result delivery failures
- Where: `src/agents/subagents/registry/subagent-registry-requester-wake-mutation.ts`:226
- Claimed failure: The new failure branch fires whenever outcome?.delivered !== true, which includes outcome === undefined. requester-settle-wake.ts calls completeBatch with no outcome for quiet settlements: cancellation already owns the result (isBatchDeliveryClosed, e.g. kill reconciliation or suppressCompletionDelivery), no remaining completion rows, no child owing a completion message, and requester turnover. It also calls it for intentional non-delivery such as store replaced or private requester replaced. For a yield batch, each of these now writes an error terminal with "The child result couldn't be delivered..." onto a requester that is still parked. It does this through the exact-run path, which can, for example, beat the kill path's terminal. For stable batches without requesterRunId, it appends a visible run-failed notice to the conversation even after the user has moved on or stopped it. Users see a spurious failure for work that was cancelled or intentionally not delivered.
