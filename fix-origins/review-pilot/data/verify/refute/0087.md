# Case 0087: findings to check

## F1: SQLite hydration warnings report zero statement time on the regular reader
- Where: `src/infra/sqlite-transaction.ts`:480
- Claimed failure: On a normal SQLite Gateway, a bounded cron hydration worker opens a native read-only connection without observeConnection(). The inherited hydration label starts the timer, but the connection never feeds it statement measurements. A slow read therefore logs statementExecutionMs as 0 and an empty statement summary, attributing the query time to callbackOtherMs. The benchmark wraps its connection explicitly, so it bypasses this failure.

## F2: Large histories can exhaust temporary storage during bounded hydration
- Where: `src/config/sessions/session-accessor.sqlite-active-context.ts`:476
- Claimed failure: On PostgreSQL with a finite temp_file_limit, a session with enough unrelated custom events to exceed work_mem and the temporary-file allowance now fails to hydrate even a small context window. The CTE stores navigation rows for all those events before the outer predicates reject them. Previously the dependency query could reject each of those rows before storing it for the final sort.

## F3: Every hydration transaction starts/stops the shared native GC profiler, not just slow ones
- Where: `src/infra/database-engine/observation.ts`:24
- Claimed failure: startSqliteStatementTiming(true) runs for every transaction under an inherited sessions.transcript-hydration.* owner, regardless of whether it ends up slow. Each call to observeGcSamples either creates a new GCProfiler plus a setInterval timer, or, when worker-memory/diagnostic-gc already subscribe, forces drain(true) (native profiler stop + restart and a synchronous fan-out to the other subscribers, which may postMessage) at both start and stop. The gc-observer explicitly limits restarts to about once per second; a worker serving many hydration reads now restarts it twice per transaction inside the read hold, adding CPU and latency to every hydration even though the GC figure is only ever logged for slow holds.
