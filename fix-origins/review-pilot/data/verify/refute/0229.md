# Case 0229: findings to check

## F1: Repair rejects imports through the staged OpenClaw host link
- Where: `src/infra/update-candidate-plugin-repair.ts`:121
- Claimed failure: A plugin that imports a host module by a relative path through its node_modules/openclaw link worked in a published-driver snapshot because the copier points that link at the staged candidate. Repair resolves the import to the staged host outside the private state directory and rejects it as an escape, blocking the update even when the snapshot is complete.

## F2: An unusable Doctor contract can now block the entire update
- Where: `src/infra/update-candidate-plugin-repair.ts`:116
- Claimed failure: A disabled custom plugin can still have a declared Doctor contract. If that contract imports a package alias whose imports target is invalid, such as a target starting with ../, the new inspection propagates ERR_INVALID_PACKAGE_TARGET and aborts candidate Doctor. Previously Doctor caught the contract load failure and continued, so the disabled plugin could remain installed during an update.

## F3: Sibling imports lose symlink names outside the plugin directory
- Where: `src/plugins/plugin-generation-source-inspection.ts`:73
- Claimed failure: If a plugin imports ../shared/value.mjs and that path is a symlink to ../lib/value.mjs, inspection returns the canonical file without the sibling symlink. Neither the fresh copy nor published-snapshot repair creates shared/value.mjs in the rehearsal, so the original module specifier still fails to resolve.

## F4: Plugin inspection fills the temporary volume before capacity selection
- Where: `src/infra/update-candidate-plugins.ts`:349
- Claimed failure: If an operator sets TMPDIR to a small volume and an enabled plugin imports a dependency with a large data payload, inventory now materializes that dependency on the temporary volume before reporting its size. The worker can fail with ENOSPC before the updater gets a chance to select the state volume, even when that volume has ample space for the rehearsal.

## F5: Candidate Doctor preflight throws on unparseable copied plugin source even when the snapshot is complete
- Where: `src/infra/update-candidate-plugin-repair.ts`:116
- Claimed failure: completeUpdateCandidatePluginRehearsal inspects every selected entry in the private copy, including Doctor contract modules of disabled plugins, with an unguarded inspectPluginSourceDependencies([entry]). Only the later inspection of the original source is wrapped in try/catch. Errors propagate through createDoctorRehearsalSnapshotPreparation into readDoctorConfigPreflightSnapshot, so they fail candidate Doctor preflight. Example: an enabled plugin, or a disabled plugin's doctor-contract module, has a source file the static inspector cannot parse or capture, even though it needs no repair. Every update driven by a published updater then fails in candidate Doctor, where before the plugin was at most reported by Doctor or plugin loading. The 'invalid source' handling only covers the original tree, and the malformed-plugin tests only cover the runtime entries of disabled plugins.

## F6: Relative imports break when they cross the managed state projection
- Where: `src/infra/update-candidate-plugins.ts`:360
- Claimed failure: If a plugin at STATE/extensions/demo imports ../../shared/value.mjs from STATE/shared, inventory finds the helper but places it under candidate-plugins while the plugin is copied to REHEARSAL/extensions/demo. The unchanged import looks in REHEARSAL/shared, so the plugin still fails to load despite the helper being copied.

## F7: Update preparation now aborts when any plugin's source cannot be statically inspected
- Where: `src/infra/update-candidate-plugins.ts`:349
- Claimed failure: prepareUpdateCandidatePlugins now runs inspectPluginSourceDependencies over every enabled plugin entry, setup entry and every declared Doctor contract module (including those of disabled plugins), and nothing catches its errors. inspectPluginSourceDependencies rethrows anything outside a short list of module-not-found codes: parse/lexer failures from visitPluginSourceReferences, 'Plugin source link leaves its package', non-regular build inputs, and so on. The repair path in the same change expects such failures from original sources and turns them into warnings, but this path has no such handling. A user whose custom or npm plugin, or a disabled plugin's doctor-contract file, contains syntax the inspector rejects or a link it refuses could update before this change, because the tree copier just copied the directory. Now the whole update rehearsal fails with an inspection error that is unrelated to the update.
