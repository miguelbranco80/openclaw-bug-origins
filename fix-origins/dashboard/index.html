Words used in this report

Fix
A change whose title starts with "fix" and that touches product code. The title is the author's label, not a judgment that something was broken.
Causing change
The earlier change that introduced the bug a fix later repaired. Every bug here has two changes: the one that introduced it and the one that fixed it.
Never worked
The faulty code was new, and it was wrong on the day it merged. Example: a new feature built a Docker command by joining strings, so it failed for any folder with a comma in its name.
Broken later
Something worked, and a later change broke it. Engineers call this a regression. Example: a change capped a data stream at 16 MiB, and long replies that used to work began to fail.
Broken from outside
Old code that was fine until something outside the project changed. Example: a package manager changed the format of its launcher files, and every command failed after an update.
Review bot
ClawSweeper, the automated reviewer that comments on the project's pull requests before they merge.

Finding 2 · random sample of fixes

SupportedAbout double by the first readers' full count; closer to even under stricter cuts and under a second model. Neither reading puts never-worked bugs clearly below.

Of the — bugs we could trace to the change that introduced them, — were new code that was wrong from the start and — were working things that a later change broke. The two kinds need different defenses. A test of the old behavior can catch a broken-later bug. A never-worked bug has no old behavior to test against, so the only chance to catch it is when the new code is reviewed or first run.

What this supports doing

  • Add a plain "find the defects" pass by a current top model to the bot's review, and compare it on this benchmark first. Rests on finding 6. The 30 cases and scripts can score any reviewer, so the claim can be re-tested before anything changes.
  • Use two different models for that pass. Rests on finding 6: the two overlapped on only — of —.
  • Have a second model check each reported problem before a person sees it. Rests on finding 7: the checkers could say no, and a third of confirmed reports were minor.
  • Review large changes in parts, and mark any change the bot never reviewed. Rests on findings 3 and 5. — traced bugs came from changes of 500 files or more that the bot acknowledged and did not review.
  • Cover what reading cannot: run it. Rests on finding 8, which is tentative. Browser checks for interface style changes and real database runs for query changes are the two places the nine cases point to.

What it does not support

  • Enforcing the bot's current verdicts more strictly. Ignored warnings were rare.
  • Leading with more written rules. Most bugs broke none, and the rules that existed could not be checked from the change alone.
  • Relying on tests of old behavior alone. They cannot catch new code that never worked, which is at least half of the traced bugs.
  • Waiting for better models. The better result came from models available now.

Limits that apply throughout

  • Every classification is a model's judgment made in hindsight from code changes and PR text. Two makers' models agreeing reduces the risk of one model's habit; it does not make the judgment a measurement.
  • Nothing was executed. No bug was reproduced and no reported problem was confirmed by a failing test.
  • The period is three weeks of one project. The figures describe that period and may not hold for another.
  • A sample of fixes cannot see bugs that were never fixed, or bugs the bot stopped before merge.
  • The model comparison covers changes of at most 30 files and one run per reviewer. The reviewers did not get identical guidance: some GPT runs read a personal review guide on the test machine, and the Claude runs had the repository's current contributor guide in context. Neither contains the answers.
  • The project is public and so is everything used here. No individual is named, and nothing here judges any person's work.
