## Fix PR #162779 description (by SunnyShu0925, opened 2026-10-01T14:53:32Z)

```text
## What Problem This Solves

ComfyUI image/video/music generation could hang past the configured workflow timeout or fail with a spurious timeout on healthy workflows when the system wall clock jumped (NTP skew, manual time change). The workflow poll deadline now uses a monotonic clock so wall-clock jumps cannot stretch or shrink the per-request timeout budget.

- Problem: `waitForComfyHistory` seeded its poll deadline with `Date.now()` and read the remaining budget with `Date.now()` too, but the remaining value is consumed by `setTimeout` (Node libuv monotonic timer) — a cross-clock-domain mismatch. A wall-clock rollback Δ inflated every per-request timeout and poll sleep by Δ (workflow hung past the configured `timeoutMs`); a forward jump Δ shrank the remaining budget to a negative value, prematurely failing healthy generation with "Comfy workflow did not finish within Ns".
- Solution: seed and read the deadline from `performance.now()` so the remaining budget stays on the same monotonic clock as the timer that consumes it.
- What changed: `extensions/comfy/workflow-runtime.ts` — `waitForComfyHistory` deadline seed (L420) and `resolveComfyRemainingMs` remaining read (L482) switched from `Date.now()` to `performance.now()`. `extensions/comfy/image-generation-provider.test.ts` — the "caps oversized local workflow timeouts" test now spies on `performance.now` instead of `Date.now`, using an advancing `monotonicNow` value driven by the fetch mock so incidental `performance.now()` calls during provider init (plugin-metadata snapshot) cannot desync the seed/read sequence.
- What did NOT change: the error message format (`"Comfy workflow did not finish within Ns"`), poll loop logic, `timeoutMs` clamping via `resolvePositiveTimerTimeoutMs`, and all other `Date.now()` call sites in the file (used only for single-shot fixed timeouts, not remaining-budget arithmetic).

## Why This Change Was Made

The fix lands in the canonical owner of the remaining-budget computation (`resolveComfyRemainingMs`) plus the single deadline seed site (`waitForComfyHistory`), so both consumption paths — `requestTimeoutMs` (→ `readJsonResponse` → `fetchWithSsrFGuard` → `buildTimeoutAbortSignal` → `setTimeout`) and `pollDelayMs` (→ `setTimeout`) — benefit from one change with no new parser, policy branch, or configuration surface. This matches the project convention stated by maintainers in #155648: "operation budgets use `performance.now()`, epoch timestamps stay `Date.now()`", and mirrors the canonical fix already merged in #155603 (BUG-081, codex remote-workspace-media) and the in-flight #155801 (BUG-085, codex attempt execution deadline).

- Best fix: yes — 2-line mechanical replacement at the canonical owner; no guard/branch added.
- Alternative considered: injecting a `now: () => number` parameter (like `scheduleAbsoluteDeadline`) — rejected as over-engineering for a single internal call site with no persistence/cross-process concern (the deadline is a closure-local variable, never serialized or shared across processes).
- Risk: `performance.now()` returns a sub-millisecond float. The `requestTimeoutMs` path is floored downstream by `resolveSafeTimeoutDelayMs` (`src/utils/fetch-timeout.ts`); the `pollDelayMs` path feeds `setTimeout`, which accepts float delays. No `AbortSignal.timeout` integer-contract issue applies here (`buildTimeoutAbortSignal` uses `setTimeout`, not `AbortSignal.timeout`). Verified with `node --import tsx` direct invocation. steipete's open PR #117905 restructures this same region (introducing `ProviderOperationDeadline`); if it lands first this patch needs a rebase but is not a duplicate — #117905 still uses `Date.now()` for deadline comparison and does not address the cross-clock-domain issue.

## User Impact

Users generating media via ComfyUI (local or cloud mode) will no longer see intermittent hangs or spurious "did not finish within Ns" failures caused by wall-clock adjustments during long-running workflow polls. The configured `timeoutMs` now bounds the actual elapsed time regardless of NTP corrections or manual clock changes.
