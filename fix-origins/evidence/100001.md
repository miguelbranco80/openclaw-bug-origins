## What Problem This Solves

The Control UI **Sessions** page had two problems with **Assign to** (session owner assignment):

1. **Silent failure.** When the Gateway rejected an owner assignment (for example, the directory was unavailable or the RPC failed), nothing happened: no error and no change. The user could not tell whether it worked.
2. **The current owner was not marked.** The assignment submenu showed the session's current owner unchecked and still selectable, so re-picking it looked like a real change.

## Why This Change Was Made

- **`ui/src/pages/sessions/sessions-page.ts`** (from 55ce95fac80) discarded the assignment outcome. It now publishes failures through the page's existing scoped mutation owner, the same path other Sessions mutations use, so a rejected assignment shows an alert. A retired or replaced page never receives a stale error.
- **`ui/src/pages/sessions/session-menu.ts`** (observable since 111ffb9e51a) omitted `currentOwner` when building the menu. It now passes the authoritative owner, so the current owner renders checked and disabled.

- **Line-cap ratchet:** `sessions-page.ts` is already over its line cap, so the single-dialog lifecycle and lazy dialog loading move, unchanged, into `ui/src/pages/sessions/page-dialog.ts` (`SessionsPageDialog`). The page does not grow, and the ratchet passes.

## User Impact

A failed owner change now says so ("Owner assignment unavailable. Try again."), and the menu shows who currently owns the session.

## Evidence

- **Regression tests:** Sessions unit tests and the owner-assignment e2e suite cover the rejected-RPC alert, retired-page isolation, and the current-owner state. They fail before the fixes.
- **Real isolated Gateway plus Chromium on a Blacksmith Testbox:** checked at 390 and 1280 px, in light and dark themes.
