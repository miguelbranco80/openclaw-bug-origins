## What Problem This Solves

Fixes browser doctor reporting a local managed Chromium executable as healthy when it cannot load its runtime libraries.

## User Impact

Linux operators see a failed Chromium executable check and the loader's actual missing-library message. Doctor no longer claims an idle browser is launchable based only on the presence of its executable.

## Why This Change Was Made

Doctor runs a bounded, cancellable `--version` probe with the managed launch environment. It does not create a browser profile or start a browser session. Ordinary status remains passive; remote, attach-only, extension, and existing-session profiles are not probed. No dependencies are installed and no sandbox policy changes.

Current main already reports loader stderr in launch failures; that behavior was verified and is retained rather than adding a duplicate launch preflight.

## Evidence

- Before: actual Playwright Chromium failed with exit 127 and missing `libnspr4.so`, while the production doctor route reported `ok: true`, executable pass, and “launchable”. After: the same route/executable reports `ok: false` and includes the missing-library cause.
- Focused route regression uses a real executable returning a loader error: 12 route tests passed (0.135s test bodies; 121.65s cold compiler/runner wall time). The actual Chromium doctor also returns healthy when the required libraries are visible.
- Fresh autoreview against `47b0ce478c8141b52ec4631b4ddbe3d8b018ff21` (Claude because Codex CLI is absent): no P0–P2 findings.
- Formatting, `git diff --check`, scoped oxlint (4 files), production extension typecheck, and 38 existing doctor/version/launch-early-exit tests passed. Hosted exact-head CI is green.
- Production: +43/-2; tests: +30/-1. The 29-line allocation covers the new real-executable route regression. The additional production code owns a bounded executable probe; no new configuration or lifecycle manager.
- Blacksmith Testbox is unavailable here; no allocation was attempted. Hosted CI is the broad gate.

+export function execBrowserProbe(
+  command: string,
+  args: string[],
+  timeoutMs = 1200,
+  maxBuffer = 1024 * 1024,
+): string | null {
+  try {
+    const output = execFileSync(command, args, {
+      timeout: timeoutMs,
+      encoding: "utf8",
+      maxBuffer,
+    });
+    return normalizeOptionalString(output) ?? null;
+  } catch {
+    return null;
+  }

+/** Read a browser executable version from platform metadata or a command-line probe. */
+export function readBrowserVersion(executablePath: string): string | null {
+  if (process.platform === "darwin") {
+    const bundleVersion = readMacBundleBrowserVersion(executablePath);
+    if (bundleVersion) {
+      return bundleVersion;
+    }
+  }
+
+  if (process.platform === "win32") {
+    // Windows GUI browsers do not report `--version` to inherited stdout.
+    // Read PE metadata first, then use the install layout only as a safe fallback.
+    return readWindowsBrowserVersion(executablePath);
+  }
+
+  const output = execBrowserProbe(executablePath, ["--version"], BROWSER_VERSION_TIMEOUT_MS);
+  if (!output) {
+    return null;
+  }
+  return output.replace(/\s+/g, " ").trim();
+}

+    return null;

+  return execBrowserProbe(

+  const configuredSystemRoot = normalizeOptionalString(process.env.SystemRoot);

+    configuredSystemRoot && path.win32.isAbsolute(configuredSystemRoot)
+      ? configuredSystemRoot
+      : "C:\\Windows";
+  const powershellPath = path.win32.join(
+    systemRoot,
+    "System32",
+    "WindowsPowerShell",
+    "v1.0",
+    "powershell.exe",
+  );
+  const metadataVersion = execBrowserProbe(
+    powershellPath,
+    [
+      "-NoProfile",
+      "-NonInteractive",
+      "-Command",
