## Fix PR #198968 description (by steipete, opened 2026-11-14T15:23:19Z)

```text
Related: #197083

## What Problem This Solves

Fixes: update failure reports drop the step that actually failed when the recovery steps that follow it also fail.

## User Impact

User impact: when an update fails and its recovery also fails, the failure report and triage prompt now include the step that started the problem, so users can report it and maintainers can diagnose it. Reports written by already-installed updaters are unchanged; this applies once a release containing it drives the update.

## Why This Change Was Made

After any post-install failure, the recovery steps that follow (for example `gateway migration recovery`, `package-backup-retention`, `gateway recovery verification`) record their own failures. The report sanitizer kept only the latest three failed steps and pruned the oldest first under its byte budget, so the triggering failure was always the record removed. On #197083 the reporter's report shows exactly this: three recovery failures, `omittedDetails: 2`, and no trace of what started recovery.

The sanitizer now keeps the first failed step alongside the latest two. When the byte budget forces pruning, it protects the first and latest failures by identity, removes other records first (including lint inventory records that follow the latest failure), and drops the first failure before the latest one when only those two remain.

## Evidence

The first two fail on base; the trailing-lint test fails on the first PR head and passes now. The existing bounded-evidence test and the recovery prompt test in `src/commands/triage-recovery.test.ts` now expect the first failure.
- All 13 test files that consume the failure sanitizer pass locally (run on head `1b3452f44ad`).
```
