## What Problem This Solves

Fixes managed Codex startup failing with `ENOENT` after Homebrew removes the Node executable used by a still-running Gateway.

## User Impact

New managed Codex JavaScript launches can recover through the same Homebrew formula's available stable executable. The running executable stays preferred while it exists, and recovery does not search `PATH`. No configuration or migration is required; restarting the Gateway after upgrading Node remains recommended.

## Why This Change Was Made

The managed launcher used `process.execPath` directly even though command relays already use `resolveLaunchableNodePath`. Reuse that existing owner through the existing **private-local** `process-runtime` SDK entrypoint. Configured commands, native binaries, and exact-runtime workers retain their existing behavior. Host-owned Git settings now remain separate from configured environment overrides: the existing spawn-environment owner applies the prepared private value after filtering, and the shared-client key hashes it. Configured `clearEnv` is no longer rewritten. This private launch field is not accepted as a user configuration option.

Required consumer checks also exposed two bounded fixture defects. The ACPX retention fixture kept its final rejected lookup promise—and therefore its generation—on the fixture's own stack; returning from a helper before collection releases that root without changing GC passes or assertions. The native-shell fixture could read the operator's Git configuration after filtering out `HOME`; its synthetic command now disables global/system Git config while preserving the `GIT_CONFIG_PARAMETERS` assertions.

Supersedes #174379, thanks @TheRealUnknownSoldier. Release-note context: managed Codex startup recovers after a Homebrew Node keg is removed while the Gateway remains running.
