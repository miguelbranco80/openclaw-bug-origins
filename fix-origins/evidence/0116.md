Related: #203194

## What Problem This Solves

Git installs now update through prepared releases (#203194), but that new path only works when `pnpm` is installed globally. The OpenClaw installers bootstrap pnpm only for their own first build. So a Git install without a global pnpm (the normal Windows `install.ps1` result, and any Linux/macOS Git install without one) can't update anymore. Every `openclaw update`, chat `/update` or automatic update fails within seconds with `missing-tool` ("spawn pnpm ENOENT"), and the install is stuck on its current release.

On Windows, preparing a Git release also failed even when pnpm was present. Some test fixture paths exceed MAX_PATH under the release folder (`Filename too long`), so no Windows Git release could be prepared at all.

## User Impact

Git installs without a global pnpm update again on Linux and macOS. The update provides the pnpm version the target commit pins (through Corepack or a temporary pinned npm install, as the previous Git updater did). On Windows, Git updates now get past preflight, create the release worktree and install dependencies. One more Windows limit remains in the build step at the release folder's path depth (see Evidence); it is tracked separately and isn't changed here. If no pnpm can be provided, the update stops before any change and says to install pnpm or enable Corepack. The Gateway keeps running throughout.

## Why This Change Was Made

The new release preparation called a bare `pnpm` and a bare `git worktree add`, bypassing the owners the previous Git updater used:

- the build-manager resolver, which finds or provisions the pinned pnpm;
- the Windows rule that installs dependencies without lifecycle scripts;
- the Git command builder, which turns on long paths on Windows.

Preparation now uses those same owners, and preflight no longer requires pnpm on PATH, since preparation provides it. No new policy or config.

## Evidence

Base vs fix on real installs (Crabbox AWS), plus a regression test that fails on base and passes with the fix.

- **Windows Server 2025, `install.ps1` Git install, no global pnpm**

  - Base with a temporary global pnpm: preparation failed at the worktree step with `Filename too long` / `Could not reset index file`.
  - Fix: a clean `install.ps1` Git install at this head with no global pnpm. The update passed preflight, the release worktree (long paths) and `pnpm install` (pinned pnpm 12.15.0 via Corepack, `--ignore-scripts`). `pnpm build` then failed: the native TypeScript tooling timed out on its named pipe (`SyncRpcChannel: timed out connecting to named pipe`).

A manual build of the same commit, with the same pnpm and flags, fails at the release-depth path (`~\.openclaw\git-install\releases\.staging-<uuid>\openclaw`, 127 characters) and succeeds at `C:\r\openclaw`. It's a separate follow-up about where releases are built; the Gateway stays up on the current release.
- **Linux Git install already on a prepared release, all global pnpm removed from PATH**

## Problem

A Git install updates in place under the running Gateway, through a managed-service handoff helper. When the new build does not start, recovery depends on that helper and on the old updater that is already installed, so a failed update can leave the Gateway down or stuck in `update-recovery-pending`.

## Change

Git installs now update through prepared releases and a resident launcher:

1. `update.run`, `openclaw update` and automatic updates admit the run, resolve the target and run preflight (Node engine, required tools, disk space, container installs refused before any change).
2. The next release is built beside the running one (`git worktree add --detach`, then the target's install and build). The running checkout is not changed.
3. `openclaw update check-release` runs the new code offline against the current config and state and reports broken plugin or config surfaces. It does not migrate state.
4. `openclaw update plugins` runs from the published release: the existing plugin maintenance owner (`updatePluginsAfterCoreUpdate`), with the new core's code and version. A plugin problem, or a target too old to have the command, is recorded as a `plugins` step with a next action and never fails the update. An already-current install still runs it from the serving code and restarts a running Gateway when plugins changed (`docs/install/updating.md`).
5. The release is published as a pending trial, and the Gateway restarts with a process-replacing reason.
6. The launcher switches the release link at the next child start, counts attempts, commits the trial when the new Gateway is ready, and otherwise rolls back and starts the previous release.
7. The Gateway that starts after the switch (new on success, old after a rollback) finishes the run and sends the outcome to a requester that received the start notice.

Routing:
- `update.run` reads the install kind from the existing install-status owner (`resolveStartupInstallStatus`). `update-run.ts` wraps `update.run`; `update.ts` is unchanged and still serves package installs.
- `openclaw update` branches after `prepareUpdateCommand`, so every existing refusal (external supervisor, host-owned, immutable, system package owner, interrupted update) applies first. A requested non-dev channel on a Git checkout still switches it to a package through the existing flow, and `--dry-run` keeps the existing preview.
- Package installs move to this path in the next change, which also deletes the old Git machinery that this PR leaves unused.

Converting an existing install:
- The old entry points of a converted install (`openclaw.mjs`, `dist/index.js`) forward to the release launcher through a marker beside the tree. Existing service definitions and PATH shims keep working without a rewrite.
- A first update driven by an older installed updater still migrates state as it does today. Released updaters require migrated state: 23 stable and 6 extended-stable tags contain that check.

Fixes found by the real-install runs below, each a separate commit:
- `openclaw update --sha` now sends the tracked upstream that the protocol requires.
- The new path restarts with `update.run` / `update.auto`, so the process is replaced instead of restarted in place.
- A Gateway started by the launcher leaves its update successor to the launcher instead of spawning one outside it.
- Preflight skips dangling symlinks in agent homes, such as Codex `arg0` shims, when it sizes state databases.
- `check-release` writes its JSON result to stdout.
- Plain `openclaw update` keeps following the run while the restarting Gateway refuses connections with a retryable HTTP 503. Before, it exited 1 although the update succeeded.

Accepted edge cases:
- After `openclaw update` runs in a Git checkout, `openclaw.mjs` and `dist/index.js` in that checkout run the current release. A developer who edits the source of a checkout they also update from runs the release, not their edits.
- A stop request handled inside a launcher child exits with code 0, and the launcher starts the child again. A stop through the service manager stops the launcher and its child.
- On a Gateway with no service manager, the first update from a released version does not restart it. The released updater does this, and says so.
- Package updates now read the install status twice per request: once to route, once in the old handler.
- After a rollback, the previous release runs with plugins maintained for the new core. A plugin that cannot load stays off for that boot, as the plugin docs describe.
- `openclaw update --accept-capabilities` reaches plugin maintenance when the CLI prepares the release itself (`--no-restart`, or no Gateway answering). Through a running Gateway, `update.run` has no field for it, so a plugin that needs consent is reported with its `openclaw plugins update` next action.
