## Fix message body

```text
#171729 made the first AWS warm-image capture non-blocking once the Crabbox CLI reported at least 0.78.0, and required `captureEstablished: true` in the `--wait=false` result. Crabbox 0.78.0 then shipped without that field (it lands with openclaw/crabbox#2834, merged after the release), so on main every first AWS capture with Crabbox 0.78.0 rejected a successful pending checkpoint as invalid. The capture became uncertain and blocked enrollment until manual recovery. No OpenClaw release contains #171729.

The fast path now requires Crabbox 0.79.0, the first release that will carry #2834. A non-waiting result without the attestation is no longer rejected: OpenClaw polls the exact checkpoint's availability about every 5 s within the existing native wait budget, honoring cancellation and live-authority checks, then publishes it available and enrolls exactly as the blocking path does. So a Crabbox build that cannot attest the capture point degrades to the old wait instead of stranding the session. Docs now say Crabbox 0.79.0.

CI note: the only red was check-docs formatting in ui/src/components/wizard-step-controls.ts and ui/src/pages/chat/components/chat-picker-overlay.test.ts, inherited from main; this change does not touch them.

Refs: https://github.com/openclaw/openclaw/pull/172846, https://github.com/openclaw/openclaw/pull/171729, https://github.com/openclaw/crabbox/pull/2834
```

```text
## What Problem This Solves

Fixes first AWS snapshot capture blocking enrollment and pausing future captures when Crabbox returns a valid pending checkpoint without a capture-point attestation.

Related: #171729; openclaw/crabbox#2834.

## User Impact

Crabbox 0.78.0 uses the existing blocking capture path. With 0.79.0 or newer, an attested first capture still publishes pending and enrolls immediately; an unattested capture waits for the exact checkpoint to become available, publishes available, refreshes SSH readiness, then enrolls. Timeout, cancellation, real create failures, and malformed results retain existing failure/recovery semantics. No configuration or state migration is needed.

Release-note context: Crabbox warm images — avoid falsely marking successful pending first captures uncertain when the CLI cannot attest the capture point. This is a main-only regression; no OpenClaw release is affected.

## Why This Change Was Made

#171729 enabled the fast path at 0.78.0, but that release does not contain the attestation work in openclaw/crabbox#2834. Its successful create JSON has no `captureEstablished` field. Move the existing version floor to 0.79.0 and return attestation as a parsed fact rather than treating its absence as an invalid checkpoint.

The capture owner reuses its existing exact-checkpoint verifier, polling every five seconds within the existing 45-minute budget, honoring cancellation and current-allocation checks. Inspect commands are capped by the remaining budget. The existing blocking result owns publication and SSH refresh; no second capability table, probe, state format, or enrollment path is added.

Production LOC: +42/-15 (net +27), tests: +107/-20, docs: +1/-1. The production growth supplies the requested bounded, cancellable availability wait and forwards the remaining timeout to the existing verifier; the parser's attestation-required rejection is removed.
```

```text
The first cloud session for a repository waited in `saving` until the provider finished uploading the warm image: about 200 s or more on AWS, measured live.
```
