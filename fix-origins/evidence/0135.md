## What Problem This Solves

Fixes: Remote access tells owners to remove people or devices when an invitation limit is reached.

## User Impact

User impact: owners are directed to review the actual limit instead of making an unrelated access removal. Existing diagnostic details remain available. No invitation, membership, node, or permission behavior changes.

## Why This Change Was Made

The same refusal code covers invitation count and lifetime limits as well as member and device limits. The display cannot infer which resource to remove from that code. It now keeps the explanation broad and preserves the specific, sanitized reason in the existing details disclosure.

- Maintainer validation: all Remote access browser unit files plus the standard canaries passed (585 tests). The final error-mapping run plus canaries passed (541 tests), along with i18n, formatting and diff checks. Production code was unchanged by this cleanup.
- Both full-app flows pass: the invitation refusal retains the email draft and reveals the actual limit in Technical details without another write; the existing member-device scenario still verifies owner-signed removal and responsive presentation.
- Scoped lint, the plugin’s browser TypeScript graph, i18n baseline/verification, formatting and diff checks pass. Current-main reconciliation found no intervening changes to the affected message owner. No broad local test suite or live account change was performed.

(#193146), so the owner-devices dialog signs with the link's claw id and seq.
A browser without that seq refuses to sign, and a device approved again since
the dialog loaded is refused by the Gateway as a concurrent change.

* fix(openclaw-id): make one recovery kit per Make reachable preparation

Pressing Continue twice could send two preparations. A late second answer
returned the dialog to the owner-key step after the owner had saved kit A, and
the next Create recovery kit made kit B while the dialog still counted the kit
as saved, so B could link the claw unsaved. One preparation now runs at a time,
only the name step accepts its answer, and each new kit starts unsaved.

* fix(openclaw-id): report an owner key stored only after IndexedDB commits it

A request's success event does not mean its transaction committed, so a write
could resolve, and notify approval lifetimes, while the transaction then
aborted and the non-extractable owner key was never stored. Writes now wait for
the transaction to complete.

* fix(openclaw-id): store the first owner device key before linking with it

The browser stored D1 only after the commit answered. The Gateway pins the
root and admits D1 before it publishes and answers, so a reload or dropped
connection in between left a linked claw whose only owner device key was never
stored. The key is now stored before the commit, and a key this origin already
holds for the claw is reused rather than replaced.

Make reachable, Your devices and owner approval each ran in their own modal
host with no tie to the feature, so turning the Labs switch off left them open,
including a recovery kit on screen, and the reachability toast could still open
Make reachable. The enabled feature's mounted lifetime now owns them: they open
only while it runs and close when it ends, and Make reachable drops its kit
secrets however it closes.
