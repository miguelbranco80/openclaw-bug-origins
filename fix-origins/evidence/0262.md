## Fix message body

```text
When an update fails and its own retained recovery then blocks the unwind, the refusal replaced the error that caused it, so 'Update <run> has unfinished recovery' hid failures such as a plugin lease that could not be acquired. The pending result now carries the redacted first failure and names openclaw update repair when that command can settle the run's plugin cohort.
```

## Fix PR #192919 description (by steipete, opened 2026-11-04T17:32:41Z)

```text
## What Problem This Solves

Fixes: a failed update prints only `Update <run> has unfinished recovery; reconcile it before starting another update.` The error that actually stopped the update was gone, and nothing said what to run.

## User Impact

User impact: a failed update now prints the first failure under that refusal, and names `openclaw update repair` when repair can settle that run's plugin cohort. It took an instrumented build to find the 2026.9.2 first-hop failure fixed by #192140 (`failed to acquire plugin lifecycle lease … Existing-state schema metadata is inconsistent`), because this path dropped it.

## Why This Change Was Made

`withUpdateCommandRecoveryUnwind` kept the first failure only as the source of the result object. The pending failure's printed detail was formatted from the admission refusal alone.

- `pendingFailure` appends `First failure: …` from `createUpdateErrorFact`, which is the redacted, cause-walking fact the update failure path already uses. It is omitted when the failure and the refusal are the same error.
- The next step is added only when `inspectPluginCohortRecoveryAdmission` returns a pair for that run, which is the condition `update repair` uses to get past this refusal. Other retained recovery keeps its existing message, because repair would refuse it. A failed inspection falls back to no next step and never replaces the refusal.

Rejected alternative: changing the `UpdateRecoveryRequiredError` message itself. That error is also raised at admission for recovery that repair cannot settle, so it would advise a command that refuses.

## Evidence

- `update-command-plugin-cohort-handoff.test.ts` now drives a real cohort pair with a failure that has a nested cause, and requires the refusal, the first failure with its cause, and the repair step in the pending failure. It fails on base with only the refusal line and passes with the fix.
- Sibling unwind and pending-recovery suites pass (55/55).
- Not proven on a real update: the known trigger was fixed by #192140, so this is proven at the unwind boundary.
- Autoreview scoped-clean; independent Codex review: no findings.
```
