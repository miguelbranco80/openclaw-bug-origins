## What Problem This Solves

A log file can be truncated between metadata sampling and reading. When that shorter read ends with a newline, the log-tail reader advances its cursor to the earlier file size rather than the bytes it actually consumed. If the file then grows back to that size, subsequent reads silently omit the newly appended records because no file-shrink reset is triggered.

## Why This Change Was Made

Advance the existing cursor to the byte immediately after the last newline actually read. The same expression already handles an unterminated record. Keep the existing reader, sampled size metadata, bounds, filtering, redaction, rolling-file selection and reset policy.

This fixes the existing file-tail owner used by log consumers; it is independent of the optional CLI severity presentation change in #146986. It does not add another read path or change that PR's feature contract.

## User Impact

Log followers can read new complete records after a concurrent truncation and regrowth instead of silently skipping them. UTF-8 byte offsets, nonzero cursors and fully filtered windows keep the correct consumed position. Incomplete records remain pending until a later newline arrives. The reader remains read-only.
