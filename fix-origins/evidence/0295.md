## Fix PR #199563 description (by steipete, opened 2026-11-15T10:13:11Z)

```text
## What Problem This Solves

Fixes long SQLite writer holds when deleting a session that owns retained transcript windows in a large session database.

## User Impact

Session deletion releases the SQLite write lock sooner. Retained transcripts, successor ordering, and deletion refusal rules stay unchanged. No schema, configuration, migration, or index changes. The reference scan still costs CPU and occupies the worker before the transaction; this does not claim lower total request latency.

## Why This Change Was Made

The slow CTE reads surviving references to protect retained history; its rows are not deletion candidates. For requests with no transcript-removal plans, the deletion worker prepares successors before BEGIN, then the row-deletion owner uses them only while the existing database identity/revision matches. Intervening writes use the existing current-row query. Other reclamation paths and PostgreSQL keep their current behavior.

This moves planning out of the write transaction while preserving the reference parser and SQL. Request-local maps and existing callback plumbing add 52 production lines; no new cache or manager. Simplification and independent Codex review found no further safe reduction or actionable finding.

## Evidence
```

```text
## Problem

Large SQLite session reclamation ran its final delete transaction and commit on the Gateway event loop. Archive encoding already used a Worker, but deleting full-text rows, cascading transcript state, and committing a large generation could still pause every Gateway request.

## Product path

An authenticated Gateway WebSocket client calls `sessions.delete` for a SQLite-backed session with a large transcript.

## Root cause

`session-accessor.sqlite-lifecycle-state.ts` owns canonical transcript-row reclamation. Its callers materialized archives asynchronously, then called that synchronous SQLite owner from the Gateway process.

## Fix

- Reuse the existing transcript archive Worker for final SQLite reclamation.
- Carry only cloneable, typed deletion facts across the Worker boundary.
- Keep archive publication, notifications, caller authority, and session lifecycle fencing in the parent owner.
- Keep native harness deletion in-process because its commit and rollback closures are parent-thread state.
- Fence current and historical generation identities until Worker commit.
- Route direct deletion, lifecycle artifact cleanup, and disk-budget history eviction through one bounded reclamation queue.
- Close Worker database handles and durable leases before reporting completion.
- Preserve the in-process path for incognito `:memory:` databases.

No schema, migration, archive format, retention policy, configuration, or Gateway protocol changed.

## Real Gateway proof

Current main baseline: `88be1b80f58df698fe730b4f3f34934ecae92e21`.

The real Gateway test seeded 200,000 transcript rows, sent `sessions.delete` over authenticated WebSocket, and verified current and historical deletion, archive publication, and unrelated-session preservation.
```
