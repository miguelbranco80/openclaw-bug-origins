## What Problem This Solves

Fixes silent Gateway crashes: after an automatic restart, operators currently see a healthy fresh process with no product-visible record of the unexpected exit.

## User Impact

The next startup records and warns about the previous unexpected exit. The last ten crashes appear in Gateway status, Doctor findings, health RPC, and authorized readiness details. Clean shutdowns and planned restart handoffs do not create crash records. Windows task supervision and the macOS app retry unexpected child exits through bounded recovery, including signal deaths. The existing Control UI Debug health/status view receives these facts; there is no new UI chrome.

## Why This Change Was Made

The existing `gateway_boot_lifecycle` table remains the single clean/unclean receipt owner. Its startup worker transaction stores metadata and bounded history in the existing `config_machine_state` key `gateway.crashes`. There is no schema change, new config, heartbeat timer, or agent/workspace scan.

Rebased onto `b55baff690681d2d115e73d8b7ae996ff9f3274c`, including #194527, #194481 and #194509. Crash recording consumes the boot owner's newly computed predecessor window. The retained per-agent intervals in `gateway.restartRecovery` remain recovery work; an old pending interval cannot manufacture another crash after a clean boot. Startup failures are recorded without creating a resumable interval. Reporting and enrichment now form one lifecycle-owned operation; the separate reporting module and exported enrichment wrapper are removed.

Production delta is **+483 net LOC** (+573/-90; tests, tooling and docs excluded). This compression removes nine production lines from the first rebased candidate. The final delta is three lines above the previous pushed revision after restoring the optional status type contract and integrating the retained-window owner. Status, Doctor and startup warnings share `formatGatewayCrash`; health transports the structured record. The startup `try/finally` remains the existing settlement boundary. Remaining growth implements persistent bounded history, native evidence, operator surfaces and two supervisor recovery gaps; removing those would remove requested behavior.

The record path adds **no synchronous I/O or SQLite writes to request/turn hot paths**. Startup and post-startup enrichment use the existing boot worker. Safe-mode startup recovery retargets metadata inside its existing transaction. Existing clean-close and lease-heartbeat writes are unchanged; the previous heartbeat comes from the existing lock-acquisition read. Health/status/readiness use the bounded committed in-memory projection; CLI status and Doctor use asynchronous exact-key worker reads.

Systemd enrichment uses indexed `(MESSAGE_ID=98e322203f7a4ed290d09fe03c09fe15 AND UNIT=<unit>) OR (MESSAGE_ID=... AND USER_UNIT=<unit>)`, without grep. The exact stall marker is searched by PID and system/user unit in at most the final 30 seconds, ending at exit or detection and narrowed by heartbeat. Both queries share a monotonic one-second budget. At most ten newest exit rows are inspected; main-process discrimination prevents an `ExecStopPost` failure from replacing the Gateway cause. Only structured exit fields supply that cause. Missing evidence stays unknown; a failed marker lookup cannot erase known exit evidence.
