## Fix message body

```text
Follow-up to #202380.

## What Problem This Solves

ChatGPT gates subscription models in two places: the `/codex/models?client_version=` listing and the `version` header on `/responses` turns. Since #202380 the listing sends the numeric OpenClaw release (`YYYY.M.P`, falling back to `99.0.0`), but OpenClaw-harness turns still send the raw runtime version. Prerelease and dev builds therefore send values the backend has never been probed with (`2026.11.5-beta.1`) or that likely fail the model gate (`unknown`, `0.0.0-dev`). Then a model can be listed but its turn rejected. On 2026-11-18, a turn with `version: 0.164.0` returned HTTP 400 for `gpt-6.2-sol`.

## Solution

- Provider attribution now owns the ChatGPT gate value. For the `openai` provider, the `version` header is the numeric release (year 2026 or later), or `99.0.0`.
- `User-Agent` keeps the full build (`openclaw/2026.11.5-beta.1`), so OpenAI still sees the real version. It is not a gate input.
- `extensions/openai/base-url.ts` reads that header for `client_version` instead of repeating the rule, so the list and the turn send the same value by construction.
- Other providers keep their headers unchanged, including xAI, which shares the OpenAI header shape.
- Codex-harness turns are unchanged: the Codex binary sends its own version.

## User Impact

- Stable releases: no change. `2026.11.5` was already numeric.
- Beta builds: turns send `2026.11.5` instead of `2026.11.5-beta.1`.
- Dev and source builds without a calendar version: turns send `99.0.0` instead of a placeholder. Turns on newly launched models then pass the same gate as the listing.

## Evidence

- **Red on main, green on the fix:** `src/agents/provider-attribution.test.ts` › "sends ChatGPT the numeric OpenClaw release …". On main, 4 of 5 cases fail (`2026.11.5-beta.1`, `2026.11.5-1+build.abc`, `unknown`, `0.0.0-dev`); the plain `2026.11.5` case passes on both. Each case also checks that `User-Agent` keeps the full build.
- **Consumers green:** `provider-attribution`, `agent-tools.prefix-stability`, `openai-transport-stream.base`, `stream-wrappers/openai`, `openai-codex-discovery`, `provider-live-listing.contract`, OpenAI TTS, realtime browser auth and device-code tests.
- **Gates:** `tsgo:core`, `tsgo:extensions` and `check:test-types` pass. `ocx build --dts` and the packed release smoke (`scripts/release-check.ts`) pass.
- **End to end** (isolated Gateway from source, fresh ChatGPT device-code login): `models.list` returned 11 subscription models with outcome `ready`, including `gpt-6.2-sol` and `gpt-6.2-astra`. A real turn on `openai/gpt-6.2-sol` returned `NVH_OK`.
- **Live values:** the 2026-11-18 probe with a real ChatGPT login returned HTTP 200 on `/responses` for `gpt-6.2-sol` with `version` set to `2026.11.5` and to `99.0.0`, the only two shapes this change sends.
- **Not proven live:** a beta or dev runtime version. The dev tooling strips `OPENCLAW_*` from the Gateway environment, so the source Gateway reported the stable `2026.11.5`. The attribution test covers those inputs.

## Merge Risk

Two-way door: no state, config or contract changes, and a revert restores the raw header. Blast radius: the `version` header on OpenAI-provider requests (ChatGPT and platform routes) for prerelease and dev builds. Stable builds send identical headers.

Co-authored-by: Ayaan Zaidi <hi@obviy.us>
```

```text
Supersedes #202284. Restores the approach of #201493. Related: #201130.

## What Problem This Solves

ChatGPT subscription model discovery calls `/backend-api/codex/models?client_version=<X>`, and the backend hides every model whose `minimal_client_version` is above X. On main (#202284), X comes from a lookup of the latest `@openai/codex` on npm, cached in memory for six hours. That puts a registry request (1 s budget) on the model-listing path. A failed or slow lookup lists at the bundled 0.169.0 floor and can hide newly launched models. The in-memory cache also does not survive a restart or eviction.

## Solution

- List with the OpenClaw release that OpenClaw-harness Responses turns already send as the `version` header (provider attribution). The list and the turn use one value from one owner.
- Send only the numeric `YYYY.M.P` part (year 2026 or later). For example, `2026.11.5-beta.1` lists as `2026.11.5`. Anything else (`unknown`, `0.0.0-dev`, a bad `OPENCLAW_VERSION` override, or a proxy without attribution headers) lists as `99.0.0`.
- Treat an empty subscription list as a failed listing. A ChatGPT account always has models, so an empty 200 response keeps the last good rows instead of replacing them. API-key access-program discovery, where an empty list is valid, is unchanged.
- Delete the npm lookup, the six-hour cache, the 0.169.0 floor, the floor contract test, and the test mocks that existed only for them. Production: +19 / −74 lines.
- Keep the Responses `version` header unchanged. Keep Codex binary selection and update behavior unchanged.

Why this replaces the earlier designs:
- #201130 and #202284 needed a network request for a value the backend only compares numerically. Any version at or above a model's minimum shows the model.
- Peer clients hardcode a value for the same reason: Hermes `99.0.0`, Zed `0.999.0`, Crush `999.0.0`.
- #202284's concern was that an OpenClaw version goes into a Codex-version parameter. The same value already passes the same gate on every Responses turn, and an npm-latest value does not describe the binary that runs a turn either.
- A version starting with 2026 stays above every Codex 0.x release, so new models appear on launch day without a lookup.
- The version check is stricter than #201493's: suffixes are dropped instead of sent, because no live probe has tested a prerelease string.

Accepted edge cases (code comment in `base-url.ts`):
- A Codex-harness binary older than a listed model fails that turn with the existing update instructions and **Start a new session** (#201130). npm-latest had the same tradeoff.
- An old OpenClaw release can list a future model whose request shape it does not support yet. Every fixed-version and npm-latest approach has this.

I also considered an omp-style background npm refresh with persistence (oh-my-pi `codex-version.ts`). Plugin keyed state is unavailable in the catalog worker threads where discovery runs (`Shared-state admission requires the host broker`). An in-memory variant still needed a network request and reset to the floor on every restart.

## User Impact

- ChatGPT subscription users see newly launched models without an OpenClaw release, without a network lookup, and without depending on npm availability.
- Listing makes one request: the ChatGPT `/models` call.
- A transient empty model list from ChatGPT no longer clears the model picker.

## Evidence

- **Red on main, green on the fix** (`extensions/openai/openai-codex-discovery.test.ts`):
  - The version-table cases fail on main, which makes two requests (npm, then `/models`). The fix makes exactly one, to chatgpt.com, with the expected `client_version`.
  - The empty-list case fails on main (`expected ['ready'] to deeply equal ['unavailable']`) and passes on the fix.
  - Main result: 14 of 16 failed (the 2 GPT-6.1 Sol cases pass on both).
- **Focused suites green:** `openai-codex-discovery`, `openai-provider`, `openai-provider.codex-catalog`, `openai-api-key-catalog`, `platform-access-programs`, `base-url`, `src/plugins/contracts/provider-live-listing.contract.test.ts`, `test/openai-model-discovery-auth-order.test.ts`, `test/model-account-catalog-authority.integration.test.ts`.
```
