## What Problem This Solves

A Gateway with many sessions keeps prepared restart-recovery rows after recovery finishes. Published admission callbacks retain the startup scope, which still references the completed recovery closure and its parsed rows.

The source chain is `session-entry-json.ts:30` (decode), `session-restart-resume-discovery.ts:72` (prepare descriptive rows), `session-restart-resume.ts:357` (capture prepared stores), and `agent-database-startup.ts:582` (retain recovery in the startup scope).

## User Impact

Completed restart recovery releases its temporary session data. Recovery ordering, readiness, failure handling, and session behavior remain unchanged. This is a retention fix; it does not claim to explain all long-running Gateway memory growth.

## Why This Change Was Made

Clear `preparation.recoverInputs` in the existing settlement `finally`, before releasing input waiters (`src/state/agent-database-startup.ts:662`). No cache, interning table, config, schema, or dependency change. Reuse the existing equivalent synchronous assertion helper to keep the startup owner below its line cap, and include that helper in the PR wrapper's extracted-source inventory.

Production delta: **−2 runtime lines**; the inventory entry is +1 (net −1 including tooling); tests: +39.
