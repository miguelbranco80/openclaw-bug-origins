## Fix PR #147492 description (by shakkernerd, opened 2026-09-13T22:40:54Z)

```text
## What Problem This Solves

Message routing can discard target-alias metadata after selecting a channel adapter. A missing alias specification from that adapter was treated as a reason to look up bundled metadata, while some target-presence checks consulted the bootstrap adapter even when selected aliases were available.

That mixes two sources of truth. An installed adapter can have different aliases from the bundled adapter with the same channel ID. Its native destination can be overlooked, or an unrelated bundled field can be interpreted as a destination. In the Gateway send regression, overlooking the selected alias causes an account-default target to be inserted; normalization then rejects the conflicting destinations. The fallback also loads bundled plugin code unnecessarily: a source-checkout Slack read with `limit=1` spent most of its time in this discovery path.

## User Impact

Message actions consistently use the selected adapter's destination metadata. Selected aliases are recognized, an adapter's known absence of aliases stays absent, and account defaults or session-derived destinations are used only when appropriate. Poll-echo and group-reply routing use the catalog captured by the tool.

Callers that have not selected an adapter or captured a catalog retain bootstrap discovery. Account validation, cross-context checks, and final dispatch authority remain in their existing owners; this change does not add plugin grants or change read-authority lifetime, configuration, persistence, or the public SDK contract.

## Why This Change Was Made

The selected adapter or captured catalog already owns this information. The internal alias helpers now distinguish an alias specification, known absence (`null`), and no selection (`undefined`). Only the last state permits bootstrap discovery.

That same fact is carried through normalization, target-presence and resource checks, session destination recovery, poll-echo/group-reply handling, and the Gateway's default-target decision. Core legacy aliases and cheap screening of standard message parameters remain intact. No new registry or cache is introduced.

The regression fixtures also declare aliases on the selected adapter. In particular, the shared `list-pins` fixture previously declared `chatId` only in its bootstrap mock; correcting that fixture preserves its existing dispatch assertion without restoring the faulty fallback.

## Evidence

- Eight regressions fail on main `7a7549b1aad` and pass after this repair. They cover selected aliases and absence, resource-versus-delivery handling, canonical session destination recovery, a retained poll catalog after registry replacement, and Gateway default-target conflicts. Existing controls cover unselected discovery, conflicting targets, implicit-target exclusions, opaque resource IDs for direct operators, and poll account/route/expiry boundaries.
- Remote message-tool, normalization, and Gateway suites passed 495 tests. `node scripts/run-vitest.mjs src/infra/outbound/message-action-*.test.ts --reporter=dot` passed all 479 action tests after the fixture correction.
- On final head `2dea84a9518`, Testbox passed `node scripts/check-changed.mjs --base 7a7549b1aad`, `pnpm build`, and `pnpm test:contracts:channels`. [Final-head CI](https://github.com/openclaw/openclaw/actions/runs/34788136177) is green, including build, type, lint, guard, and contract checks. Independent review found no blocking issues; [ClawSweeper reviewed that exact head as Platinum](https://github.com/openclaw/openclaw/pull/147492#issuecomment-5656700480).

The native timing comparison ran the message tool, caller wrapper, dispatcher, and bundled Slack adapter against a synthetic HTTP server on the same Linux VM, with Node 24.19.0 and pnpm 12.3.4. Both revisions completed the `limit=1` read.
```
