Message (truncated):

```text
## What Problem This Solves

Fixes: when Telegram rate-limits a bot (`429 Too Many Requests: retry after N`), for example while it answers in several forum topics at once, the final answer can be lost and the user sees "I couldn't confirm the reply reached Telegram. Check OpenClaw chat history…" instead.

## User Impact

User impact: under Telegram flood control the real answer is delivered after Telegram's wait. The "couldn't confirm" notice only appears when a reply still cannot be sent after a five-minute flood budget.

## Why This Change Was Made

A Telegram 429 penalizes the bot token, but OpenClaw handled it per call: each send retried on its own (3 attempts), and stream previews kept their own suspension window. Previews in other topics kept spending the budget, so three consecutive 429s on a final reply exhausted the send retries and the turn fell through to the failure notice.

The per-token account limiter (`account-throttler.ts`) is now the only owner of flood waits:

- One limiter per bot token: a global pause gate plus the existing per-chat budgets (grammY throttler: about 1 message/s per chat, 20/min per group).
- A 429 closes the gate for every chat and topic on that token until `retry_after`. The gate keeps the later of the current and new deadline, so a shorter 429 that lands during a longer pause never shortens it. A bare 429 without `retry_after` gets one fixed 1 s pause. No strike count or exponential fallback carries state between responses. This follows python-telegram-bot's `AIORateLimiter`: a single global pause on `RetryAfter`, on top of proactive per-chat budgets. Telegram 429s carry `parameters.retry_after`, so a backoff ladder only adds shared state (and its ordering bugs) for a case Telegram does not send.
- Final replies, deletes and other non-replaceable calls wait and retry within `TELEGRAM_OUTBOUND_FLOOD_BUDGET_MS` (5 min). After that, the 429 surfaces and the existing honest failure path runs.
- Stream previews and typing are replaceable: while the gate is closed they are skipped, not queued. In a group they also yield to a pending reply in the same chat. The draft stream keeps the newest text pending and no longer spends its failure budget on skipped previews.
- One enforcement point where a request leaves for Telegram, after every group scheduler and throttler queue wait. A closed gate holds the request back, and the caller's writer check re-runs against the current writer. Waiting and retry policy stays outside the queues. The writer check comes from the prepared sender, the API-context helper, and final stream edits. A replaced writer's stale final is never posted, even when it was queued behind another topic.
- A 429 on a typing action (thrown by the chat-action handler) also pauses the whole token. The handler's own 401 and transient backoff is unchanged.
- Superseded paths removed: the draft-stream suspension window, `TELEGRAM_OUTBOUND_RETRY_AFTER_CAP_MS`, and 429 retries in the Telegram send retry predicate.

The Telegram E2E proxy's `telegramApiReject` can now return a Bot API 429 with `retry_after` (`retryAfter`, `0` for a bare 429) for `times` consecutive matching requests. The run summary includes `telegramApiRequestLog` (`method`, `at`, `status` only, with no bodies or IDs), so live runs can prove what reached Telegram inside a flood window.
```
