## Fix message body

```text
## What Problem This Solves

Fixes #203512. Since #203487, Stop does not cancel an MCP loopback tool call from a CLI-backed turn (Claude CLI and other CLI runtimes). If the user stops the turn while a message action waits on a channel lookup, the action still finishes: `test/cli-message-authority.integration.test.ts > stops the reaction lookup after abort retirement` gets `isError: false`.

## Why

The MCP loopback server rebuilds the tool caller from the CLI grant (`src/gateway/mcp-http.ts`). That caller had no `approvalSignals`. The turn's abort signal reached the tool only through the receipt boolean `isGrantAndLineageCurrent` → `isMcpLoopbackClientGrantCurrent`. That boolean also checks the grant row, the admitted run's delegated authority and the capture, so it mixes run lifecycle with permission. #203487 removed the synchronous receipt boolean from `captureGatewayToolCallerAssertion` as an authority re-check. Stop was lost with it.

## Fix

- `resolveMcpLoopbackClientGrant` now returns the grant's existing `abortSignal`, which is the CLI turn's abort signal. The MCP caller passes it as `approvalSignals`, the lifecycle channel that `captureGatewayToolCallerAssertion` already checks. The permission part of the receipt stays out of the synchronous check, as #203487 intended.
- Removed: the MCP `cronAuthorityCheck` pass-through (grant field, mint copy, resolved field, caller field) and `bindActiveCronAuthorityCurrentness`. #203487 removed the only reader of the identity `cronAuthorityCheck`, so this chain had no reader left.
- No new export, name, flag or guard. Production: +3 / −17.

## Sweep of #203487, #203503 and #203516

- I traced every production caller that sets `receiptAuthority` (`agent-tools.caller`, embedded `attempt-gateway-tools`, `settled-turn-finalization`, harness `tool-authority.runtime`, `plugin-native-subagent`, `scheduled-owner-tool-guard`, `cron-tool`, `node-claude-skill-runtime`, worker `placement-turn-claim-events` and `worker-turn-tool-surface`, plugin `hooks`). Each one still delivers Stop through `approvalSignals` or through the tool's own execute signal. The MCP loopback was the only caller where the receipt carried Stop alone.
- The 1b and 1c call sites run inside in-process Gateway dispatch. That dispatch still runs the caller assertion (`in-process-gateway.ts`, `server-plugin-in-process-authority.ts`), or the tool's own signal covers them. No other instance was found, so this PR has one fix and one test.

## User Impact

When you stop a CLI-backed turn, a running message action is cancelled before its write. The tool result reads "The message turn has ended. Start a new turn to retry." A permission change in the middle of a call still does not interrupt a started call (#203487).

## Tests

- `test/cli-message-authority.integration.test.ts` "stops the reaction lookup after abort retirement": red on main (`isError: false`). Green on head, with no PATCH or PUT after Stop. The expected text is now the message route's "message turn has ended". Before #203487 the text was the generic "authority is no longer active", which #203487 removed.
- `test/cron-message-read.integration.test.ts` (claude-cli, disabled before 429): Stop now reaches the tool, so the result text is the message route's "message turn has ended". The regex now accepts it. The single PATCH and the absent retry are unchanged.
- `cron-creator-authority-context.test.ts`: the two lines that read the deleted helper are removed. The revocation assertion on the creator stays.
```
