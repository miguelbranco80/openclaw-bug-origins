## Fix message body

```text
fix(usage): don't hold every decoded transcript in memory during keyed incognito usage refresh

Keyed incognito usage refresh decoded every transcript payload and kept all of them in memory at once before summing usage, which added avoidable heap pressure and risked Gateway out-of-memory failures on large histories. It now reads and drops each payload as it goes; the usage results are unchanged.

Evidence: built Gateway, eight incognito sessions each filled with 48 × 768 KiB chat.inject appends through the shipped RPC. During a keyed usage refresh, main retained 50 decoded messages (about 37.7 million characters) at the scanner boundary (twice); with this change it retains none (twice), and the reported usage is identical.

Thanks @HerbertHuerto.

Co-authored-by: Ayaan Zaidi <hi@obviy.us>
```

## What Problem This Solves

Incognito usage refresh retains every decoded transcript message while computing small usage totals. Large conversations therefore incur an unnecessary second decoded-text allocation during refresh.

## What Changed

Project each parsed event into the existing canonical navigation fields and its usage contribution immediately, rather than retaining its message payload. Preserve the canonical hash of the last raw event before dropping it. Branch selection, rewind/side appends, totals and checkpoint semantics are unchanged. This updates the contributor's repair for the current actor-owned memory route; it does not restore the retired worker/cursor implementation.

## Evidence

Built Gateway CLI, Node 24.22.1 in isolated Linux Docker, fresh state per arm. State was created only through authenticated shipped RPCs: `sessions.create(incognito: true)`, a real `chat.send` against a local streaming provider, 48 `chat.inject` document appends per session, then keyed `sessions.usage`. Eight sessions each contain 36 MiB of appended text. A small real model turn and refresh calibrated the scanner boundary before the large workload.

Two completed main-baseline runs consistently retained 50 decoded messages (37,749,447 text characters) per measured scan. The candidate retained zero message payloads at the same production scanner boundary. Forced-GC inspector samples at that boundary showed roughly 151 MB additional heap on main versus 75–76 MB on the candidate. These are retained-boundary observations, not peak-RSS measurements or a claim that total session memory is bounded. The actor transcript and immutable serialized snapshot still scale with input size; one event is still parsed whole.

All eight normalized public usage responses were identical between baseline and candidate: 101 input / 7 output tokens, 50 messages (one user, 49 assistant), identical costs and model/tool totals. Both completed main runs and candidate stayed on one authenticated connection. An earlier baseline attempt timed out collecting inspector GC and is not counted.

- Focused formatting and lint passed.
- Real OpenAI `gpt-5-mini` turn through the built CLI returned `LIVE_GATE_OK`, exit 0. The first setup attempt could not resolve the model before catalog refresh; the corrected shipped catalog-refresh sequence succeeded.

Simplification reuses `projectTranscriptNavigationFields`, removing the contributor's duplicate navigation-field projection. Whole production delta: +20/-7 lines; regression tests: +93 lines. Growth is the per-event usage/navigation projection and raw-tail hash needed to release decoded payloads without changing branch or checkpoint behavior. No SDK, configuration, schema or permissions change.

## Merge Risk

Two-way door: reverting restores the previous scan behavior without a migration. Blast radius is incognito usage refresh and its branch/checkpoint accounting; durable transcript scanners and provider behavior are unchanged.
