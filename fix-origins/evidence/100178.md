## Fix PR #162197 description (by adamczhang, opened 2026-09-30T23:06:10Z)

```text
Closes #146442

## What Problem This Solves

Fixes: a Telegram send or typing action aimed at topic 0 (`-100123:topic:0`, `-100123:0`, or a `threadId` of 0) is sent to Telegram as if it were a real topic. Topic ids start at 1 (General). Per the review of #146442, Telegram treats 0 like "no topic", so the message can land in General and OpenClaw then reports a topic mismatch after delivery.

## User Impact

Topic 0 is now rejected before anything is sent or looked up. Lower-level send and typing errors name the topic ID; the CLI resolver retains its generic invalid-target error. Valid targets, including General topic 1, behave as before. I found no internal path that produces topic 0 (topic ids from inbound updates come from Telegram and start at 1), so the only behavior change is for callers that pass 0 themselves: they get an immediate error instead of a delivery followed by a mismatch error.

## Why This Change Was Made

Forum topic ids are positive integers, as channel Direct Messages topic ids already were. The target parser now requires a positive id for every topic form. Explicit thread options (`threadId` from tools, `messageThreadId`) go through the same check for sends and for typing, and that check now runs before the chat lookup, so a bad option cannot cause a `getChat` request or a target write-back. When the topic is what was rejected, the error says so instead of blaming the chat id. General still sends `message_thread_id: 1` for typing, which the docs call out and a test now pins.

## Evidence

- **Real send boundary:** `send.history.test.ts` drives `sendMessageTelegram` and `sendTypingTelegram` through grammY against the local Bot API stand-in (`useTelegramHttpFixture`, a real HTTP server). For seven zero-topic inputs it asserts the topic error and zero requests: forum marker, shorthand, internal group form, username target, numeric thread option, a thread option before a username lookup, and a thread option beside a valid topic target.
- **Fails before the change:** I ran the original six cases against the unmodified production files with the tests kept. All six fail: the send goes out and OpenClaw reports `Telegram delivered message 902 to topic unknown; expected topic 0 | CHANNEL_PARTIAL_DELIVERY` (the stand-in answers like the Bot API server does for `message_thread_id=0`, per the source trace in the #146442 review). The seventh case and the topic-specific message were added after review and each failed before its fix (typing let an explicit 0 through next to a valid topic target; target-form zero reported "numeric chat ID").
- **Parser:** the existing topic-id table in `targets.test.ts` now covers the forum zero forms and fails on the old parser (`-1001234567890:topic:0` parsed as topic 0). A small truth table covers `hasRejectedTelegramTopic`, including garbage base targets that must keep the plain invalid-recipient error.
- **Cost (`node scripts/run-vitest.mjs <files> --maxWorkers=1`):** the seven new send-boundary cases take 10-13 ms each (about 80 ms in total) inside `send.history.test.ts`.
