## Fix message body

fix(oc-path): refuse frontmatter keys that cannot be read back



`path set` on Markdown frontmatter accepted keys outside the reader's key grammar (for example `9name`, `name.dot` or `café`). It reported success and changed the file, but the new field could not be read back. The writer now checks the same existing key grammar as the reader and refuses those keys, leaving the file unchanged. Valid keys write and read as before.

Evidence: built CLI in secretless Node 24.22.1 Linux Docker. For each bad key, main reported success, changed the bytes and then failed to read back, twice; with this change all six writes were refused with the original bytes kept. Valid insert, read and edit controls passed on both builds with identical output across LF, CRLF and BOM or no-frontmatter files. Details: https://github.com/openclaw/openclaw/pull/191421#issuecomment-6588273381.

Thanks @LinzeShi.

## What Problem This Solves

`openclaw path set` can report success after inserting a Markdown frontmatter key that the next reader cannot address. For example, `9name`, `name.dot` and `café` are written to disk successfully, then `path resolve` reports no match.

Validate new frontmatter keys against the reader's existing ASCII grammar before mutation: start with a letter or underscore, then letters, digits, underscores or hyphens. Unsupported keys return the existing `not-writable` error with the file untouched. Valid writes, the reader grammar, public API and other formats' key rules remain unchanged.

Preserves @LinzeShi's original production commit. Regression cases reuse the existing immutable-edit table; sentinel and whole-line coverage are consolidated, and the added test allocation exception is removed. The existing CLI documentation describes the grammar.

## Evidence

[Inspectable built-CLI before/after captures and file bytes](https://github.com/openclaw/openclaw/pull/191421#issuecomment-6588273381), exact candidate `241258e423342fe99ea035ce9f7ac0f9d989f029` versus pinned main `3bbe6e23b99d0986d15a959f0e13d0266074e281`:

- Secretless Node 24.22.1 Linux Docker; source-built ordinary CLI and bundled plugin, isolated task-owned config/state/workspace.
- Each of `9name`, `name.dot`, `café` tested **twice per build** with `path set`, independent byte capture and a fresh `path resolve` process.
- Main: set exit 0 / unresolved read exit 1, file changed **6/6**. Candidate: clear `not-writable` refusal, byte-for-byte original file retained **6/6**.
- Valid `_Name-9` insert/read/edit/read controls passed twice for LF, CRLF/no-final-newline and BOM/no-frontmatter documents: **6/6 per build**, with identical main/candidate output buffers.
- Focused suites **129/129**; identical main regression fails only the three invalid-key cases; changed TypeScript lint passes.
- Whole PR delta: production +7; tests **−3**; docs +3.

## Merge danger

**Two-way door:** revert restores permissive insertion; no migration, schema or public API change. Blast radius is new Markdown frontmatter insertions through `oc-path`. An incorrect grammar check could reject a readable key; the guard matches the existing reader and valid-key readback/EOL controls remain covered. Existing saved files and other format policies are not rewritten.
