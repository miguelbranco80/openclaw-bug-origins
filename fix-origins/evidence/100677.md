## Fix message body

```text
Closes #149139

## What Problem This Solves

MiniMax chat login keeps acquiring tokens after owner permission is revoked. Saving revoked credentials was already blocked.

## Why This Change Was Made

The existing chat authority check decides whether sign-in may continue. MiniMax consumes it before requests and after awaited work: 18 lines in oauth.ts and 1 in provider-registration.ts.

Growth accepted under the owner's standing acceptance (2026-09-15).

## User Impact

Revoked sign-ins stop exchanging tokens. Allowed sign-ins still save once.

## Evidence

Registered `/login` with real guarded TCP/TLS transport, synthetic discovery/endpoints, and the existing current-policy test seam:

- After code presentation: later requests 2 → 0; issued tokens 1 → 0.
- During a pending response: later requests 3 → 0; issued tokens 1 → 0.
- Browser-opening revocation stops before polling on both versions.
- Revoked results save nothing; allowed login saves one profile once.

These are isolated handler receipts. Live Slack delivery and Gateway refresh are unverified. Config-reload deferral is unchanged.

## Compatibility

No configuration, storage, protocol, or SDK change.

## Consumers

Both global and CN device-code methods share this callback.

## Invalidation

Authority is read again before requests and after awaited work.

## Tests

222 MiniMax tests and four hosted `commands` project `/login` regressions pass. The latter use real plugin registration/OAuth and synthetic fetch replies; base production fails both polling cases. Existing config/result assertions remain.

Co-authored-by: Ayaan Zaidi <hi@obviy.us>
```
