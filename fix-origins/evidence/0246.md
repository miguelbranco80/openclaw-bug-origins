## Fix PR #202018 description (by jalehman, opened 2026-11-19T19:32:17Z)

```text
## What Problem This Solves

When a Gateway sits behind a trusted proxy, an automation created from an authenticated chat records the Gateway's shared-auth "generation". For trusted-proxy Gateways this value is only a hash of the proxy admission settings (`userHeader`, `requiredHeaders`, `allowUsers`, `allowLoopback`, `trustedProxies`). Every later run had to match that hash exactly. Any change to those settings therefore refused each of these automations permanently, even one that only tightens access, like adding a required header. The jobs were then auto-disabled with "The operator authority that created this automation was refused … Cause: Restart recovery authentication owner changed".

This also happens on upgrade when the deployment layer changes the rendered proxy settings. For example, a newer OpenClaw Enterprise controller adds `gateway.auth.trustedProxy.requiredHeaders: [x-openclaw-scopes]` to Gateways that enable HTTP chat. The saved configuration doesn't change, but the proxy settings the Gateway runs with do, and so does their hash. Every proxy-created automation saved before the upgrade is then refused and disabled at its next run.

## User Impact

User impact: automations created through trusted-proxy authentication keep running after proxy transport settings change. This covers both upgrades that change rendered proxy settings and operator edits. They are still refused when the proxy user's access actually changes: removal from `allowUsers`, changed identity scopes, or the Gateway leaving trusted-proxy mode. Rotating a shared token or password still refuses jobs created with that credential. Jobs that were already auto-disabled with this error keep their saved authority, so the owner can re-enable them with `openclaw automations edit <id> --enable` once this ships; they don't need to be recreated. Re-enabling does not change the job's execution revision, so the saved source is kept.

## Why This Change Was Made

Saved operator sources already carry the grant fingerprint for the proxy user (`authPolicy`). That fingerprint records whether trusted-proxy mode is on, whether the user is still in `allowUsers`, the user's identity scopes and the browser-origin decision. It is rechecked on every restore. Live proxy clients already follow this rule: a proxy policy change only revokes them when `allowUsers` or the password fallback changes (`resolveSharedAuthInvalidation`). Restoring a saved automation was the one path that still compared the raw handshake hash. Restore now skips that comparison for sources authenticated by the proxy itself (`authMethod: "trusted-proxy"`, with no OpenClaw ID principal) and relies on the saved grant check. Token and password sources, password fallback behind a proxy (`authMethod: "password"`) and OpenClaw ID tunnel sources keep the exact generation check.

Tradeoff: a saved proxy automation now survives `trustedProxies`, `userHeader`, `requiredHeaders` and `allowLoopback` changes. These settings control which requests the proxy hop admits, not who the saved user is. New connections still face the new rules. Adding a required header only tightens admission for new requests, so it should not retire work an allowed user already authorized. An operator who wants to retire proxy automations should remove the user from `allowUsers` or change identity scopes, which still refuses the jobs.

## Evidence

- New `src/gateway/operator-run-recovery.trusted-proxy.test.ts`. It captures a proxy-authenticated source, persists and decodes it as cron storage does, publishes a new generation through the config-write owner, then restores it through `restoreGatewayQueuedOperatorRecovery`.
  - Adding `requiredHeaders`: **red on base** (`GatewayOperatorRecoveryAuthorizationError`), green with the fix.
  - Removing the user from `allowUsers`: refused (base and fix).
  - Switching to token mode: refused (base and fix).
- The existing shared-credential rotation tests still refuse after rotation. These suites pass: `operator-run-recovery`, `cron-stream-source-authority`, `run.operator-continuation`, `server-shared-auth-generation` and `provider-create-recovery`.
- `pnpm check:changed` passes, including format, lint and core plus core-test typecheck.
- Upgrade-path reproduction with a synthetic Gateway: trusted-proxy auth with an env SecretRef password fallback, a private `trustedProxies` CIDR, and a saved proxy-created automation. Startup and config hot reload alone kept the generation unchanged and the job passed; only adding a `requiredHeaders` entry changed the generation and, before the fix, refused the job.

Update contract: this changes no stored format, Doctor step, config or update path. Older saved sources keep their shape and are read as before, so no migration or upgrade-from-stable run is needed.
```
