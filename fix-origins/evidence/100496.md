## Fix PR #160130 description (by steipete, opened 2026-09-28T05:02:54Z)

```text
## What Problem This Solves

Main-session restart recovery resumes an internal-ingress run only when the latest input carries human evidence. The provenance reader mapped every non-special kind (missing, invalid/unknown, and `external_user` alike) to a generic "other" source, which the recovery store treats like human input. A restart claim whose latest input had missing or invalid provenance was therefore resumed as if a human had sent it.

This correction was made on the abandoned `release/2026.9.7` branch during review of 086223757f20 (fixture follow-up beab1d9adec6, #159642) and never reached main; this forward-ports it before that branch is deleted.

## Summary

- `readMainSessionRecoveryCheckpoint` recognizes only verified `external_user` provenance as human; missing or unknown provenance maps to no source, so the existing tombstone path handles it.
- The positive human-origin recovery fixture is marked with `external_user` provenance.
- `docs/gateway/restart-recovery.md` states that recovery requires verified human provenance.

## Evidence

- New cases in `main-session-harness-completion.test-harness.ts` ("requires human evidence for internal recovery") reproduced all four missing/invalid provenance failures on unchanged main and pass with the fix; 229 related tests passed.
- `pnpm check:changed`: production types, all test-type shards and the coercion guard passed locally before a host-load interruption; full result is on this PR's CI.
- Autoreview: scoped-clean at P0/P1.
```
