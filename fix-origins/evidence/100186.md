fix(completion): keep PowerShell completion context after a quoted subcommand

In the generated PowerShell completion script, a quoted subcommand (for example `openclaw completion 'fish'` style input) lost the command context, so completion fell back to file names and root flags. Quoted literal words now count as the subcommand they spell, and expression tokens are still never evaluated.

Evidence: real pwsh 7.6.8 on Linux loading the scripts generated by the built CLI. On main completion after a quoted subcommand offered the wrong candidates (twice); with this change single- and double-quoted subcommands complete correctly (twice), and a nested quoted `gateway run` offers --bind again. An expression token is still left unevaluated. Production +5/-1.

Thanks @LinzeShi.

Co-authored-by: Ayaan Zaidi <hi@obviy.us>

## Fix PR #177584 description (by LinzeShi, opened 2026-10-19T18:28:44Z)

```text
## What Problem This Solves

Generated PowerShell completion reads a completed command token from its source extent, including quote delimiters. After `openclaw 'completion' --shell f` or its double-quoted equivalent, it loses command context and offers a root-command or filename match instead of `fish`.

## Changes

For PowerShell string-literal AST nodes, use the already parsed literal `Value` when building command context. Other expressions retain their source-text handling; nothing is evaluated. The existing quoted flag-value handling uses the same AST distinction.

Thanks to @LinzeShi for the focused fix and native regression cases; their commit is retained.

## Evidence

Built main `30103ebc0ebfb5b9112ba26ffdf4b6e1a63b5aaa` and candidate independently in isolated Node 24.22.1 Linux Docker. Each built shipped CLI generated its own actual `completion --shell powershell` script. Loaded that script in clean native PowerShell 7.6.8 and called its real `TabExpansion2`.

- Main: unquoted `completion --shell f` offers `fish`; single-quoted `completion` twice and double-quoted `completion` instead offer `file-transfer`.
- Candidate: all three quoted cases offer `fish`, matching the unquoted control.
- Nested unquoted `gateway run --b` offers `--bind`; candidate also retains that context when both command tokens are quoted.
- Partial `--shell po` continues offering `powershell`.
- A nonliteral `$(throw "SHOULD_NOT_EVALUATE")` token is not evaluated and retains existing source-text behavior.

Simplification: one existing loop now uses the native literal/source distinction; no new parser or evaluator. Whole PR production delta +5/-1, tests +4/-0. Existing completion documentation remains unchanged because this restores normal quoted-command semantics.

Merge danger: two-way door; generated scripts must be regenerated to receive the fix, with no persisted-state migration. Blast radius is command-context discovery in generated PowerShell completion only; other shells are unchanged.
```
