Growing session transcripts were republished with a whole-source
replacement on every dirty sync, so DB/FTS/vector churn and embedding
work scaled with the full transcript instead of its new tail.

Session publication now keeps rows whose content-addressed chunk ids are
unchanged. The manager only plans: it reads indexed ids through the
publication worker and embeds new chunks. The worker kernel, inside its
write transaction, verifies retained rows, writes new rows, deletes ids
the publication omits, and refreshes provenance only when it changed.
If a retained row vanished before the write lock, nothing is written and
the manager immediately republishes the source in full. Full reindexes
into a shadow keep the existing whole-source path. No schema, config, or
search-result changes.

Related: #40919

## What Problem This Solves

Growing session transcripts rewrite every indexed chunk on each sync. With the embedding cache disabled, they also send unchanged text to the embedding provider again, spending local CPU/GPU time on repeated work.

## User Impact

Session appends retain unchanged chunk rows and embeddings. Only new or changed chunks are embedded and published, including when caching is disabled. Truncation and provenance changes still take effect; full rebuilds retain complete replacement.

No user configuration, database schema, row encoding, chunk identity, or migration changes. Existing indexes remain usable. Full transcript preparation still occurs; this fixes embedding and publication amplification.

## Why This Change Was Made

Delta publication stays inside the existing SQLite worker. Retained rows are staged first and validated transactionally before indexed writes. Missing rows cause one full-source retry after releasing the workspace lock. Both indexing paths share preparation and recovery. The existing lazy chunk writer owns provenance updates, and vector cleanup/rebuild debt retain their existing owner. Empty sources preserve the optimization from #146150.
