## Fix message body

```text
Related: #172026

## What Problem This Solves

Fixes: MCP servers that sign in per user (`auth: "oauth"` with `oauth.identity: "per-requester"`, or a plugin connection resolver) never reach Claude CLI turns, even when the user has connected their account and sends the message themselves. Nothing tells the agent or the operator that the server was left out, so the agent guesses at the reason.

## User Impact

User impact: on Claude CLI turns, a user's own per-requester MCP tools are listed and every call uses that user's credentials, as on the default runtime. Turns without a verified user (completions, automations, subagent runs) keep the same tool list but get an explicit refusal that says why. No call ever uses another user's account.

## Why This Change Was Made

#172026 moved configured MCP servers on managed Claude CLI turns onto the loopback bridge so that ordinary and completion turns list one catalog and keep Claude's cached prompt prefix. To keep that catalog sender-independent it acquired MCP with no requester at all, which silently removed every requester-scoped server from every Claude CLI turn.

The Codex app-server harness already solves the same problem: requester-scoped tools come from the session's advertised catalog (stable across senders), and each call binds to the current turn's verified sender. The Claude CLI bridge now uses that same owner (`materializeRequesterScopedMcpToolsForHarnessRunCore`) next to the shared-server runtime instead of dropping the servers.

Two gaps in that shared owner are closed for both runtimes:

- A turn without a verified user returned nothing until a requester had connected in the session, so the sign-in tool appeared on user turns and disappeared on completion turns. It now lists the same sign-in tool, built from config, and refuses the call.
- The refusal for a turn without a verified user now says that there is no verified user, that no other account is used, and what to do. A sender who has not connected still gets the existing sign-in flow.

A senderless Claude CLI turn also logs which requester-scoped servers stayed listed but refused calls.

Child runs keep the rule documented in the plugin SDK infrastructure docs: subagent, cron, heartbeat and completion runs carry no requester identity, so requester-scoped servers refuse on those turns. This PR does not change that rule.

**Cause.** The loopback bridge resolved the requester-scoped partition with no sender. `resolveRequesterScopedMcpConnections` fails closed without a sender (correct), so those servers were omitted from every Claude CLI turn, including turns where a verified sender was present on the run.

**Who is affected.** Every Claude CLI turn (and any CLI backend turn served through the loopback bridge) on a Gateway with a per-requester OAuth or resolver-based MCP server, since #172026. Shared MCP servers were not affected.

**Why tests missed it.** #172026 added Claude CLI coverage with one static `probe` server (`prepare.configured-mcp.test.ts`, `mcp-http.configured-mcp-authority.test.ts`, empty plugin registry). No Claude CLI test configures a per-requester or resolver server, and nothing compared a Claude CLI turn with the default runtime for the same server. Reviewer live evidence on #172026 also used a static server only. The `undefined` was a deliberate choice for catalog stability; the docs line it added ("not offered on these turns") stated the removal, but no test held the requester-scoped outcome.

**Prevention.** `prepare.configured-mcp.test.ts` now runs shared, per-requester OAuth and resolver servers through Claude CLI turn preparation and the loopback tool resolution: user, senderless, second-user and user-again turns must list identical tool definitions; the user's call must return the user's credential, the same result as the default runtime's acquisition; the senderless and unconnected turns must not reach the server. It fails on current `main` for both requester-scoped modes.

## Evidence

- Focused tests: `prepare.configured-mcp.test.ts` (8 passed; the 2 requester-scoped cases fail on `main` with `expected 'probe:hi' to be undefined`, which is the Claude CLI turn returning no tool while the default runtime returns the user's result), `agent-bundle-mcp-harness.test.ts` (21 passed; the senderless sign-in case fails on `main`), plus the requester-connect, requester-lifecycle, completion-tools, existing-session and Codex app-server configured-MCP suites (102 passed in total).
- Grant ends mid-call (`prepare.configured-mcp.test.ts`, "stops a requester-scoped call when its grant ends during the token refresh"): alice signs in through the real OAuth flow, her access token expires, and a Claude CLI loopback `tools/call` (the Gateway handler with the grant check) starts with a current grant. The grant ends while the OAuth token refresh is in flight. Result: the call returns `Tool call authorization expired`, the MCP server receives no `tools/call` for it, and the next call with a current grant uses the refreshed token (one upstream `tools/call` in total). This uses the existing loopback grant check that runs before configured-server I/O; no new guard. It fails on `main` (`expected 1 to be 2`: no requester tool, so no refresh is ever attempted).
- Live, isolated Gateway on macOS with a real Claude CLI (`claude-sonnet-5-5`) behind the QA channel, a local OAuth authorization server and an OAuth-protected MCP server with two test accounts, one shared session, six turns:

| no sender (`openclaw agent`) | no notes tool | explicit "no verified user … No other account is used" refusal; server not called |
| bob, not connected | no notes tool | bob's own sign-in link; alice's token not used |

| alice | no notes tool | `ALICE-NOTE-7731…` |

  MCP server call log on this PR: `alice`, `bob`, `alice` — one call per connected user turn, none for the senderless turn, no cross-account call. On `main`: no calls.

- Prompt cache, same six turns: the Claude CLI tool list is identical (64 tools) on every turn after sign-in. Steady-state turns read the cached prefix and create about 1k tokens (`cache_read_input_tokens` 49,128 and 51,203; `cache_creation_input_tokens` 1,178 and 903), the same pattern as `main` (1,161 and 2,980). The senderless and new-sender turns start a new live Claude process on both builds (about 21–45k tokens created on each), so that cost is not from this change.

## Limits

- The catalog changes once per session when the first requester connects (sign-in tool → real tools), and once after a Gateway restart until a connected requester's turn records the catalog again. Both are real surface changes, not per-turn churn.
- Live proof used a local OAuth server, not a third-party provider.
- The new regression tests add 283 test lines (allocation file included); they replace no existing case because no Claude CLI test covered requester-scoped servers.
- The grant-ends-mid-call proof is a focused test through the Gateway loopback handler, not a live trace.
- The non-exclusive native Claude CLI path and the Codex CLI native projection still exclude requester-scoped servers by design; they are not changed here.

## Open question: child identity

Today a subagent child runs without the parent's requester identity, so a child of alice's turn cannot use alice's per-requester servers (documented in the plugin SDK infrastructure docs; same on every runtime). Granting a child its parent's verified requester would let delegated work use the parent's account, which is a security and product decision. Recommendation: keep the current rule; if wanted, add it later as an explicit, additive trusted field on the spawn path with its own review.

## Merge danger

Two-way door: no config, schema or stored-state change; a revert restores the previous behavior. Blast radius: Claude CLI and other loopback-bridged CLI turns on Gateways with per-requester OAuth or resolver MCP servers, plus Codex app-server senderless turns, which now list the sign-in tool instead of nothing. Shared MCP servers are unchanged. If the change were wrong, the likely failure is a requester-scoped tool listed but refusing, not a credential crossing users: calls still resolve credentials only from the current turn's verified sender.
```
