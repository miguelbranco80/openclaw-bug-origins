## Fix PR #160684 description (by steipete, opened 2026-09-28T20:05:13Z)

```text
## What Problem This Solves

The one-time dashboard pairing links from `openclaw dashboard` and graphical onboarding had two problems when they were reopened after they expire (10 minutes) or are used.

1. **Wrong diagnosis.** The login gate said **"Gateway secret rejected"** and told the user to replace their Gateway secret. Nothing was wrong with the secret; only the one-time link had expired or been used. This sent operators toward rotating credentials that were valid.
2. **Correct credentials still rejected.** After that screen, pasting the correct Gateway token and clicking **Connect** still failed for about 30 seconds. The consumed bootstrap token stayed in the connection and took priority over the manually entered token.

Both were reproduced with a real Gateway and Chromium, by reopening a consumed link in the same browser and in a second browser, and by waiting until 28 s after a link's expiry.

## Why This Change Was Made

- **Diagnosis** (`ui/src/components/login-gate-feedback.ts`, from ed9861f2e87): `AUTH_BOOTSTRAP_TOKEN_INVALID` now gets its own feedback: **"Pairing link is no longer valid"**. It explains single use and expiry and points to `openclaw dashboard`, with `openclaw dashboard --json` (`browserUrl`) as the fallback when no browser or clipboard is available. It no longer suggests changing the secret. The English strings are in `ui/src/i18n/locales/en-login.ts`, and `docs/web/control-ui/connect-and-pair.md` documents the recovery.
- **Precedence** (`ui/src/app/gateway-store.ts`, from 9cca9afa702): when the Gateway explicitly rejects the bootstrap token with `AUTH_BOOTSTRAP_TOKEN_INVALID`, the store clears that bootstrap token and profile. Manual credentials then reach the normal shared-auth path. A fresh handoff still takes precedence, and pairing policy is unchanged.

## User Impact

A stale pairing link now says exactly that and how to get a fresh one. Pasting the right token after that connects immediately instead of staying rejected.

## Evidence

- **Regression tests:** `ui/src/components/login-gate.test.ts` fails before the fix on the wrong heading. `ui/src/app/gateway-store.auth.test.ts` fails before the fix on the retained bootstrap. Both pass after, with 30 and 27 tests in their suites.
- **Real isolated Gateway plus Chromium on a Blacksmith Testbox:**
  - A fresh link recovers in 210 ms.
  - Correct manual credentials after a rejected link connect in 308–312 ms, where before the fix they stayed rejected for 30 s.
  - Five fresh token trials, including wrong and whitespace-padded tokens, plus password mode, basePath, storage clearing, and Gateway restart recovery, all behave as documented.

| Before: a reused link blames the secret | After: a reused link explains itself |
| --- | --- |
| ![before](https://github.com/user-attachments/assets/9dc095e7-a27d-4a2b-ba14-852eb4c93921) | ![after](https://github.com/user-attachments/assets/59c75eb2-82e3-46a7-b065-a7195da0c895) |

- UI build, i18n verification, and `node scripts/check-changed.mjs` pass. Codex autoreview ran on the final head.
```
