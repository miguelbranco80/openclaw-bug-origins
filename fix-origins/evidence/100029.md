```text
## What Problem This Solves

Fixes an issue where a late startup launch-at-login status read could overwrite a user's newer toggle choice. Rapid enable/disable changes also started independent asynchronous operations, allowing an older enable to continue toward restarting the app after the user disabled autostart. On fresh remote-only installs, a missing Library/LaunchAgents directory could prevent the plist from being saved while launchctl actions still continued.

## Why This Change Was Made

LaunchAgentManager owns ordered intent, status publication, and serialized login-job mutations. AppState records changes directly with that owner. The duplicate LaunchdManager restart path is removed and its caller uses the same mutation queue. Persistence creates the parent directory and reports failure before any launchctl action; disabling an already absent plist remains idempotent. Superseded enables stop before further launchctl actions; disabling future autostart continues to leave the running app alive.

## User Impact

The launch-at-login toggle follows the latest user choice. Startup hydration cannot undo it, and older asynchronous enable work cannot continue once superseded. Named profiles still perform no login-agent integration, and transient bundle restrictions are preserved.

## Evidence

- Existing LaunchAgentManagerTests now exercise isolated temporary plist files and a suspended launchctl runner: stale hydration, enable then disable, loaded/unloaded jobs, profile restrictions, and existing plist behavior.
```
