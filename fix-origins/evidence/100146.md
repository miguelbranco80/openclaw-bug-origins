## Fix message body

```text
Related: #168823 (this fixes fresh channel-owner messages queued for followup/collect execution, not every parent-resumption path).

## What Problem This Solves

Fixes: an authenticated channel owner sees only the current conversation's automations when their message waits in the followup queue.

## User Impact

Owners retain their existing ability to manage gateway-wide automations after a queued message starts; revoked ownership and non-owner or internal messages remain restricted. No configuration changes or migration are required.

## Why This Change Was Made

The original ingress capability expires before queued execution starts with a new run identity. Preserve a source-bound capability factory through queue collection and overflow, then enter a fresh scope for that queued run. The original sender, transport identity, current-owner check, and run-settlement/abort revocation remain authoritative; presentation defaults cannot supply another turn's capability.

## Related work and scope

Related: #148790 (merged channel-owner automation management) and #160018 (merged owner-authority preservation after a child reply). #148294 tracks the broader distinction between admission authority, continuation ownership, and delivered completion. This PR fixes fresh authenticated channel-owner messages crossing the followup/collect queue. The Control UI parent-resumption report #168823 enters through a different path; neither that entire issue nor the broader completion contract is claimed resolved here.

## Reproduction and environment

Observed on macOS with packaged OpenClaw 2026.10.2 and a configured Telegram channel owner. The controlled comparison restored the exact original versions of the three affected runtime modules, then applied the qualified fix; the installation also contained disclosed unrelated backports. The isolated Gateway cases used synthetic external Telegram/model endpoints. The separate October 15 Telegram check used the normal channel and provider. These runtime results belong to the earlier qualified patch, not to a new deployment of the October 16 integration head.

1. Configure an explicit owner in `commands.ownerAllowFrom` and use a Gateway with automation jobs belonging to multiple conversations. Confirm a fresh owner request can list the full inventory.
2. Start owner request A with a bounded wait. While A is still running, send a separate owner request B asking the native `automations` tool for `action=list, includeDisabled=true`, with the inline `/queue followup` directive at the end of B's message.
3. Confirm B arrives while A runs and executes afterward with a different run identity. Inspect the actual native tool result, not just the model's answer or a CLI list.
4. Before the fix, the exact-original control returns `scope=caller` with 1 of 6 jobs. After the fix, it returns `scope=gateway` with all 6; the separate real Telegram run returned all 73 jobs with `hasMore=false` and matching operator-inventory IDs.

The non-owner, foreign-source and authenticated-cancellation controls and the deferred-revocation limitation are linked below. This reproduction makes no mutation-race claim.
```
