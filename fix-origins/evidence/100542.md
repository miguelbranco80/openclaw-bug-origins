## What Problem This Solves

Fixes the compact Control UI rail losing its warm-reload snapshot with large session rosters or retaining the previous view after visiting Pages. The cold-load campaign observed lists filling at about 4.25 seconds after a signed-in dashboard deep-link reload, shifting the selected row.

## User Impact

Returning operators retain their visible rows, pins, selected view, and display identity while the Gateway reconnects. Connection status and mutation permissions still come from the live connection. No configuration or server-data migration is required.

## Why This Change Was Made

Two existing gates prevented the sidebar snapshot from being refreshed:

- Its embedded routing roster accepts at most 200 rows, but capture copied the entire live result. Valid owner-first results can include up to 60 additional owned rows, and pagination can grow the window further. Validation then rejected the entire sidebar snapshot. Capture now applies the existing roster bound; validation uses the same constant.
- Pages readiness waited for the inactive Sessions roster, which is cleared when Pages becomes active. Pages now waits for its dashboard catalog instead. Retry-pending reads retain the snapshot; terminal errors render live but cannot replace the last good cached catalog.

The existing snapshot remains the sole cache owner. Its visible rows and pins are retained separately from the bounded routing roster. Production LOC delta: **+6 net** (9 added, 3 deleted across four production files). The growth enforces the existing bounded-cache contract; the change removes the unrelated Pages readiness dependency and the validator's duplicate magic number.
