```text
fix(sessions): read and index Postgres transcripts that contain escapes jsonb rejects

Fixes #194517.

On PostgreSQL, session transcript JSON that contains an escaped lone surrogate (for example \ud83d) or an escaped NUL cannot be cast to jsonb. Every follow-up turn in such a session failed with 22P02, and a user message containing NUL could not be stored at all, because the full-text index insert failed with 22021 and the message was dropped. SQLite accepts the same text. Covered: the model-context reader and its navigation cache, tree and reset-boundary navigation, detached-context validation, the reset kept-tail window, the active-context fallback, chat.history run-input visibility, the transcript mirror run lookup, retained custom-data reads, session-entry maintenance, and the full-text index on both engines.
```

## Fix PR #194591 description (by ylcn91, opened 2026-11-07T11:17:50Z)

```text
Closes #194517

## What Problem This Solves

On PostgreSQL, a session whose transcript holds a JSON-escaped lone surrogate (for example a tool result or a user message with `\ud83d` or `\udc00` alone) or an escaped NUL broke: the next turn failed with `invalid input syntax for type json` (22P02), and a user message containing NUL could not be stored at all (22021, the whole append rolled back). SQLite handles the same transcripts.

## Why This Change Was Made

PostgreSQL stores each transcript event as its original JSON text. `jsonb` rejects escaped NUL and unpaired surrogate escapes, while `json`, SQLite and JavaScript accept them. Several readers cast stored event text to `jsonb`, some behind `jsonValid()`, which checks `json` validity and so lets these rows through. Separately, the transcript full-text index wrote the message text into a PostgreSQL `text` column, which cannot hold 0x00.

## User Impact

PostgreSQL-backed sessions holding these characters keep working: turns complete, chat history shows the original text, search finds the message, and stored rows are not rewritten.

## The fix

One guard owns "read stored transcript JSON natively on PostgreSQL": the existing `jsonNativeFieldsValid()` (`pg_input_is_valid(x, 'jsonb')`, from #183560). Rows it rejects reach JavaScript unchanged and are decoded there.

- ylcn91's commits: the per-turn model-context reader routes these rows through the shared JavaScript projection (`projectModelContextJson`), keeps that classification across cached navigation pages, and moves tree and reset-boundary navigation onto the guard.
- Added on top:
  - `projectModelContextNavigationSql` (detached context validation, reset kept-tail window, dependency fallback): guarded, and the cast is fenced so bound writer inputs cannot be constant-folded past the guard.
  - Bounded active-context dependency fallback, chat.history run-input visibility and the transcript mirror run lookup: guarded field reads; undecodable rows are matched in JavaScript with the existing readers.
  - Retained custom-data suffix reads: guarded; undecodable rows keep their data and are rewritten byte for byte, the path SQLite already uses for over-depth rows.
  - Session-entry maintenance: guarded.
  - Full-text index: NUL in the derived search text becomes a space on both engines. The transcript row keeps the original bytes.

No schema change, no migration, no rewrite of stored rows, nothing stripped from the stored transcript.

Follow-ups, not in this PR: the Doctor session-entry rewrite still casts entries to `jsonb`; `readTranscriptMirrorFacts` with an empty key list and a `sourceRunId` emits `IN ()` on PostgreSQL (unrelated, pre-existing).

## Evidence

Built Gateway (node 24.22.1, Docker, PostgreSQL 17.11 official image, local fixture model provider), main twice, candidate twice, SQLite once each. Proof comment: https://github.com/openclaw/openclaw/pull/194591#issuecomment-6734036405
```
