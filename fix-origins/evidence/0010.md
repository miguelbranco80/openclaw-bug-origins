## Fix message body

```text
fix(cron): reject --on-exit-cwd without --on-exit when editing a stream automation

When editing a stream automation, the stream path returned early before the existing "--on-exit-cwd requires --on-exit." check, so openclaw cron edit <id> --stream-cwd /x --on-exit-cwd /y applied the stream change and silently dropped --on-exit-cwd. The check now runs on that path too, so the edit fails with the existing message before anything is sent and the job is unchanged. Other edits are unchanged. No new text.

Evidence: the built CLI against a real gateway on an isolated profile in a secretless node:24.22.1 container, main twice and candidate twice. On main the edit exited 0, changed the stream working directory and dropped --on-exit-cwd. With this change it exits 1 with the existing error (byte-identical to main's message) and the job keeps its old working directory. --stream-cwd alone, --on-exit-cwd alone on an on-exit job, and a valid --on-exit with --on-exit-cwd behave the same on both. One row in the existing edit-reject table fails on main, at net 0 test lines. Details: https://github.com/openclaw/openclaw/pull/198588#issuecomment-6871024659.

Fixes #198587. Thanks @Wang-Zephyr.

Co-authored-by: Ayaan Zaidi <hi@obviy.us>
```

* fix(cron): preserve whitespace in command cwd CLI options

normalizeOptionalString, which trims leading/trailing whitespace. A path

Use readNonBlankString instead, matching the existing onExitCommand
handling in the same function. Blank values are still rejected (returns
undefined), so the blank-gate behavior is unchanged.

whitespace-only cwd falls back to process.cwd()) and apply the same rule
to Windows bare-command PATH lookup, so lookup and spawn agree on
untrimmed cwd without treating a blank cwd as a literal directory.
