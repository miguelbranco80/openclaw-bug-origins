* fix(sessions): stop truncating the sidebar roster

The Control UI asked sessions.list for 50 rows (60 with ownerFirst) and the
gateway defaulted an absent limit to 100, so a roster larger than the page
silently lost its tail. Sidebar categories are seeded from the group catalog
and filled from that page, so a category whose newest session fell outside the
window rendered as an empty header -- on team.openclaw.ai, 184 live sessions
meant only 6 of 28 categories had a visible row, and one category holding 25
live sessions rendered empty. With an owner filter active the empty section is
hidden outright, so the category disappeared entirely.

Rosters now send no limit and an absent limit means the whole list, matching
the vocabulary `openclaw sessions --limit all` already uses. This is close to
free: the store filter/sort is O(store) at any limit, and per-row transcript
reads are separately capped at SESSIONS_LIST_TRANSCRIPT_FIELD_ROWS (100) with
a yield every 10 rows, so extra rows are lightweight.

The Sessions page keeps a real page size under its own
SESSIONS_PAGE_DEFAULT_LIMIT, because that limit is an explicit operator-edited
field rather than silent truncation. The owner-first window keeps its 60-row
cap: it only decides which of your own rows are hoisted and hides nothing.

Also drops the 200-name cap on sessions.groups.put and the matching 232-entry
sectionOrder caps. The read path was already unbounded and the gateway
registers new categories on session patch without a cap, so a catalog could
grow past 200 and then fail every catalog write.
