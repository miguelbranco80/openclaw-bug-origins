## Fix message body

```text
* fix(macos): give reused launchd gateways the cold-start readiness budget

A launchd PID the app did not install (started at login after a reboot, or
by a repair) had no fresh-install evidence, so its readiness never extended
past the first 6s window. The timeout armed a forced LaunchAgent repair, and
the reinstall SIGTERMed the gateway mid-startup; every slow cold start hit
the same path, looping until the app was quit.

Let an unchanged launchd PID that still owns the port use the same bounded
startupMigrationTolerance budget as a fresh install. A PID that changes or
loses the port keeps today's behavior, and a PID still unready after the
budget is still repaired.

Fixes #158936

* fix(macos): re-prove a reused launchd PID at every readiness extension

Address review on #158954: a reused PID's startup grace no longer becomes
standing grace after the first extension, so a PID replaced during the wait
stops extending at the next deadline. Fresh installs and responsive
progress keep their existing standing grace.

Gate the cold-start regression test on the first launchd inspection instead
of a wall-clock sleep, add coverage for a PID replaced after its first
extension, and drop the unused setProjectRoot/projectRootPath wrappers the
dead-code scan flags on this file.

* fix(macos): give reused launchd gateways a reboot-sized readiness budget

A real reboot on this branch took about 139s to reach ready, past the
120s first-run budget the reused-PID path shared. The timeout left repair
evidence for a gateway that was still starting. Reused launchd PIDs now
probe through their own 300s budget; the PID is still re-proven against
launchd at every deadline, so a replaced or dead PID loses it at once.
```

## Fix PR #158954 description (by MertBasar0, opened 2026-09-26T15:03:57Z)

```text
Closes #158936

## What Problem This Solves

Fixes: OpenClaw.app kills and reinstalls a gateway that is still legitimately starting whenever a cold start (for example after a reboot) takes longer than the app's 6-second readiness window, looping until the app is quit.

## User Impact

User impact: a slow-starting gateway that launchd started on its own is left to finish starting (up to 300s, while the same PID keeps owning the port) instead of being SIGTERMed and reinstalled every cycle. A gateway that is still unready after that budget is still repaired.

Tradeoff: an unchanged launchd PID that owns the port but has a wedged health RPC is now repaired after up to 300s instead of right after the first window. A PID that exits, is replaced, or loses the port still fails at the next 6s deadline, so the longer wait only applies to a process that is still alive and still holding the port.

## Why This Change Was Made

The readiness deadline could only be extended past the first window with fresh-install evidence (or a responsive "still starting" reply). A PID launchd starts at login, or one started by a repair, never has install evidence, so the first window timed out, recorded that PID as failed, and the next enable request force-reinstalled it. The new process hit the same path, which produced the loop in the report.

The extension authorization now also accepts an unchanged launchd PID that still owns the port (or while nothing is listening yet), bounded by a new `reusedLaunchdColdStartTolerance` (300s). Fresh installs keep `startupMigrationTolerance` (120s). The reused budget started out shared with the fresh-install one; the reboot trace below measured a ~139s cold start that ran past 120s, so it now has its own, sized with about 2x headroom over that measurement for slower hardware. Unlike fresh-install grace, this grace is not standing: the PID is re-proven against launchd at every deadline, so a PID that exits or is replaced mid-wait stops extending at the next deadline. A PID that changed or lost the port gets no grace and keeps today's behavior.

## Evidence

New `GatewayProcessManagerTests` cases, driving the launchd readiness path without install evidence:

- `reused launchd gateway gets the cold-start budget before repair`: the first health probe stalls past the window and a later probe succeeds. On `main` this fails with `Gateway did not start in time` and arms repair. With this change it ends `.running`, records no failure, and the next enable request does not reinstall.
- `reused launchd gateway outlasting the first-run budget is not repaired`: every health probe hangs; the test releases them only after the sixth launchd inspection, which is past the fresh-install budget passed to the hook (0.2s) but inside the reused budget (5s). It ends `.running` with no repair evidence and no reinstall. With a shared budget (the previous head), the attempt fails before that point, which is the case the reboot trace hit.
- `reused launchd gateway still repairs after its bounded budget`: a never-ready reused PID still fails after the budget, and the next enable request still installs once.
- `changed launchd PID does not inherit the cold-start budget`: launchd now reports a different PID and nothing owns the port, so there is no extension and no repair evidence.
- `reused launchd PID replaced during its grace loses the grace`: 4242 earns the first extension, then launchd reports 4243; the next deadline re-checks and stops (3 launchd inspections instead of probing 4242 until the budget).

The cold-start case releases the first health response only after the first launchd inspection, which happens only once the first window has timed out, so it cannot pass without exercising an extension.

Existing fresh-install, repair, and deadline tests are unchanged.

`macos-swift (tests)` on the first head (5f722d3bd45): `Test run with 2294 tests in 263 suites passed`. The follow-up commit also removes the two unused `setProjectRoot`/`projectRootPath` wrappers that `Scan macOS dead code` flags on this file.
```
