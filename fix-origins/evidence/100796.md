fix(cli): keep the first records when `logs --follow` switches to a larger log file

When the log file path changed during `openclaw logs --follow` (for example at a date rollover) and the new file was already larger than the old byte cursor, the first records of the new file were skipped. A source change now rereads the new file from the start without a cursor, using the selected local source when config is unavailable. Each record still appears exactly once.

Proof: built CLI against an isolated authenticated Gateway: on main the new file's first record was lost; the candidate emits file A, both initial records of file B, and the appended B record exactly once, in plain and --json output. The unavailable-config local fallback still reads locally.

Fixes #150843. Thanks @zhangguiping-xydt.

## What Problem This Solves

Fixes missing initial records when `openclaw logs --follow` switches to a different log file whose size exceeds the previous byte cursor.

## User Impact

Following logs preserves the new file's available tail and subsequent appends in plain and JSON output, within the existing tail limits. Unreadable-config recovery continues reading local files rather than unexpectedly requiring a working, authenticated Gateway.

## Why This Change Was Made

Bind the existing byte cursor to its file path and reread without that cursor when the path changes. The reread uses the already-selected local source during config recovery, preserving the intent of #164158. Journal recovery and failed-reread retry behavior remain covered. Same-path inode replacement is outside this fix.

The new regressions control the polling/retry delay boundary instead of using real timers. Existing command tests now reuse the same fixture rather than duplicating its transport and output setup.

Thanks to @zhangguiping-xydt for the report and original repair. No overlap with Pash/Sarah changes.
