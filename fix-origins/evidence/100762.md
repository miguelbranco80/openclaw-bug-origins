## Fix PR #159683 description (by Yigtwxx, opened 2026-09-27T14:05:15Z)

```text
Closes #159682

## What Problem This Solves

Fixes: Memory Wiki search finds nothing for multi-word queries in non-Latin scripts (for example `проект альфа` or `東京 会議`) and ranks unrelated pages first for accented Latin queries (for example `Müller Straße`), because the query splitter treats every non-ASCII letter as a separator.

## User Impact

User impact: `wiki_search`, `openclaw wiki search`, the Gateway wiki search method, and the wiki corpus supplement for memory search match non-ASCII query words the same way they match English words, so pages written in Cyrillic, CJK, Greek, accented Latin, and other scripts are found when the words appear on the page in any order. ASCII-only queries produce exactly the same query terms as before.

## Why This Change Was Made

`buildQueryTokens()` split the lowercased query on `[^a-z0-9@._-]`. A query such as `проект альфа` produced no terms at all, so a page matched only when the exact phrase was present, and `Müller Straße` produced the fragments `ller` and `stra`, which matched `controller strategy`. The split now uses `[^\p{L}\p{N}\p{M}@._-]` with the `u` flag, the same Unicode class the plugin already uses in `claim-health.ts` and in `slugifyWikiSegment` (`markdown.ts`). `a-z` and `0-9` are subsets of `\p{L}` and `\p{N}`, and `@._-` plus the length filter are unchanged, so English and identifier-style queries are unaffected. Page text is already lowercased before matching, so dropping the `i` flag changes nothing.

## Evidence

Tested on `c991b6bf8f1` (current `main`) plus this change, Node 24.21.0, Windows 11.

`searchMemoryWiki` against a real temporary vault (`initializeMemoryWikiVault`, pages written with `renderWikiMarkdown`, `searchBackend: "local"`, `searchCorpus: "wiki"`), run without and with a compiled digest (both give the same output). Pages: an English, Russian, Japanese, and German note plus an unrelated `The controller strategy is documented here.` page.
```
