## Fix PR #149354 description (by steipete, opened 2026-09-15T19:08:17Z)

```text
Related: #149284

## What Problem This Solves

Fixes managed Chrome being restarted by the next operation after a slow but successful startup, and prevents profile lifecycle operations from acting on stale requests or moving data while browser ownership is uncertain.

## User Impact

Slow healthy browsers keep their process and tabs. Stopping a profile cancels pending readiness work, while canceling one waiter does not cancel an admitted shared launch. Reset/delete stop a verified browser left by an earlier runtime before moving data; uncertain ownership preserves the profile and reports the next action.

Locks naming another hostname are preserved, including after a machine rename. Starting Chrome also leaves those locked preferences untouched. An operator must close the browser using that profile and verify the lock before retrying. Personal and attach-only browser ownership remains unchanged.

## Why This Change Was Made

Keep launch and owned-browser operations on one readiness allowance, eliminate the duplicate discovery request on the owned path, and give the WebSocket handshake and health command separate deadlines. Carry lifecycle cancellation through discovery, readiness, and ownership probes; malformed advertised URLs now return a structured diagnostic.

The existing lifecycle owner now handles explicit stop/reset/delete cleanup, with typed stopped/absent/unverified outcomes and current-request admission immediately before mutation. Process matching rejects sibling directory prefixes and duplicate flags. Cleanup removes redundant timers, result construction, a defensive existence wrapper, and mock-only branch coverage; existing preference preservation has stronger tests.

## Evidence

- Browser suite: **3,280 passed, 45 skipped**, across 199 passing test files. `node scripts/run-vitest.mjs extensions/browser/src/browser --reporter=dot`.
- Real loopback HTTP/WebSocket fixtures prove independent phase budgets, cancellation during body/upgrade/command waits, socket cleanup, and malformed advertisements. The diagnostic and public-context cancellation regressions were demonstrated failing before their fixes.
- Negative-control tests reproduced the second-launch regression, stale request admission (including a microtask boundary), missing cross-runtime cleanup, other-host lock misclassification, locked preference writes, sibling directory ownership confusion, and replacement-lock handling. The repaired cases pass; current-host dead/zombie recovery and shared-start cancellation contracts remain covered.
- Changed-file typechecks, lint, formatting, plugin boundaries, dead exports, storage guards, and import-cycle checks passed. Independent review used complete owner/caller sources and its hostname-lock finding was fixed and regression-tested.
- No production deployment, live overloaded-Gateway reproduction, or new Windows cross-runtime cleanup proof is claimed.
```
