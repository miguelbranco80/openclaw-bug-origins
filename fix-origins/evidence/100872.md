## Fix PR #167708 description (by steipete, opened 2026-10-09T08:07:41Z)

```text
## What Problem This Solves

Fixes premature cancellation of the first corrective model request after a long response hits its output limit. The stalled-run detector counted the entire initial response as repeated-request stagnation, so its first retry could be aborted almost immediately.

## User Impact

A corrective request now gets the existing recovery window from the first retry. Later retries still share one deadline; streamed transport activity does not renew it. Persistent no-progress loops still abort and drain through the existing recovery owner.

## Why This Change Was Made

Start the repeated-request clock on the second request, keeping the original run-owner and semantic-progress reset contracts. Remove the redundant request counter; owner identity and the optional repetition timestamp describe all needed states. Production LOC delta: -5 (5 additions, 10 deletions).

The tradeoff is intentional: repeated-request recovery is delayed by the initial request's duration. Single-call inactivity and provider timeout handling remain in their existing owners.

## Evidence

Read-only production forensics found the same sequence in three sessions: an incomplete tool call at `max_output_tokens`, retry 1/8 with a corrective instruction, then abort 9.5–12.5 seconds after retry scheduling. Recovery reported `aborted=true drained=true forceCleared=false`; one interactive session then started a continuation. The sampled pre-error transcripts contained distinct tool calls rather than a repeated identical-call loop or compaction churn.

The regression extends the real heartbeat → recovery → queued-delivery integration: a 960-second initial stream must not consume the first retry's 90-second test window; subsequent requests must not renew that window; recovery must deliver queued work exactly once.
