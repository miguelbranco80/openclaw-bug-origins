## Fix PR #181225 description (by roboclaw-bot, opened 2026-10-23T02:34:41Z)

```text
## What Problem This Solves

Settings search has no visible keyboard-focus outline when forced-colors mode suppresses its shadow-based focus ring. Tabbing into the input leaves keyboard users without the distinct focus indicator shown on surrounding Settings controls.

## User Impact

Keyboard users can identify the focused Settings search input in high-contrast mode. Normal light and dark themes retain their existing focus shadows, and searching, clearing the query, and moving focus continue to work as before.

## Why This Change Was Made

The search input explicitly removes the normal outline and uses a box shadow for focus. A forced-colors media rule now gives its `:focus-visible` state a 2px `Highlight` outline, using the browser's system color. The rule stays with the input's existing stylesheet; the search component and its keyboard handlers are unchanged.

## Evidence

On base `87aada17522b9146cf5e26df3352b81d8cc0669b`, the bundled Chromium regression reaches the real Settings input with keyboard focus and `:focus-visible`, but both the outline style and shadow are `none`. The regression fails there. On head `0e05b45c194f0144191974201bf16e5f18f0e200`, it passes with a solid 2px system-color outline. The capture scenario also verifies searching, Escape-to-clear, moving focus away and back, and settled normal light/dark themes. The unfocused before/after frames are byte-identical, and no configuration mutations occur.

A separate WebKit 27.2 check passes the same keyboard-focus and unfocused-outline conditions. WebKit's media emulation retains normal page colors and shadows, so Chromium provides the forced-palette and shadow-suppression evidence shown below. Both use the production UI bundle with synthetic Gateway data; these checks do not claim physical OS high-contrast or assistive-technology certification.

Changed-file formatting, lint/style checks and the affected E2E type graph pass. The [full UI run](https://github.com/openclaw/openclaw/actions/runs/39929148816) passes all three UI unit rows, nine mocked-browser rows and two real-Gateway rows; the original regression passed in 1,260 ms. Declared live opt-in cases remain skipped. The broader run retains baseline failures in unrelated tooling, session diagnostics, Windows fixture cleanup, native/update checks and dead-code checks; it is not a green whole-suite result. The Windows installer recovery passed on the same head, and the target branch includes the independent exec-completion test correction in #181563. The [earlier selected run](https://github.com/openclaw/openclaw/actions/runs/39890553360) also covers the stylesheet's direct test consumers and 36 Settings-sidebar/search cases.
```
