## Fix PR #147141 description (by steipete, opened 2026-09-13T15:25:52Z)

```text
## What Problem This Solves

Fixes Gateway CPU spikes and delayed chat responses when status polling repeatedly loads the entire retained task registry on the main thread.

## User Impact

Status keeps the same task counts, audit totals, retained-lost handling, and live ownership decisions while database work runs on the existing SQLite worker. No schema migration, configuration change, task deletion, or retention change is required.

## Why This Change Was Made

The status path restored task payloads and delivery-state maps and ran physical integrity checks on every request. It now streams narrow metadata into fixed-size history aggregates and returns only candidates needing Gateway-owned liveness reconciliation. Cron recovery matches are selected in the same read snapshot without another full job-history read. Overlapping task-summary reads coalesce; completed results are not cached, and each caller revalidates its database admission.

Summary scans bypass secondary indexes so stale indexes cannot hide records. Full registry restoration and Doctor retain physical integrity verification; the summary is not a substitute for that verification. Known database failures and quarantine still refuse reads.

Related: #147110 removes unnecessary full-status requests from resource graphs; this PR repairs the backend status path itself.

## Evidence

- Focused task, audit, status, read-only, reconciliation, and worker regressions passed. Coverage includes stale indexes, cron first-match order, subagent ownership markers, artifact-preserving reads, and fresh results after coalesced requests settle.
- On an isolated 35,000-task synthetic fixture, the unchanged full snapshot took 680–1,559 ms; the new metadata summary took 96–101 ms and returned a 431-byte aggregate. These are local measurements, not a production improvement claim.
- Running the original status source and candidate against that fixture reproduced six task/integrity statements on the calling thread before and zero afterward, with identical task/audit totals. A smoke test of the production build took 967 ms for the initial request including worker startup, then 91–93 ms for warm requests on the same fixture.
- Core typecheck, full production build, and independent review passed. CI identified SQL annotation, retired-export and test-process routing cleanup; those are fixed. [Exact-head CI passed](https://github.com/openclaw/openclaw/actions/runs/34768324656). Live comparison will follow deployment.
```
