## What Problem This Solves

Fixes: an agent that waits on a slow external result (CI, a review bot) keeps one turn alive for many minutes. It polls a background command every 30 s and starts new sleep-and-check commands while earlier ones are still running, even though the command's exit would wake the conversation.

## User Impact

User impact: when a background command's exit will start the next turn, the agent is told so and ends its turn instead of polling. Hidden subagents, which get no exit wake, are no longer told that they do. Fewer model round trips while waiting, and the final answer still arrives through the exit wake.

## Why This Change Was Made

**Observed incident (production dashboard session, Claude Opus).** One turn ran for about 20 minutes waiting for a PR's CI and review result. It started four overlapping waiters (`sleep 290; gh pr checks …`, `sleep 280; …`, `sleep 240; …` and a 70-iteration `gh` loop) and made 21 `process poll` calls of 30 s. Each poll returned `(no new output)` / `Process still running.`. Each exec asked for `yieldMs` 270000–2150000 and came back after about 121 s as a background handle. All four commands had different text, so a duplicate-command guard would have caught none of them.

**Root cause (current `main`):**

- The system prompt said `Long wait: no rapid poll. Use exec yieldMs or process(poll, timeout=<ms>)`. But `yieldMs` is silently capped at 120000 and the poll timeout at 30000, so a requested 5-minute wait returned after 2 minutes as a background handle.
- Sessions that are not chat channels default to `notifyOnExitEmptySuccess=false`. There, the running result never said that the exit wakes the conversation. It said to "collect the result before ending the turn if empty success matters". Idle polls said only `Process still running.`.
- Waiters started earlier in the same turn do not appear in the turn-start "Active exec sessions" snapshot.
- Hidden subagent sessions get no wake turn, yet their running results said that completion wakes them.

**Fix (inside the existing exec/process owners; no new tool, state or config):**

- `hasExitWake(session)` beside the exec result formatter, fed by the facts the process owner records: the process owner captured a wake target (`notifySessionTarget`). This is the single fact behind all guidance. Hidden subagents and failed target captures have no target.
- Running results: when the exit wakes the conversation, they say so and say to end the turn if only waiting remains, instead of polling or starting another command that waits for the same result. To wait for a condition, the agent should loop inside one command. They also list the other background commands still running in the conversation, and say when `yieldMs` was capped. Sessions without a wake target get the existing manual-collection guidance.
- Idle `process poll` results of a waking command repeat the end-the-turn guidance. `process` list/poll/log mark sessions without a wake target with the manual-collection follow-up.
- Wait guidance in the system prompt, the exec description and the `yieldMs` schema description now match: end the turn when the exit wakes you; `yieldMs` max 120000.
- Docs: `docs/tools/exec.md`.

Not done: a duplicate-command guard. The observed waiters were all different commands, and judging "same intent" would be a heuristic on model output. The running result lists the other running commands instead, so the model can judge.

## Evidence

**Real agent, isolated Gateway from source** (`ocx src`, pinned Bun fork), `openai/gpt-6-astra` on the OpenClaw runtime, direct tool surface (`tools.codeMode=false`). Each trial is a fresh session: "I just pushed PR #N. `ci-status` prints its current status. Once all checks pass, write the summary line to RESULT.md, then tell me the PR is ready." The fake CI flips to passed 240 s after the agent's first check. Base = merge base `18892937`; fix = this head.

S2: `automations` denied, so the agent must wait with `exec` (the incident's mechanism):

| Arm | Valid trials | Final answer delivered | Duplicate waiters | `process poll` calls | Background waiters | Turns | Tokens / trial | Cost / trial |
|---|---|---|---|---|---|---|---|---|
| base | 12 | 12/12 | 0 | **76** (6.3 per trial) | 33 | 21 | 433k | $0.93 |
| fix (previous head) | 6 | 6/6, all via exit wake | 0 | **0** | 7 | 13 | 237k | $0.69 |
| fix (this head) | 6 | 5/6 | 0 | **0** | 5 | 10 | 192k | $0.60 |

- Base pattern, every trial: `sleep 30; ci-status` with `yieldMs`, returned as a handle, then `process poll timeout=30000` until exit, then a new sleep-and-check, repeated.
- Fix pattern: one looping waiter, end the turn, the exit wake delivers the result, then write RESULT.md and reply.
- This head also tells the agent that, under the default `notifyOnExitEmptySuccess=false`, a silent success wakes nobody, so the waiter must print its result. The one undelivered trial on this head started a correct single looping waiter and ended its turn, but its own status check never matched the final `all 15 checks passed` text, so the loop kept running past the trial window. That is the agent's parsing bug, not a missing wake; it made 0 polls.
- An earlier fix head without the "loop inside one command" sentence also made 0 polls in 4 trials. One trial ended its turn after each 20 s check and was woken 8 times. The loop sentence removed that pattern.

S1, all default tools (control): base and fix both chose a one-shot automation in every trial: 0 exec waiters and 0 polls in both arms, 6/6 final answers each. The automation path is unchanged.

Neither arm reproduced *concurrent* duplicate waiters with this model. The OpenAI agent waited for each waiter to exit before starting the next one. The duplicates came from the Claude incident above. The sibling listing in the running result is covered by the regression test below, not by the E2E.

**Tests** (`vitest-source`):

- `bash-tools.exec-background-followup.test.ts`: a woken conversation gets the end-the-turn guidance, a second waiter lists the first, and an idle poll repeats the guidance. A hidden subagent gets manual collection, not a wake promise. Both are red on the merge base and green here.
- The exec/process, system prompt and prefix-stability suites pass. The shared process fixture now models an ordinary wake-armed session.

**Full tier** on this head: `ocx build --dts` plus packed tarball install: `openclaw --version` and `gateway --help` pass.

**Limits:**

- E2E used one OpenAI model on the direct tool surface. Code Mode (the default for this model) waited in-turn with `awaitResults` in a smoke run; I did not measure it per arm.
- Two trials in an earlier fix batch never started: the Gateway rejected concurrent first sends with `Agent creation no longer owns its originally observed target`. That is a session-creation race outside this change (later batches stagger sends).
- The process-session record shape is unchanged. Only the model-facing text and the `followUp` in `process` results for sessions without a wake target change.

Co-authored-by: Ayaan Zaidi <hi@obviy.us>
