## What Problem This Solves

Two gaps in the managed system-service update handoff, both found in review on the abandoned `release/2026.9.7` branch (2dc8fb8e29a5, with lint/fixture follow-ups 64deeeb77c01, 26478a45f25a and 7aecd8624360) and never forwarded to main:

- **Premature settlement.** The Gateway replacement join (`joinSystemServiceUpdateHandoffs`) treated the detached update helper as settled whenever it closed with an exit code and no signal. The helper's own SIGTERM handler exits with code 143, so a helper interrupted mid-update counted as settled and replacement could proceed while its detached updater was still running.
- **Dueling installs.** When the same systemd unit exists in both user and system scope, `admitSystemdUpdate` only kept system-scope restrictions for `kind === "system"`, so the operator-restart restriction for the system unit was silently dropped.

## Summary

- The helper writes a completion receipt (`system-update-settled`) for system-service handoffs; `observeManagedServiceUpdateHandoffClose` marks the owner settled only with that receipt plus an unsignalled close.
- `admitSystemdUpdate` admits `dueling` installs under the same system-owner restriction; lifecycle discovery stays user-first.
- `docs/install/update-troubleshooting.md` explains the behavior.

## Evidence

- Both defects reproduced on unchanged main via the ported regressions (settlement-control, dueling cases in `update-command-system-service.test.ts`, single-flight unwritable install); after the fix 52 focused cases passed (9 Linux-only real-process skips on macOS).
- `pnpm check:changed`: production typecheck and preceding guards passed locally before a host-load interruption; remaining lanes are on this PR's CI.
- Autoreview (branch mode): scoped-clean, no actionable findings.
- Not proven here: Linux real-process settlement run, live system unit, published-driver upgrade.
