Related: #154370

## What Problem This Solves

Fixes native browser pairing accepting a manifest whose file is replaced after its ownership and mode checks but before its contents are read.

## User Impact

Native browser pairing and registration inspection validate the actual manifest and launcher bytes they consume. Existing owned private hardlinks remain supported, with the same real-user ownership and POSIX permission requirements.

## Why This Change Was Made

One private-file reader now uses the existing fs-safe descriptor admission path for both native-host pairing and registration inspection. This removes duplicate path-based checks while preserving the plugin's policy. It uses the existing released fs-safe dependency; no dependency change, migration, or operator action is required.

Existing installations remain compatible: registration JSON serialization, manifest fields and origin grammar, owned-launcher parsing, and immutable launcher construction/publication are unchanged. The change replaces admission/read sites and validation before cleanup; it preserves real-user ownership, private/executable modes, canonical paths, hardlinks, and separate Windows routing. No stored-format, schema, configuration, or protocol change is introduced.
