## What Problem This Solves

Fixes missing Control UI setup data and failed session creation when many users connect to one Gateway at once.

## User Impact

Concurrent setup requests can wait for their turn instead of receiving retryable server-busy errors. A single connection retains its previous waiting allowance; aggregate count, serialized bytes, control reserves, FIFO ordering, and yielding remain bounded. No configuration or protocol change is required.

## Why This Change Was Made

A two-job Control UI bootstrap can run three approval-list RPCs and two cron RPCs together. At 100 clients that is 500 ordinary requests competing for only 256 waiting slots. A stall makes this easier to hit, but a fixed-clock owner regression reproduces the capacity mismatch without one.

The existing request-start owner now allows 1,024 ordinary waiting requests across connections and caps each connection at 256. It shares the existing control per-connection accounting instead of adding another scheduler. The 50 MiB ordinary byte limit and the separate 1,024-request/1 MiB control reserve are unchanged, as are 64 starts/12 ms yielding. This is bounded burst tolerance, not a CPU optimization or a fix for the remaining main-thread stalls.

Update/restart behavior: the request-entry owner still joins accepted preparation and rechecks closure and live authority after each queued start; this change adds no timeout, persistent state, or shutdown owner. The independent worker-drain shutdown fix is #162616; this PR is not stacked on it.
