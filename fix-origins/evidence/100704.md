## What Problem This Solves

Custom model endpoints could inherit the standard catalog endpoint's compatibility flags. Inherited Code Mode preference could suppress Tool Search even when the custom endpoint did not support the same tool behavior. Config materialization and runtime resolution now use the endpoint that owns those capabilities.

## User Impact

Catalog capabilities apply to their matching API and physical endpoint. Equivalent Anthropic `/v1` and `/v1/` spellings retain the canonical endpoint's capabilities. When configuration selects catalog endpoint A after discovery returned endpoint B, resolution selects A's catalog capabilities, including provider-only overlays with no model row. Same-endpoint discovery keeps its refreshed metadata.

**Upgrade note:** Custom endpoints that implicitly borrowed `codeMode: "preferred"` now use the normal Tool Search controls. An endpoint verified to support Code Mode can retain the existing explicit `models.providers.<provider>.models[].compat.codeMode: "preferred"` setting. Other endpoint-specific flags, including `supportsTemperature`, also belong in the custom endpoint's existing `compat` declaration. No new configuration field is introduced.

## Why This Change Was Made

Keep compatibility decisions at the existing catalog and transport owners. Reuse Anthropic endpoint normalization and consult the existing static catalog lookup only when discovery's endpoint differs from the selected endpoint. Doctor retains its unique-route and equality checks when removing redundant compatibility declarations; divergent and custom declarations remain protected.

Related: #154964, whose Gateway/MCP proof exposed the original defect.
