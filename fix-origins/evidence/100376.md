## What Problem This Solves

A profile limited to session scopes can be eligible to read a conversation while still being excluded as a mention recipient. Its own Inbox methods also require broad read access, and the targeted change notification is filtered out before reaching the browser. Together, these gates prevent an eligible guest from receiving and managing a mention through the existing Inbox.

This recipient and Inbox contribution builds on the sender and lookup support merged in #178038. Related sender lookup context is in #178031.

## User Impact

Eligible signed-in guests can receive automatic Inbox updates, list their currently accessible mentions, and dismiss their own entries using `operator.sessions.read` or the read access implied by `operator.sessions.write`. Current profile, role, and conversation visibility continue to govern every read and dismissal. Another profile cannot select that guest's Inbox or dismiss its entries, and a mention does not grant conversation access or membership.

This uses the existing Inbox and replay records. It introduces no configuration or storage migration. Optional browser/OS push retains its existing subscription and permission requirements; the change concerns the live Inbox.

## Why This Change Was Made

The recipient policy now uses the same session-read scope implication as the sender path. The shared method mapping gives the profile-owned `mentions.list` and `mentions.dismiss` methods their narrow admission alternative, which the existing UI capability check also consumes.

The existing `mentions.changed` event remains a targeted invalidation containing a Gateway identity and view revision. The broadcaster admits it to session readers only through the targeted personal-invalidation path. The Inbox still selects the current authenticated recipient and filters entries through current conversation access. The sidebar's health and cron inventory guards remain unchanged.

+## Human mention delivery
+
+The Control UI binds each [selected person](/concepts/multi-user#mentioning-people) to the submitted message text. `chat.send`, the initial message on `sessions.create`, and `sessions.send` accept an optional `mentions` array of `{ profileId, start, end }` annotations. There are at most ten annotations; `start` is inclusive and `end` is exclusive, measured in UTF-16 code units. The Gateway validates their text ranges and recipients before accepting the input. Plain `@name` text and agent output do not create human mentions; copying or quoting text does not copy its recipient selections.
+
+The mention becomes eligible for an Inbox entry and optional browser push only after the original human message is newly committed to the transcript. An early `status: "started"` acknowledgment, a staged initial message, or durable pending-input custody is not that commit. A queued or remotely placed first message therefore does not notify while it is still waiting to be recorded. A later agent failure does not undo a mention whose human message was already committed.
+
+Transport retries preserve the exact submitted text, mention annotations, and original send identity, even when execution gets a different run id. Replaying that committed input does not create another mention or restore a dismissed entry. An intentional new send has a new identity and may notify again, even when its text is identical. Transcript loading, hidden continuations, and attachment enrichment are not new human sends.
+
