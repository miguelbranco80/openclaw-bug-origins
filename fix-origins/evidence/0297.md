## Problem

A message queued while a turn runs could be dropped because a check failed, not because anything ended it.

The custody contract (`docs/concepts/session-controller.md`) lets an accepted input end only as consumed, deliberately dropped, cancelled or interrupted, and requires every accepted input to stay accounted for. The access-policy contract (`docs/plugins/sdk-runtime/gateway-and-nodes.md`) says an owner aborts its signal when a source is revoked, and that an internal assertion error "refuses the operation without revoking the person or their admitted runs".

The code did the opposite in two places:

- The authority owners latched a revocation they found inside `assertCurrent()` without aborting their signal (`operator-run-authority.ts`, `admitted-run-context.ts`). Revocations found by event rechecks were recorded; ones found by a direct check were not.
- Seven queue and mailbox readers ended custody when `assertCurrent()` threw: `isFollowupOperatorAuthorityCurrent` and its four callers (followup runner, drain retry filter, stalled-turn handoff, goal return), mailbox claim release, early injection and steer admission, `reserveSteerCandidate`, and the channel steer caller. Each re-derived the owner's decision from the thrown error with its own rule.

On a real Gateway with an access-policy plugin, a 30 s policy outage while a message was queued dropped it as `withheld`; it never ran after the policy returned.

## Fix

- Owners record revocation: `assertCurrent` in `operator-run-authority.ts` uses its existing `revoke()`, and `createAdmittedRunOperatorAuthority` aborts a local revocation signal, composed with the upstream one, instead of keeping a private latch. A policy outage stays non-terminal.
- Queue and mailbox custody end only on recorded facts: the input's abort signal (which already includes the source authority's signal), retirement, cancellation, or consumption. A failed check now only refuses that attempt; the input stays queued and the drain retries it.
- Deleted `isFollowupOperatorAuthorityCurrent` and every inferred custody end listed above. The deletions in `drain.ts`, `agent-runner-execute.ts` and `goal-continuation-return.ts` match #200231.
- Notices survive the owner's new revocation signal. The stalled-turn handoff refuses a continuation while the source authority is aborted or refusing, without ending custody, so the original dispatch keeps its fallback notice. `runReplyAgent` still returns a prepared preflight failure notice when the operation was aborted by the source authority's own revocation; an explicit Stop, supersession or restart stays silent.

No new helper, flag, retry, backoff, schema or config. Production code: net −43 lines.

Replaces #200413, which taught two of these readers a wider "temporary" rule; that rule disagreed with the owner on remote-ingress "owner changed" errors and would have retried such an input forever.

## User impact

- A message queued during a temporary access-policy outage runs after the policy recovers.
- An internal policy error no longer silently drops a queued message.
- Revocation, Stop, delete and graceful restart behave as before: revoked, stopped and deleted messages are cancelled with zero model calls.

Affected installs: those using an access-policy plugin whose evaluation can fail. No built-in policy reaches the outage path.

## Evidence

- Regression tests, red on the merge base `b4254cb2`, green on this head:
  - mailbox: the exact controller input survives a refusing run or adapter authority (base: consumed);
  - followup runner: policy outage and an unsignaled internal assertion error keep the input (base: dropped);
  - authority owners: a revocation found by `assertCurrent` aborts the owner's signal, including remote-ingress owner replacement (base: signal not aborted);
  - steering: early and guarded steer assertions, `reserveSteerCandidate`, and the channel steer caller keep the source after an unsignaled failure and still end it on recorded cancellation (base: retired).
- Real Gateway from source (`ocx src`, isolated state, real model, a test access-policy plugin loaded through `plugins.load.paths` that reads its grant from a file; non-owner sender), base vs head, with the message confirmed queued before each event:

  | Event | Base `b4254cb2` | Head |
  |---|---|---|
  | 30 s policy outage (grant file moved away and back) | withheld; never answered | same queued run answered after restore; 0 model calls during the outage; no failure notice for the queued message |
  | Grant revoked | cancelled, 0 model calls, socket 4001 `grant-revoked` | same |
  | Outage, then grant revoked | already withheld during the outage | kept through the outage, then cancelled; 0 model calls |
  | Stop | cancelled, 0 model calls | same |
  | Delete | removed, 0 model calls | same |
  | Graceful restart | resumed and answered | same |

  During the outage the head logs 14 refused attempts in 30 s (peak 2/s), each refused before any model call.
- Accepted edge: a long outage keeps the message queued on the drain's existing retry cadence.

Co-authored-by: Ayaan Zaidi <hi@obviy.us>

- No authority is widened. Revoked input is still refused and is never replayed.
