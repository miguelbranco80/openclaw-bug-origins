fix(gateway): match canonically equivalent workspace filenames in file search

Workspace file search compared names with a raw lowercase match, so a query in one Unicode form (NFC) missed a file named in the other (NFD), and the reverse. Search now matches canonically equivalent names and still returns the original filenames.

Evidence: built Gateway over WebSocket, sessions.create then sessions.files.list on Linux. On main both cross-normalization searches missed the file (twice); with this change they found the original filenames (twice). Files whose NFC and NFD names coexist stay distinct, and ASCII and case searches behave the same on both refs. Details: https://github.com/openclaw/openclaw/pull/186329#issuecomment-6455031623. Production 5 lines.

## What problem this solves

Workspace file search misses canonically equivalent NFC/NFD filename/query pairs. A file named `cafe\u0301.md` is visible in the browser tree but absent from an NFC `café` search; the reverse pairing fails too. `sessions.files.list` currently compares lowercase strings without canonical normalization.

## Fix and user impact

Normalize only the query and candidate comparison text to NFC after case folding, following the comparison-only pattern in #184847. Users can find either canonical spelling regardless of the filename's stored form. Returned paths and on-disk names retain their original bytes; no path identity, authorization, traversal, result-limit, or persistence behavior changes.

The contributor's production fix is preserved. The conflict with main is resolved using main's existing test ceiling, dropping this PR's ceiling refresh. The redundant ASCII unit test is removed, and the retained table covers both cross-normalization directions with original returned-path assertions. ASCII and case behavior are checked through the actual Gateway RPC below.
