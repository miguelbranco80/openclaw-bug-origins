```text
After a parent turn yields to announcing subagents, Telegram keeps updating the same confirmed progress card with privacy-projected child progress instead of sending a generic waiting acknowledgment, then delivers one final and deletes the card; /stop, reset, NO_REPLY and failures retire it. The card lifetime stays with Telegram's draft-stream owner and follows the subagent registry. ## Fix PR #166101 description (by roboclaw-bot, opened 2026-10-06T11:49:57Z)
```

```text
Related: #150995 (same intent; no code reuse). Builds on the progress-continuation contract from #152517 / #153028.

## What Problem This Solves

When a Telegram parent spawns announcing subagents and calls `sessions_yield`, the live progress card is deleted at the yield and replaced by a generic "I'm continuing this work and will send the result when it is ready." The user sees nothing while the children work, until the final answer arrives about a minute later.

## Design

Telegram keeps the card. The waiting-status payload of a yielding turn carries a one-shot `progressContinuation.adopt(draft)` capability (`src/auto-reply/reply/waiting-status.ts`). Telegram's `deliverReply` hands over its **confirmed, still-live** progress stream wrapped as `{ push(item), retire() }` (`retainProgressDraft`). Rendering, throttling, the account limiter and deletion stay with Telegram's own draft stream. If the card is adopted, the waiting ack is not sent and the stream is detached from the finished turn.

**SDK handoff (versioned).** Channels receive the capability as `ReplyDispatchRuntimeInfo.adoptProgressDraft(draft): boolean` from `openclaw/plugin-sdk/reply-runtime`. **Deprecation:** `ReplyDispatchRuntimeInfo.adoptProgressContinuation(receipt): Promise<boolean>`, which shipped in 2026.9.8, is deprecated and replaced by `adoptProgressDraft(draft)`. The type stays exported and source-compatible, so third-party plugins still compile, until the next Plugin SDK major. The host never offers it, so an adapter written against it keeps ordinary waiting-reply delivery and the host never receives a receipt. Telegram, the only bundled adopter, uses the draft handoff. This is recorded as `reply-dispatch-progress-receipt-handoff` in the compat registry and documented in `docs/plugins/sdk-channel-plugins/status-and-media.md#progress-card-handoff` and `docs/plugins/sdk-migration/compatibility-policy.md#progress-card-handoff`.

**Retirement fence.** `retire()` revokes the retained card synchronously. Every retained edit carries an assertion that the account limiter re-checks at network admission, so an edit still waiting in the per-chat scheduler is rejected before any Telegram I/O. The draft stream now keeps an update's send authority until that update lands or a newer accepted update replaces it. A skipped or failed attempt that a scheduled flush retries is therefore still fenced. A generation reset (rotation, `forceNewMessage`) drops the pending update together with its authority.

Core custody (`src/agents/subagents/registry/subagent-progress-draft.ts`, ~230 lines) is process-local and attaches to owners that already exist:

- **Adoption** succeeds only if every announcing spawn's current registry row is still owed to its requester: `requesterSettleWake` is set, there is no accepted suppressing cancellation, and no wake is already dispatching.
- **Updates** carry only child status rows and child tool **names + status**. Child prose, commands, arguments and results are never pushed.
- **Lifetime** follows committed registry state. A projection subscription reconciles the draft on every publication. It follows a task's replacement execution (steer, or a resumed child yield, under the same task id). It drops members that are no longer owed and retires the card once none remain. Settlement, wake retries, `/stop`, `/reset` and row removal all commit through publications, so the card has no settle or kill hooks of its own. A kill intent can still roll back, so only accepted cancellation ends a member.
- **The resumed parent**: the existing settle wake is still the only final-delivery owner. `withSubagentProgressDraft` shows the resumed requester's tool rows on the same card. If that parent yields again, the new cohort joins the same card (`trackSubagentProgressYield` in the yield commit).

### Why the original continuation module was replaced

Credit to the original implementation in this PR (head `2496977694`). It proved the UX and the privacy projection, and its live matrix found the right cases. The rewrite keeps those invariants but removes the second owner of the presentation lifetime:

- `subagent-progress-continuation.ts` (699 lines) is gone. It ran its own edit queue and timer, made edits through `runMessageAction`, did cohort/generation re-checks, and listened for session facts scoped only by key. Telegram's draft stream and committed registry state now cover all of this. The earlier review findings no longer apply: key-only revocation, disabled edit/delete actions, `/stop` with a completed member, and `NO_REPLY` orphaning.
- Also removed: the `AsyncLocalStorage` promote context, the JSON streaming-identity channel-policy fence, the separate presentation module, the canonical-`to` receipt fix, and cron/batch authority moving under presentation. The receipt handoff is replaced by the versioned draft handoff above.
- The queued-follow-up attach is removed. Queued Telegram replies go out through `routeReply` and never reach the adopting dispatcher, so queued turns keep the waiting ack exactly as on `main`.
- A queued turn admitted after an adoption now gets its own fresh answer stream (`createAnswerStream`).

## Discord: dormant path removed

Discord's adopt path (#153028) has had no producer since #159179 removed the Tasks runtime. This PR deletes that adopt path and its tests (−84 prod lines). Discord keeps the ordinary waiting ack.

## Bounded cost

- At most one retained card per adopted yield. It only exists while the registry still owes that cohort to its requester. Edits use Telegram's existing throttle and account limiter: one draft stream, no new timers.
- Per card, core keeps one registry projection listener plus one agent-event listener per tracked child (and one for the resumed requester). Each registry publication costs O(tracked children × rows for that child session) through the existing child-session index.
- Nothing is persisted. After a Gateway restart the card is not revived; it stays as a stale message, the same as any in-flight progress draft on `main` today. Stopping the Telegram account while a card is retained has the same local-transport limitation; core releases its listeners when the tasks settle.
- Data model: no stored rows, columns, schema or migrations change. The card handoff is process-local, and the registry rows it follows are read, never extended, so upgrade and downgrade see the same stored data as `main`.
- No new config, schema or permissions. No new user-visible messages: an adopted card replaces the ack, and opt-outs are unchanged.

## Not changed

- Final delivery, `NO_REPLY` handling and the settle-wake retry policy. Case (d) shows `main` already re-prompts a yielded requester that answers `NO_REPLY` and then sends its incomplete-turn notice. That behavior is identical on both sides and is out of scope here.
- Queued Telegram turns, `streaming.mode` `off`/`partial`/`block`, quiet progress, Slack, Codex, Discord (waiting ack), cron and collector delivery.

LOC vs `main` (`9e5692852d60`): prod +532/−195, tests +866/−316, docs +54/−27, scripts +1 (the wrapper inventory entry for the new compat record). The original PR was prod +979/−38.
```
