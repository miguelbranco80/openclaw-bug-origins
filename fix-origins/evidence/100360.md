## Fix PR #160813 description (by steipete, opened 2026-09-28T23:56:13Z)

```text
## What Problem This Solves

Model setup verification against an endpoint that cannot be reached took more than a minute, and then gave the wrong reason. This applies to the Control UI **Models** first-run setup and to `openclaw onboard`. Examples are a custom OpenAI-compatible URL on a closed port, or a hostname that does not resolve. The UI showed **"Testing your AI connection…"** for about 80 s, and then reported **"The setup response check timed out."** Nothing was timing out: the connection was refused immediately, eight times over.

## Why This Change Was Made

The setup probe (`src/system-agent/setup-inference-turn.ts`) runs through the embedded agent runner, so it inherited the ordinary session transient-retry policy (`failover-retry-controller.ts`, from a9e9dec42df). Recovery also dropped the transport error code on the way (`attempt-recovery.ts`, `assistant-failure.ts`), so the setup owner could not tell a refused connection from a slow one.

- Transport codes are now carried through embedded recovery into the retry decision.
- A new internal run parameter, `retryConnectionErrors: false`, is set only by the one-shot setup probe. It makes the controller reject definite connection failures (`ECONNREFUSED`, `ENOTFOUND`, `EHOSTUNREACH`, `ENETUNREACH`) instead of spending the retry budget.
- Ordinary agent runs keep their retries unchanged, because the parameter defaults to the existing behavior.
- `describeSetupInferenceError` in the shared UI/CLI setup owner turns those codes into actionable guidance for the configured origin: nothing listening, name not found, or host unreachable. The existing "No default model was changed." is kept.

There are no config, protocol, or SDK changes.

## User Impact

A wrong or stopped endpoint now fails in under a second, with a message that says what is wrong and what to do. For example: **"Nothing is listening at http://127.0.0.1:38827. Start the server or check the URL, then retry setup."**

## Evidence

- **Regression tests:** `attempt-recovery.test.ts` checks that the code is carried through and connection retry is disabled only when requested. `setup-inference-turn.test.ts` checks that setup fails fast with guidance. Both fail on the old code. 167 focused tests pass.
- **Real isolated Gateway plus Chromium on a Blacksmith Testbox,** median of 5 fresh runs each:

| Case | Before | After |
| --- | ---: | ---: |
| Closed port (ECONNREFUSED) | 79.8 s | 0.72 s |
| Unknown host (NXDOMAIN) | 69.4 s | 0.85 s |
| HTTP 401 (control, unchanged path) | 1.00 s | 0.86 s |
| CLI onboarding, closed port | 66.7 s | 1.31 s |

- **Before, details text:** `The setup response check timed out. Retry setup, or choose another model or runtime. No default model was changed.` Its diagnostics show `transportCode: ECONNREFUSED`.
- **After, details text:** `Nothing is listening at http://127.0.0.1:38827. Start the server or check the URL, then retry setup. No default model was changed.`
- **Happy path:** successful activation, a real chat, and a reload are unaffected.
- **Checks:** all 26 core type graphs and `node scripts/check-changed.mjs` pass. Codex autoreview is scoped-clean.
```
