## Fix message body

```text
fix(cron): stop pending cron reads promptly on Ctrl+C

Pressing Ctrl+C or sending SIGTERM during openclaw cron status, get, runs or a scratch read did not reach the Gateway request, so the CLI kept the socket open until its cleanup force-killed it about 2 seconds later. These reads now go through one helper that passes the command's existing abort signal to the Gateway call, and the existing cron error handler already drops the resulting abort, so nothing prints afterwards. The scratch read before a set or unset is cancellable too, so Ctrl+C there stops before the write is sent. Mutations still wait for their receipt. This completes the cron read commands after #187726. No new text.

Evidence: the built CLI in a real PTY with --json against a real built Gateway behind a WebSocket proxy holding the read replies, two runs each plus the exact head. On main every interrupted read kept the request open and was SIGKILLed about 2.1 s after Ctrl+C or SIGTERM; with this change the CLI exits 130 within 0.03-0.16 s with empty stdout, and SIGTERM exits 143. Uninterrupted reads return the same JSON on both, and an interrupted cron add whose receipt arrives still prints its confirmation on both. Net 0 test lines. Details: https://github.com/openclaw/openclaw/pull/197315#issuecomment-6804766828 and https://github.com/openclaw/openclaw/pull/197315#issuecomment-6805203208.

Thanks @Alix-007.

Co-authored-by: Ayaan Zaidi <hi@obviy.us>
```
