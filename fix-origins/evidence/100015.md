## Fix PR #165487 description (by steipete, opened 2026-10-05T09:38:16Z)

```text
## What Problem This Solves

Fixes: interrupting one Codex-runtime chat (Stop + send, or `queueMode: "interrupt"`) makes the follow-up turn wait until every other active Codex chat on the same app-server finishes — 84 s, and once 215 s, in live runs — because cleanup retires the shared app-server process after a perfectly normal interrupt.

## User Impact

User impact: after an interrupt, the replacement turn starts right away (0.7 s live) even while other Codex chats keep working, and those other chats are no longer pushed onto a retired process. Genuinely failed cleanup still retires the client as before.

## Why This Change Was Made

Interrupted turns intentionally leave `settledTurnStatus` unset, so attempt cleanup releases their thread subscription. That unsubscribe ran under the attempt's foreground `connection.withCurrent`, whose authority is already cancelled by the interrupt, so the unsubscribe reported "not released" and cleanup treated it as an unsafe subscription: it closed and retired the shared client. The next turn on that thread then waited for the retired process to exit, which cannot happen while sibling chats hold leases. Unsubscribe now runs under the attempt's existing cleanup authority (`cleanupAuthority.withCurrent`), which keeps the host/session lineage checks and still retires the client when an unsubscribe genuinely fails. Writer barrier and ring-zero/client-bound rules are unchanged.

## Evidence

Live, dev Gateway (OpenAI provider, `@openai/codex` 0.160.0 managed app-server): Codex session Y runs a 90 s `sleep`; Codex session X is interrupted mid-turn.

| Build | Old run stopped | Replacement turn started | Sibling Y |
| --- | --- | --- | --- |
| main | 0.13 s | 84.1 s (released ~0.5 s after Y finished) | blocks X |
| this branch | 0.13 s | **0.68 s** | still running, unaffected |
