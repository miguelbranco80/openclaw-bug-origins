## Fix PR #182436 description (by roboclaw-bot, opened 2026-10-24T08:34:16Z)

```text
## What Problem This Solves

Fixes: messages queued in the web chat repeatedly fail during a Gateway suspension and do not promptly resume when the same connection becomes ready.

## User Impact

User impact: mobile and desktop chat keep messages queued quietly during a known suspension and send them once the Gateway accepts work again. Existing idempotency, delivery receipts, and uncertain-send protections remain intact.

## Why This Change Was Made

A connected WebSocket does not mean the Gateway is accepting work. Keep transport ownership separate from admission readiness, pause new outbox work during suspension/restart, and wake recovery when admission returns. A safe suspension refusal that races the announcement stays queued without a misleading delivery-error banner; ordinary transient-error pacing is unchanged.

## Evidence

- Reproduced in the actual rendered mobile (393×852) and desktop (1280×900) Control UI: before the fix, an announced suspension caused three rejected `chat.send` requests within two seconds. After the fix, there are zero sends while suspended and exactly one submission after same-socket readiness, with no duplicate after reconnect. Gateway transport is mocked in this deterministic browser regression.
- Focused queue/send/composer tests: 169 passed. Both standard and Steer inputs retain their idempotency identity while parked; a raced suspension refusal recovers without a false error.
- Production build, UI typecheck, touched-file lint/format, and diff check passed. Independent P0–P2 review found no actionable defects in the patch.
- Isolated real Gateway + agent + mobile browser: suspension → quiet local queue → same-socket delivery, then process stop → offline queue → new-process delivery passed. Two inputs produced exactly two sends, two inference requests, and one history entry per input. Inference uses a local synthetic Responses provider; no live hosting Gateway was restarted.
```
