## Fix PR #195171 description (by obviyus, opened 2026-11-08T10:37:30Z)

```text
Fixes #143390
Related: #143391 (earlier fix by @ruel225, closed unmerged), #142820, #117956, #195172

## What Problem This Solves

Fixes: `/compact` on a Claude CLI session can be billed to the stored Anthropic API key instead of the Claude CLI login.

## User Impact

Manual compaction of a CLI-backed session runs on the same account as that session's reply turns. A subscription-only Claude CLI session never spends a stored, auto-selected `anthropic:default` API key when the user runs `/compact`. An explicitly selected compatible account is still used. If an explicitly selected account no longer exists, compaction refuses. It never substitutes another account, and the message tells the user how to restore the sign-in or pick another account, then retry `/compact`.

## Why This Change Was Made

`compactNativeCliSession` forwarded the raw session auth pin to the CLI child. The reply path, the command path and the system inference route all convert that pin through the CLI account selector (`resolveCliExecutionAuthProfileId`). Native compaction was the one entry point that skipped it. This change runs the pin through the same selector, including the session binding:
- a binding pin still wins;
- an automatic model-provider pin is dropped, so the child keeps its own login;
- no competing stored CLI account is introduced into a resumed native session.

This rebuilds @ruel225's #143391 on current `main`. The selector has since gained session-binding handling that covers that PR's extra `discoverFallbackAccount` opt-out, so no resolver change is needed.

## Evidence

**Real-runner proof.** A built Gateway (isolated state) runs the real CLI runner and the real `claude-cli` backend, which spawns a stub `claude` on `PATH`. The stub records which credential it received: the kind and a SHA-256 prefix of the value, never the value. Compaction goes through the shipped `openclaw sessions compact <key>` path. Results:

| Scenario | `main` (`56b15bd`) | This PR |
|---|---|---|
| Native-login session; `anthropic:default` API key stored; competing `claude-cli:work` OAuth added before `/compact` | child: native login | child: native login |
| User-selected `anthropic/…@anthropic:default` | child: the selected API key | child: the selected API key (unchanged) |
| Session first ran on the embedded runtime with the API key, then switched to `claude-cli` | child: native login | child: native login |

No run passed `ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_AUTH_TOKEN` to the child through the environment.

**Honest gap.** In a fresh install on current `main`, I could not reach the bug's precondition (an automatic `anthropic:default` pin reaching native compaction) through the shipped flows above. This matches the review's note that saved-session normalization protects today's manual entry points. This PR therefore closes the boundary itself, for any caller or stored session that still carries an automatic model-provider pin. The dispatch-seam tests cover that case, and it fails on `main`.

**Out of scope:** if a credential is deleted out-of-band while the Gateway runs, both reply turns and compaction keep using the Gateway's cached copy. That is shared behavior, not changed here. The supported `openclaw models auth logout` refuses while the Gateway owns state. Recorded in #195172.

**Tests.** `compact.native-cli.test.ts` runs the real CLI account selector against a fixture auth store:
- automatic API-key pin with a native-login binding and a competing CLI account → nothing forwarded;
- automatic API-key pin with no binding → nothing forwarded;
- explicit selection → forwarded;
- missing explicit selection → refused with recovery guidance, and the child never runs.

Three of these fail on `main`. `compact.hooks.test.ts` (88) and `cli-execution-auth.test.ts` (18) pass, and lint is clean. The `tsgo:core` failure in `src/test-utils/retention.ts` callers comes from `main` (#195158) and touches no file in this PR.

**Review.** The hosted ClawSweeper review found no P0–P2 defect. Its P3 (no recovery action on the refusal) is addressed in this head. A maintainer approved the security-sensitive change.
```
