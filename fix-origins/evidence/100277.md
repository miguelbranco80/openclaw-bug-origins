## Fix PR #166578 description (by VACInc, opened 2026-10-07T11:59:58Z)

```text
## What Problem This Solves

Fixes: `sessions_history` / `chat.history` with a `messageId` returns an empty page for messages from before the latest reset when the session is bound to a Claude CLI session.

## User Impact

Agents and clients can open history around older messages in Claude CLI-bound sessions again, matching sessions without a CLI binding. Current-window behavior (including rows deliberately hidden by the CLI merge, and missing anchors) is unchanged.

## Why This Change Was Made

### Summary

#### High Level TLDR

A session reset closes the previous interval, and the CLI history index only covers the latest reset window. When a Claude CLI binding exists, anchored reads go through the CLI index's around-id override; an anchor from a closed interval is not in the index, so the override reported `found: false` and the page came back empty. The normal canonical reader already reopens closed reset intervals for explicit anchors. This change sends anchors (and cursors) that belong to the canonical history source to that reader instead.

#### Root Cause

- Before: on a CLI-bound session, `messageId` anchored at a pre-reset message returned `messages: []`. The same anchor returned the expected page on the same session whenever no CLI binding existed (reset clears CLI bindings, so the failure appears only after the first CLI turn following a reset, which made it look intermittent).
- Evidence: the around-id override in `prepareCliSessionHistoryReader` (`src/gateway/cli-session-history.ts`) builds on index ordinals from the latest reset window only and has no fallback, so `chat-history-page-kernel` turns `found: false` into an empty page. The canonical SQLite reader explicitly reopens closed reset intervals for explicit anchors, but the CLI branch bypasses it.
- Contract: explicit anchors must resolve through the canonical reader when the anchor is not part of the CLI index window.

#### Change

- Anchors absent from the CLI index delegate to `readSessionMessagesAroundIdWithStatsAsync`; missing anchors still return empty from that reader.
- Rows on a canonical (reopened) page keep their canonical sequence, including rows retained across the reset via `firstKeptEntryId`, so cursors page correctly.
- Cursor-bound reads route by the cursor's source, so walking through a reopened interval's reset marker no longer reports a false `windowReset`.
- Anchors present in the current window but hidden by the CLI merge or display projection stay hidden.

#### Real behavior proof

- Environment: self-hosted Gateway, Linux, Claude CLI-bound Telegram topic session with resets. A read-only nightly retrieval canary anchors on an old assistant message in that session.
- Before: anchored reads of a message just before the latest reset returned `messages: []`, while a message just after the reset returned its page. The canary failure/pass pattern matched exactly whether a Claude CLI turn had occurred since the last reset.
- After (focused regression tests through the `chat.history` handler):
  - `reopens a pre-reset local anchor while a post-reset CLI import is bound`: fails on `main` with `expected [] to include 'old-answer'`, passes with the fix.
  - `keeps reopened-interval cursors on the closed interval across its reset marker`: fails before with `expected true to be undefined` (false `windowReset`), passes after; the bound walk equals the unbound walk.
  - `pages a reopened interval into a message retained across the reset`: fails before with `expected [] to deeply equal [ 'old-answer' ]`, passes after.
  - `keeps a current-window failure hidden when an imported answer recovers it`: guard, passes before and after.
  - Mutations removing each part of the fix make the corresponding test fail.

#### What was not tested

- The patched build was not deployed to the live Gateway; live proof is the pre-fix behavior plus the handler-level regression tests above.
- When walking older from a reopened interval's reset marker, the final older page is empty both with and without a CLI binding. That is existing canonical-reader behavior and is left unchanged here.
```
