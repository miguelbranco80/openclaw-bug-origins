## Fix message body

```text
* fix(update): keep later plugin changes instead of refusing cohort rollback

A plugin cohort rollback refused outright when a later writer had changed a
plugin migration obligation or install record after the update published it.
The refusal wrote nothing, so the later value survived either way, but the
cohort could never settle and `update repair` failed on every attempt.

Rollback now keeps those later values, restores everything that still matches
the update's publication, completes, and records what it kept as a warning on
the update run, which repair prints and Doctor and status reports show.

* fix(update): keep an installation's snapshots with its later record

Install records are keyed by installation owner while source snapshots are
keyed by plugin ID, so keeping a later `package-owner` record left `demo`'s
snapshot restoration queued and the index owner rejected it. Kept
installations now drop every snapshot they own.

Also prove that cohort rows stored by released updaters settle unchanged, and
describe the kept-change outcome in the npm plugin rollback docs.

* test(update): match best-effort rollback test-line allocation to added lines
```

## Fix PR #193632 description (by fuller-stack-dev, opened 2026-11-05T17:32:45Z)

Related: #193132

## What Problem This Solves

Fixes: `openclaw update repair` fails on every attempt when a plugin's data/settings obligation or install record changed after an update published it.

## User Impact

User impact: repair now finishes the plugin rollback instead of refusing forever. It keeps the newer change, restores everything else, and reports what it kept as a warning. The warning shows in repair output, in `openclaw doctor` under update history, and in the update report.

## Why This Change Was Made

When rollback found a plugin migration obligation or install record that matched neither the update's original value nor what the update wrote, it threw. That throw happened before anything was written, so the newer value survived either way. The only effect was that the cohort could never settle. Repair, Doctor and triage then kept pointing at each other, and the cohort pinned capture and rollback artifacts indefinitely.

Rollback now keeps that newer value, skips it, restores every item that still matches, and completes. `restorePluginCohortMigrationRowsInDatabase` returns the plugins it kept. `settleUpdatePluginCohort` collects those along with any install records it kept, and writes one `warning:plugin-cohort:later-changes-kept` step on the update run. Doctor and the run report already show completed warning steps. A kept install record also keeps its source snapshot, so the record and snapshot can't disagree.

One related refusal goes the same way. If the obligation table itself is gone, because the database was restored from a backup older than it, rollback no longer refuses. It now leaves that state alone instead of initializing the candidate schema, and reports the original obligations as kept.

The settlement result shape is unchanged, so the worker callers' strict result parsing still holds. Commit does not restore anything and is unaffected. The live updater rollback still rechecks the database before it restores the previous package. Repair's ordering doesn't need to change: once rollback can't refuse, repair no longer gets stuck settling the cohort before package recovery runs.

Three refusals are left for a follow-up: published artifacts that changed, config files edited after publication, and a source snapshot that changed while its install record did not. Corrupt publication chains still refuse, because that is a journal integrity failure rather than a later writer.
