## Fix PR #186085 description (by etzelm, opened 2026-10-27T15:31:20Z)

```text
Related: #185404, #153545, #166127, #159930

## What Problem This Solves

Long tool-heavy `claude-cli` turns on current Claude Code (seen on 2.1.296 and 2.1.310) fail with `CLI JSONL output exceeded 20000 lines`, because every streamed token frame is charged as a full ordinary record again. The same overcharge pushes long production turns past the 8 MiB budget (`exceeded 8388608 characters`); that part is estimated from session transcripts below, not reproduced.

## User Impact

Agents on the `claude-cli` backend can again finish long turns with many tool calls and streamed tool input on current Claude Code instead of stopping at the 20,000-line limit. Text, tool-input and nonempty thinking frames again cost their payload plus 32 characters of the 8 MiB budget instead of their full envelope; empty thinking progress frames and `signature_delta` frames stay fully charged, as before. The limits stay as they are, and no setting is added.

## Why This Change Was Made

#153545 charges a recognized partial-message frame (`stream_event` / `content_block_delta` with a text, thinking or tool-input delta) for its payload plus a fixed 32 characters, and keeps the 20,000-line limit for ordinary records only. It recognizes a frame only when every top-level key is known. Current Claude Code (seen on 2.1.296 and 2.1.310) attaches two extra fields to these frames: `api_message_id` on every `stream_event`, and the display setting `thinking_display` (`"updates"`) on thinking frames. No frame matches any more, so each 12 to 16 character delta is charged its full envelope of about 300 characters and counts as an ordinary line, which is the accounting #153545 replaced.

This change accepts the two fields as bounded frame metadata beside `uuid`, `session_id` and `parent_tool_use_id`: `api_message_id` as a string of at most 64 characters on any recognized delta (captured ids are 28), and `thinking_display` as a string of at most 32 characters on `thinking_delta` frames only, the only delta type that carries it in the captures below. Accepting it only there keeps the recognized shape to what Claude Code sends; any other placement keeps full accounting, like any other unrecognized frame. OpenClaw reads neither field: the parser takes message ids from `message_start` (`src/agents/cli-output-stream.ts:521`, `src/agents/cli-output-events.ts:449`), and no other tracked file mentions either name (search under Evidence).

Unknown keys, non-string or oversized metadata, `thinking_display` on other delta types, and empty deltas keep full accounting as before, and outer padding is still charged on top of a discounted frame. The per-line cap, the 20,000 ordinary-line limit, the 8 MiB budget and the per-frame charge are unchanged. As with the existing `uuid`, `session_id` and `parent_tool_use_id` fields, metadata values are not charged: the caps now allow up to 480 characters of values per recognized frame instead of 384, so a flood of maximal frames can pass more raw bytes through the parser than the budget counts while still stopping at 233,016 frames.

This PR repairs the accounting; #185404 proposes operator overrides for the same budgets. #166127 (tool-result payloads) and #159930 (Edit/Write file echoes) discount other record types and compose with this change.
