## What Problem This Solves

Fixes foreground Gateways exiting after an in-process restart refuses configuration and automatic triage declines, removing the operator's signal-based recovery path.

## User Impact

A declined triage keeps the process alive and prints the startup refusal, Doctor command, and applicable recovery step. Unmanaged runs also remain available for manual recovery after an admitted triage failure or failed startup retry. Recorded supervisors retain the nonzero-exit recovery path. Windows and external supervisors receive their own restart instructions.

## Why This Change Was Made

The restart recovery owner treated every outcome other than `completed` as terminal. It now distinguishes a declined handoff from a confirmed, admitted triage failure and uses the run loop's existing supervisor identity to decide whether exiting can recover the Gateway. Successful triage still gets one startup retry after confirmed cleanup. Startup cleanup and cancellation barriers remain intact, and the updater's return contract is preserved.

Recovery messages live with the existing startup-recovery owner; `run-loop.ts` shrinks by two lines. The exit contract is documented in `docs/cli/triage.md`. This changes restart recovery without changing configuration, storage schemas, dependencies, or updater backup/rollback behavior.

Refs #159539, #160173
