## Fix message body

```text
Root cause: `src/meeting-bot/realtime-browser-audio-transport.ts:127` (and its `stop` at `:75`, plus the node bridge's `invoke` at `src/meeting-bot/realtime-node-audio-transport.ts:38`) dispatches the recurring capture `pull`, the final `stop` and every chrome-node bridge command from the async context of the request that joined the meeting, so once `googlemeet.join` (or the agent tool turn) finishes, the Gateway refuses those calls and the live-voice bridge closes.

Fixes #173896
Refs #167246 (same mechanism on the Zoom tool path; see Evidence)

## What Problem This Solves

In a `bidi` meeting that uses managed browser audio capture (no `chrome.audioInputCommand`), the bot joins, says its greeting, and then goes deaf about 300 ms after the join call returns. The Gateway logs `Meeting browser audio capture failed: Gateway requester authority changed` (or `Browser requester is no longer active`), the realtime bridge closes, and participant speech never reaches the model. The chrome-node transport fails the same way with `Gateway client authority closed before dispatching node.invoke`.

## Why This Change Was Made

The transports are created inside the join request, and their recurring browser and node calls inherit that request's context. In-process dispatch resolves the ambient request (and operator tool) authority, which closes when the join responds.

Work that outlives a plugin call already has an owner on `main`: the plugin instance's background context (`api.lifecycle.runInBackgroundContext`, docs: plugins/sdk-runtime "instance-bound background context"). Meeting transcript capture moved onto it for the same failure in #178415. This PR puts audio capture pulls, capture cleanup and node bridge commands on the same owner:

- `captureCurrentPluginBackgroundRunner()` (in `plugin-instance-invocation.ts`) returns the active plugin call's background runner, or runs inline outside a plugin call. The transcript bridge, browser capture and node bridge now share it instead of inlining the lookup.
- The join-time capture `start` still runs under the joining request, so authority is checked once when the session starts, as `AGENTS.md` requires ("Check authority one time, when work starts... A started request may finish"). Leaving the meeting, plugin retirement and reload still stop the work through the plugin lifecycle. No new authority, custody contract, config or SDK surface.

The original fix is @valkyriweb's (#191059); the `/meet/<code>` URL support that was bundled with it is dropped here so it can land on its own. @jeremynorris diagnosed the same owner in #173896 and #173898.

## User Impact

Google Meet (and the other shared meeting plugins) keep hearing participants and speaking after the join command or agent tool call returns, on both local Chrome and chrome-node. Nothing changes for configured `chrome.audioInputCommand` or while the join is still running.

## Evidence
```
