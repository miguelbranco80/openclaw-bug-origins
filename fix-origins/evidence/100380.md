## What Problem This Solves

Fixes an issue where users mentioning an agent after restart recovery exhausted its attempts received no response explaining how to recover. Admission rejected the tombstoned session before reply generation; Buzz only logged the propagated exception.

Reported by @chachi-max (#146276).

## Why This Change Was Made

The shared reply dispatcher sends a recovery reminder through the normal channel reply path while preserving the original admission rejection. A bounded, process-local cache suppresses repeated attempts for the same session and recovery cycle; reset, deletion, or Gateway restart clears suppression. Every visible admission rejection logs the session key, tombstone reason, and recovery hint at warn level.

The notice also works in message-tool reply mode. Explicit send-policy denial, private ACP delivery, and non-user events retain their existing restrictions. Model-locked sessions point to WebChat's **Resume in new session** instead of an unavailable reset.

There are no new configuration options, schema changes, or durable recovery records. Automatic replacement remains an open persistence-design decision. No CLI cleanup behavior or command family changes.

## User Impact

A session tombstoned by restart recovery now tells the room once how to recover instead of silently dropping messages. An authorized `/reset` or `/new` starts a fresh context while preserving the existing transcript; later ordinary inbound can be admitted again.

Suppression retains at most 1,024 session entries. An evicted entry or a new Gateway lifetime can produce another reminder. Notification delivery failures preserve the original rejection; the warning log remains available.
