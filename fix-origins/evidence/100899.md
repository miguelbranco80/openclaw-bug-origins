## What Problem This Solves

Fixes an issue where updating an older npm or Git installation could leave the new Gateway unable to start on legacy config. A February Git updater could write its original config after candidate Doctor returned, restoring retired metadata, the old agent roster, and plugin install records.

## Why This Change Was Made

Doctor now applies the existing historical-parent write boundary to early automatic writes and passive plugin-record imports. After that parent finishes, startup admits recognized legacy fields without writing state, validates plugin settings against the prospective merged inventory, and uses the existing import owner before the guarded canonical config write. Existing persisted install records keep precedence, and restored legacy records trigger migration even after a same-build checkpoint.

The final write revalidates canonical records under the plugin lifecycle lease and checks the import receipt under the config lock. Original backups, environment references, includes, malformed records, invalid plugin settings, externally managed config, future config, and source-change guards retain their contracts. No store, schema, config option, or obsolete runtime sidecar is added.

CI also exposed an unrelated main regression from #146275: the TLS renewal caller still passed an array after the lifetime owner changed to variadic handles. A separate one-line repair was verified and carried during integration. The identical correction landed independently in #146412 before this PR merged, so the final Doctor squash excludes that TLS file.

## User Impact

Older updaters can complete their final config write and hand off to a Gateway that performs the supported migration automatically, preserving agent workspaces, plugin settings, provenance, and backups. Ordinary Doctor also completes fully validated deterministic migrations while leaving consent-dependent repairs in their existing flow.
