## Fix message body

```text
* fix(memory): record operator-created dashboard roots as direct chats

Sessions created without a message and later run by sessions_send, cron, or the agent method had no durable chat type, so the host minted no memory audience. Each turn still decides owner status.

* fix(memory): let owner-private audience follow an owner spawn into another agent

A child spawned into another configured agent was denied any memory audience. Lineage now reads each hop from its own agent's session store and, when an owner-attributed spawn crosses agents from the owner's direct chat, grants owner-private audience for the child's own agent. Conversation audiences never cross agents; parent resets still revoke the child.

* fix(memory): log every memory audience denial at info with its session

Ineligible denials were debug-only, so memory tools failed with no visible reason.

* fix(memory): bound operator memory reads by role agents and owner status

Operator memory reads release an agent's private memory. The memory provider RPC now rejects agents outside the caller's operator role and, on a Gateway shared by several people, requires operator.admin for content reads. Plugin session actions receive the role's agents and a sharedGateway fact so feature plugins can apply the same rule.

* fix(memory): recheck operator memory policy before every provider effect

The role and shared-Gateway checks ran only before provider open. They now ride the live authority guard the provider calls before each effect, so a roster or role change during open refuses a read the policy forbids.

* test(plugins): supply the shared-Gateway fact to the session-action contract harness

plugins.sessionAction now passes sharedGateway from the resident profile catalog, which the Gateway installs before admitting requests. The contract harness supplies that fact and asserts handlers receive it.

* fix(plugins): give session actions live owner-policy checks instead of snapshots

Session actions received the caller's role agents and the shared-Gateway fact as values captured at dispatch, so a role or roster change during an awaited action went unseen. Handlers now get allowsAgent() and isSharedGateway(), which re-read current role config and the profile roster on every call, so they can check right before each effect.
```

## Fix PR #181359 description (by jalehman, opened 2026-10-23T05:14:25Z)

```text
## What Problem This Solves

Fixes: memory tools such as Knowledge fail with "no host memory authority" for legitimate owner work. This happens when a session is created without a message and then started by `sessions_send` or cron, or when an owner spawns a subagent into another configured agent. The real reason was logged only at debug level.

## User Impact

User impact: owner-started work in dashboard sessions and in cross-agent subagents can read and write the agent's memory. A Gateway shared by several people no longer lets non-admin operators read an agent's private memory through the memory provider RPC, or read another agent's memory outside their role.

## Why This Change Was Made

The memory audience gate denied these cases for incidental reasons, not because they crossed an owner or audience boundary:

- Operator-created dashboard roots record a `direct` chat type when they are created. Before, that chat type was stamped only when chat.send ran the first turn. Each turn's owner status still selects owner-private or conversation memory.
- Lineage resolution reads each hop from its own agent's session store. An owner-attributed spawn that crosses agents from the owner's direct chat grants the child owner-private audience for its own agent. Conversation audiences never cross agents, and a parent reset still revokes the child. Session creation already enforces `subagents.allowAgents` and the requester's operator role for the target agent.
- Every audience denial is logged at info (stale lineage stays at warn) with the session key.
- Operator memory reads are bounded by the caller's role agents. On a shared Gateway, content reads require `operator.admin`, which is the same owner status that gives turns the owner-private audience. Plugin session actions receive two live checks, `client.allowsAgent(agentId)` and `client.isSharedGateway()`. They re-read current role config and the profile roster on every call, so a feature plugin like Knowledge can apply the same rule right before each effect rather than trusting dispatch-time values. These are additive optional fields.

Operator memory reads recheck the role and shared-Gateway policy inside the live authority guard that the provider calls before every effect, not only at admission.

Upgrade and data compatibility: there is no schema or config change. `chatType` is an existing optional session field. New operator roots record `direct` at creation. Existing roots without it are left unchanged and denied exactly as on `main`, until their next chat.send turn stamps `direct` (existing behavior). Existing spawned children keep their receipts. A cross-agent child spawned before this change keeps being denied unless its receipt carries the owner bit, which every receipt has recorded since memory lineage receipts shipped.

Accepted edge: a role change after spawn does not retroactively revoke a cross-agent child's grant; it is checked when the child is created.
```
