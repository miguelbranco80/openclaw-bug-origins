## What Problem This Solves

Fixes an issue where users running `openclaw update` exhaust a small temporary filesystem while validating an installation with large active plugin payloads. The snapshot admission counted SQLite families but omitted the plugin dependency owners that the copy worker materialized.

## Why This Change Was Made

Inventory and copying now share one file plan, including active plugin payloads and dependencies. Admission selects a usable explicit `TMPDIR`, then the existing private `<state-dir>.update-captures/` sibling, then system temporary storage, using the measured SQLite/plugin sizes and scratch budget. A typed pre-copy refusal reports the required bytes, checked destinations, available bytes, and remedy. Chosen locations and sizes survive the existing update report and wire projection.

Active payloads remain available to candidate config/startup validation. The snapshot is disposable rehearsal state; rollback continues to use its existing recovery owner. Copying uses only admitted files and bounded writes, and refuses changed owners or enlarged admitted files.

## User Impact

Updates can validate large plugin installations on machines with small `/tmp` filesystems. Operators can select a sufficiently large filesystem with `TMPDIR`, and insufficient capacity produces an actionable report before payload copying.

Release-note context: the installed 2026.9.3/2026.9.4 updater owns the first snapshot, before candidate code runs. For that first hop, use `TMPDIR=/var/tmp openclaw update --yes` on a filesystem with enough space; subsequent updates use the new allocator.

The failure/repair regression protects the existing nonzero exit when the requested update was not applied. Successful updates with warnings remain successful. No production exit-code change is claimed: current source and the tested published-driver cases already exit 1. The reporter's exit-0 observation remains an investigation gap.
