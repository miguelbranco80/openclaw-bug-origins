## Fix PR #201755 description (by freeqaz, opened 2026-11-19T09:29:12Z)

```text
## What Problem This Solves

After a Gateway restart, a dedicated workspace node reconnects a few seconds after the Gateway is back. Restart recovery enqueues the interrupted session's restart input right away. If that input reaches the workspace node path before the node is back, the workspace read fails with `WorkspaceAccessUnavailableError` whose cause is the Gateway's `node.invoke` answer `UNAVAILABLE` / `NOT_CONNECTED` with `nodeCommandDispatched: false`. Nothing was dispatched, but `enqueueSessionEventAttempt` settles the occurrence as a terminal failure (the only re-admission today is the config-change one, `retainForConfigChange`), so recovery records a restart failure and the user has to send a new message.

## User Impact

A user whose Agent was in the middle of a turn when the Gateway restarted gets that turn resumed once the workspace node is back (usually a few seconds), instead of a restart failure notice and having to send a new message. If the node does not come back within 60 seconds, the outcome is the same failure as today, about a minute later.

## Why This Change Was Made

`src/auto-reply/reply/session-event-terminal.ts` (next to the existing re-admission owner) now decides re-admission for both reasons, and `session-event-handoff.ts` asks it once per settlement:

- A restart-sourced occurrence is re-admitted every 1 s, within one 60 s window that opens at its first attempt, when all of these hold:
  - the failure is a workspace-access error whose cause chain carries `nodeError.code === "NOT_CONNECTED"` and `nodeCommandDispatched === false` (the same pre-dispatch proof the exec node-host classifier already treats as retry-safe; missing provenance stays ambiguous and terminal);
  - the occurrence was never accepted, adopted or started, committed no conversation result, and attempted no delivery;
  - it was not cancelled or abandoned, and its staged input was cancelled durably (a failed cleanup is never retried).
- Dispatched or ambiguous failures, other errors, and anything past the window settle terminally as before.
- Config re-admission keeps its own attempt counter, so reconnect retries do not use up its two-attempt budget, and its conditions and backoff are unchanged. The per-occurrence state (overall attempt, config attempt, reconnect deadline) is one small `SessionEventReadmission` value; `enqueueSessionEventForHost` takes it as an optional third argument that producers never pass, replacing the private `enqueueSessionEventAttempt` wrapper.
- The retry reuses the existing re-admission path (`readmitSessionEventOccurrence`): the same occurrence, the original target and source assertions, and fresh native preparation on each attempt. The wait is abortable.

`session-event-context.ts`: comment only. Any live admission retry, not only a policy retry, may reclaim its own cancelled staged input.

No new setting, no protocol or stored-data change.
```

Message (truncated):

```text
## Problem

An accepted (acknowledged) queued chat message could disappear without a trace:

- It could be cancelled with no stored reason. History showed nothing, and retrying the same message ID could return a cached success although the message never ran.
- A Gateway crash (SIGKILL) lost it. Recovery depended on a graceful-shutdown marker, so a crash before the acknowledgment, or between claiming the message and the turn taking it over, left neither a queued row nor a running turn. On restart nothing answered and nothing explained why.

This changes #185730's accepted SIGKILL loss for acknowledged queued input.

## Fix

**Recorded end causes**
- Store a closed `end_cause` (`user-stop`, `delete`, `reset`, `revoked`, `restart-unrecoverable`, `overflow`, `policy-refused`, `failed`) through the existing pending-input owner. One settlement owner classifies causes (an explicit Stop, delete, reset or revocation wins over a temporary outage), releases consumed custody and records terminal endings.
- Temporary authority or dispatch outages: before the input is accepted (no acknowledgment sent; the caller gets the error), the row ends `failed`, as main cancels it today. After acceptance, the row stays queued and the failed attempt gives up its live ownership, so the existing owner (follow-up drain, mailbox, or startup replay) runs it once.
- Read durable cancellation before cached success/abort responses; a queued retry reports in flight.
- Chat shows one translated sentence per cause (for example "The Gateway restarted before this message ran. Send it again."). A message the user stopped shows no notice, as before (#186073).
- Channel redelivery under a fresh run ID still reclaims an attempt that ended `failed`, `restart-unrecoverable`, or with no recorded cause (#193602). Explicit caller retries may reopen a cancelled row unless a final completion receipt exists or the user stopped it. One function (`isRetryableSessionPendingInputEndCause`) defines retryable endings for redelivery and Doctor repair; when Doctor merges two copies of one input, a deliberate ending in either copy wins.

**Crash recovery**
- Store the already captured, authenticated sender source on the pending row (`origin_source_json`). Startup replays queued, unconsumed rows in FIFO order after running-root resume admission and revalidates current authority when work starts. A missing source ends as `restart-unrecoverable`. The column is cleared when custody ends. It is not the retired, untrusted `recovery_intent_json` envelope; historical v24 interruption is unchanged.
- The transaction that appends the user message and consumes the pending row also writes the turn's existing lifecycle start fields, so restart recovery always finds the input as either a queued row or a running turn. No new table, scheduler or reconstruction machinery.
- If replay defers because authority or dispatch is temporarily unavailable, the session keeps its older rows ahead of new input: the shared admission point (`waitForAgentInputAdmission`) runs that session's deferred replay once before admitting fresh input, and refuses fresh input with the same retryable error while it still defers. Other sessions are unaffected. No timer or retry loop.
- Legacy `queuedInputSources` move from shutdown markers to their pending rows through the startup/Doctor rewrite owner. #200394's `resumeAfterRestart.operatorSource` (the interrupted root requester) is kept; a crash writes no marker, so source-less root recovery keeps the existing session-principal policy.

## Agent schema 43 (one bump)

The agent database schema advances from 42 to 43 on SQLite and PostgreSQL through the existing versioned migration owners. It adds nullable `end_cause` and `origin_source_json` to `session_pending_inputs` and, in the same transaction, sets `end_cause = 'user-stop'` for older cancelled rows whose message carries `__openclaw.pendingInputCancelledByUser: true` or `display: false` (message bytes unchanged; dismissed rows stay hidden). Runtime readers use only `end_cause`.

Every pre-43 historical schema, including the schema-14 preflight, is derived without the two columns; PostgreSQL v42 predecessor DDL is unchanged. Older builds refuse schema 43; rollback needs the pre-upgrade backup and the matching binary. No schema-version bypass.

Pre-migration backup: `session_pending_inputs` is the agent schema's only `AUTOINCREMENT` table, and the scoped migration snapshot does not cover `AUTOINCREMENT` tables (shared `sqlite_sequence`), so Doctor takes its existing full-database backup for 42 → 43 wherever that table exists. Upgrades from stable 2026.11.4 already take a full backup (schema 30 has no scoped entry). For stores already on 42 this is a one-time copy about the size of the agent database (3.0 GB on one measured long-lived store). The migration inserts no rows, and no backup code changes.

- A queued message survives a crash: it is answered once, or ends with a visible reason. Same-ID retries never start a second answer.
- Cancelled messages explain why, in plain words, instead of looking successful.
- During a startup access outage, new messages in an affected session get a "try again" error until its older messages have run; nothing runs out of order.
```
