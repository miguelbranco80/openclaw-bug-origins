## What Problem This Solves

Porting a store to PostgreSQL leaves copied data, and the later agent memory rebuild, without planner statistics until autovacuum catches up. PostgreSQL backup restore uses the same bulk-copy path and has the same gap.

## User Impact

Newly ported and restored stores have statistics before returning to their caller. Agent ports refresh them again after the memory manager finishes and closes. Statistics refresh failures produce warnings while preserving the verified data; autovacuum can finish the optimization later.

## Why This Change Was Made

The shared bulk-copy owner now runs namespace-scoped `ANALYZE` after canonical verification and commit, in a separate transaction. Catalog discovery includes the destination's derived tables, identifiers are quoted, and unrelated namespaces are untouched. A 10-second statement timeout and 1-second lock timeout bound the work. Port reports expose success/table counts or a warning, including the post-rebuild result. PostgreSQL backup restore automatically uses the same helper through the materializer.

The existing worker owns SQL and the post-port offline owner retains custody through the memory refresh. No configuration, CLI options, dependencies, schemas, data verification, or steady-state autovacuum policy change. Simplification review retained one statistics helper for all bulk-copy callers; no parallel restore implementation was introduced.

+import type { Client } from "pg";
+import { createSubsystemLogger } from "../../logging/subsystem.js";
+import { quoteSqliteIdentifier as quote } from "../sqlite-schema-sql.js";
+
+export type PostgresPlannerStatistics =
+  | { status: "analyzed"; tables: number }
+  | { status: "warning"; warning: string };
+
+/** Offline bulk-load maintenance; the caller owns the namespace and an idle client. */
+export async function refreshPostgresPlannerStatistics(
+  client: Client,
+  namespace: string,
+): Promise<PostgresPlannerStatistics> {
+  try {
+    // A separate transaction keeps an optimization failure from undoing verified data.
+    await client.query("BEGIN; SET LOCAL statement_timeout = '10s'; SET LOCAL lock_timeout = '1s'");
+    const { rows } = await client.query<{ relname: string }>(
+      `SELECT c.relname FROM pg_catalog.pg_class c
+       JOIN pg_catalog.pg_namespace n ON n.oid = c.relnamespace
+       WHERE n.nspname = $1 AND c.relkind IN ('r', 'p', 'm') ORDER BY c.relname`,
+      [namespace],
+    );
+    if (rows.length) {
+      await client.query(
+        `ANALYZE ${rows.map(({ relname }) => `${quote(namespace)}.${quote(relname)}`).join(", ")}`,
+      );
+    }
+    await client.query("COMMIT");
+    return { status: "analyzed", tables: rows.length };
+  } catch {
+    await client.query("ROLLBACK").catch(() => {});
+    // SQL errors can contain connection details or data. Only emit recovery guidance.
+    const warning =
+      "PostgreSQL ANALYZE did not complete; verified data is retained. Autovacuum can refresh planner statistics later.";
+    createSubsystemLogger("database").warn(warning);
+    return { status: "warning", warning };
+  }
