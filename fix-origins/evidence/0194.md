# Fix rank 194: fix: stop skills.update from replacing a SecretRef skill API key with plaintext (#200539)

- sha: `aa73da727c8e92d45c130d417bc6064c5a42b422`
- date: 2026-11-17T15:39:01+05:30
- author: Ayaan Zaidi
- parent: `aa73da727c8e92d45c130d417bc6064c5a42b422^`

## Fix message body

```text
Root cause: src/skills/config/mutations.ts:24 `updateSkillConfigEntry` wrote any non-empty `apiKey` from `skills.update` over `skills.entries.<key>.apiKey` without checking whether the authored value was a SecretRef or `${VAR}`, so a raw Gateway call turned an env reference into plaintext in openclaw.json.

Fixes #193149

## What Problem This Solves

#197319 stopped the Skills page from typing a key over a SecretRef, but the Gateway itself still accepted it. Any client calling `skills.update` with an `apiKey` silently replaced a skill's env SecretRef (or `${VAR}`) with the plaintext key, writing the secret into openclaw.json.

## User Impact

`skills.update` now refuses to replace a referenced skill API key with plaintext and returns the same error the Skills page shows (`API key not saved — skills.entries.<key>.apiKey is set by a SecretRef or environment variable. Change it in Settings Raw mode or openclaw.json.`). The stored reference stays as it was. Setting a plaintext key where none was referenced, clearing the key, and replacing a reference with another `${VAR}` work as before.

## Why This Change Was Made

`updateSkillConfigEntry` is the only writer behind `skills.update` (its only caller), so the check lives there once. It reads the authored value (`authoredConfig`, falling back to `sourceConfig`), because the mutation draft already has `${VAR}` substituted. `config.set` and `config.patch` do not go through this owner: they are the deliberate full-config edit path (Settings Raw mode) that the error message points users to, so they are unchanged.

## Evidence

Isolated Gateway (`dist-nodts` build, own state dir, config and port, fake env values only), stored `skills.entries.example-skill.apiKey = {"source":"env","provider":"default","id":"FAKE_EXAMPLE_KEY"}`, raw `openclaw gateway call skills.update`. Only the shape of the stored key is printed, never its value.

| Call | Base 0ffeebc9df | This PR |
|---|---|---|
| plaintext over env SecretRef | ok, stored key becomes plaintext | refused with the existing error, SecretRef unchanged |
| plaintext over `${VAR}` | ok, stored key becomes plaintext | refused with the existing error, `${VAR}` unchanged |
| plaintext over plaintext (control) | ok | ok |
| SecretRef replaced by another `${VAR}` (control) | ok | ok |
| clear the key with `""` (control) | ok, removed | ok, removed |
| plaintext once nothing is referenced (control) | ok | ok |

Full proof output: https://github.com/openclaw/openclaw/pull/200539#issuecomment-6944635063

Focused test: `src/gateway/server-methods/skills.update.normalizes-api-key.test.ts` 7/7 on this head; the two refusal cases fail on base (2 failed, 5 passed).

Merge danger: two-way door. A revert restores the old overwrite; nothing is migrated or rewritten. Blast radius: only `skills.update` callers that send `apiKey` for a skill whose key is a reference; the Control UI already refuses that case before calling, and Android only toggles `enabled`.

Thanks @tommyjoseph for the report and the exact reproduction.

Co-authored-by: Ayaan Zaidi <hi@obviy.us>
```
