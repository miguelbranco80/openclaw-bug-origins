```text
fix(cli): show why a command failed when the config cannot be read

When the config file could not be read, for example because an included file is missing, commands such as openclaw status printed only "The CLI command failed." and pointed to openclaw doctor, which failed the same way. For this case the CLI now prints the existing config-read reason from createConfigReadError and drops the Doctor hint. Other unexpected errors keep the generic line and the hint, and no wording is new.

Evidence: the built CLI on node:24.22.1 in Docker with a config containing an include of a missing file. On main, status and doctor --non-interactive printed only the generic failure line and the Doctor hint, exit 1. With this change both print "Reason: Config could not be read at .../openclaw.json: - <root>: Failed to read include file: ./missing.json (resolved: ...)" with no Doctor hint, exit 1. status --json gives the same JSON on both, an unrelated failure still prints the generic line and the hint on both, and a valid config behaves the same on both. Details: https://github.com/openclaw/openclaw/pull/196816#issuecomment-6777681195.

Closes #196815. Thanks @masatohoshino.

Co-authored-by: Ayaan Zaidi <hi@obviy.us>

## Fix PR #196816 description (by masatohoshino, opened 2026-11-10T19:08:46Z)

```text
Closes https://github.com/openclaw/openclaw/issues/196815

## What Problem This Solves

Fixes: when the config file cannot be read, commands such as `openclaw status` say only "The CLI command failed." and send the user to `openclaw doctor`, which fails the same way, instead of naming the file that could not be read.

## User Impact

User impact: a user with an unreadable config now sees why the command failed:

```text
[openclaw] The CLI command failed.
[openclaw] Reason: Config could not be read at /home/user/.openclaw/openclaw.json:
- <root>: Failed to read include file: missing.json (resolved: /home/user/.openclaw/missing.json)
```

The circular "run `openclaw doctor`" line is no longer printed for this failure, since Doctor cannot read the file either.

## Why This Change Was Made

Before a command runs, the CLI reads the config to choose the storage engine. When that read fails, the error is thrown without being printed, and the root failure output only showed a reason for invalid configs and a few named commands, so the read error was dropped. The root failure output now treats a config read failure the way it already treats state-database refusals: it prints the title and the redacted reason, without the Doctor line. https://github.com/openclaw/openclaw/pull/158671 separated read failures from invalid configs and removed Doctor advice for them on the paths it touched; this is the root path it did not reach.

Behavior to know:

- Only errors with code `CONFIG_READ_FAILED` change. Invalid configs, state-database refusals and every other failure keep their current output.
- The reason goes through the same redaction as other reasons; nested causes and stacks stay behind `OPENCLAW_DEBUG=1`.
- `--json` failure output is unchanged.
- `openclaw config validate`, setup and bare `openclaw` are not changed here; https://github.com/openclaw/openclaw/pull/166573 (open) owns their read-failure wording, and this change does not touch its files.

Docs: `docs/cli/index.md` gains one line under failure output.
