```text
A modify/delete merge conflict leaves index stages 1 and 3 with no stage 0.
When the user replaces that path with a directory, the snapshot inventory still
added it, and because HEAD holds no blob for it, update-index --add rejected the
directory outright and aborted idle cleanup:

  error: entry: is a directory - add files inside instead

Skip an indexed path that is a directory on disk and absent from HEAD. It can be
```

## Fix PR #151259 description (by steipete, opened 2026-09-18T00:00:17Z)

```text
## What Problem This Solves

Fixes: idle worktree cleanup aborts and the managed worktree is never collected when a merge conflict's path has been replaced by a directory.

## User Impact

User impact: a managed worktree left in a modify/delete conflict whose conflicted path was replaced by a directory is now snapshotted and garbage collected normally, instead of sticking around forever with a repeated `worktree snapshot failed; removal aborted` warning.

## Why This Change Was Made

A modify/delete conflict leaves index stages 1 and 3 for the path and no stage 0, and HEAD (the deleting side) holds no blob for it. The snapshot inventory added every parsed index entry, so the conflicted path entered the snapshot even though the user had replaced it with a directory.

The private snapshot index is seeded with `read-tree --reset HEAD`, so only HEAD paths exist there at stage 0. `update-index` resolves a directory argument at stage 0: found records the deletion, not found fails. The conflicted path therefore hit the hard error and aborted the whole removal:

```
worktree snapshot failed; removal aborted: git ... update-index --add --remove -z --stdin failed (exit code 128):
error: entry: is a directory - add files inside instead
fatal: Unable to process path entry
```

The inventory now skips an indexed path that is a directory on disk and absent from HEAD: it can be neither stored as a blob nor deleted by name. Nothing is lost, because the directory's untracked children already arrive through the `ls-files --others` walk, and nested-repository detection still sees them. HEAD-tracked paths keep their existing behavior. The extra `lstat` only runs for index entries absent from HEAD, so a clean checkout pays nothing.

This defect is pre-existing and independent of the recent bounded untracked-listing work; it reproduces identically on the commit before that change.
```

```text
listing, so the few paths where Git cannot confirm a plain file are

skips.
```
