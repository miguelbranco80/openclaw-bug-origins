## Fix PR #164951 description (by SunnyShu0925, opened 2026-10-04T14:27:16Z)

```text
## What Problem This Solves

Running `voicecall continue` while the system clock shifts (NTP correction, laptop sleep/resume, manual time change) could make the command overrun its configured poll budget or report a spurious timeout after only ~1s of real polling. The continue-result poll loop now measures its deadline on the monotonic clock so the budget is unaffected by wall-clock jumps.

- Problem: `pollContinueGateway` seeded the poll deadline with `Date.now()` (wall clock) — `deadlineMs = Date.now() + timeoutMs` — then read the remaining budget back with `Date.now()` and fed it to two `setTimeout`-based consumers (the gateway RPC timeout via `callVoiceCallGateway`, and the inter-poll `sleep`). A wall-clock jump between seed and consume makes `remainingMs` diverge: a forward jump sends it negative and breaks the loop early; a backward jump inflates it and lets the poll overrun the budget.
- Solution: Seed and read the deadline with `performance.now()` (monotonic). The seed, both reads, and both `setTimeout` consumers now share one clock domain that cannot be moved by NTP or sleep/resume.
- What changed: `extensions/voice-call/src/cli-gateway-call.ts` — three `Date.now()` calls in `pollContinueGateway` replaced with `performance.now()` (deadline seed, `remainingMs` read, `sleepMs` read). No new helper, branch, or configuration surface. Budget value, clamping, poll interval, `Math.min` bounding, and break/throw behavior are all unchanged.

## Why This Change Was Made

Mechanical clock-domain alignment: the deadline was already consumed by monotonic `setTimeout` timers, so seeding/reading it on the monotonic clock makes seed, read, and consume consistent. Matches the established pattern in merged sibling PRs (#159555, #155799, #162813, #162779).

- Best fix: the three replacements sit in `pollContinueGateway`, the canonical owner of this deadline. No caller repeats the seed/read, so no guard duplication is needed.
- Alternative rejected: injecting a `monotonicClock` abstraction. `pollContinueGateway` reads the clock directly and `performance.now()` is the language-level monotonic primitive — injection would add a test seam with no production benefit.
- Risk: `performance.now()` returns sub-millisecond floats; both consumers are bare `setTimeout` (the RPC path goes through `clampTimerTimeoutMs`, which floors; `sleep` truncates floats). Neither uses `AbortSignal.timeout` (which would reject floats), so no flooring is required. Consistent with the sibling PRs.

## User Impact

`voicecall continue` now respects the configured poll timeout budget even when the host clock jumps. Operators on laptops that sleep/resume, or hosts under NTP correction, no longer see premature "voicecall continue timed out waiting for gateway operation" errors or silent budget overruns on this path.
