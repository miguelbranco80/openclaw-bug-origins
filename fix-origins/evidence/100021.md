## Fix message body

```text
fix(gateway): keep the Gateway responsive while the tools catalog loads

Building the tools catalog resolved plugin tool registrations in one uninterrupted pass. On a cold Gateway, other requests on the same process, including health, waited until the whole catalog was finished. The catalog build now yields between plugin registrations, so other requests are answered while it is still loading. The catalog result is unchanged.

Evidence: independently built main and candidate, using real protocol-4 WebSocket requests to two cold Gateways per ref. On main, health was answered only after the catalog finished, with no registrations after it (twice). With this change, health was answered while the catalog was pending, with 8 and 9 registrations still to come. Every run returned all 12 optional tools, and core-only controls worked without plugin registration. Details: https://github.com/openclaw/openclaw/pull/188033#issuecomment-6523979099 and https://github.com/openclaw/openclaw/pull/188033#issuecomment-6524227876.

Thanks @ctbritt.

Co-authored-by: Ayaan Zaidi <hi@obviy.us>
```

## Fix PR #188033 description (by ctbritt, opened 2026-10-30T01:54:41Z)

```text
Closes #188031

## What Problem This Solves

Opening the plugin tool catalog can freeze unrelated Gateway activity while plugin discovery performs a synchronous registration chain.

Reported and originally fixed by @ctbritt; the contributor's commits and production repair are retained.

## User Impact

Other Gateway requests can progress between plugin registrations while `tools.catalog` loads. Optional and unresolved tool rows, requested-agent workspace, metadata ownership, name conflicts and sorting remain intact. Individual synchronous plugin callbacks still block for their own duration; this is not a general latency guarantee.

## Why This Change Was Made

The catalog reuses its Gateway generation's already-admitted load context and metadata with the existing asynchronous inspection owner instead of repeating synchronous preparation. It retains generation authority, projects rows within inspection lifetime, awaits resource release, then checks authority before publishing success. Standalone inspection retains settled owners so failed registration cannot trigger synchronous fallback reload.

No new cache, registry manager, timeout, service, dependency, permission or persisted schema is introduced. No authentication, SDK, product configuration, prompt or update paths change.

## Evidence

[Independent built-Gateway main/candidate WebSocket comparison and regression receipts](https://github.com/openclaw/openclaw/pull/188033#issuecomment-6523979099).

Independently installed and built pinned main `1891469e2bf5bf68f2de45c2683bfa59ad200448` and contributor candidate `da27dd52ad37718bad16f67aa8d6e09a7317f241` in secretless Docker with Node 24.22.1. The maintainer follow-up changes tests, documentation and isolated benchmark tooling only; production catalog/inspection bytes match the proven candidate.

A real authenticated protocol-4 WebSocket client requests `tools.catalog` from the compiled Gateway, then sends `health` after the first actual synthetic registration begins. Twelve local plugins each perform 80 ms of synchronous registration work, armed only after normal Gateway startup. Later registrations inspect a marker written only after the client receives health, so an initial yield or cleanup-only yield cannot satisfy the proof.
```
