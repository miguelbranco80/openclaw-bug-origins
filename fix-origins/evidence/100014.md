## Fix PR #185392 description (by steipete, opened 2026-10-27T03:35:37Z)

```text
## What Problem This Solves

Fixes: on externally supervised installations, `openclaw update cleanup` keeps every Doctor `.pre-startup-migration-*` rollback original protected as `awaiting-later-completed-update` forever. This happens because the supervisor's updates never reach update history.

## User Impact

Operators of externally supervised installs can retire superseded migration originals with `openclaw update cleanup` after a later update is accepted, as on every other install. `openclaw update status` and the Control UI also show those accepted updates. The UI shows the standard recently-finished update entry, dismissable, for 24 hours.

Update behavior: the candidate release must contain this change, because the supervisor runs the candidate's own `update finish`. Supervisors and the bundled Team deployer need no change. Nothing is deleted automatically; cleanup still needs `--yes` and its usual offline ownership.

## Why This Change Was Made

Cleanup releases these originals only after update history records a succeeded update that started after the migration completed. The documented release rule is unchanged. Externally supervised updates run the candidate's hidden `update migrate --backup-root` and then, after the supervisor accepts the release, `update finish`. That protocol already mints a run ID in its receipt, but it never wrote the update-run ledger. On a supervised production install we observed about two dozen finished native updates over two weeks and no succeeded history row. So the release condition could never become true.

Owner decision: `update finish` is the step the supervisor runs only after acceptance and after retiring its rollback journal. It now records that update through the canonical ledger owner, `createUpdateRun`, under the receipt's run ID. There is no second cleanup rule, no supervisor-side ledger writer, and no new protocol command. `update migrate` stamps `startedAtMs` in its receipt, and the recorded run starts there. So a later accepted update releases earlier originals, while the latest update's own originals stay protected. Captures follow the same rule ("the capture of the latest successful update").

Receipts written before this change have no start time. They stay readable, so `update finish` and `update restore` still work on backups already on disk, but they are not recorded: without a trustworthy start they cannot prove they began after an original was made.

Failure handling follows the existing backup-cleanup warning. The run is recorded after the backup is removed. A history write failure becomes a `warning` with "retry update finish", and a retry keeps one row because the run ID is idempotent.

Accepted gaps, named rather than coded around:
- Releases a supervisor swaps without the native protocol (same-schema deploys) are still not recorded. Originals are released by the next native update instead.
- A supervisor recovery path that accepts a migrated candidate but keeps its native backup without calling `update finish` is not recorded.
- Restores are not recorded. `update restore` replaces the databases with the pre-migration snapshot anyway.

Alternatives rejected: a cleanup rule that reads supervisor receipts would add a second release owner. Running the native protocol on every deploy would add a full database backup to same-schema updates.
```
