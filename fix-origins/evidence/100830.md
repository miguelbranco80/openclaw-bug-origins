## Fix PR #176201 description (by YangManBOBO, opened 2026-10-18T12:13:44Z)

```text
Closes #176200

## What Problem This Solves

Fixes: `openclaw approvals` commands silently drop a `--node <node>` target when `--gateway` is also passed, operating on the gateway approval policy instead — including security-relevant writes such as `allowlist add` and `set`.

## User Impact

User impact: passing both `--gateway` and `--node <node>` to an approvals command now fails immediately with `Pass only one of --gateway or --node.` instead of silently mutating the wrong policy target and exiting 0.

## Why This Change Was Made

`resolveTargetNodeId` in `src/cli/exec-approvals-cli.ts` returned `null` whenever `--gateway` was set, so the `--node` value was never resolved and `loadSnapshotTarget` routed the whole command to the gateway. The CLI already rejects conflicting target flags elsewhere (capability commands reject `--local --gateway` with the same "Pass only one of ..." wording), so this aligns approvals commands with the established convention.

## Evidence

**Real shipped-CLI behavior** (source checkout, isolated fixture state; `logging.consoleStyle=json`):

```
$ openclaw approvals get --gateway --node macbook
exit 1
stderr: {"level":"error","message":"Pass only one of --gateway or --node."}

$ openclaw approvals allowlist add /usr/bin/uname --gateway --node macbook
exit 1
stderr: {"level":"error","message":"Pass only one of --gateway or --node."}

$ openclaw approvals get --gateway        # control: single target
exit 1
stderr: {"level":"error","message":"gateway exec.approvals.get requires credentials before opening a websocket"}
```

The conflict commands exit non-zero with the rejection message before any policy access; the single-target control passes the conflict check and fails later at gateway auth, confirming the fix is scoped to the conflicting pair.
```
