## Fix PR #202602 description (by vyctorbrzezowski, opened 2026-11-20T16:57:13Z)

```text
## Problem

When a Claude CLI conversation cannot get a warm process because the host has no room for another one (16 busy live sessions, or less than 1 GiB free memory with only busy sessions to close), the live-session registry refused the turn as a `rate_limit` failure with a synthesized HTTP 429.

That one wrong fact had two visible effects:

- **Text.** For the session limit (no code), the chat reply and the WebUI failure card said `⚠️ The AI service needs a short break. Please try again in a few minutes.`: the provider was blamed for something the host did.
- **Retry policy.** CLI run settlement treats `rate_limit` as a provider fact, so both refusals put the conversation's saved Claude login into a rate-limit cooldown. A later message could then be refused for the cooldown (and a successful fallback could make the session prefer the fallback model) even after memory or a session slot was free again. The host-memory copy said "try again after active conversations finish", but the policy said "the provider is limiting you".

#192534 kept the `rate_limit` category on purpose and named it as a limit; this PR fixes it at the producer.

## Solution

- `cli-live-session-registry.ts`: both local refusals are now `FailoverError`s with reason `overloaded`, **no HTTP status**, and a code naming the cause: the existing `cli_live_session_host_memory` and a new `cli_live_session_limit` for the 16-session cap. `overloaded` keeps the original behavior that the turn can fail over to another model, and the existing policy never records it against a saved login (`resolveAuthProfileFailureReason`) and never makes a session prefer a fallback (sticky fallback is `rate_limit`-only). No provider request had been sent, so failing over does not replay work; this is unchanged from before.
- `failover/error.ts`: the two refusal codes keep their host-authored copy beside them (`CLI_LIVE_SESSION_REFUSAL_TEXT`, read by `renderFailoverCodeUserCopy`). New copy for the session limit: `⚠️ This host is already running as many sessions as it allows, so it could not start another one. Try again after active conversations finish.` The host-memory copy is unchanged.
- `agent-runner-failure-reply.ts`: for an `overloaded` failure, a host-authored failover code renders its own copy before generic "The AI service is temporarily overloaded" text (the cooldown code keeps its existing path), so the reply text and the policy describe the same cause.

A real provider 429 is unchanged: it stays `rate_limit`/429, cools the saved login down, and shows rate-limit copy.

## Impact

Gateways that use a warm CLI runtime (today Claude CLI). In the WebUI chat and in channel replies, a host refusal now explains the host and suggests waiting for active conversations; the saved login stays usable for the next message. One explanation reaches the reply and the run-failure card (the card's notice is the same reply text; the existing transcript projection already keeps the toast from repeating a failure shown by the card).

The macOS onboarding model test is not affected: its setup probe runs with an auth-binding callback, which never takes a warm live session.

No config, schema, protocol or stored-state change. `overloaded` is an existing failover reason; the codes are diagnostic strings on the existing error.
```

Message (truncated):

```text
## What Problem This Solves

Fixes: a Gateway using the Claude CLI runtime can push its host into memory exhaustion when several conversations start new Claude processes close together.

On an 8 GB Linux VM without swap, several Slack/Teams turns arrived within about 3 minutes. The Gateway went from 3 to 7 warm Claude CLI processes, available memory fell from ~3.8 GB to ~250 MB and stayed there, and the VM thrashed (no OOM kill, CPU ~5%) until a reboot about 2 hours later. The only limit on warm processes was a fixed count of 16; idle warm processes were kept even while the host ran out of memory.

## User Impact

User impact: when host memory is low, a new Claude CLI conversation first closes idle warm processes (least recently used first). If memory is still low and every warm process is busy, that turn fails over instead of starting another process, and a channel reply says: "⚠️ This host is low on memory, so it could not start another session. Try again after active conversations finish." (Before, any such failure would have shown the generic "AI service needs a short break" rate-limit copy.) Hosts with enough free memory behave as before; turns that reuse their own warm process are unaffected; busy turns are never closed.

## Why This Change Was Made

Before a turn starts a new warm process, the live-session registry reads host free memory through the existing `readHostFreeMemoryBytes()` helper (`os.freemem()`, which is `MemAvailable` on Linux; `process.availableMemory()` on macOS). It walks the warm processes once in least-recently-used order: while memory is below 1 GiB, it closes each idle process and waits for it to exit before the next reading. If memory is still below the floor after that pass, the turn fails over with the `rate_limit` category the 16-session cap already uses, plus a distinct `cli_live_session_host_memory` code. The existing failover-code copy (`renderFailoverCodeUserCopy`) owns its user text, and the rate-limit reply renderer now returns a host-authored code's copy before generic rate-limit text (auth-profile cooldown keeps its expiry-aware copy). The registry map is now kept in least-recently-used order, so both the memory path and the existing count cap close the conversation that has waited longest.

The 1 GiB floor comes from measurements of one warm session:

| Measurement | RSS |
| --- | --- |
| Claude Code 2.1.314, Linux arm64 container, stream-json, idle after start | ~180 MiB |
| Same, after one Haiku turn / three concurrent Sonnet turns | ~195–198 MiB each |
| Full warm session under a Gateway (macOS): Claude Code + two Node supervisor helpers | ~490 MiB (264 + 138 + 87) |

1 GiB leaves room for about two more warm sessions before the kernel has to reclaim. The 16-session cap stays as the upper bound. No config key is added.
```
