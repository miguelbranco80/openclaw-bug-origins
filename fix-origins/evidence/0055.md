## Fix message body

```text
fix(telegram): skip reply media that duplicates the current attachment

When a Telegram user replied to an image with that same image, the message pipeline downloaded both the current attachment and the replied-to copy, so the agent received the identical image twice. The pipeline now skips reply and external-reply media whose file_unique_id matches media already on the current message. Different images, replies to bot-sent photos and a failed current download keep their existing behavior.

Evidence: Telegram Test Server userbot with a built Gateway on node:24.22.1 in Docker and a stand-in vision model recording image hashes per provider request. Replying to photo A with the same A sent 2 identical images on main in both runs and 1 with this change; an external reply with the same A went from 2 to 1 with one fewer getFile. A reply with a different photo B kept B and A, a rejected current download still brought the replied copy, and replies to a bot-sent photo were unchanged on both. A 3-row table in bot.create-telegram-bot.native-pipeline.test.ts replaces the earlier e2e test at -17 net test lines. Details: https://github.com/openclaw/openclaw/pull/155273#issuecomment-6785042971.

Thanks @amittell.

Co-authored-by: Ayaan Zaidi <hi@obviy.us>
```

## What Problem This Solves

Fixes: the agent receives the same Telegram image twice when a user replies to an image with that same image, because the current message and the reply ancestor are staged at different local paths.

## User Impact

User impact: a same-source image in a reply reaches the agent once instead of twice. A successfully downloaded current attachment claims its Telegram `file_unique_id`, so a reply ancestor or external reply with that id is not downloaded again. Distinct images and attachments without an id are unchanged. If the current download fails it claims nothing, so the replied-to copy still arrives next to the `[media unavailable: ...]` notice. Replies to images the bot sent keep delivering that image, as on `main`.

## Why This Change Was Made

Telegram's `file_unique_id` is the stable source identity across file-id changes and local restaging. It is carried on the transient `TelegramMediaRef` from singleton ingress, album ingress, retained reply media and downloaded reply media, and checked at the current-media/reply-media join before a reply ancestor or an explicit external reply is hydrated. Since the merge in `1a7948f2ad71` that check lives in main's inline hydration path in `bot-handlers.message-pipeline.ts`.

Earlier heads also skipped reply media the bot had sent. That is gone: `main` hydrates it on purpose (`hydrates allowlisted group reply ancestors`), the bot's earlier image is context the user may be asking about, and ClawSweeper flagged the skip as P1. #57278 tracks the attribution proof and the reply-photo product decision; this PR does not close it.

No config, default, protocol, SQLite or persisted-schema change: `TelegramResolvedMedia.fileUniqueId` was already part of the persisted message-cache value, and the new optional field is on the transient ref. Six files, +390/-3.

## What Problem This Solves

Telegram mention-gated groups lose useful discussion outside the recent context window, and the agent cannot retrieve that older discussion from the existing message cache.

## User Impact

The agent receives a bounded recent window (existing `historyLimit`, default 50), then can use `message(action="read")` to retrieve earlier permitted discussion instead of receiving thousands of messages in its prompt. Unmentioned messages do not start agent turns. Explicit replies, existing transcripts, direct messages, and `requireMention: false` activation remain supported.

This reuses the existing SQLite table and primary-key index: no new table, column, index, database, schema-version bump, Doctor migration, or configuration key. Recorded group history survives restarts and remains readable after `/new` or `/reset`. `historyLimit: 0` disables automatic context, not explicit reads.

**Retention and downgrade tradeoff:** group records no longer expire by message count, so disk usage grows with observed traffic. Only messages delivered to and permitted by OpenClaw are available; this is not Telegram server-side backfill. Older binaries retain their old eviction/quota behavior and must not write to expanded retained history. Restore a compatible pre-update backup before downgrading; this change intentionally does not add a database-version fence.

## Why This Change Was Made

- Use one durable Telegram message owner for recent context, explicit reads, edits, and reply metadata; remove the separate in-memory group-history buffer.
- Add generic retained namespaces, indexed key-range paging, and atomic promotion to the existing plugin-scoped store. Telegram is the first consumer; other channels can adopt these primitives without Telegram-specific core policy.
- Keep reads scoped to the trusted current account, chat, and topic, with native message-ID cursors and permission/session/plugin authority rechecked after storage awaits. Embedded reply snapshots do not become authorized history merely because they are cached.
- Move eligible legacy group rows atomically before bounded writes can evict them; bounded stores and ordinary DM caching retain their existing limits.

Related prior work: #99143 and #121907. This implements the hybrid selected in #150575 rather than reopening the closed retrieval-only proposals #143665, #143892, or #147799.
