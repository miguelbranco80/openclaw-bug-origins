## Fix PR #165212 description (by steipete, opened 2026-10-05T00:26:00Z)

```text
## What Problem This Solves

Fixes: Code Mode tool calls and `computer` actions fail with idempotency conflicts when the model provider reuses the same tool call id (`exec_0`, `computer_0`) in every assistant response, as opencode/kimi-k3 on `openai-completions` does.

## User Impact

User impact: agents on providers that reuse tool call ids can run Code Mode and computer use across many steps without nested calls failing with `Transcript idempotency key ... conflicts with the admitted message` or `computer.act idempotency key reused with different parameters`, and no longer need to make throwaway calls to work around it.

## Why This Change Was Made

Provider tool call ids are only unique within one assistant response, but two keys assumed they were unique per run:

- Each Code Mode `exec` creates a fresh Tool Search runtime, so nested ids restarted at `tool_call:exec_0:<tool>:1` every step. The attempt-scoped nested-activity transcript key then collided with the previous step's admitted row.
- `computer.act`, `computer.observation` and `mobile.ui.act` keys hashed only the run id plus the call id, so a new action in a later step reused an earlier step's key.

Both now include the assistant step's existing durable identity: the provider `responseId`, or the runtime-assigned `turnId`. No new counters were added. Nested ids include the existing Code Mode replay digest (session, run, assistant turn, call id, code). The act and observation keys include the turn id read through a new `getAgentToolAssistantTurnId()` helper in agent-core; Code Mode already read the same value inline. The key composition changed, so the prefixes bump to `v2`. Replays of the same assistant message and call still produce identical ids and keys. Parent tool call ids are unchanged, so UI pairing still works.

The outer `exec_0` tool results are unaffected: they carry no idempotency key, and screenshot frame tracking already matches the latest result together with an image digest.

## Evidence

Live evidence came from the affected Gateway session, read-only. One attempt scope admitted `tool_call:exec_0:web_fetch:1`, `...:nodes:1`, `...:exec:1` and so on, once per step. Later steps then failed with conflicts on the same keys. The direct `computer_0` calls failed with `computer.act idempotency key reused with different parameters` once they targeted the same node.
```
