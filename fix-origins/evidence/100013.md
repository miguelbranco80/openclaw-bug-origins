## Fix PR #173419 description (by eleqtrizit, opened 2026-10-15T19:18:51Z)

```text
## Summary

Isolated cron turns select their model through the shared subagent selection chain, which deliberately prefers `agents.defaults.subagents.model` over the agent's own primary model. When that inherited default (or a fallback candidate, runtime override, or explicit payload model) is served by a CLI backend (such as `claude-cli` or `google-gemini-cli`), the cron dispatch ran a local AI CLI whose native tools execute on the gateway host as the gateway OS user — silently moving tool execution out of an agent's configured Docker sandbox while sandbox diagnostics still reported the session as sandboxed. This PR fails closed at the existing cron runtime-admission seam (`src/cron/isolated-agent/run-admission.ts`): a session whose sandbox classification claims containment now refuses host-executed CLI backends before process launch with precedence-correct recovery guidance.

## What Problem This Solves

When an agent is configured with `sandbox.mode: "all"` (or `non-main`, or a session carrying `sandbox: "required"`), isolated cron turns inherit `agents.defaults.subagents.model` ahead of the agent primary and could dispatch to a host-executed CLI backend (`claude-cli`, `google-gemini-cli`), running native tools on the Gateway host outside the configured Docker sandbox. This PR rejects host-executed CLI candidates at the cron runtime-admission seam before process launch.

## What this Problem Solves

1. **Silent host execution for sandboxed cron turns (`src/cron/isolated-agent/model-selection.ts`, `src/agents/agent-scope.ts`, `src/cron/isolated-agent/run-prompt-executor.ts`)** — An operator configures an agent with `agents.entries.<id>.sandbox.mode: "all"` (or `non-main`, or a session carrying `sandbox: "required"`) while `agents.defaults.subagents.model` (or a fallback / `agentRuntime` override) selects a CLI-backed model. `resolveSubagentModelConfigSelectionResult` in `src/agents/agent-scope.ts` prefers the global subagent default over the agent's own primary; `createCronPromptExecutor` in `src/cron/isolated-agent/run-prompt-executor.ts` then dispatched `runCliAgent` (`src/agents/cli-runner.ts` → `src/agents/cli-runner/execute-process.ts`) on the gateway host with no sandbox placement check.
2. **Net effect** — Native CLI tools ran on the gateway host outside the configured Docker sandbox while `openclaw sandbox explain` continued to report `runtime: sandboxed`; after this change, any CLI candidate for a sandboxed cron session fails closed before child-process spawn and instructs the operator to override `agents.entries.<id>.subagents.model`, `agents.defaults.subagents.model`, or the automation payload `model` (and clear any pinned CLI runtime override), or change the agent's sandbox policy explicitly.

## Why this design

- Fail closed at the existing runtime-admission seam (`src/cron/isolated-agent/run-admission.ts`), directly beside `assertCronRuntimeAuthorityCandidate` — the same seam OpenClaw already uses to keep authority-carrying automations off incompatible runtimes.
- Reuse `Parameters<typeof resolvePreparedSandboxRuntimeStatus>[0]` in `resolveCronSandboxPlacement` so `preparedSessionEntry` preserves the non-undefined contract (`SessionEntry | null`) under strict TypeScript (`pnpm tsgo:core`).
- Check every candidate inside `runCandidate` (`src/cron/isolated-agent/run-prompt-executor.ts`): initial selection, `runWithModelFallback` fallback candidates, and `models.<ref>.agentRuntime` CLI runtime overrides are all gated before `runCliAgent` can launch a child process. Because the thrown `AgentHarnessPreflightError` is unowned, `runWithModelFallback` treats it as terminal across the candidate chain.
- Recommend precedence-winning overrides (`agents.entries.<id>.subagents.model`, `agents.defaults.subagents.model`, or the automation payload `model`, plus clearing any pinned CLI runtime override) rather than changing the agent's primary model, which is outranked by `agents.defaults.subagents.model`.
- No new config surface, no default change, no model-selection precedence change, and no SQLite or session-store schema/writer change.

## SDK / caller upgrade contract

- **Permitted callers (unchanged):** Unsandboxed sessions (`sandbox.mode: "off"` without `sessionEntry.sandbox === "required"`, and `non-main` main-session turns) continue to run CLI backends (`claude-cli`, `google-gemini-cli`, `codex-cli`) through `runCliAgent`. Sandboxed sessions configured with API-backed models (or recovered via per-agent `agents.entries.<id>.subagents.model` or payload `model`) continue to dispatch through `runEmbeddedAgent`.
- **Fail-closed callers:** Sandboxed sessions (`sandbox.mode: "all"`, `non-main` non-main sessions, or `sessionEntry.sandbox === "required"`) that resolve a CLI execution provider via inherited `agents.defaults.subagents.model`, fallback candidates, `models.<ref>.agentRuntime` overrides, or payload `model` fail closed with `AgentHarnessPreflightError` before any CLI subprocess is spawned.
- **Stored-data compatibility:** This change touches no SQLite table, session-store writer, or migration step; pre-existing sessions from `v2026.10.3` (schema 24) migrate to schema 27 and preserve `sandbox: "required"` and `sandboxMode: "off"` fields verbatim.

## Boundary decisions requested from maintainers

1. **Fail-closed candidate rejection vs. silent model fallback:** Confirm that failing closed with `AgentHarnessPreflightError` (naming `agents.entries.<id>.subagents.model`, `agents.defaults.subagents.model`, and payload `model`) is preferred over silently altering the documented subagent model precedence order (`#58823`).
