## Fix PR #199034 description (by steipete, opened 2026-11-14T17:05:33Z)

```text
## What Problem This Solves

On Team r331 (16:58:32Z), one live `session.actor.appendTranscriptEvent` request to the roboclaw agent-database worker spent 4.9 s in **delivery**, the gap between the broker posting it and the worker receiving it, while the broker considered the worker's slot idle. A lifecycle replacement and four more live appends queued 1.6–4.2 s behind it, so messages arrived up to ~3.6 s late. The transaction itself was fast, with no slow-hold line.

Neither GC mechanism explains it:
- There was no `slow idle worker garbage collection` warning (#198857).
- The new worker GC counters (#198866) were flat over the window (mark-sweep 0.14 s in 2 min).

Request phases show *where* the time went but can't tell a busy worker event loop (non-job work on the thread) from an idle one that woke late.

## Why This Change Was Made

When request timing is enabled (on Team because the Prometheus exporter consumes it), the broker passes the worker's `performance` handle to `observation.started()`. The observation then snapshots the worker's event-loop utilization from the parent at dispatch; the parent can read a worker's utilization without its cooperation. For deliveries of 1 s or more, it logs one `slow SQLite worker delivery` warning (subsystem `worker/delivery`) with these fields:
- `deliveryMs` and `executeMs`
- `workerActiveMs` and `workerIdleMs`
- `workerActiveOutsideExecuteMs`

Busy time outside execute that roughly matches the delivery time means the worker loop held the request. Idle time that matches means the worker woke late. The logger loads through a runtime module only on that path, so small worker graphs keep their module budgets.

## User Impact

None at runtime. Slow worker deliveries say whether the worker was busy. The cost is one native utilization snapshot per timed request.

## Evidence

- New `worker-request-diagnostics.test.ts`: a 4,944 ms delivery reports busy time outside execute, and a 999 ms delivery reports nothing. The slow case fails on main.
- Verified locally that worker threads share the process `performance.timeOrigin`, so the delivery phase is a valid cross-thread difference, and that parent-side utilization attributes an 800 ms busy loop exactly.
- Broker, write-admission and diagnostics suites pass (3 files, 58 tests).
- On a fresh install, the dist build exits 0 with no `INEFFECTIVE_DYNAMIC_IMPORT`, and `check-worker-module-budget` keeps `agents/identity-file.worker.js` at 203 of 220 modules.
- `pnpm tsgo:core`, oxlint, oxfmt and the line-cap ratchet are clean, and Codex autoreview through P2 is scoped-clean.
```
