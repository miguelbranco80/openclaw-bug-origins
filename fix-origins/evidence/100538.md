```text
## What Problem This Solves

Fixes macOS `openclaw gateway restart` failing with “Process ancestry could not be fully inspected” from a terminal that native service membership already verifies is outside the Gateway job.

## User Impact

Verified external terminals can restart the Gateway even when an ancestor cannot be inspected. In-service callers retain detached handoff protection; unknown membership and absent containment retain their existing guards. No config or migration changes. Update/maintenance callers use the same corrected membership owner.

## Why This Change Was Made

The native probe returned `outside`, but its caller still required the ancestor walk to reach PID 1. This redundant requirement was introduced by commit 6209f31ce9bb on September 26 and first appears in release tag v2026.9.7; it is present in the v2026.10.2 tagged source as well as the reported 5b29c85 build. Accept verified outside containment while retaining ancestry checks when containment is absent.
```

fix(gateway): restart inside a marker-less LaunchAgent no longer kills its caller (#139628) (2026-09-05T19:31:19-07:00, Peter Steinberger, 8 files)

Message (truncated):

```text
PR #139393 removed the configured-label-only fallback from launchd in-service
detection so the detached update helper's recovery CLI stops being misdetected
as running inside the LaunchAgent. That left a hand-written plist that sets
OPENCLAW_LAUNCHD_LABEL but neither the service marker nor launchd's own label
variables undetected, so `openclaw gateway restart` from inside such a service
ran `launchctl kickstart -k` synchronously and killed its caller.

Add a process-ancestry fallback: isCurrentProcessInsideLaunchdService keeps
the env check as the fast path, then asks launchd for the job's PID and treats
the caller as in-service when that PID is in its ancestry. Restart, stop,
maintenance park, install, and uninstall use it. The recovery CLI inherits the
label but is reparented to launchd after the gateway exits, so it stays on the
synchronous path.

Related: #139393
```
