## Fix PR #151169 description (by shakkernerd, opened 2026-09-17T21:40:53Z)

```text
## What Problem This Solves

Pending Signal deliveries can continue after their originating caller is canceled or superseded. The shared delivery owner checks the caller before entering the adapter, but Signal can then await reply lookup, media preparation, socket setup, or a rejected native quote before starting its next request. Dropping the caller's check across those steps lets an obsolete delivery reach the daemon.

Fixes #151114.

## User Impact

Signal text, attachments, formatted message chunks, and reaction additions or removals honor the originating delivery's existing lifetime check at the request boundary. A caller that ends during preparation cannot start the next request, including an unquoted fallback after a definitive quote rejection.

A request already submitted is allowed to settle, and its accepted result is preserved. Earlier delivered chunks remain reported even when later chunks are blocked. Account selection, recipient policy, available actions, and Signal's native payload formats keep their existing behavior; this change adds no configuration or scheduled-action capability.

## Why This Change Was Made

Core already supplies `assertDirectAdapterHandoff` for task-progress sends, agent final delivery, and durable delivery custody. Signal now carries that same callback through its registered message and outbound adapters, quote fallback, and reaction helpers to the native HTTP, Unix RPC, and container REST request writers.

The transport performs the check after its own preparation. This matters for Unix socket opening and for the container's additional attachment read and base64 conversion, which happen below the shared send helper. The formatted send functions use the existing SDK parameter types, and container mutation helpers share their existing request-option type. This keeps the caller and timeout fields together instead of maintaining separate copies.
```
