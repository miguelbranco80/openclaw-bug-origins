## Fix PR #164896 description (by obviyus, opened 2026-10-04T11:50:02Z)

```text
## What Problem This Solves

Fixes: after a multi-step turn that ends by asking the user for approval, the answer is replaced (or followed) by a short restatement of the blocker when the run's progress card still has a pending step.

On our setup (Telegram forum topic, `openai/gpt-6-astra`) the topic showed the answer and then a second bubble: "The remaining step is getting the seller's confirmation and quote. That requires your permission to contact them; I haven't sent an enquiry or placed an order." On a Telegram Test Server DM with origin/main, the same shape delivers **only** the restatement. The answer with the actual results never arrives.

## User Impact

A reply that already explains why work stopped (approval, user input, an external dependency) stays the turn's only reply. A plan that the agent genuinely abandoned early still gets the completion check and the agent keeps working. No new messages, notices, or settings.

## Why This Change Was Made

Root cause, with provenance:
- #160297 (3ba0a0b2376) added one completion self-check before a run ends with an unfinished saved plan. Its rationale: "an agent can end its reply while its newly saved plan still lists unfinished, authorized work, leaving the session idle. … The built-in agent gets one chance to reconsider that stop: continue feasible work, reconcile the plan, or explain a concrete blocker. This can add one model response."
- The injected check (`attempt-stream-prepare.ts`, `openclaw.plan-completion-check`) tells the model: "If user input, approval, an external dependency, or an explicit pause prevents further work, **report that concrete limitation**." When the stop was legitimate and the reply already asked for approval, the model obeys and writes a fresh report.
- That fresh text becomes the run's final answer (the check continues the same run, and the payload owner uses the latest answer). Non-streamed delivery loses the original answer. When the original was already visible, the user gets a second bubble.
- The gate can't tell a legitimate stop from a premature one. Only the model can, so the decision stays with the model.

Fix: one bounded edit to the existing check text: "…report that concrete limitation; if your previous reply already reported it, end with only `NO_REPLY`." With #164774 (now on main), an answer followed by a `NO_REPLY` stop keeps the earlier answer as the reply. The check's follow-up is a custom message, not user input, so it doesn't reset that answer. Continuing, reconciling, and reporting a blocker that wasn't mentioned all work as before.

Not changed (decisions kept from #160297): the check's gates, its once-per-run budget, cancellation/steering/approval/child/media precedence, and "a checkpoint already shown in chat stays in the conversation".

Rejected alternative: skipping the check when an answer was already delivered or kept. Without deferred terminal delivery the stop answer is already visible on streaming channels, so that would turn the check off there. It also depends on the response's split shape, not on whether the work is done.
```
