## Fix message body

```text
fix(ui): refresh Tool access after a run discovers MCP tools

After a run discovered tools from an MCP server, opening Tool access in the chat composer still showed an empty list, because it reused the effective-tools result cached before the run. Opening Tool access now refreshes when the tools may have changed, without adding duplicate requests.

Evidence: built Gateway serving its own built Control UI, with a real stdio MCP server configured through shipped commands. On main Tool access stayed empty after the run (twice); with this change it shows both MCP tools (twice). A page reload shows them on both. Screenshots and evidence: https://github.com/openclaw/openclaw/pull/168668#issuecomment-6347566305. Production +4/-3.

Thanks @ericcurtin.

Co-authored-by: Ayaan Zaidi <hi@obviy.us>
```

## Fix PR #168668 description (by ericcurtin, opened 2026-10-10T22:05:28Z)

```text
Closes #168627

## What Problem This Solves

Tool access can remain empty after an agent run discovers MCP tools. Reopening the menu reuses a pre-run effective-tools result because discovery does not change its cache key.

## User Impact

Opening Tool access now refreshes its inventory, so newly discovered MCP tools appear without reloading or reconnecting. Concurrent opens still share an in-flight request; ordinary rendering keeps its cached result.

## Why This Change Was Made

Keep the existing cache and request owner, but let explicit opens request fresh inventory. No new permission policy, config, or SDK surface.

## Evidence

Built the Gateway and Control UI together in isolated Docker. Configured an actual stdio MCP server through shipped config commands, opened Tool access before discovery, and ran a real `chat.send` against a local Responses fixture.

- Real MCP protocol logs record `initialize` and `tools/list`; independent `tools.effective` readback confirms `list_issues` and `search_items` after the run.
- Main, twice: reopening retains the empty notice and sends no second browser inventory request.
- Candidate, twice: reopening sends request two and immediately lists both tools without reconnecting or reloading.
- Control: reloading main also displays both tools, isolating the stale UI cache.
- Both new regressions fail on main and pass on the candidate. All 17 capability-host tests pass, including request sharing, stale-result ordering, reconnect retirement and error retry. The focused browser regression passes; touched-file formatting passes.
- Exact-head built CLI with real OpenAI `gpt-5-mini` returns `UI smoke ready`.

[Inspected before/after screenshots and DOM/RPC/MCP evidence](https://github.com/openclaw/openclaw/pull/168668#issuecomment-6347566305).

Whole-diff simplification keeps one existing cache owner and reuses the current test harness instead of duplicating host setup. Production +4/-3 lines (net +1); tests +58 lines. Contributor commits and credit are preserved.

Merge danger: two-way door; reverting fully restores prior cache behavior with no persisted-state changes. Blast radius is explicit Tool access opens in the chat composer, which issue one fresh inventory request per settled reopen.
```
