## What Problem This Solves

Fixes bulk Delete targeting a replacement session after the Sessions list refreshes while an older session with the same key remains selected.

## User Impact

Selections survive paging, but a disappeared, filtered-out, replaced, or unverifiable session is deselected after a completed refresh. A replacement does not inherit an earlier selection, including while the deletion confirmation is open.

## Why This Change Was Made

The page previously retained only session keys and looked up deletion targets later. It now captures the selected session's identity and archive facts, reconciles selections against completed roster snapshots, and rechecks the captured selection after confirmation. The existing Gateway `expectedSessionId` fence remains authoritative. Pending lifecycle changes retain selections for rollback.

Selection transformations live in a small adjacent module; the page owns the sole selection map. No RPC, storage, or permission contract changes.

+  const currentRows = new Map(rows.map((row) => [row.key, row]));
+  const selected = new Map(selection);
+  for (const [key, captured] of selected) {
+    const current = currentRows.get(key);

+    // Keep that selection for rollback, but never transfer it to a successor.
+    const retained = current
+      ? Boolean(captured.sessionId?.trim()) && current.sessionId === captured.sessionId
+      : isPending(captured);
+    if (!retained) {
+      selected.delete(key);
+    }
+  }
+  return selected.size === selection.size ? selection : selected;
+}
