## What Problem This Solves

Fixes: when an agent runs an automation that targets its own conversation, `automations run` can hold the turn for the whole wait (60 s by default) and then return without an outcome. This happens when the job is a current-session job whose result is committed back to the calling conversation, or a named-session job written as an alias of the caller's session (for example `session:main`, or `session:agent:<id>:main` when `session.mainKey` is customized).

## User Impact

User impact: those runs return their acknowledgement immediately, as #162481 intended, so the turn ends promptly and the run, which can only start or commit after the turn, delivers as usual. Waits for isolated jobs and other sessions are unchanged.

## Why This Change Was Made

#162481 skipped the wait only for `main` jobs and for `session:<key>` targets whose raw suffix equalled the caller's session key. That check missed two real cases:

- A `current` job commits its result into `job.sessionKey`. The commit waits for that session's active work (`commitCurrentSessionCronCompletion`, from the serialized delivery contract in #126860), and that work is the calling turn.
- Named targets are run under `resolveCronAgentSessionKey`, which applies agent scoping and `mainKey` aliases (#29683 / #30654). The raw suffix `main` never equals the caller's `agent:<id>:main`.

The check now applies only to agent-turn payloads (command and script jobs run as processes and never queue behind a turn) and compares only the session the run actually depends on: the named execution target, or for `current` jobs with announce delivery the `job.sessionKey` they commit into (quiet `current` jobs run detached and never commit, so they keep waiting). Both go through the execution owner's `resolveCronAgentSessionKey` (agent scoping and `mainKey` aliases), so they compare equal to the caller's canonical session key. The raw-suffix comparison is deleted. Archival bindings such as the creator `sessionKey` that the automations tool stamps on named-session jobs are deliberately not considered, because those runs execute elsewhere and can finish while the caller waits. The `main` case and every other invariant from #162481 are unchanged.

## Evidence

- Live proof on the Telegram Test Server: owner DM, live OpenAI `gpt-5.5` behind a pass-through proxy (key never in the Gateway config), same scenario before (merge-base `ab1b93295ad`, which contains #162481) and after (`62ef249055c`). In each run the model creates three disabled jobs, then for each job calls `automations run` with `runMode: force` and replies `RUNn-DONE` once the tool returns. Times are from the user's send to the bot's reply, taken from the recorded Telegram timeline:

  | Job | Before: tool turn | Before: tool result | After: tool turn | After: tool result |
  |---|---|---|---|---|
  | `isolated` (control) | 13.8 s; report at 10.5 s | `run {status: ok, deliveryStatus: delivered, summary: ISOLATED-REPORT}` | 9.7 s; report at 7.7 s | same `run` |
  | `current` announce into the DM | 68.8 s (blocked for the full 60 s wait) | runId + note | 8.5 s | runId + note (immediate) |
  | `session:main` (alias of the DM's `agent:main:main`) | 73.8 s; NAMED-REPORT at 75.8 s | runId + note | 7.5 s; NAMED-REPORT at 10.0 s | runId + note (immediate) |

  Run history matches: before, the `session:main` run took 64.7 s because it queued behind the caller's turn; after, it took 4.3 s.
- Out of scope: in both runs the `current` job itself fails with `attempt disposed before transcript write`, so its report is never delivered (before after 62 s, after after 4.8 s). A manual run started from an agent turn inherits that turn's transcript-write lifecycle. The same error shows up as a mirror warning on the other jobs. It is pre-existing, identical on origin/main, and not touched by this PR; it is being handled separately.
- `cron.validation.test.ts` drives the real `cron.run` handler with the real binding resolver and runtime config. `session:main`, `session:agent:ops:main` with `mainKey: "work"`, and a `current` announce job bound to the caller return the plain ack without calling the wait. `isolated` jobs, quiet (`delivery: none`) `current` jobs, and a named job for another session that carries the creator's `sessionKey` (as the tool creates it), still wait. On origin/main the three own-session cases fail; the creator-`sessionKey` case catches the over-broad first version of this fix; the quiet-current case catches the second. A separate test runs a quiet `session:main` command job as a real Control UI management caller (the only callers that can see command jobs) and confirms it still waits; it fails on the previous head.
- `pnpm tsgo:core` clean. `cron.validation.test.ts`: 266 passed, 29 s wall / 25.9 s Vitest (before this PR: 264 tests, about 24 s wall / 21.4 s). `server.cron.test.ts`: 17 passed.

### Bounded cost

No new waits, runs, model calls or messages. The change only makes more own-session runs skip a wait that could not succeed anyway.

### Hermes

Hermes never blocks the caller on a manual run, so it has no equivalent of this check. Keeping the bounded wait and skipping it only when the run depends on the caller is the smallest change that keeps #162481's same-call outcome for everything else.

LOC (vs origin/main): production +21/-3 in one handler, tests +77/-9.

Co-authored-by: Ayaan Zaidi <hi@obviy.us>
```

## What Problem This Solves

Fixes: when an agent runs an automation with `automations run`, the call returns as soon as the run is queued, so the model never learns whether the run worked. It then posts guesses, or schedules a separate "verify" job. That job runs with only its own scope, can't see the result, and reports a false "blocked".

## User Impact

User impact: when an agent runs an automation, it gets the finished run (status, error, delivery status and summary) in the same tool result if the run ends within the call's `timeoutMs` (default 60 s, capped at 10 min). A longer run returns its `runId` and a note to check it later with `runs jobId runId`, not with a scheduled check. The CLI is unchanged.

## Why This Change Was Made

`cron.run` became enqueue-only in #40204 (closing #40192). Back then a synchronous run held the RPC until the 60 s gateway timeout and returned a misleading timeout error while the job kept running. #81929 later added `openclaw cron run --wait`, polling `cron.runs` from the client, and deliberately kept `cron.run` from holding the request open. The agent tool never got a wait at all. A client-side poller would not work for the tool anyway: management-grant turns can run a job, but `cron.runs` is not one of their allowed methods.

This PR keeps that invariant (no unbounded request, no false failure) and gives the one owner of run completion a bounded, opt-in wait:

- The cron service records each accepted manual run's settlement. `waitForManualRun(runId, timeoutMs, signal)` resolves when the run has written its history row. It is event-driven, with no polling.
- `cron.run` accepts an optional `waitTimeoutMs`. When the run finishes in time, the ack also carries `run`, read through the existing `cron.runs` handler so the same visibility and authority rules apply. When the wait ends first, the ack is unchanged and the run continues.
- When an agent turn runs a main-session job, or a `session:<key>` job in its own session, the call returns at once. The caller's turn holds the main lane and its own session lane: heartbeats skip while `CommandLane.Main` is busy, and a main-session run waits up to 2 min for that busy turn. Waiting there would only burn the budget.
- The `automations` tool's `run` passes its `timeoutMs` as the wait. `runs` now forwards `runId`. The tool descriptions now steer models away from verify jobs. Against a shipped Gateway, which rejects the new param before enqueueing, the tool retries the plain call once, the same way it already does for `compact` on `cron.list`.
- Accepted runs stay accepted, and outcomes go only to callers that may still read them. After the history read, the handler rechecks read authority (caller authority, agent runtime and any management grant), with no await between that check and the response. If the read or the recheck is refused, for example because a delegated grant lapsed or was revoked during a long wait, the caller gets the plain ack and nothing about the outcome. If the run finished but its history is not visible (for example a one-shot that deleted itself after succeeding), the ack carries `finished: true`. Management-only turns are pointed to the Automations page instead of `runs`.

The CLI keeps its client-side `--wait` polling in this PR. Moving it onto the Gateway wait is a separate, compatibility-reviewed follow-up.

The run kept going and delivered, and a later `runs` call with that `runId` returned the single finished entry.
