## Fix PR #117369 description (by steipete, opened 2026-08-01T11:01:04Z)

```text
## What Problem This Solves

Provider endpoints can return HTTP 200 with the wrong media family or an ambiguous Content-Type, causing speech and video generation to produce bogus media. Sora also holds its consumed submission request throughout polling and download.

## Why This Change Was Made

Validate a single well-formed audio/video Content-Type in the existing shared binary reader, preserving missing headers, both octet-stream aliases, Ogg audio, raw PCM/Opus, quoted or escaped codec parameters, and generic binary callers. Release Sora’s submission guard immediately after reading its response.

This current-source integration preserves the newer bounded readers, request-header redaction, lazy imports, shared generated-video downloader, and transport/deadline policy. It does not reintroduce the historical PR’s superseded plumbing.

## User Impact

Malformed successful media responses fail visibly. Rendering no longer retains an unnecessary submission guard. Existing media formats, provider configuration, and authentication remain unchanged.

## Evidence

- 29 shared-reader regressions failed before repair; all 122 final shared-reader tests pass afterward.
- Five real TCP Sora release-order regressions fail on the baseline and pass with the repair, including queued text/image/video-edit and already-completed jobs. Four failure branches release exactly once.
- All 15 real-adapter acceptance tests pass through production speech/Sora adapters and the shared video download owner: malformed/repeated Content-Type, held response clones, byte limits, timeouts, socket release, and persisted debug capture readback after SQLite closure.
- All 247 affected tests pass on the final source: shared-reader, production TCP adapters, existing OpenAI adapters, shared video/music assets, compatible speech, and ElevenLabs streaming. This includes empty-parameter, Ogg-audio, and generic-binary compatibility corrections.
- Local TCP fixtures were used; no paid external generation is claimed. Unfinished captured bodies may correctly have an error terminal record; successful request/response capture and all terminal records were verified.

The current-source repair addresses the earlier hosted review’s Ogg compatibility and stale-owner concerns. Fresh independent review is clean (no actionable P0–P2 findings). Final changed-file static checks pass, including all four typecheck lanes, lint, formatting and repository guards. [Exact-head CI](https://github.com/openclaw/openclaw/actions/runs/35195842153) passes on `3630a0ec7d9e3ad533071aac038c77e41a6c54f1` (139 successful jobs). Original contribution by @steipete; current-source integration by @fuller-stack-dev.


## Review Disposition

The [current-head hosted review](https://github.com/openclaw/openclaw/pull/117369#issuecomment-5151159652) confirms the Ogg compatibility fix and reports no actionable defects. Its remaining merge-risk note is accepted within this repair's intended scope: a present malformed or wrong-family audio/video Content-Type now produces a visible provider error instead of returning bogus media. This is the assigned correctness change, not a request to accept arbitrary third-party headers. Missing headers, both generic octet-stream aliases, audio Ogg, valid codec parameters, raw audio formats, and legacy generic-binary callers remain covered and accepted.
```
