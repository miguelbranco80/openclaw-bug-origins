fix(google-meet): keep googlemeet export --output paths literal

googlemeet export trimmed the --output path it was given, so a path that started or ended with a space wrote the export bundle to a different, trimmed location. The path is now used exactly as given.

Evidence: built googlemeet export --output against a trusted Google REST fixture through the existing --access-token override (no real OAuth). ## Fix PR #187619 description (by SunnyShu0925, opened 2026-10-29T11:26:23Z)

```text
## What Problem This Solves

`openclaw googlemeet export --output "custom output "` silently trims the requested directory name. The tool's `outputDir`/`output` arguments have the same problem. Files land in a different directory than the literal filesystem destination supplied by the caller.

## User Impact

Nonblank output paths retain their leading and trailing spaces through CLI and tool export. Empty, all-whitespace and omitted values still use the generated default. Export contents, atomic publication, native-separator handling and ZIP layout remain unchanged.

## Why This Change Was Made

Replace the two trimming coercions at the existing export writer and tool adapter with the existing `readNonBlankString` primitive. It rejects blank input without changing a nonblank string. No configuration, public API or competing path owner is added.

Contributor commits, including the concurrent updated head, are retained. The invalid result-type imports identified in review are eliminated by consolidating the duplicate new writer fixture into the existing writer/ZIP and tool suites. The contributor's added CLI case is incorporated into the existing richer CLI bundle test. No private type is newly exported.

## Evidence

[Built CLI before/after matrix and focused regression results](https://github.com/openclaw/openclaw/pull/187619#issuecomment-6497185202).

- Independently built main and candidate in secretless Node 24.22.1 Linux Docker. Used explicit task-owned profile/config/state/database paths and the real shipped **`googlemeet export --output`** command.
- With leading-space and trailing-space destinations, main twice wrote to the trimmed path; candidate twice wrote to the exact literal path and left the trimmed sibling absent. Ordinary-path controls passed on both refs.
- A trusted local Google REST transport fixture used the existing `--access-token` synthetic override, recording nine expected requests per export. Actual artifact/attendance parsing, six-file bundle publication and sibling ZIP generation ran unchanged. No real OAuth account or paid key was used; no live Google-account claim is made.
- Baseline regressions fail at CLI, writer and tool boundaries because the literal manifest is missing or the reported path is trimmed. Candidate passes **75 tests across 2 affected files**. Targeted formatting, oxlint, changed-page MDX and whitespace checks pass.
- Simplification leaves no new test file or production abstraction. Against pinned main: production +7/-3 (net +4), tests +23/-25 (net -2), docs +2. Windows native/alternate separator controls remain; trailing-space filename assertions are scoped to POSIX.

## Merge Danger

Two-way door: revert restores the prior trimming behavior; no schema, state migration or published API changes. Blast radius is Google Meet export destinations with meaningful surrounding whitespace. On affected inputs, the intended write location changes to the literal path the caller requested; ordinary paths and blank-input fallback are unchanged.
```
