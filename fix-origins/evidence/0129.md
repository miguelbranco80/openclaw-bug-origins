## Fix PR #198975 description (by SunnyShu0925, opened 2026-11-14T15:35:21Z)

## What Problem This Solves

`openclaw models status --agent " "` and `openclaw models list --agent " "` reject the blank flag but collapse the **text** channel to a generic two-line failure — the remedy the guard already composed (`--agent must not be blank`) never reaches the operator on the route fast path. When an operator accidentally passes `--agent " "` (common in shell scripts with `--agent "$AGENT_NAME"` where the variable is unset), they see only `[openclaw] The CLI command failed.` plus a doctor hint, not the actionable hint about what went wrong.

- **Problem**: `resolveModelsTargetAgent` in `src/commands/models/shared.ts:235` throws a plain `Error`. On the Commander-registered path (e.g. `models auth login`) the `runCommandWithRuntime` wrapper catches and re-renders it; but the `route.ts` fast path for `models-status` / `models-list` (`route.ts:488-495`) uses `defineRoutedCommand` which awaits the command function directly with no wrapper, so the raw Error bubbles to the root failure renderer. `formatCliFailureLines` (`failure-output.ts:264-266`) only prints `humanOutput` for expected CLI errors; for plain `Error` it falls through to the generic failure block, yielding the two-line collapse on text mode. The json envelope keeps the message via `formatCliOperatorError` fallback, but the stderr path also collapses.
- **Solution**: Replace `throw new Error(...)` with the canonical `throwExpectedCliError(...)` already imported and used on line 41 of the same file.
- **What changed**: `src/commands/models/shared.ts` — one throw-site swap, import already present.
- **What did NOT change**: The guard condition, the message text, the exit code, the Gateway bootstrap chain, the json envelope `message` field, and every Commander-registered command path that already handled the plain Error correctly.

## Why This Change Was Made

The failure renderer already owns the remedy-printing contract: an `ExpectedCliError` carries `humanOutput` and `machineOutput` fields, and `formatCliFailureLines` / `formatCliJsonFailure` print them verbatim. Reusing the canonical `throwExpectedCliError` owner is the established per-site remedy for this exact anti-pattern. The file already imports it on line 41 where `throwExpectedCliError("Choose either --json or --plain, not both.")` handles a sibling guard in the same function family — so this is not a new dependency or a new design decision, just finishing a partial adoption.

- **Best fix**: This is the best approach — single throw-site swap, zero new imports, zero new types, zero behavior change outside the text-channel remedy print. The per-site `throwExpectedCliError` pattern is already adopted across the repo for the same reason (see sibling anchors below).
- **Alternative**: (1) Wrap route.ts routed commands with `runCommandWithRuntime` — wider blast radius across every routed command, not just this one guard, and the wrapper's re-throw path would still need the error to be an `ExpectedCliError` for the text channel to print. (2) Add `models` to the show-reason whitelist in `failure-output.ts` — would print raw reasons for every `models` failure, including unforeseen internal errors that should stay collapsed. Both rejected.
- **Risk**: Very low. The `ExpectedCliError` constructor in `expected-cli-error.ts:27-28` sets `humanOutput: message` and `machineOutput: message`, so both renderer lanes receive the identical remedy string verbatim. The exit code stays 1. Sibling guards in the same file already use this pattern (line 41). The only edge case would be if some downstream code pattern-matches on `instanceof Error` specifically to strip remedies — but the failure renderer code path (`handleCliUncaughtException` → `formatCliFailureLines`) already knows how to handle both variants.

## User Impact

Operators who pass `--agent " "` to `models status` or `models list` now see the actionable `--agent must not be blank` message directly instead of a generic failure and a doctor hint. Valid invocations are untouched; the command still exits 1. Both the text channel stdout and the `--json` envelope message carry the remedy. This reduces the cycle of "failed → doctor → search logs → understand" down to "failed → read remedy → fix flag → retry" for a common scripted-onboarding misconfiguration.
