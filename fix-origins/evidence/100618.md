* fix(onboard): a rerun rewrites a trusted-proxy gateway to token auth

Onboarding carried an existing gateway auth mode forward only when it was
`token` or `password`. A gateway configured with `trusted-proxy` therefore
fell back to `token`, so a rerun of `openclaw onboard` wrote
`gateway.auth.mode: "token"`, minted a new token, and left the configured
`trustedProxy`/`trustedProxies` blocks behind as orphans. The running
Gateway then dropped proxy identity headers and required token login.

`GatewayAuthChoice` is the config owner `GatewayAuthMode` now, and the
quickstart defaults carry any explicitly configured mode through the setup
write untouched. Only token and password still collect a secret, and an
explicit `--gateway-auth` choice still wins over the stored mode. The
QuickStart summary stops labelling a non-password kept mode as "Password".

Finalization previously assumed only token/password exist. It now resolves
the trusted-proxy local password the way the Gateway credential owner does
(`gateway.auth.password`, including a SecretRef, falling back to the
ambient `OPENCLAW_GATEWAY_PASSWORD`), sends it with the readiness probes
and the health check, hands terminal chat the loopback probe endpoint with
that password instead of the advertised LAN address the credential is not
valid for, and gates the token completion guidance to token mode.

Evidence: a PTY-driven `openclaw onboard --flow quickstart` rerun over a
trusted-proxy config on origin/main wrote
`{"mode":"token","trustedProxy":{...},"token":"<generated>"}`; with this
change the same command leaves `{"mode":"trusted-proxy","trustedProxy":{...}}`
with no token. Covered by quickstart/advanced tests against
`configureGatewayForSetup`, a `resolveQuickstartGatewayDefaults` case, and
`finalizeSetupWizard` boundary cases for the probe credential, the handoff
endpoint, and the completion guidance.

* fix(onboard): a funnel rerun must not rewrite a trusted-proxy gateway to password

`configureGatewayForSetup` forces `authMode` to `password` whenever Tailscale
Funnel is selected and the mode is not already `password`. That was safe while
`resolveQuickstartGatewayDefaults` could only ever hand it `token` or `password`,
but this branch widened the carried-forward modes to any configured value, so a
gateway set to `trusted-proxy` now reaches that branch. The rerun then writes
`{"mode":"password","trustedProxy":{...},"password":""}`: the identity blocks are
orphaned and password mode is left without a secret, so the Gateway refuses to
start with "gateway auth mode is password, but no password was configured."

Only `token` is a mutable default, so funnel may still switch it to `password`.
Any other mode is identity-bearing config the operator owns, so the wizard now
refuses the combination with an actionable error instead of silently rewriting it.

Covered by `configureGatewayForSetup` cases for the refusal and for the kept
token->password switch.
