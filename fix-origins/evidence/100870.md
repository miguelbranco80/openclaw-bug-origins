Related: #159431

## What Problem This Solves

Fixes `openclaw update` refusing an owned Bun Gateway at a different package root with `original-service-unverified`, and Bun package commands selecting bare `bun` from PATH instead of the verified executable.

## User Impact

Owned split-root Bun Gateway installations update in place with their recorded runtime pin; the invoking CLI installation stays unchanged. Package probes and installation retain the selected Bun even when PATH has no Bun or contains a different build.

Update behavior: the installed updater runs first. In the live Linux fixture, published 2026.9.6 with no Bun on PATH refused early with ENOENT, leaving the Gateway and both roots unchanged. With the fork Bun on PATH, that same published driver updated service root B in place and restarted healthy while CLI root A stayed unchanged. This PR's routing and verified-executable selection apply from the first candidate containing them; a newer candidate cannot retroactively change its installed driver's first hop.

## Why This Change Was Made

Reuse the existing service-root update route and the shared Bun/SQLite executable validation, while preserving Node service routing and destination ownership checks. Bun's emulated Node version is not checked against `engines.node`. A Node-based updater still passes the target's Node engine and SQLite preflight because finalization retains the updater runtime. Bun package commands use the verified service Bun, then the current Bun process executable, with PATH only as the final fallback.

The two commits were rebased onto the prerequisite squash merge without conflicts. Initial production LOC: **+10 net**; the Doctor follow-up below adds **+6 net**. The three installation/update docs describe runtime selection and first-hop behavior; the changelog remains release-owned.
