## Fix message body

```text
## What Problem This Solves

Fixes: Telegram posts a "Working / Last activity: Message" progress card below the bot's answer when replies go through the `message` tool (`messages.visibleReplies: "message_tool"`, the usual group setup) and the run keeps working after the send. Example: the `claude-cli` runtime continues after a final `message` send.

## User Impact

User impact: in message-tool reply mode, the progress card stops and is removed as soon as the `message` tool delivers the final answer. No card appears under the reply. This matches DM behavior, where the final reply takes over the card.

## Why This Change Was Made

The `message` tool already records the delivered source reply on the reply operation (`markSourceReplyDelivered`) at send time. Channels only heard about it through `onObservedReplyDelivery` after the whole run ended, so progress events from the rest of the run still created or updated the card.

The reply operation now lets callers observe that moment. `runReplyAgent` forwards it to the existing `onObservedReplyDelivery` callback, only for `message_tool_only` runs. Channels already handle that callback by stopping and removing their live preview (Telegram, Discord, Matrix, Mattermost). The later end-of-run call stays a no-op through the existing dedupe in dispatch. No channel code changes.

A `final: false` send still keeps the card, because the model declared that more work follows.

## Evidence

- Regression test `reports a message-tool source reply mid-run only in $mode delivery`: it fails on `main` (callback not called mid-run) and passes with the fix. Automatic mode stays unchanged.
- `agent-runner.runreplyagent.e2e.test.ts` (200), `src/sessions/` and `dispatch-from-config.test.ts` pass. `tsgo:core`, core test typecheck shards, oxlint and oxfmt on changed files pass.
- Live Telegram Test Server, real QA user via TDLib, DM, `streaming.mode: progress`, `visibleReplies: message_tool`. The scripted model sends one response with a final `message` send plus `exec sleep 4`, so the run continues after the reply:

  | Build | SUT events after the user message |
  | --- | --- |
  | `main` | 4.1s reply → **5.1s new card `Working / Exec: running` below the reply** → 9.3s card deleted |
  | this PR | 4.0s reply only; no card. The typing indicator continues to 12.2s in both runs, so the run length is the same. |

Gap: this was not proven through the `claude-cli` backend (no Claude login on the proof host). The two-tool script reproduces the same "final send, run continues" path.

Size: about +22 production lines (one listener on the reply operation, one forwarding hook in the runner) and +26 test lines. No new state, no channel code changes.

Co-authored-by: Ayaan Zaidi <hi@obviy.us>
```
