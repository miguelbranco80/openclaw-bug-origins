## Fix PR #160575 description (by steipete, opened 2026-09-28T17:07:59Z)

```text
## What Problem This Solves

Fixes: a headless node host on a Bun-only macOS or Linux install finds a new release but can never install it, because preparing the update runs `npm view`, `npm pack`, and an npm global install.

## User Impact

On macOS and Linux, a node host running on Bun now prepares its private update runtime without Node or npm. It fetches the release manifest and tarball from the registry in-process, verifies the tarball's `dist.integrity`, and installs it into the private runtime generation with Bun. It then activates the new version through the existing launcher, as before. Node hosts are unchanged.

Windows keeps npm preparation: the shared staging owner refuses every Bun stage on Windows because Bun's Windows binary launchers cannot be relocated (the main updater has the same limit). The Bun compatibility page documents it.

## Why This Change Was Made

#160154 made discovery in-process under Bun, and #159431 added the Bun preinstall launcher marker and native Bun staging. This PR connects preparation to those owners instead of adding a second installer:

- **Metadata and archive:** under Bun on POSIX, `prepareNodeRuntimeUpdate` reads `<registry>/openclaw/<version>` through one registry-document reader, now shared with discovery (the reads live in the leaf module `src/infra/registry-package-archive.ts`, which only the node host imports, so plugin install owners gain no new dependency). It then streams the tarball into the install workspace. The tarball must share the registry's origin, redirects are refused, and the sha512 SRI must match `dist.integrity` before anything is installed.
- **Install:** `resolveGlobalInstallTarget({ manager: "bun" })` and `runGlobalPackageUpdateSteps` install `openclaw@file:<archive>` into the private generation, which uses the same `<gen>/lib/node_modules/openclaw` layout as npm, so the published launcher and generation retention are unchanged. `BUN_INSTALL_GLOBAL_DIR` and `BUN_INSTALL_BIN` point inside the generation, so the update never touches the user's `~/.bun/bin`. The only shared-owner change is an optional `env` on `resolveGlobalInstallTarget`, so the Bun owner check honors that private global dir.
- **Staging prerequisites found by the live proof:** `createGlobalInstallEnv(env, { manager: "bun" })` skips the npm freshness policy, whose npm config probe spawned `npm config get globalconfig`. The Bun branch creates `<gen>/lib/node_modules`, because the shared `bun pm bin -g` preflight runs from there, and seeds `<gen>/lib/package.json` as `{"private":true}`, because Bun requires a global project manifest (the Bun-only smoke harness seeds one the same way).
- **Candidate compatibility on Bun:** the node host no longer checks a system Node against the candidate's Node `engines`. On a Bun host the launcher runs the candidate with the same Bun, so that check only failed Bun-only hosts ("No system Node was found"). The candidate's runtime guard and the launcher's readiness fallback own Bun compatibility. The launcher caps automatic restarts at one per 12 hours, so a candidate that cannot start on the host's Bun costs one fallback restart per 12 hours, not a loop.
- **Registry target:** the loopback test seam (`OPENCLAW_UPDATE_PACKAGE_SPEC=openclaw` plus a loopback `NPM_CONFIG_REGISTRY`) now serves discovery and preparation alike. Production stays pinned to public npm.

**Registry source (maintainer decision, @steipete, carried over from #160154):** under Bun, the node host never spawns npm. Discovery and now preparation both read the public registry in-process (the loopback test seam aside), so the two always agree on the release they select. A Bun host whose npm points at a private mirror therefore fetches OpenClaw's own tarball from public npm; dependency resolution during `bun add` still follows Bun's registry configuration. Recovery for hosts that must use a mirror: set `nodeHost.autoUpdate.enabled: false` and update through `openclaw update`.

### Update behavior

The installed node host is the updater: it discovers, prepares, and asks its launcher to activate. Code in this PR therefore helps only once a node host runs this version or later.

| Driver → target | Node host runtime | Outcome |
|---|---|---|
| 2026.9.x → this candidate | Node | Unchanged: npm discovery and preparation, launcher activation. Live Node cell below: published 2026.9.4 → candidate passed. |
| 2026.9.x → this candidate | Bun with npm/Node present | Unchanged: 2026.9.x discovers and prepares with npm; the launcher starts the new runtime with the running Bun. |
| 2026.9.x → this candidate | Bun-only (macOS/Linux) | Cannot reach it by itself: published discovery and preparation spawn npm. The node keeps running its current version and logs the failure hourly. It reaches this version through its installation owner (the app or a manual update). No marker set by the published driver lets candidate code change that. |
| this candidate → later | Bun-only macOS/Linux | Discovery (#160154) and preparation (this PR) run without Node or npm. The launcher activates the private generation. Live proof below. |
| this candidate → later | Bun on Windows | npm preparation as before; a Bun-only Windows host logs the failure hourly and keeps running (documented). |
| this candidate → later | Node | Unchanged. |

Failures stay recoverable. Preparation writes only into a fresh private generation, and a failed preparation leaves the running node serving and retries hourly, as before. There is no config, state, schema, service, or Doctor change.
```

```diff
+export async function downloadRegistryPackageArchive(params: {
+  tarballUrl: string;
+  registryUrl: string;
+  integrity: string;
+  cwd: string;
+  timeoutMs?: number;
+  signal?: AbortSignal;
+}): Promise<{ ok: true; archivePath: string } | { ok: false; error: string }> {
+  const { signal, cleanup, refresh } = buildTimeoutAbortSignal({
+    timeoutMs: Math.max(1, params.timeoutMs ?? UPDATE_NETWORK_TIMEOUT_MS),
+    signal: params.signal,
+    operation: "npm-registry-package-download",
+  });
+  let response: Response | undefined;
+  let archivePath: string | undefined;
+  try {
+    const url = new URL(params.tarballUrl);
+    if (url.origin !== new URL(params.registryUrl).origin) {
+      throw new Error("Package tarball must share the registry origin.");
+    }
+    if (!/^sha512-[A-Za-z0-9+/]{86}==$/u.test(params.integrity)) {
+      throw new Error("Package archive requires supported sha512 integrity.");
+    }
+    // Reject redirects so a same-origin URL cannot send the download elsewhere.
+    response = await fetch(url.toString(), { signal, redirect: "error" });
+    if (!response.ok || !response.body) {
+      throw new Error(`Package archive download failed: HTTP ${response.status}`);
+    }
+    refresh();
+    const hash = createHash("sha512");
+    archivePath = path.join(params.cwd, `${randomUUID()}.tgz`);
+    await pipeline(
+      response.body,
+      async function* (chunks) {
+        for await (const chunk of chunks) {
+          hash.update(chunk);
+          refresh();
+          yield chunk;
+        }
+      },
+      createWriteStream(archivePath, { flags: "wx", mode: 0o600 }),
+      { signal },
+    );
+    signal?.throwIfAborted();
+    if (`sha512-${hash.digest("base64")}` !== params.integrity) {
+      throw new Error("Package archive integrity mismatch.");
+    }
+    return { ok: true, archivePath };
+  } catch (error) {
+    if (archivePath) {
+      await fs.rm(archivePath, { force: true });
+    }
+    return { ok: false, error: `Registry package archive failed: ${String(error)}` };
+  } finally {
+    await cancelUnreadResponseBody(response);
+    cleanup();
+  }
+}
```
