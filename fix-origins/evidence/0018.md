## Fix PR #193205 description (by mikasa0818, opened 2026-11-05T05:08:58Z)

```text
## What Problem This Solves

The existing `SessionWorkStartChangedError` becomes an opaque internal error on the OpenAI-compatible HTTP surface. Clients lose the existing reason and stable code even though the Gateway already uses HTTP 409 / `invalid_request_error` for session conflicts.

Closes #192465.

## Changes

Recognize only the existing `SESSION_WORK_START_CHANGED` code when its error graph contains an existing string message, including wrapped/serialized errors. Forward that message and code using the existing conflict response. The session module merely exports its already-existing constant; its value and producer behavior do not change.

Remove the proposed invented fallback sentence and the broader invalidated/code-only mapping. Code-only objects keep the existing fallback rather than receiving new retry guidance. Responses failure adapters retain an already-mapped optional error code, falling back to the mapped type when no code exists.

No automatic retry, admission, ordering, cancellation, authorization, persistence, configuration, or migration change is introduced. This does not guarantee that replaying a whole request is safe.

## Evidence

[Final-head qualification](https://github.com/openclaw/openclaw/pull/193205#issuecomment-6912871882), with [natural JSON/SSE conflict receipts](https://github.com/openclaw/openclaw/pull/193205#issuecomment-6912299434).

Current head `1e73bc856889` changes only explicit test-DTO construction from the runtime-proven `1001419598bb`; production is identical and the live receipts are retained. Current-head type-aware lint, all eight envelope cases, full declarations, and public packed smoke pass.

Real source-tier Node Gateways, real agent/model execution, authenticated `/v1/responses`, isolated HOME/state, and an immediate local OpenAI-compatible SSE provider. Provider replies are never held or delayed; no rejection or event-loop stall is injected. Cold-start/module-load stalls occur naturally in the Gateway.

Send a streaming request on a new session key, then a second message six seconds later while draining both replies immediately:

| Route/observation | Main `b7e618de5d27` | Candidate `1001419598bb` |
| --- | --- | --- |
| Nonstreaming conflict, independent run 1 | HTTP 500, api_error/internal error | HTTP 409, existing changed-session code/message |
| Nonstreaming conflict, independent run 2 | HTTP 500, api_error/internal error | HTTP 409, existing changed-session code/message |
| Streaming race loser | HTTP 200, response.failed api_error/internal error | HTTP 200, response.failed SESSION_WORK_START_CHANGED and existing message |
| Successful peer and separate-session control | HTTP 200, completed | Unchanged |

Both streaming replies end with one `[DONE]`; the failed reply never reports completion. Natural scheduling selects the race loser. Gateway logs identify the actual native `SessionWorkStartChangedError`; the rejected turn never reaches the provider. The source and provider fixtures are not an injected agent-command rejection.

Three focused owner/consumer files pass 22 selected cases. New direct, nested, and serialized-message regressions fail on main with 500 instead of 409; code-only fallback and the existing TLS/cancellation/timeout contracts remain covered. All existing mapped/unmapped/without-lifecycle SSE cases remain. Targeted formatting/lint, public full declaration build, tarball integrity, and packed Gateway version/help smoke pass.

Production +27/-3. Tests +37/-41, net -4. The allocation and unnecessary SSE-helper extraction are removed; no baseline case was dropped.

## Risk

Two-way door: reverting restores the old HTTP classification without changing stored state. Blast radius is error envelopes for the existing changed-session condition and preservation of already-mapped Responses error codes; normal turns and session coordination are unchanged.
```
