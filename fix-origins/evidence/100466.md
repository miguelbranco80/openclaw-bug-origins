## Fix message body

```text
* fix(update): continue the update when runtime retention cannot complete

Runtime retention protects the running updater's lazy imports while the update
replaces its runtime, but any retention failure aborted the whole update: a
worker output cap, a source file changing during the copy, a host-owned
dependency link, or unsafe temporary storage. On large installations that made
every update fail.

Retention is now best effort. A failure before the runtime is bound logs its
reason with "continuing update without a verified retained rollback runtime",
retains nothing and lets the update continue; native recovery and rollback still
apply. Cancellation, a lost update lease, or a failure after import hooks are
bound still stop the update.

* fix(update): keep native recovery and subprocess custody in retention fallback

Fall back only after the retained native recovery helper is bound, so
native service recovery can still run after replacement removes the
installed helper; earlier failures such as unsafe temporary storage keep
stopping the update before activation. Propagate uncertain retention
subprocess cleanup instead of continuing with unsettled custody.
```

## Fix PR #185178 description (by fuller-stack-dev, opened 2026-10-26T23:29:43Z)

Related: #184958

## What Problem This Solves

Fixes: `openclaw update` aborts at `updater-runtime-retention` whenever runtime retention can't complete, for example from a worker output cap, a file that changes size during the copy (`file exceeds limit`), or a host-owned dependency link. On large installations this blocked every update.

## User Impact

User impact: the update continues when retention fails after the updater has kept its own copy of the native recovery helper. The log records the reason with "continuing update without a verified retained rollback runtime". Native recovery and the existing rollback protections still apply. The update still stops before activation when no private storage outside the installation exists for that helper (for example unsafe temporary storage), when the retention worker's process cleanup can't be confirmed, on cancellation, or when the update loses its lease.

## Why This Change Was Made

Runtime retention exists so the running updater's lazy imports keep working while the update replaces its runtime. The code already had a fallback for one case, a failed retained-tree verification (`unusableReason`), but every other retention error was fatal.

Retention is now best effort, as the maintainer directed. A failure after the native recovery helper is retained and bound, but before the full runtime is bound, takes that same fallback: nothing else is retained, the installed runtime is untouched, and the private tree is removed at close. These still throw:
- a failure before the native helper is bound, since native service recovery needs that retained helper after replacement removes the installed one;
- an error carrying uncertain command-process cleanup, so the update never continues with unsettled subprocess custody;
- cancellation or a lost update fence;
- a failure after import hooks are bound (falling back then could leave the process importing from a removed tree). `docs/cli/update.md` now describes the fallback; the older guidance stays for failures recorded by earlier updaters.
