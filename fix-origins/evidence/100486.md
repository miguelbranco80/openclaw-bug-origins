## Fix message body

```text
* fix(cloud-workers): retain refreshed bundles until receipts record them

Runtime refresh installs the Gateway's current worker bundle before it
records the new bootstrap receipt. A retain pass processed by the node after
that install acknowledged the new install generation while the Gateway's keep
set still held only the old receipt, so the next pass pruned the refreshed
bundle and the next worker launch failed with ENOENT, the same failure #160730
fixed for cold provisioning.

Provisioning and refresh share one cause: both install the current build
before recording it. The retain coordinator now keeps the current build on a
node until every live environment there has recorded it, which completes the
reachability snapshot instead of suspending retention. This replaces the
provisioning-only special case from #160730. Persistent hosts keep their
existing current-build pin and status target; cloud nodes keep reporting
their environment receipt.

The installer regression now covers both phases with the real node installer
and coordinator. The runtime-refresh phase reproduces ENOENT on the previous
code and also proves the previous bundle is pruned once the new receipt is
recorded.

* fix(cloud-workers): keep workspace retention when build preparation fails

Cloud nodes now resolve the Gateway's current build for bundle retention.
If that preparation rejects, send workspace-only retention without a bundle
keep set, generation acknowledgement, or status query, and warn instead of
failing the whole pass. Workspace retention previously did not depend on
bundle preparation for cloud nodes.
```

Related: #160730

## What Problem This Solves

Fixes: after a Gateway update, a cloud worker's first turn could fail with `ENOENT ... realpath '<node-host>/gateway-<ns>/bundles/<bundleHash>'` because node cleanup deleted the worker bundle the in-place runtime refresh had just installed.

## User Impact

User impact: cloud machines that are refreshed in place after a Gateway update, and cold-provisioned machines, keep the newly installed worker bundle until the environment records it, so the next turn launches instead of failing with a missing bundle.

## Why This Change Was Made

#160730 fixed this failure for cold provisioning and explicitly left runtime refresh open. Refresh has the same window: `provider-runtime-refresh.ts` installs the new bundle, then records the new receipt afterwards (`store.refreshBootstrapReceipt`). Throughout that window the environment stays `ready`/`idle`/`attached` with its old receipt.

The node marks each finished install with a new generation. It protects that bundle only until the Gateway acknowledges the generation, and the Gateway acknowledges whatever generation the previous retain pass returned. A retain pass that the node queues behind the install (its per-namespace queue serializes them) returns the new generation, even though the Gateway built its keep set from the old receipt. The next pass then prunes the refreshed bundle.

This is reachable after every Gateway update. The node reconnects, and its first retain pass lands behind the refresh install. The first bundle-status acceptance on a new connection (`undefined -> installed`) reschedules the same node, so a second pass races the receipt write. The 60 s placement reconcile and node inventory changes can also supply that pass during long installs.

Persistent hosts were already safe because the coordinator always pins the Gateway's current build there. Environment-owned cloud nodes were deliberately excluded from that pin (#140449), so they were exposed.

Provisioning and refresh share one cause: both install the Gateway's current build (the same memoized `prepareInstallation("bundle")` artifact that `bundleRetention.currentBuild()` returns) before recording it. The retain coordinator now applies one rule: **keep the current build on a node until every live environment there has recorded it.** This completes the reachability snapshot instead of suspending retention, and it replaces the provisioning-only `bundleRetentionReady` special case from #160730. Pruning of other bundles continues during provisioning and refresh.

If preparing the current build fails, the coordinator now sends a workspace-only retain request (no bundle keep set, generation acknowledgement or status query) and warns. Workspace retention on cloud nodes therefore still does not depend on bundle preparation; this addresses ClawSweeper's P2 on the first head.

Other behavior is unchanged:
- Persistent hosts keep their existing always-on pin and status target.
- Cloud nodes still report their environment receipt as bundle status.
- The status pin appears only while an environment is converging.
- Cloud nodes now resolve `currentBuild()` when bundle retention is supported. The provider reconcile loop already prepares that artifact for every ready, idle or attached environment.
- No protocol, schema, store or lifecycle changes.
