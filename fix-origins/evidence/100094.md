```text
Closes #182175

## What Problem This Solves

Fixes: Claude CLI parent replies can remain in progress indefinitely after a background Agent launches another background task.

## User Impact

User impact: the parent reply finishes when its own background work settles, without waiting for a nested task's reply on the wrong stream. Top-level background work still keeps its parent reply open. No configuration or migration is required.

## Why This Change Was Made

Claude identifies nested Agents and workflows with `parent_task_id`, but reserves `owned_by_subagent` for nested Bash tasks. Treat all tasks with a parent as owned by that subagent instead of inheriting ownership of the outer input. Keep the existing completion, replay, and watchdog policies unchanged.

## Evidence

- Native stdio regressions for nested Agents and workflows fail on the base revision because the final result is incorrectly marked interim; both pass with the fix. They also verify warm-session reuse with the same process.
- Anthropic CLI runtime suites: 69 tests passed. Host CLI execution/watchdog suites: 32 tests passed. Targeted typecheck, lint, formatting, and diff checks passed.
- Claude 2.1.296 producer source confirms `parent_task_id` means the launching local Agent, while `owned_by_subagent` is emitted only for nested Bash.
- Canonical fresh autoreview completed with no P0–P2 findings; simplification review retained one ownership rule and removed parent-input inheritance.
- A built, isolated Gateway at implementation commit `6802faaa` completed `chat.send` → native Claude stdio → `agent.wait` with `status: ok` and terminal reply `parent final`; `chat.history` retained both interim and final text. The focused E2E test passed, and its owned Gateway and state were removed. Publication added a metadata-only commit; the published tree is identical to the tested tree.
- Live Claude subscription inference has not been exercised. The Gateway proof used a synthetic external Claude protocol executable and synthetic credentials, not a live Anthropic account. An earlier in-process fixture failed native-supervisor startup before reaching the protocol; the final proof uses a separately built Gateway process.
```

```text
fix(claude-cli): don't hold the final answer for stopped or earlier-input tasks

With the Claude CLI runtime, a real final answer could be held and then lost when a stopped background task, or a task started by an earlier input, was treated as work the current turn still owned. Stopped tasks now settle, and tasks from earlier inputs no longer hold the current final answer; genuinely running background work still holds it until its answer arrives. This does not resolve the broader missing-reply reports, which have other causes.

Evidence: real Claude Code 2.1.308 through built Gateway RPC in Docker with a local Messages fixture. On main the final answer was held in both cases; with this change stopped work settles and earlier-input work does not hold the current final, a live background Agent is still held until its answer, and the next input reuses the same native process and session. A live gpt-5.4-mini run passes. Production +53 (down from +148).

Thanks @cassthebandit.
```

```diff
+import { isRecord } from "openclaw/plugin-sdk/string-coerce-runtime";

+export function readReplayedTaskId(
+  message: Record<string, unknown>,
+  submittedInputUuids: ReadonlySet<string>,
+): string | undefined {
+  if (
+    message.type !== "user" ||
+    message.isReplay !== true ||
+    message.parent_tool_use_id !== null ||
+    (typeof message.uuid === "string" && submittedInputUuids.has(message.uuid)) ||
+    !isRecord(message.message)
+  ) {
+    return undefined;
+  }
+  // Before Claude Code 2.1.274, inline notification receipts omitted origin.
+  if (
+    message.origin !== undefined &&
+    (!isRecord(message.origin) ||
+      message.origin.kind !== "task-notification" ||
+      message.origin.subkind !== undefined)
+  ) {
+    return undefined;
+  }
+  const content = message.message.content;
+  const first = Array.isArray(content) ? content[0] : undefined;
+  const text =
+    typeof content === "string"
+      ? content
+      : isRecord(first) && first.type === "text" && typeof first.text === "string"
+        ? first.text
+        : "";
+  return /^<task-notification>\s*<task-id>([^<]+)<\/task-id>/u.exec(text)?.[1];
+}
+
+export function recordTaskOwnership(
+  session: { taskOwners: Map<string, string | false>; taskRuns: Map<string, string> },
+  task: Record<string, unknown>,
+  inputUuid: string,
+): string | undefined {
+  const taskId = task.task_id;
+  if (typeof taskId !== "string" || !taskId) {
+    return undefined;
+  }
+  const previous = session.taskOwners.get(taskId);
+  const owner =
+    task.owned_by_subagent === true
+      ? false
+      : (previous ??
+        (typeof task.parent_task_id === "string"
+          ? session.taskOwners.get(task.parent_task_id)
+          : undefined) ??
+        inputUuid);
+  if (owner !== previous) {
+    session.taskOwners.set(taskId, owner);
+  }
+  if (typeof task.run_id === "string" && task.run_id) {
+    session.taskRuns.set(task.run_id, taskId);
+  }
+  return owner === false ? undefined : taskId;
+}
```
