## Fix PR #168986 description (by steipete, opened 2026-10-11T07:42:58Z)

```text
## What Problem This Solves

The Codex harness docs say an authored `models.providers.*.models[].contextTokens` cap is forwarded to Codex thread start and resume as `model_context_window`, so Codex compacts at the capped window. For ordinary configured models that Codex also lists in its own catalog, the cap was never forwarded.

Seen on a dev Gateway with a real OpenAI provider. The config caps `openai/gpt-5.6-sol` at `contextTokens: 40000`, and agent `codex` runs that model on the Codex runtime. A probe sent a fact plus several ~30k-character documents:

- per-turn context grew 28.7k → 35.4k → 41.9k → 48.5k → 53.1k tokens, with no compaction and no notice;
- the Codex rollout recorded `"model_context_window":"unset"` on every turn;
- the built-in runtime, with the same config and documents, stayed under the cap (26.2k).

## Why This Change Was Made

`model-harness.ts` suppressed the authored cap whenever `nativeModelOwned` was set. But `model-setup.ts` also sets that flag for ordinary models discovered in Codex's catalog, not only for sessions pinned to a native Codex model. The cap is now suppressed only for sessions with a durable `pinnedHarnessId`, which is what the suppression was meant for.

Behavior after the change:

- configured chats forward the authored cap on thread start and resume;
- unauthored caps are still omitted;
- pinned native sessions keep their own settings.

The sibling Codex source confirms that it clamps `model_context_window` to the model's native maximum, derives auto-compaction from it, and passes it to child threads.

## User Impact

Codex-runtime agents with a configured `contextTokens` cap now get the cap they asked for: smaller requests, and compaction at the limit, as documented. Agents without a cap are unchanged.

## Evidence

- A regression composes real merge-mode config, model policy, dispatch and both Codex start/resume request builders. It covers a 40,000-token cap, no authored cap, oversized caps, non-native catalog budgeting and subagents. With only `model-harness.ts` reverted, 3 cases fail with `model_context_window` undefined instead of the authored cap.
- `run.overflow-compaction.loop.test.ts` 15/15 (106 s wall; the new cases take 8–17 ms). `setup.test.ts` 27/27. Setup, ownership and `thread-lifecycle.test.ts` together 137/137. `pnpm tsgo:core`, test types, oxlint, madge (0 cycles) and the docs checks pass. Autoreview is scoped-clean. Production change: +1/−1.
- Live A/B on dev Gateways with fresh state and a real OpenAI provider. Same config (`contextTokens: 40000`), same Codex agent, same probe (a fact, then ~30k-character documents):
  - main 390f0f0acb98: rollout `"model_context_window":"unset"` on every turn; context 28.7k → 53.1k tokens, never compacted.
  - this branch: rollout `"model_context_window":38000` (the 40k cap after Codex's 95% effective-window factor); context ended at 34.1k tokens; all 6 document answers correct.
  - not changed here: after Codex's native compaction, the model could not recall a code word that the probe had marked "for this conversation only (do not save it to memory)". Codex's own summary dropped it. That is native summarization, which OpenClaw does not control.
```
