## Fix message body

```text
fix(telegram): forward message effects on private-chat sends

Telegram sends dropped the existing `effectId` option, so a requested message effect never reached Telegram. The effect is now forwarded through an optional send option on private-chat sends. Group sends omit it, as Telegram does not support effects there, and still deliver normally. Sends without an effect are unchanged.

Evidence: built Gateway on the Telegram Test Server with a userbot in a private chat, twice per ref. Main delivered effect `0`; with this change the requested effect was delivered. Rich-text, location and retry controls pass, and group sends deliver normally with no effect on both refs. Media is covered by an HTTP regression. Details: https://github.com/openclaw/openclaw/pull/191646#issuecomment-6632234535.

Thanks @aspalagin.

Co-authored-by: Ayaan Zaidi <hi@obviy.us>
```

## Fix PR #191646 description (by aspalagin, opened 2026-11-03T03:47:20Z)

```text
Closes #191644

## What Problem This Solves

The shared message tool already accepts `effectId` (alias `effect`), but Telegram drops it before sending. Private-chat messages therefore arrive without the requested native effect metadata and without an error.

## User Impact

Forward a numeric Telegram message-effect ID for known private chats, on the first accepted message of a send. Rejected attempts retain the effect for retry/fallback; later parts do not repeat it. Preserve ordinary delivery for groups, channels, unresolved username targets and non-numeric effect names by omitting the effect rather than introducing a new failure. Sends without an effect are unchanged.

## Why This Change Was Made

Carry the existing tool parameter through Telegram's legacy and prepared payload routes into the existing text, rich, media and location send owners. Use existing resolved-chat facts to avoid sending a private-only field to groups, and reuse the sender's accepted-part list rather than adding lifecycle state. The existing send option type gains one optional member; no SDK exports, configuration, schemas or migrations are added.

Original implementation and contributor commits by @aspalagin are retained. The repair removes the proposed new rejection errors and consolidates coverage into existing owner suites instead of adding a separate test file/allocation. Against pinned main `490aff93f1073897caff7c6db6909375c1b4ea00`: production +81/-8 (net +73); tests/support +107/-108 (net -1).

## Evidence

[Built Gateway / real Telegram Test Server evidence](https://github.com/openclaw/openclaw/pull/191646#issuecomment-6632234535): main twice records native `effect_id=0`; candidate twice records the requested Test Server-advertised ID. Additional real rich-message and location controls distinguish the refs. No-effect controls remain unchanged. Both refs deliver group sends without an effect; direct group API controls reject an explicitly forwarded effect. One rejected 429 attempt proves that the effect survives until the first accepted part.

Candidate build, changed-file format/lint, and 147 focused tests pass. Media is covered by HTTP regressions only: the real-media attempt encountered the unchanged local-media directory guard on both refs. The proof asserts native metadata, not rendered animation or group animation; a deterministic provider fixture drives the real Gateway/tool and real Telegram transport.

## Merge Danger

Two-way door: reverting restores the old omission without persisted-state or configuration changes. Blast radius is Telegram outbound message sends requesting an effect, including prepared presentations and location/media paths; sends on other channels are unaffected.
```
