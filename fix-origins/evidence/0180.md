## Fix PR #197032 description (by obviyus, opened 2026-11-11T04:59:09Z)

```text
Closes #189214
Related: #156442

## What Problem This Solves

Fixes: the first Claude CLI turn after an idle period stalls for about 10 seconds or fails with "another Claude Code process is refreshing it or exited mid-refresh" when OpenClaw cancels its Claude login check during a token refresh.

## User Impact

User impact: when model discovery is cancelled while Claude Code is refreshing an expiring login, Claude Code finishes the refresh and releases its lock. The next Claude CLI turn starts normally instead of waiting on an orphaned lock or falling back to another provider.

## Why This Change Was Made

The availability probe runs `claude auth status --json`. When the OAuth token is close to expiry, that command refreshes it while holding Claude Code's `.oauth_refresh.lock`. Before this change, the probe passed the caller's abort signal to the process runner, so a cancelled discovery sent SIGTERM to the process group and then SIGKILL 300 ms later. Claude Code defers SIGTERM until the refresh finishes, and a real refresh takes longer than 300 ms, so the SIGKILL landed mid-refresh and left the lock behind.

Now the probe no longer gives the caller's signal to the process. A cancelled caller waits for `auth status` to exit by itself (about 0.5 s in the runs below) and then rejects with the cancellation reason. Cleanup still joins the child, so no probe process outlives its caller, and cancellation is still not reported as a logged-out account. The 10 s deadline remains the only path that terminates the probe.

Accepted edge case: if a refresh is still running when the 10 s deadline expires, or when the Gateway process exits, the probe can still be killed mid-refresh. Recovering from contention that is already in progress belongs to #156442.

## Evidence

Claude Code 2.1.322, macOS arm64. Each run used a throwaway `CLAUDE_CONFIG_DIR` with an expired synthetic OAuth token, so the real binary performs a real refresh request, which the server rejects. The host Claude login was not used or modified. All Keychain entries created for these throwaway config dirs were deleted.

**Real CLI through OpenClaw's probe** (the real `probeClaudeCliAuthStatus` and process runner; the caller's signal aborts as soon as `.oauth_refresh.lock` appears, then one real `claude -p` runs in the same config dir):

| Lock left after the cancelled probe | 3/4 | 0/4 |
| Next `claude -p` duration | 2.0 s (1 clean run), then 8.9 / 9.5 / 10.6 s | 0.9–1.5 s |
| Cancelled caller settles after | ~0.47 s (killed) | ~0.55 s (joined exit) |

Direct Claude Code check (no OpenClaw): sending the runner's exact sequence (SIGTERM, 300 ms grace, SIGKILL) once the lock appears left the lock 5/5 times. When the lock was left without an owner record, the next `claude -p` waited 8.7 s and then failed with `Failed to refresh OAuth token: another Claude Code process is refreshing it or exited mid-refresh`. When an owner record was present, Claude Code took the lock over after about 9.9 s.
```
