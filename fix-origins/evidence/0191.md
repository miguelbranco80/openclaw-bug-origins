## What Problem This Solves

A live account can report a narrower set of reasoning levels than the hosted model catalog. Catalog enrichment overwrote that account list, so the effort picker offered unsupported levels. This caused the [main real-Gateway UI test](https://github.com/openclaw/openclaw/actions/runs/44024086924/job/133840776161) to fail.

## User Impact

The picker and model consumers retain the account's reported reasoning levels, including an explicitly empty list. Hosted context limits, input capabilities, and pricing still apply.

This fixes the overwrite introduced by https://github.com/openclaw/openclaw/pull/200403 at its owner; no UI assertions or production UI code change.

Message (truncated):

```text
## What Problem This Solves

Some providers list their models live from the account: Together, Tencent TokenHub/TokenPlan, and other OpenAI-compatible live catalogs. When a listed model is missing from the plugin's built-in rows, OpenClaw ignores the hosted catalog's details for it and uses discovery defaults: 128k context, a 32k output cap and text-only input. For example, Together `moonshotai/Kimi-K3` has a 1M context window and accepts images according to the hosted catalog. Before this change, the picker showed it as 128k text-only and requests were capped at 32,768 output tokens.

## User Impact

Live-listed models now get the hosted catalog's context window, output limit, input modalities, reasoning/compat data and price. This reaches the picker, `models list`, run-time model resolution, compaction limits and request `max_tokens`. The account listing still decides which models exist. A catalog row the account does not list stays hidden, and a listed ID with no catalog row keeps its discovered values. Stored catalog rows are unchanged.

## Why This Change Was Made

The planner already merges bundled and hosted rows correctly (`planEffectiveModelCatalogRows`). The prepared catalog then drops planned rows for runtime/refreshable providers on purpose (#143837): a manifest row must not publish a model the account does not list. The live projection is left to fill in the details for a listed ID, but it only searches the plugin's own static rows.

This change does not add a second merge. `ModelRegistry`, when it reads a generated (live-listed) provider catalog, describes each listed ID with that planner's effective row. The catalog value wins field by field, and a discovered value fills only what the catalog omits. The row keeps its ID, its route and a declared non-chat kind.

<details><summary>Single-owner trace: every consumer reads the registry rows</summary>

- **Picker / `models list`:** `buildModelsListResult` reads the published snapshot from `prepareFullCatalogFacts` (`src/agents/prepared-model-runtime.full-catalog.ts`). It passes `templateModelRegistry.getAll()` (`ModelRegistry`) as `models` into `buildPreparedModelCatalogSnapshot`, whose `dynamicManifestKeys` filter (`src/agents/model-catalog.ts`) still drops the planned rows, so registry rows are the only source for these providers.
- **Run-time resolution:** `resolveModelAsync` → `resolveExplicitModelWithRegistry` (`model.registry-resolution.ts`) reads `preparedCatalogModel ?? modelRegistry.find(...)`. `preparedCatalogModel` comes from `completeConfiguredRuntimeModels`, which resolves through the same registry.
- **Context window / compaction:** `src/agents/context.ts` projects `owner.modelCatalog.entries`, the registry-derived snapshot above, and the resolved model's `contextWindow`.
- **Request max tokens:** taken from the resolved runtime model (above). The captured request moves from 32768 to about 1M for Kimi-K3.
- **Usage cost:** `withResolvedPricing` → `resolveModelCostConfig` and the Gateway usage paths (`captureModelCostPricing`) price through `prepareModelPricingContext`. That pricing owner already reads the same planner plus hosted prices, so turn cost was already correct for these rows on main (measured below). The registry row now carries the same price, so the two agree. No change was made to the pricing owner.
- **Persistence:** `models-config.plan.ts` keeps the plain admission filter (`filterGeneratedPluginModelCatalogProviders`), so stored generated rows stay as discovered and the description is applied at read time only.

</details>

+/**
+ * Admits generated providers the catalog plugin still owns, then describes their listed models
+ * with the effective catalog rows (bundled plus hosted). Read-time only: callers that persist
+ * generated rows use the plain admission filter so stored rows stay as discovered.
+ *
+ * The account listing alone decides which models exist: an unlisted catalog row is never added,
+ * and a listed ID without a catalog row keeps its discovered values. For a listed ID with a catalog
+ * row, the catalog owns the metadata field by field. Generated rows carry no marker separating a
+ * provider-reported value from a discovery default (128k context, a $0 cost placeholder), so this
+ * applies the rule live discovery already applies to a plugin's own static rows: the catalog value
+ * wins and a discovered value fills only what the catalog omits. The row keeps its ID, route and a
+ * declared non-chat kind.
+ */
+export function readGeneratedPluginModelCatalogProviders<
+  T extends { models?: readonly { id: string; cost?: unknown; inference?: { chat?: boolean } }[] },
+>(params: Parameters<typeof filterGeneratedPluginModelCatalogProviders<T>>[0]): Record<string, T> {
+  const providers = filterGeneratedPluginModelCatalogProviders(params);
+  const plugin = params.pluginMetadataSnapshot?.manifestRegistry?.plugins.find(
+    (candidate) => candidate.id === params.catalogPluginId,
+  );
+  if (!plugin?.modelCatalog?.providers) {
+    return providers;
+  }
+  return Object.fromEntries(
+    Object.entries(providers).map(([providerKey, provider]) => {
+      if (!provider.models?.length) {
+        return [providerKey, provider];
+      }
+      const providerId = normalizeProviderId(providerKey);
+      const rows = planEffectiveModelCatalogRows({
+        registry: { plugins: [plugin] },
+        config: params.config ?? {},
+        providerFilter: providerId,
+      }).rows.filter((row) => row.provider === providerId);
+      const catalogRows = new Map(rows.map((row) => [row.id, row]));
+      const catalogModels = new Map(
+        buildEffectiveManifestProviderConfig(rows)?.models.map((model) => [model.id, model]),
+      );
+      const models = provider.models.map((model) => {
+        const row = catalogRows.get(model.id);
+        const catalogModel = catalogModels.get(model.id);
+        if (!row || !catalogModel) {
+          return model;
+        }
+        const { api: _api, baseUrl: _baseUrl, headers: _headers, ...metadata } = catalogModel;
+        const { inference: discoveredInference, ...discovered } = model;
+        // A declared non-chat kind is listing evidence; weak "unlikely" evidence yields to the row.
+        const inference = discoveredInference?.chat === false ? discoveredInference : row.inference;
+        return {
+          ...discovered,
+          ...metadata,
+          ...(row.cost ? {} : { cost: model.cost }),
+          ...(inference ? { inference } : {}),
+        };
+      });
+      return [providerKey, { ...provider, models }];
+    }),
+  );
