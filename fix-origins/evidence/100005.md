* fix(gateway): operator Stop misses OpenAI-compatible HTTP runs before the runner starts

A session Stop (chat.abort { sessionKey }, sessions.abort { key }) reached
controller-less runs only through the embedded run handle, which the runner
registers just before the provider call. In the seconds before that, while
sessions.list already showed the run as active, Stop found no owner and the
HTTP request ran on to the provider.

agentCommandInternal already reserves a session-work admission before it is
projected active and holds it until cleanup. The admission now declares its
exact run, a targeted capture interrupts only that run after revalidating the
live admission, and the shared Stop plan credits it only on the owner's

sessions.abort, lifecycle drain). Apply the same gate to admitted runs so a
chat.send interrupt, worker placement cancel, or queued-collector Stop keeps
leaving them alone, and move the admitted-run cases into their own test file.

* test(gateway): prove admitted-run Stop authority boundaries

* fix(agents): retain first command cancellation reason on Node 24

## Fix PR #168359 description (by steipete, opened 2026-10-10T09:08:12Z)

```text
Related: #168080 (follow-up to its "Not covered" note)

## What Problem This Solves

Fixes: operator Stop (`chat.abort { sessionKey }`, TUI Esc, `sessions.abort { key }`) does nothing when it arrives in the first seconds of an OpenAI-compatible HTTP run, even though `sessions.list` already shows the session as running. The request goes on to the provider and the HTTP client gets a normal answer later.

## User Impact

User impact: Stop now stops a run started without a Gateway chat controller, such as `POST /v1/chat/completions` or `POST /v1/responses`, from the moment it is admitted, including while it is still queued for its session. The waiting HTTP request ends right away with `500 "agent run was cancelled"` and the provider is never called. `chat.abort` returns the run id in `runIds`, and `sessions.abort` returns it as `abortedRunId`.

## Why This Change Was Made

#168080 made the shared session Stop plan stop controller-less runs, but only through the embedded run handle. The runner registers that handle just before it calls the provider, yet the run is already admitted and shown as active well before then. On a loaded host the gap measured 0.6 to 12 s. A Stop in that window found no owner: live, `chat.abort` answered `aborted: false, runIds: []` and `sessions.abort` answered `no-active-run`.

The command already holds the right owner for that window. `agentCommandInternal` reserves a session-work admission before it waits and before the run registry projects it, and keeps it until cleanup. That admission's interrupt already aborts the command's lifecycle controller.

This change lets the admission declare which run it belongs to. The shared Stop plan then uses a targeted capture to interrupt exactly that run, and credits the stop only when the owner returns its `{ runId }` receipt. The Gateway `agent` RPC admission already follows that receipt contract. Right before the side effect, the capture rechecks that the admission is still live, not already interrupted, and in the current lifecycle generation, so a delayed Stop cannot land on a released or replacement run. Run liveness stays with the agent-run registry; no abort handles were added there or to the embedded run registry.

The existing selection rules carry over:
- The embedded handle stays the preferred owner once it exists.
- Controller-backed runs stop only through their controller.
- Narrow `operator.sessions.write` callers only reach their admitted incarnation.
- Internal and subagent-coordination runs stay hidden, using the same visibility fact the run registry uses.
- Exact-`runId` and `global` requests never take this path.
- Like the embedded stop, the admitted-run stop only runs for callers that opt in with `stopEmbeddedRun` (`chat.abort`, `sessions.abort`, archive/delete drain). The `chat.send` `/stop` pre-admission path, worker placement cancel, and queued-collector Stop leave these runs alone, as they do on `main` today.

Three read-only admission queries moved unchanged into the existing queries module to keep `session-lifecycle-admission.ts` under its line cap.

Release-note context: user-visible fix to session Stop for OpenAI-compatible HTTP and other controller-less runs while they are admitted or queued, before the runner starts.
