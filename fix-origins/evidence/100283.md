## Fix PR #165426 description (by shakkernerd, opened 2026-10-05T07:44:00Z)

```text
Fixes #165315

## What Problem This Solves

In the Control UI chat, a finished code-mode step whose nested tool calls are all routine loses its title once the run settles. The row that named the step while it ran no longer says which step it was.

In code mode an agent works in titled steps. Each step is an `exec` call whose script can call other tools, and while a step runs its row in the transcript shows the step's title. Once the run settles, the Gateway summarizes a step by the operations recorded inside it, so a step that read a file reads as "1 read" instead of counting the step and the read. Routine calls inside a step, such as plan and progress-card updates, process polls and waits, are deliberately kept out of those summaries.

#165315 reported what happens when a step's only recorded call is routine: the step was replaced by its contents, its contents were hidden, and the row fell back to **Raw details**. Two things were wrong there. The step was counted as nothing, and its row lost the step's title. The issue asks for both to hold: "The settled step stays identifiable and counted."

#165358 landed first and closed the issue, but it resolved only half of it, and in a narrower way than the issue calls for. It keeps such a step counted, so the row on `main` now reads **1 command**. It deliberately kept the counted row, so the step is still not identifiable, and its rule decides from a step's direct children only. This PR corrects both.

**The step is still not identifiable.** What `main` shows today:

- The collapsed row reads **1 command**. Opening it reveals exactly one row, the titled step, still closed. Opening that reveals the progress update and **Tool input**. The count is a wrapper around a single row, and the contents sit two clicks away.
- The same step with no nested call at all already renders as its own titled row, because one tool card is never grouped. Adding a quiet plan update to a step therefore changes its settled row from the step's title to **1 command**.

People see this wherever a turn's rows stay exposed, most often after a handoff that waits for subagents and so ends without a final answer, and inside an opened **Worked for …** rollup.

**The counting rule looks one level down.** A step is replaced by its contents when one of its direct children is recorded and visible. When none of them is, but a call further down is visible, the step is kept and that call is counted too, so the workflow is counted next to its own contents. That is the double count these summaries exist to avoid. I have not found a tool that records this shape today, so this part corrects the rule rather than something people currently see.

## User Impact

Settled activity that consists of exactly one successfully completed step, with every other call nested under it and all of those calls routine, now shows that step's own titled row. One click opens it and shows the routine calls and **Tool input** directly underneath. This is the row a step with no nested calls already gets.

Counting changes in one case only: a completed step is no longer counted alongside a visible call nested deeper inside it, when none of the step's direct children is itself recorded and visible. Every other shape, including the reported one, is counted exactly as on `main`, and the existing test for the reported shape passes unchanged.

Behavior that stays the same:

- A step with at least one visible nested call is still summarized by those calls.
- A step whose recorded calls are all routine stays counted as one operation, and **Worked for …** still reports it as one tool call.
- A step that failed, was blocked or has no recorded outcome keeps the counted row, because that row carries the status ("1 command", "1 failed").
- A nested call that is still active when a run settles has no recorded outcome yet and does not by itself stand in for its step, as on `main`.
- Activity with several operations still reads as counts.
- Steps that went through an approval review keep the counted row with its review status.
- The live row keeps showing the running step's purpose until the run settles.
- Rows with no prepared activity at all still read **Raw details**.

The counting rule is shared: history projection and live run settlement both use it, and channel progress, the terminal UI and the native apps read the same prepared activity. For the shapes tools record today they receive what they receive on `main`. I have not checked those clients visually.

There is no configuration, protocol or schema change, and nothing stored changes. History activity is prepared when a client reads it, so existing sessions show the new row after the update without a migration.

One thing behaves differently for people who use `/verbose full`: tool rows open automatically there, so a lone step now opens itself, where the counted row stayed closed. Its nested calls stay inside the same bounded, scrollable area as before.

## Why This Change Was Made

**Gateway: one rule that follows nesting.** `resolveCompletedActivityWrappers` in `src/agents/agent-activity-presentation.ts` decides which completed steps are replaced by their contents. The version on `main` asks whether a direct child is recorded and visible. This PR replaces that check with one that evaluates steps children first: a completed step is replaced only when a recorded call anywhere beneath it stays visible to stand for it. A nested step that is kept for its own routine calls therefore stands for the step above it, and so does a visible call under a hidden one, and in every case exactly one operation represents the work. What the rule on `main` already does is kept: a step whose recorded calls are all routine stays the operation, and a call with no recorded outcome does not by itself stand for its step.

**Control UI: one settled step is drawn as that step.** The transcript groups any activity with more than one tool message or card into a counted disclosure. A step with one nested routine call has two cards, the step and the call, so it is grouped even though only one operation is visible. That is why a single operation ends up behind a count.

`renderActivityGroup` in `ui/src/pages/chat/components/chat-message-group.ts` now recognizes that shape and renders the step's own row, with the nested calls beneath it, instead of the counted summary. It does so inside the existing activity container, so the bounded scroll for opened activity and the file-link owner apply unchanged. The condition is deliberately narrow, and each part of it maps to a behavior kept above:

- the activity is not the live one;
- it has a single root card with nested calls;
- that step is the only visible prepared operation, and its prepared status is completed;
- no approval review is attached.

Everything else falls through to the counted row exactly as before.

The stylesheet change follows from the new shape. Rows inside an opened counted disclosure hide their chevrons until hover, because the disclosure above them is the control. A lone step is its own disclosure, so its chevron stays visible and only the rows beneath it hide theirs.

One move in the diff is unrelated to the behavior. `chat-message-group.ts` has 688 counted lines on `main` against the repository's cap of 700, and this change alone would have taken it to 711. The counted row's review-status badge therefore moves, unchanged, into `chat-tool-outcome-summary.ts`, the module that already renders that row's failed and skipped badges, which leaves the file at 690.

Two alternatives to the titled row were considered. Putting the step's title into the counted row's label would keep both levels and show the same title twice, once on the count and once on the row inside it. Leaving the count as it is keeps the extra click and the inconsistency with a step that has no nested calls.

`docs/web/control-ui/chat.md` now describes both the counting rule and this row.
```
