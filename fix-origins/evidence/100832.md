```text
Refs #157167. Thanks @PennyVibe for the Ubuntu 20.04 reproduction.

## What Problem This Solves

Update failure reports hide a native addon's missing GLIBC requirement when the loader message follows a worker error or contains private paths.

## User Impact

Reports retain a bounded numeric diagnosis such as `GLIBC_2.33 not found`, while paths, token text, and custom version labels remain redacted. This is diagnostic repair, not a claim that an already-installed 2026.9.5 updater can complete its first upgrade hop. No dependencies, native modes, configuration, or filesystem safety guarantees change.

## Why This Change Was Made

The failure-fact owner keeps one diagnostic line, and public reports redact filesystem paths. A loader cause on a later line or after `/lib/...` therefore disappears before report formatting. Extract only the exact numeric missing-GLIBC fact before those existing boundaries, then admit that fixed fact in the public projection.

The ABI and snapshot-copy repairs are already on main: fs-safe 0.20.0 targets glibc 2.28 (#158640), and #154354 uses guarded portable create-only plugin copying instead of a native-only no-replace move. SQLite integrity/content checks remain owned by the snapshot implementation. [fs-safe #709](https://github.com/openclaw/fs-safe/pull/709) separately fixes its move boundary to preserve the original loader cause; it needs a release before consumers can receive that improvement.

The unchanged published 2026.9.5 driver launches its own snapshot worker and fs-safe 0.13.1 before candidate code executes. A newer candidate dependency alone cannot repair that driver. The issue remains open for that first-hop limitation; this PR deliberately uses `Refs`.
```
