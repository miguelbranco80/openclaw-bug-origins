## Fix PR #201163 description (by roboclaw-bot, opened 2026-11-18T11:49:19Z)

```text
## What Problem This Solves

In mobile web chat, tapping the message box can open the keyboard and immediately dismiss it. It can take several taps to start typing.

## User Impact

One tap should keep the message box focused and ready for a reply, even if the keyboard moves the composer before the finger lifts.

## Why This Change Was Made

Chrome can finish the tap on the element now beneath the finger. The composer already discarded that element’s click, but the preceding mouse-down could take focus first. The same gesture guard now prevents that focus transfer without canceling taps within the editor.

## Evidence

A Chromium touch regression uses the actual chat UI with a synthetic Gateway. It supplies the keyboard viewport change between finger-down and finger-up, then checks focus **before** typing. The regression fails on `e25ad96fb3d6` and passes on `43fc07d1c754`; all five composer pointer tests pass on the fix. [Before video](https://github.com/user-attachments/assets/15a0260f-2d0e-489a-a077-3967ae34563c) · [After video](https://github.com/user-attachments/assets/74b08028-b2e3-40c1-b169-f550de5a14aa). These are Chromium recordings with a simulated keyboard viewport, not Android screen recordings. The Android emulator booted, but repeated system/launcher “not responding” dialogs prevented a usable native Chrome capture.

Reported by @VACInc.
```
