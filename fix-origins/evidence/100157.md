## What Problem This Solves

Fixes: a scheduled automation's runtime is decided at run time from whatever runtime override its cron session copies, not from what the job was created with. A job created from a conversation that runs Claude through `claude-cli` was bound to an account chosen for the embedded runtime, then ran on the CLI. On 2026-10-20, before #180492, that failed twice with "Automation candidate is incompatible with its recorded inference account and route". Since #180492, a forwarding CLI accepts the account, but the runtime still follows the copied override on each run. The error also didn't say which account or runtime was involved.

A related failure on 2026-10-25: an hourly automation with no recorded account failed 10 times in a row after the default model moved to a provider with a stored profile. The message ("Automation has no recorded inference account…") named neither the account nor the runtime, so it was unclear what to record.

## User Impact

User impact: new automations record the runtime they will run on next to their account, and every run executes on that runtime. **The account is unchanged:** capture binds exactly the account it bound before this PR, so nothing changes who pays for a run. A job created from a `claude-cli` conversation records that account with `runtime: "claude-cli"`, and claude-cli keeps receiving it, as #180492 does today. A job bound for the embedded runtime stays embedded, even if its cron session later copies a different runtime override.

- Errors name what's wrong. A bound job whose account was removed fails with `Automation inference account <profile> on runtime <runtime> was removed or signed out…`. A job with no recorded account fails with `…Runtime <runtime> would run <provider/model> with stored account <profile>. Record the account with openclaw automations edit <jobId> --model <provider/model>@<profile>, or with openclaw doctor --fix.`
- Doctor's existing account-adoption warning now also says the job's runs are refused until it records the account.
- Existing jobs are not migrated. Bindings recorded before this change have no runtime and keep today's resolution, and their errors say `(no recorded runtime)`. Older Gateways ignore the extra field, so a downgrade keeps working.

## Why This Change Was Made

Phase 5 of the scheduled-run execution context (design: "One tuple, one resolver"):
- **One resolver.** `resolveCronCandidateExecution` decides a candidate's runtime and execution route. It's shared by inference capture and every scheduled-run candidate, so the two can't disagree for the same inputs.
- **Capture records the tuple.** Account selection is unchanged from main. Capture adds the runtime, resolved from the same entry the cron session will copy: the target row for `session:` jobs, or the runtime the creating conversation carries for `current` jobs. That carry rule is extracted from `isolated-agent/session.ts` unchanged, so both sides use one rule. Capture stores the result as `runtime` on the binding.
- **Runs use the captured runtime.** On detached runs and on `session:` jobs (the shared reply path), run preparation, harness selection and candidate dispatch read the binding's runtime instead of the session's override.
- **Account edits keep the runtime.** `automations edit --model <ref>@<profile>` records the new account with the job's existing runtime. If that runtime is no longer available for the same provider, the edit is rejected and the stored binding stays unchanged, so an edit never silently moves a job to another runtime. An edit to an unbound or legacy job resolves the runtime the same way create does.
- **One drift guard.** `assertCandidate` refuses a candidate whose provider or runtime differs from the binding, naming both. The unrecorded-account refusal now has one helper, shared by the embedded auth plan, the cron CLI path, the reply-path CLI candidate and CLI preparation.

Deferred to openclaw-84c: Codex app authority (row N1) still reads `trigger` and `scheduledRuntimeAuthority`. Moving it to `ScheduledExecutionFacts` needs the same plugin SDK harness facts contract as rows 41/43. Behavior is the same either way.
