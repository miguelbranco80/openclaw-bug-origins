## Fix PR #203688 description (by roboclaw-bot, opened 2026-11-22T20:48:15Z)

```text
## What Problem This Solves

When someone presses Play on a QuickTime recording in chat, OpenClaw can re-encode the whole clip even when the video and audio are already browser-compatible. The inline player waits for polling and shows “Preparing playback…” before it knows whether the file needs more time.

## User Impact

User impact: Compatible MOV attachments can start playing inline sooner without losing quality or changing the original download. Recordings that still need a full conversion retain the existing fallback.

## Why This Change Was Made

Copy compatible streams into a streamable MP4 first and give the first playback check up to 500 ms to pick up the result. Reuse the same job across requests and fall back to encoding if the copy fails. The inline player shows preparation only after the server reports the rendition is still pending; audio and the lightbox keep their existing loading behavior.

## Evidence

- In a Chromium replay with a synthetic 7.77-second H.264/AAC MOV, a mock Gateway, and the real conversion code, playback started in 2.3 s on a patched run versus 8.1 s on the deployed baseline. The patched first check returned ready on that run; the playback copy preserved the original 1842 × 1200 resolution. This is a fixture replay, not a production benchmark or a guarantee that every remux finishes within 500 ms.
- 45 focused media, staging, and Gateway tests and 33 focused video/audio player tests passed. One conversion pipeline still owns staging, validation, caching, and fallback; the patch adds 94 net lines including 60 lines of regression tests. The UI bundle built, but its size and boot-request budget checks reported violations. Full CI and independent review are not claimed.
- [Clean and annotated before/after screenshots](https://github.com/openclaw/openclaw/pull/203688#issuecomment-7085562813). The before image uses the deployed baseline, not a fresh build of `main`.
```
