## Fix message body

```text
Three Slack live QA harness defects made curated scenarios unreliable: the mock directive parser no longer matched the fixtures' printf/sleep command, so progress scenarios returned final-only replies; curated scenarios sent through the raw driver client without registering receipts, so driver, progress and final messages were left behind; and the cached debug-capture reader went stale after a Gateway restart, failing final capture with STATE_DATABASE_READ_ADMISSION_INVALIDATED. The mock matches the current command, every scenario write (driver, commentary, tool summary and output, final) is registered with the native cleanup owner even on assertion failure, and the capture reader follows the Gateway lifetime. QA harness only; found by our Slack bug hunt.

Co-authored-by: Ayaan Zaidi <hi@obviy.us>
```

## Fix PR #168507 description (by obviyus, opened 2026-10-10T15:53:17Z)

```text
## What Problem This Solves

Fixes false progress failures and incomplete message cleanup when running Slack QA scenarios, including after a Gateway restart.

## User Impact

No production behavior changes. Slack QA operators get accurate progress assertions and cleanup of their owned driver messages and correlated SUT replies, even when an assertion fails.

## Why This Change Was Made

- Match the current progress fixture command, including Slack's escaped redirection character, instead of the retired `grep` command.
- Use the existing native receipt owner for scenario sends and matched replies before running assertions.
- Acquire current database read admission for capture operations instead of retaining admission across Gateway restarts.

## Evidence

Real Slack/Gateway transport with the deterministic mock provider:

- Before: all five curated progress scenarios failed with final-only replies and empty owned-message receipts.
- After: all five passed their existing commentary, tool-progress, output and deduplication assertions. The follow-up cleanup repair was then proven on the full-verbose scenario: all five messages (driver, commentary, tool summary, tool output and final reply) were recorded by the native owner, deleted automatically and verified absent.
- An intentionally failing scenario retained both driver and SUT receipts, deleted both, and verified both absent.
- The restart scenario passed, finished capture without an admission-invalidated error, and deleted all five owned messages with absence readback.
- A separate real-provider Slack canary passed with `openai/gpt-5-mini`, low reasoning, and verified cleanup.

Focused regression tests: the initial 28-test selection passed, followed by 37 passing owner/adapter/runtime tests on the latest head (6.88 seconds including the test runner). The new real-owner composition fails on the prior head with the three standalone progress messages left behind, and passes with the repair while preserving unrelated messages. Extension typecheck, formatting and the private QA runtime build passed. Live proof used isolated Docker state and a single leased bot pair; credentials were removed and the lease released. Earlier diagnostic leftovers were recovered from exact captured receipts; the latest full-verbose run needed no manual cleanup.

Merge danger: two-way door. Reverting restores the previous QA harness behavior; no schema or persisted configuration changes. The blast radius is the Slack QA adapter and the mock provider's Slack progress protocol, not production Slack delivery.
```
