## Fix message body

```text
The Tlon channel's Urbit SSE client split events only on LF and read a single data line, so legal events that used CRLF or CR line endings, or carried multiple data lines, were silently dropped while the connection stayed open. The parser now follows the SSE spec: LF, CRLF and CR line endings, and multiple data lines joined with a newline. Single-line LF events parse as before. Proof: an isolated Gateway with the real Tlon channel against loopback Urbit login, scry, SSE, poke and ack endpoints, and a recording model provider. On main only the LF single-line control reached the agent; with the PR all six LF/CRLF/CR single-line and multi-line cases arrived exactly once and in order, and both kept one open SSE connection. Thanks @ly85206559.

Co-authored-by: Ayaan Zaidi <hi@obviy.us>
```

Fixes: Tlon can keep an SSE connection open while silently missing events when the stream uses legal CRLF/CR line endings or multiple `data` lines.

Tlon delivers those events to its subscriptions and acknowledges handled events. Existing LF streams, bounded buffering, failed-handler replay, reconnect, and shutdown behavior remain in the same owner. No configuration change is required.

Handle the line endings and data-field joining defined by the [SSE parsing contract](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream). - normal SSE events are still delivered through the stream path;
- an unterminated stream that would grow beyond 16 MiB is rejected before
  unbounded accumulation;
- a single SSE payload above 16 MiB is rejected before JSON.parse.

The script passes on this branch and fails 2/3 assertions when run against
origin/main's sse-client.ts, providing the before/after proof ClawSweeper
requested.

single oversized chunk never lands in the pending buffer. The old

this hardening is meant to prevent.

Add a single-oversized-chunk test to prove the guard fires before
the chunk is concatenated into the pending buffer.
