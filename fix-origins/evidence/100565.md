## Fix message body

```text
fix(mcp): don't cancel relayed runs after the 15-second submit timeout

MCP relay submissions kept their 15-second AbortSignal after the Gateway had returned a successful run ID, so replies that ran longer than 15 seconds were cancelled even while they kept making progress and the client request was fine. The 15-second guard now covers only the submission itself; an accepted run continues until it finishes, and disconnects and revoked grants still stop it.

Evidence: real MCP SDK HTTP client through the relay to the shipped plugin (normal pairing and grant), with a provider fixture streaming steady progress for about 30 seconds, in new and existing conversations. On main the runs aborted at about 15.1 to 15.4 s (twice each); with this change they keep running past 18 s and complete in about 32 s with the full reply and 31 progress events (twice each). Short runs, revoked grants and disconnects behave as before, and a submission that is never accepted still times out at 15 s. A live gpt-5.4-mini run passes. Production +7/-1.

Thanks @crwohlfeil.

Co-authored-by: Ayaan Zaidi <hi@obviy.us>
```

## What Problem This Solves

MCP relay submissions leave their 15-second request deadline armed after returning a successful conversation/run ID. The accepted run retains that signal, so a reply that keeps making progress can be cancelled near 15 seconds even when the MCP client requests a longer observation window and remains connected.

## Changes

Use the existing clearable SDK timeout helper in the relay's request wrapper and clean up the deadline when that RPC settles. The original 15-second deadline still bounds a request that has not returned acceptance. `agent.wait` retains its separate observation timeout, and grant revocation/relay disconnect still cancel owned work.

@crwohlfeil's commit and regressions are retained. Whole-diff simplification keeps the one existing request owner rather than adding another lifecycle abstraction: production **+7/-1**, tests **+70/-1**. No SDK export/type, configuration, scope, grant, or storage-policy change.

## Evidence

Built main `a6067465a8a281270d74a3183df3103b6158b72e` and candidate `59232c876d2bd35b5e5885320fbe1622907f8a98` on Node 24.22.1 in isolated Docker state.

No private grant table or principal-bound Gateway request helper is substituted.

The local OpenAI-compatible Responses endpoint sends visible text approximately once per second for 30 seconds. There is no held tool, exec timer, silent provider pause, or system-clock change.
