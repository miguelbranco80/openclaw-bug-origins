## What Problem This Solves

Fixes an issue where users updating an installation with Policy `requireExplicitRateLimit` would have candidate validation refused even though `gateway.auth.rateLimit` was configured. The rehearsal replaced the entire auth object, so its own synthetic configuration triggered `policy/gateway-rate-limit-missing`.

Reported by @jj5638521 (#146017).

## Why This Change Was Made

The isolated-config builder now starts with the existing auth object and overrides the isolated authentication fields: token mode, a fresh temporary token, no password, and no Tailscale identity authentication. The strict auth schema has only two secret fields, token and password; both are replaced or removed. This preserves rate limits, identity scopes, and trusted-proxy metadata without maintaining a second list of non-secret fields. Explicitly disabling `allowTailscale` matters because it overrides the default derived from `tailscale.mode`, even when that mode is off.

Gateway binding remains loopback, with the rehearsal's allocated port, TLS disabled, and Tailscale/Control UI disabled. Production configuration is unchanged. Production code grows by six lines to preserve the auth object and keep the credential and alternate-auth overrides explicit.

## User Impact

Candidate rehearsal keeps policy-observed Gateway auth settings such as `rateLimit`, so policy lint no longer refuses updates because the rehearsal discarded them.

**First-hop limitation:** the already-installed 2026.9.3/2026.9.4 driver runs its own rehearsal builder, so that hop may still trip the Policy lint until the corrective release is installed once. This change protects subsequent updates initiated by a driver containing the fix. Published-driver × candidate recovery remains separate work and is not claimed by this PR.
