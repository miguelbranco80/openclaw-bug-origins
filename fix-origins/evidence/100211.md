## Fix PR #181286 description (by steipete, opened 2026-10-23T03:43:37Z)

```text
## What Problem This Solves

Fixes: in a new chat, pressing Enter (or Start) in the first moments after the composer appears can do nothing at all — the text stays in the box, the Start button still looks enabled, and no message, error, or explanation appears — while the page is still restoring the last session setup or refreshing agent defaults.

## User Impact

User impact: while a new chat is not ready to start, the Start button is visibly disabled; if you press Enter or Start (or paste and press Enter) during that moment, the reason appears below the composer ("Restoring your last session setup…" or "Refreshing agent defaults…") and stays until the chat is ready. The text stays editable, and Enter or Start then sends it. Opening a new chat without trying to send shows no notice and no layout shift. A submit attempt never silently disappears.

## Why This Change Was Made

The new-session submit owner already rejects a start while agent defaults or saved model preferences are being prepared, but its explanation was bound to the single rejected attempt and vanished as soon as that gate changed or cleared, and the composer exempted reasoned gates from native disabling, so Start kept its enabled look. Start now uses native disabling with the existing muted style for as long as a gate applies. A submit attempt during that window records that feedback is owed; the composer then shows the current gate's reason (following gate changes) until readiness, below and aligned with the composer but outside its measured box, so the composer does not move. The command palette keeps readiness out of its creation-error channel. The attempt-bound tracker, its terminal notification callback, and the special blocked-button styling are removed. No queueing, protocol, config, persistence, or cancellation change.

## Evidence

- Live, real Gateway with a built-in and a Codex agent: opening a new chat and pressing Enter immediately after the composer appeared dropped the message 4 of 4 times on `main` with no explanation in 3 of 4 and an enabled-looking Start in 2 of 4; with this change all 4 showed the reason ("Restoring your last session setup…" / "Refreshing agent defaults…") with Start disabled, and the next Enter sent each message. Earlier timing probe on `main`: the Codex agent dropped Enter at 0 ms and 300 ms after the composer appeared and accepted it from 600 ms.
- Browser regression (`ui/src/e2e/new-session-page.early-submit.e2e.test.ts`, mocked Gateway holding `agents.list` / `models.list`): real composer, native paste+Enter and Start click during the blocked window; checks the visible reason, preserved text, zero accidental sessions, then exactly one creation with the exact message after release. Fails on the original production code (no explanation), passes with the fix; together with the new-session draft-handoff, config/startup and model-catalog e2e files and the palette cases, 24 browser cases pass (51 across the broader UI e2e run). Unit: 222 passed across the composer, submit gates, native terminal start, command palette, and submission flow. The prior-production control fails all four early-submit cases.
- `pnpm tsgo:ui`, oxlint, stylelint, oxfmt, `git diff --check` pass. Autoreview (Codex): scoped-clean, no actionable findings.
- Review/CI follow-ups: an always-visible notice shifted the composer on every open (model-catalog layout e2e) and leaked into the palette error channel; the notice is now attempt-triggered, aligned, and outside the measured composer, and the layout e2e passes unchanged.
```
