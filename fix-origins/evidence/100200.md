Prerequisite for #166311.

## What Problem This Solves

Fixes: without a running Gateway, `openclaw models list --refresh` lists every configured `anthropic/*` model that runs through Claude CLI as unavailable, even when Claude Code is logged in. Only the default row is left (unavailable); the usable models show up only as their `claude-cli/*` copies.

## User Impact

After `openclaw onboard --auth-choice anthropic-cli`, `openclaw models list --refresh` without a Gateway now lists the configured Claude models as available on Claude CLI, the same as the Gateway picker. Gateway output doesn't change.

## Why This Change Was Made

A prepared model-catalog owner carries its own plugin registry, and that registry can differ from the process's active one. The standalone `openclaw models list` and the embedded TUI use a temporary owner, and Gateway owners belong to a workspace generation. `prepareModelsListResult` already passes `owner.pluginRegistry` to some calls, but CLI backend bindings, Claude CLI auth evaluation and runtime choices still read the ambient registry (for example `listCliRuntimeModelBackendBindings()` in `model-catalog-decisions.ts`). The standalone command's active registry has no CLI backends. So `anthropic/*` rows pinned to `claude-cli` fail auth, and the default view drops 9 of the 10.

`prepareModelsListResult` now resolves the owner first (`resolveModelsListOwner`), then runs preparation inside `withPluginRuntimeRegistryScope(owner.pluginRegistry, …)`, the helper the row projection already uses for worker placement. Reads stay pure projections of the prepared facts and never enter a plugin scope, keeping #162326's published-read invariant (`models.prepared.test.ts`); the existing per-row worker-placement scope is kept as is. The one read-time plugin fact, the CLI backend bindings behind picker runtime choices, is now resolved once from the decisions owner's `pluginRegistry` in `createModelCatalogDecisions` instead of from the ambient registry on every read. The scoped preparation covers every `prepareModelsListResult` caller: the Gateway handler, `chat.metadata`, the standalone CLI, the TUI and the preloaded projector. Not covered and unchanged: uncached runtime-choice auth evaluations (`model-auth-availability.ts`) and `chat-metadata-session-projection.ts` projecting its preloaded catalog before preparation still read the ambient registry; the tests here don't claim those paths. Owner resolution moved unchanged into `models-list-result.owner.ts`, because `models-list-result.ts` is at the repository line cap.

One existing runtime-choices case changed its fixture: `picker-fixture` + generic harness `picker-native` → `picker-fixture` + `codex`. The old case only came out `unsupported-runtime` because the registered fixture harness was invisible to ambient-registry lookups. A registered generic harness is compatible with any provider, while `codex` explicitly rejects non-OpenAI providers (`session-runtime-compat.ts`), so the case still asserts "registered harness, incompatible provider → `unsupported-runtime`".

#166311 (one picker row per Claude CLI model) depends on this. Its twin collapse has to read CLI backends from the same registry as availability.

- A standalone list runs `claude auth status --json` three times (`extensions/anthropic/cli-auth-seam.ts`, 3 s timeout). If the second probe times out, it counts as unreadable, so every Claude row is unavailable.

- On a Gateway, #166305's background recheck corrects a timed-out probe within a minute.

Known and unchanged: the read-only `openclaw models list` (no `--refresh`, no Gateway) reads a cached owner that has no plugin registry. It still shows the single unavailable default row.
