## Fix message body

```text
## What Problem This Solves

Fixes: after a Gateway restart on a new build (or after a model catalog or pricing config update), the Usage page takes minutes to load and shows "Partial results" with a total far below the real one. Each cached usage rollup stores the pricing fingerprint it was built with: a hash of every price source (bundled catalog rows, hosted catalog, `models.providers` costs, plugin pricing policies). Any change to any of them, even for a model no transcript uses, rejects every rollup, and the first Usage read rescans every transcript in the range. On one large Gateway, a restart onto a build with no pricing-code changes rejected all 13,253 rollups in a 30-day range; while they rebuilt, the page showed about 5% of the real cost.

## User Impact

User impact: a restart, update or catalog refresh no longer forces a full usage rebuild. Sessions whose turns all recorded their own cost (nearly all sessions with current providers) keep their cached totals, so the Usage page stays fast and complete. Only sessions with a turn that has no recorded cost are rescanned, because only their totals can change with a new price.

## Why This Change Was Made

Catalog prices are inputs only for turns that need a cost estimate (`needsUsageCostEstimate`). A rollup with no such turn has the same totals under every price list, so its fingerprint should not depend on prices.

- `usageCostEstimateUsesPricing` (next to `applyUsageCostEstimate`) decides whether a price can change an entry: it can when the entry has tokens, or when it has no recorded cost (then a missing price counts it as missing cost). A zero-token turn with a recorded $0 cost cannot change.
- The rollup scan stores the current fingerprint only when some entry used pricing, and otherwise stores `USAGE_COST_UNPRICED_FINGERPRINT`. An incremental append keeps a priced rollup priced.
- `decodeUsageCostRollupEnvelope`, the only place that compares fingerprints, accepts an unpriced rollup under any fingerprint.

No schema, version or format change. Existing rows keep their real fingerprint until their next rescan, so the first restart after this lands still rebuilds once if the fingerprint moved; after that, pricing changes rescan only priced sessions. An older build reading an unpriced rollup rejects it and rebuilds, as it does today after any pricing change, so rollback works.

## Evidence

- Real Gateway, synthetic state (200 sessions, 34,544 events over 30 days, every turn with a recorded cost). The Gateway built its usage cache; then `openclaw.json` gained a priced model that no transcript uses, and a restarted Gateway answered the Usage overview (`sessions.usage`, `projection: "overview"`) and `usage.cost` until the cache was fresh:

  | Build | Rollups rewritten after the pricing change | Totals after restart |
  |---|---|---|
  | `main` (`80b9e7b71fb2`) | 200 of 200 (fingerprint `b58e3f57` → `5df3be2e`) | exact |
  | this PR | 0 of 200 (all `unpriced`) | exact, cache not refreshed |

  At this size a full rebuild takes seconds; on the large Gateway above it took about six minutes, with partial answers meanwhile.
- Large Gateway, read-only: of 8,229 sessions with usage in 30 days, 8,175 (99.3%) have no turn with tokens and no recorded cost (sampled from uncompressed transcript rows), so nearly all would keep their projection.
- `session-cost-usage-cache.sqlite.test.ts` (new cases, real SQLite cache and worker): a session whose turn recorded its cost stays fresh under a changed fingerprint; a session whose turn needed a catalog estimate is still marked stale. On `main` the first case fails (the session is stale).
- The usage infra and Gateway usage suites pass.
- `tsgo` (core and core tests), core lint and format on the changed files pass. `pnpm check:changed` fails only in wrapper shadowing and the dead export scan, whose entries are all in files outside this diff (current `main`).

Co-authored-by: Ayaan Zaidi <hi@obviy.us>
```
