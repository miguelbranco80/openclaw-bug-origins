## Fix message body

```text
* fix(update): start detached workers from the retained updater runtime after activation

A pnpm updater that a previous OpenClaw update installed runs from its
group's project-local virtual store. Activating the next version moves
that group into the transaction backup, so the running updater's own
`dist` disappears. Work started inside the update loads workers through
the retained-runtime generation, but process-wide owners that start
workers from detached or earlier async contexts (the state lease
heartbeat carrier, the file-log worker pool) still resolved them from the
installed package. Their spawns failed with `Cannot find module`, the
plugin lifecycle lease was lost, and the update unwound as
`update-recovery-pending` while the new Gateway was already serving.

The retained-runtime generation now also registers a process-wide
resolver for as long as it is bound, and `createCpuTrackedWorker`, which
every tracked worker spawn goes through, applies it. Async-context
bindings keep precedence; nothing changes outside an update that
retained its runtime. `WorkerCpuHandle` and `WorkerMemoryMessage` move to
`worker-cpu-types.ts` to keep `worker-cpu.ts` within its line cap.

* fix(update): resolve a captured worker through the retained runtime only once

A worker captured inside the generation was resolved again by the
process-wide resolver at spawn time. The retained-runtime mapping is
idempotent, but a generation's resolver need not be: the heartbeat
generation test's wrapping resolver then imported itself and the worker
never started (Bun shard timeout). A URL the generation already produced
is now final.
```

## Fix PR #203458 description (by fuller-stack-dev, opened 2026-11-22T09:33:04Z)

```text
## What Problem This Solves

Fixes: on a pnpm install, the second update between two releases that both contain this fix-line ends `update-recovery-pending` (exit 1), even though the new version is installed and the Gateway serves it. Afterwards, every further update is refused with "Update <run> has unfinished recovery; reconcile it before starting another update."

## User Impact

User impact: once the updater running the update contains this change, pnpm updates between OpenClaw versions end `ok`, and the run is recorded `succeeded`. npm installs were not affected and are unchanged.

What changes nothing: a pnpm install whose updater is already a release without this change still hits the failure on its own next update, because the installed updater cannot be patched. Users who already hit it on an unfixed build stay blocked, and this PR does not change that. In a real cell, after the failed B → C, every later `openclaw update` (to F1, then F2) was refused within 2 s with "Update <id> has unfinished recovery … It belongs to the installation at <the removed B store path>". `openclaw update repair` exits 1 with "Plugin cohort recovery belongs to a different installation." Settling that stranded record is a separate follow-up at the recovery-admission owner; it is described under "Not proven".

## Why This Change Was Made

**Root cause, proven in a real cell with a resolve/spawn trace.**
- A pnpm package that an earlier OpenClaw update installed lives in its group's project-local virtual store: `global/v11/<group>/node_modules/.pnpm/openclaw@…`. Activating the next version moves that group into the transaction backup, so the running updater's own `dist` disappears.
- Work started inside the update loads workers through the retained-runtime generation, an AsyncLocalStorage binding to a retained copy. Two process-wide owners start workers from detached or earlier async contexts and still resolved them from the installed package:
  - the state lease heartbeat carrier (`runInDetachedAsyncContext`);
  - the file-log worker pool, whose URL was resolved at startup.
- The trace shows `new Worker(…/dist/state/openclaw-state-lease-heartbeat.worker.js)` and `…/dist/logging/logger-file.worker.js` from the removed store, then `ERR_MODULE_NOT_FOUND`. The plugin lifecycle lease was lost ("First failure: plugin lifecycle lease core:plugin-lifecycle/global was lost … Cannot find module"). The command then unwound with the run's own unfinished recovery record.

**Which installs it hits.**
- **First update after the user's own `pnpm add -g`:** passes. That package lives in pnpm's shared `store/v11/links`, which activation does not move.
- **Every later pnpm update:** fails, on pnpm 12 and on 11.28.
- **npm:** passes, because the new package lands at the same path. Those detached workers then silently load the new version's worker files; with this change they load the retained copy, so the code matches.

**Not the cause.** `completeUpdateCommandRun` and `assertNoPendingUpdateRecovery` are not where it fails. CLI runs never get `completionOwner: "gateway-restart"`. The own-record refusal is the unwind's response to a genuine mid-activation failure; it is a consequence, not the cause. The recovery admission rule is unchanged, so an earlier run's unfinished recovery is still refused as today.

**Fix.** While the retained-runtime generation is bound, it also registers a process-wide resolver. `createCpuTrackedWorker`, through which every tracked worker spawn passes, applies it. An async-context binding still takes precedence, and outside an update that retained its runtime nothing changes. A URL the generation has already produced is final, so a worker captured in scope and then spawned is resolved once. The first CI run had shown a Bun-shard timeout in the heartbeat generation test, whose wrapping resolver imported itself when applied twice; the second commit fixes that, with a regression test that fails without it. `WorkerCpuHandle` and `WorkerMemoryMessage` move to `worker-cpu-types.ts` to keep `worker-cpu.ts` within its line cap. No stored field, config or schema changes.
```

```diff
+import { fileURLToPath, pathToFileURL } from "node:url";
+import { resolveGlobalSingleton } from "../shared/global-singleton.js";
+
+/**
+ * The worker-code generation of the whole process, set while an updater retains its running
+ * runtime. Async-context bindings cover work started inside the update; process-wide owners
+ * (state lease heartbeats, the file-log pool) start workers from detached or earlier contexts
+ * and must still load the retained copy once activation has replaced the installed package.
+ */
+const holder = resolveGlobalSingleton(
+  Symbol.for("openclaw.processRuntimeWorkerGeneration"),
+  (): { resolve?: (url: URL) => URL } => ({}),
+);
+
+export function setProcessRuntimeWorkerResolver(resolve: ((url: URL) => URL) | undefined): void {
+  holder.resolve = resolve;
+}
+
+/** Map a worker script to the retained runtime when this process retains one. */
+export function resolveProcessRuntimeWorkerFile<T extends string | URL>(
+  filename: T,
+): T | URL | string {
+  const resolve = holder.resolve;
+  if (!resolve) {
+    return filename;
+  }
+  if (filename instanceof URL) {
+    return filename.protocol === "file:" ? resolve(filename) : filename;
+  }
+  if (typeof filename === "string" && filename.startsWith("/")) {
+    const resolved = resolve(pathToFileURL(filename));
+    return resolved.protocol === "file:" ? fileURLToPath(resolved) : filename;
+  }
+  return filename;
+}
```
