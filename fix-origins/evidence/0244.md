## Fix PR #201804 description (by freeqaz, opened 2026-11-19T12:20:02Z)

```text
## What Problem This Solves

Restart recovery marks the input it enqueues for an interrupted session as input provenance `{ kind: "internal_system", sourceTool: "restart" }` (`src/auto-reply/reply/session-event-context.ts`). Later stages trust that mark: an adopted Codex thread whose earlier turn is still running waits passively for it (up to 120 s) instead of refusing the input, and the attempt keeps an earlier unanswered user message in history.

The `agent` RPC only needs `operator.write` for a plain message, and its preflight (`src/gateway/agent-turn/agent-request-preflight.ts`) passes a caller's `inputProvenance` through. It reserves two internal marks for backend callers (progress refresh and exec completion) but not the restart mark, so any write-scoped operator client could label its own input as restart-sourced. `chat.send` already needs admin scope for any system provenance, so `agent` was the only entry point with this gap.

## User Impact

None for normal use: restart recovery does not go through the `agent` RPC (it enqueues session events in process), and no bundled client sends the restart mark. A non-backend `agent` caller that sends it now gets `INVALID_REQUEST` "Restart input is reserved for restart recovery.", like the two existing reserved marks.

To be clear about what was possible before: the only restart-specific effect a client could get was on its own input, mainly a passive, abortable wait of up to 120 s on an adopted Codex thread that was still busy. The point of the change is that restart handling can keep trusting the mark as it grows.

## Why This Change Was Made

One check next to the exec-completion check in `prepareAgentRequestPreflight`: `internal_system` with `sourceTool: "restart"` from a caller that is not a backend client (`canUseInternalRuntimeHandoff`, the same test the other reserved marks and internal session-effect controls use) is rejected with the same `INVALID_REQUEST` shape. Backend callers are unchanged.

I did not reserve every `internal_system` value on `agent`: the agent handler tests model an admin CLI client sending `internal_system` input as accepted, and `chat.send` deliberately lets admin clients set system provenance. Changing that contract is a separate decision.

## Evidence

The existing exec-completion case in `src/gateway/agent-turn/agent-request-preflight.test.ts` is now a table over both marks (exec completion, restart), each sent by a write-scoped CLI-mode client, by no client, and by a backend client.

Run with `--maxWorkers=1` on a Linux runner against main `8a23d7c11d3`:

- with the change: `pnpm test src/gateway/agent-turn/agent-request-preflight.test.ts`: 22/22 pass;
- without the change (main's preflight, new test): the restart case fails at its first caller, the write-scoped CLI client, whose request is admitted with the restart mark (`expected { request: … } to be undefined`); the exec-completion case passes on main too, as it should; 21/22;
- `scripts/run-format.mts --check` and oxlint on the two touched files: clean;
- `pnpm tsgo:core` and `pnpm tsgo:test:src`: pass.

Not run: the full test suite and a live Gateway run. No bundled caller sends this mark through `agent`, so there is no user flow to replay; the boundary is the preflight, which the test drives directly.

## Risks

- A third-party operator client that set the restart mark on `agent` input itself now gets `INVALID_REQUEST`. No bundled client does.
- The rule decides "backend caller" exactly as the two existing reserved marks do; this change does not alter that decision.
```
