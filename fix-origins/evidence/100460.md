Related: #138042, #148057, #148442, #148445, #148504

## What Problem This Solves

Cleanup, exact-session searches, and ACP replay appends repeat SQLite work over unrelated or already-protected history as stores grow.

## User Impact

Reduces synchronous CPU spent on large session stores while preserving search visibility, cleanup eligibility, replay limits, and byte accounting. No schema change, new index, migration, configuration option, or retention change.

## Why This Change Was Made

Cleanup rejects recently updated nodes before scanning transcript timestamps. Exact-session search narrows its dirty-state lookup to the selected session, and transcript generation creation stops reading back an unused value.

ACP replay uses indexed minimum/maximum sequence values to exclude histories that cannot exceed the event cap. Possible overflows still receive an exact count, preserving gapped sequences and stricter limits after reopening.

## Evidence

Synthetic CPU measurements on Node 26.8.2 / SQLite 3.53.4, using existing canonical indexes:

| Measured operation and fixture | Original CPU | Updated CPU |
| --- | ---: | ---: |
| ACP replay append, 20 sessions / 100,000 events | 6.208 ms | 0.707 ms |
| ACP replay append, over-cap gapped history | 7.518 ms | 4.756 ms |
| Full cleanup planner, 12 fresh nodes / 96,000 retained events | 17.402 ms | 0.397 ms |
| Exact-session FTS query, 10,000 clean session states | 0.248 ms | 0.078 ms |

Complete result comparisons passed for 6 cleanup shapes, 144 FTS cells, and 9 replay fixtures. The paired replay comparison used one warmed connection, seven alternating pairs of 40 appends, identical seeding, and 21 matching retained-row fingerprints. Its 100,000-event fixture is about 14.4 MB, with an explicit larger byte cap to isolate event-count work. Final emitted ACP SQL matches the measured query exactly.

These are component measurements. The search reconciliation preflight remains a separate cost (6.810 ms in the clean 10,000-state fixture). Removing the unused generation read has no reliable latency claim. A blanket search `NOT EXISTS` rewrite and a fixed-status partial-index rewrite were rejected after opposite workloads regressed, including a 17× slowdown for a recent delivery hit.
