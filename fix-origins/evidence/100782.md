Related: #144291

## What Problem This Solves

Fixes an issue where a completed cross-agent `sessions_send` reply could disappear after a configuration reload because detached follow-up work retained the completed caller's runtime identity.

## Why This Change Was Made

The detached A2A flow already owned an independent Gateway work root, but it still captured both the caller's cleanup context and prepared-runtime generation. The repair clears those inherited scopes before creating the independent root, so later reply turns re-admit against the current runtime without weakening explicit stale-generation rejection.

The obsolete test-shard edits from the earlier revision were removed.

## User Impact

Cross-agent replies that finish after a configuration reload continue on the newly published model runtime instead of silently failing on the retired caller generation.

## Evidence

- Added an end-to-end runtime regression using an ephemeral production Gateway and a mock OpenAI-compatible provider. It dispatches `sessions_send` with `timeoutSeconds: 0`, holds the target turn across a `config.patch` from model A to model B, then verifies:
  - the target reply remains visible;
  - the detached requester reply runs on model B;
  - the independent `session:a2a-send` root settles before teardown.
- Red/green proof: the E2E failed on pre-fix current-main production code because no model-B detached reply occurred, then passed with this repair.

* fix(agents): don't inject A2A turns into isolated-cron sessions_send (#92257)

Fire-and-forget sessions_send (timeoutSeconds === 0) with announce
delivery runs the A2A ping-pong loop. For a cross-session send
(requester != target) the loop's first iteration feeds the target
agent's reply back into the requester session as a new turn. For a
normal requester that roundtrip is intended, but for an *isolated cron*
requester it injects reply context into the isolated run and causes an
agent feedback loop.

Narrow the fix to isolated-cron requesters only (detected by a session
key containing ":cron:" or channel "cron" -- the same signal used by
src/agents/subagent-registry.ts and set in
src/cron/isolated-agent/run.ts), NOT by timeoutSeconds. Gating on
timeoutSeconds was too broad: it disabled the intended ping-pong for
normal cross-session fire-and-forget sends.

Two hunks in src/agents/tools/sessions-send-tool.ts, both reusing one
`isIsolatedCronRequester` gate:

1. Force maxPingPongTurns to 0 in the runSessionsSendA2AFlow invocation
   only for an isolated-cron requester. The a2a flow's ping-pong guard
   (`maxPingPongTurns > 0`) then skips the requester-injection loop and
   proceeds straight to the announce step in the TARGET session,
   preserving fire-and-forget announce delivery. Normal requesters keep
   the configured turn count.

   behavior) OR isolated-cron. Without a baseline fingerprint, a2a.ts
