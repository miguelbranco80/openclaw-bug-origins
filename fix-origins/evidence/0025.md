## Fix PR #199193 description (by roboclaw-bot, opened 2026-11-14T20:51:54Z)

```text
## What Problem This Solves

Fixes: the Portal panel reports a device startup failure when a status check fails, or when a device is stopping or unavailable.

## User Impact

User impact: the panel distinguishes an unknown status from a reported device state, and makes clear that its recovery button checks status rather than starting the device again.

## Why This Change Was Made

A failed status read is not evidence that startup failed. The existing device summary also distinguishes stopping, unavailable, and error states. The panel now uses those existing facts instead of giving every case the same startup-failure diagnosis. Reported unavailable/error devices keep the useful instruction to ask the agent to check them; diagnostic details remain visible.

“Check again” describes the existing status-read action. Device startup, stopping, polling, permissions, portal creation, and state ownership are unchanged. No new requests or recovery mechanism were added.

## Evidence

- The initial-read regression fails on main with the false startup diagnosis; reported stopping/unavailable/error cases also fail for the intended wording distinction. After the change, all 35 portal-page/reachability tests pass (1.22 seconds wall).
- Three focused full built-app scenarios pass before and after. The normal Gateway presentation event opens the Portal panel beside chat, then the actual recovery control makes another status read. A recovered read and a reconnected node show “Device ready. Waiting for your app…”; a stopping worker remains stopping. No device-start or portal-list request is sent by that action.
- Keyless i18n, scoped lint, UI typecheck, formatting, and diff checks pass. Generated translations and the raw-copy baseline are unchanged.
- Self-review/simplification completed. No independent agent review or broad E2E matrix was run. Hosted CI timing is not yet available.

Before uses verified main **9ea18a1b8e06b03ab26b8d98da76301d3dc6cc1a**. These are inspected, matched crops from the complete built app at 1280 × 900 in light theme. Synthetic Gateway responses represent a failed status read, a stopping worker, and an unavailable paired node. This is the **Portal panel beside a conversation**, opened when the agent presents a device while preparing an app preview—not a failure on the requester’s account. No real device or cloud resources were changed.
```

```diff
+export function PendingEnvironment(props: {
+  model: PortalsModel;
+  error?: string;
+  retry?: () => void;
+}) {
+  const environment = () => {
+    const state = props.model.state();
+    return state.pendingEnvironment?.id === state.pendingEnvironmentId
+      ? state.pendingEnvironment
+      : null;
+  };
+  const failed = () =>
+    props.error ||
+    (environment() &&
+      environment()!.status !== "starting" &&
+      environment()!.status !== "available");
+  return (
+    <section class="portals-empty" role="status" aria-live="polite">
+      <div class="portals-empty__title">
+        {t(
+          failed()
+            ? "portalsPage.environmentUnavailable"
+            : environment()?.status === "available"
+              ? "portalsPage.waitingForApp"
+              : "portalsPage.environmentStarting",
+        )}
+      </div>
+      <Show when={props.error || environment()?.worker?.error}>
+        <p>{props.error ?? environment()?.worker?.error}</p>
+      </Show>
+      <Show when={failed()}>
+        <button
+          class="btn"
+          type="button"
+          onClick={() => {
+            if (props.retry) {
+              props.retry();
+            } else {
+              void props.model.loadPendingEnvironment();
+            }
+          }}
+        >
+          {t("portalsPage.retry")}
+        </button>
+      </Show>
+    </section>
+  );
+}
```
