perf(gateway): stop re-parsing live chat replies after a prose directive

After a reply contained a prose directive, the Gateway re-parsed the whole live reply on every update, so work grew with reply length. Live replies are now projected incrementally after the directive, and the delivered text is unchanged.

Evidence: live Gateway chat turns. The audio canonical path is not covered and is listed under "Not fixed here". The one red CI job (check-test-types-core-2, TS2345 in reply-agent-turn-preparation.test.ts:646) fails the same way on current main; see the maintainer override comment.

## What Problem This Solves

The live display filter latched onto a `[[` marker and kept transforming the entire accumulated reply on every delta, even after a prose directive or wiki-style marker had settled. Keep the settled projected result in the existing owner and append safe prose directly. Deltas that can change directive syntax or Markdown ownership still use the canonical transform.

Reuse the existing Markdown ownership check through its append-only form. Image alt completion, provisional tables, inline-code/link-title ownership, incomplete markers, audio-removal interactions, replacements, and empty updates retain their existing semantics. No second parser, global cache, configuration, or generated prompt change is introduced.

## Evidence

[Observed built Gateway capture and work-bound results](https://github.com/openclaw/openclaw/pull/184543#issuecomment-6424348648).

Built main (`71eacdfe9b5ba058abc4555b4e2a672e932961d2`) and the candidate (`c524c79c3f082bcfa1b8216afd3dc03a0490a337`) with Node 24.22.1 in clean secretless Linux Docker after integrating the current base.

### Measured work bounds

The same committed four-character-delta regressions on unchanged main production preserve text but fail with **8,179** display-transform calls for the settled directive workload and **6,384** through the live projector for the prose-marker workload. The candidate passes both **fewer than 64 calls** assertions. This measures removal of repeated owner-level parse work, not a browser frame-time or end-to-end latency claim.

- Plain prose, image-alt completion, table invalidation, and audio-then-image controls also deliver byte-identical main/candidate text.
- Both streamed assistant text and the actual final `chat` message match for every scenario. All **12 chat turns** finish `status: ok` with nonempty assistant events and a final chat event.

The Gateway coalesces these provider deltas into 11–13 assistant frames for the long cases. Wall samples are mixed (main 2.561 / 1.172 s; candidate 2.349 / 1.248 s), so no end-to-end speedup is claimed from this delivery fixture. ## Not Fixed Here

Replies containing an `audio_as_voice` directive deliberately retain the canonical parsing path because audio removal can change Markdown ownership. This does not optimize that audio-bearing workload or every cause of a live-chat stall. Display-text parity for audio/image syntax is verified, but no audio-path speedup, binary-media workflow, or complete closure of the linked issue is claimed.

## Compatibility and Merge Danger

Internal display projection only; no SDK, configuration, stored format, or public API change. Reverting fully restores the prior projection owner: a two-way door. Blast radius is live assistant display text around directives and Markdown boundaries; terminal delivery policy and canonical directive parsing remain unchanged.
