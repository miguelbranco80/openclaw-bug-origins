## What Problem This Solves

Windows update candidates can fail with `Candidate executor binding does not match its parent` even when the recorded update owner and candidate lease are current, because admission additionally requires the candidate's immediate parent PID to equal the recorded spawner.

Refs #166004. Thanks to @wqj11a for the independent reproduction and lease observations, and @H0Nm4M1suZu for the original report.

## User Impact

A Windows candidate can continue an authorized handoff when its launcher ancestry differs from the recorded spawner. The candidate-side repair accepts existing handoff formats from older installed updaters without new options or schema changes. It does not repair the separate plugin-migration/readiness and Scheduled Task recovery symptoms in the issue.

## Why This Change Was Made

The existing candidate binding and delegated executor owners now use the lease store's live executor-ownership check on Windows. The security property remains: only the PID/start identity registered for this run and installation may perform effects while the exact lease generation, original owner, and spawner remain current. Foreign PIDs, changed start identities, and revoked owners are refused. The existing fallback for an unreadable self identity still requires the immediate live parent; POSIX ancestry checks remain unchanged. Windows creation times retain their existing millisecond normalization and exact comparison.

The related report #166509 needs a separate finalization/recovery repair. Package rollback already restores Scheduled Task autostart before restarting the verified previous package. In the already-current flow, however, fresh Doctor can park the Gateway into `rollbackStopState` while error recovery still receives `params.preManagedServiceStop`; that older receipt may say `stopped: false`. The redacted report does not establish its exact refusal or whether state remained restart-compatible. This PR does not claim to fix it.
