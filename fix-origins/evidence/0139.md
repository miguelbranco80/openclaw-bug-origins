## Fix message body

```text
fix(slack): stop reasoning streams from stalling the Gateway when Slack streaming is off

In Slack sessions with /reasoning stream on and Slack streaming off, each reasoning chunk was merged into a progress buffer that kept growing and was never flushed, so the Gateway's main thread spent most of its time re-processing that buffer. The Slack reasoning handler now skips the progress buffer when there is no preview to update. The delivered reply is unchanged.

Evidence: main and this change on node 24.22.1 in Docker, Slack in HTTP mode against a local Slack API stand-in, streaming off, a local model streaming 1.2 MB of reasoning in 24-character chunks, /health polled every 500 ms, two runs each. There was no full freeze, but on main the reply arrived 18 to 22 minutes after the model finished, the turn used about 1600 s of Gateway CPU, /health took up to 2.28 s, and a CPU profile put 46.9% of main-thread time in pushReasoningProgress. With this change the reply arrived 3 to 6 minutes after the model finished, the turn used 506 to 629 s of CPU, and pushReasoningProgress took 0.0%. The final reply text was identical in every run, and short streams with streaming off and with the Slack preview on produced identical messages on both. Details: https://github.com/openclaw/openclaw/pull/196250#issuecomment-6774705761.

Closes #196249. Thanks @ptu-gh.

Co-authored-by: Ayaan Zaidi <hi@obviy.us>
```

## Fix PR #196250 description (by ptu-gh, opened 2026-11-09T20:53:02Z)

```text
Closes #196249

## What Problem This Solves

Fixes: the Gateway freezes during a long reasoning stream in a Slack session when Slack streaming is off.

## User Impact

User impact: Slack sessions with `/reasoning stream` and no Slack preview keep the Gateway responsive however long the model reasons. Sessions that do show a Slack preview behave as before.

## Why This Change Was Made

Outside `progress` mode, Slack merged each reasoning delta into the accumulated text twice, then handed the result to `pushToolProgress`. That call returns `false` immediately when the preview is inactive. Each merge reprocesses the whole accumulated text, so with no preview the Gateway did growing amounts of work per delta and threw the result away.

Slack now returns before merging when `previewToolProgressEnabled` is false. The compositor builds its own check in `noteProgress` from the same inputs (`active`, account config, mode). So the change skips exactly the calls that could never be shown. The compositor's own `pushReasoningProgress` (`progress` mode) already checks before merging, and no other channel calls `mergeReasoningProgress`.

Accepted edge case: when a preview is shown (`partial` or `block` with tool progress), each delta still normalizes the whole accumulated text. That path is unchanged here; making the accumulator incremental would be a separate change.

## Evidence

Reported by @ptu-gh in #196249.

- Observed on 2026.10.7: a Slack DM with `/reasoning stream`, streaming `off`, GLM-5.2 thinking `high`. The Gateway main thread ran at 100% CPU for about 75 minutes, with event-loop stalls growing to 24 s; SIGTERM could not complete. A CPU profile put the time under Slack `pushReasoningProgress` → `mergeReasoningProgress`. Details in the linked issue.

### Built Gateway in Docker (current main vs this PR)

Setup: `pnpm build` of `main` (b21829a4c85f) and of this branch merged with that `main`, node 24.22.1 in Docker, no secrets. Slack runs in HTTP mode against a local stand-in for the Slack Web API and Events API (signed `event_callback` posts). The model is a local OpenAI-compatible stand-in that streams 1.2 MB of `reasoning_content` in 24-character deltas, then the reply `PROOF_FINAL_OK: the answer is 42.`. Each run is a Slack DM that first sends `/reasoning stream` (the Gateway answers "Reasoning stream enabled."), then the prompt. `/health` was polled every 500 ms with a 15 s timeout. Slack `streaming.mode: "off"`.

- There was no full freeze on current main: `/health` always answered. What the user sees is multi-second event-loop stalls and a reply that arrives 18 to 22 minutes after the model finished. With this PR the Slack reasoning merge is gone; the cost that is left is outside Slack (shared assistant-text cleanup such as `stripPlainTextToolCallBlocks` and `findFinalTagMatches` shows up in both profiles) and is not changed here.
- Controls, identical on both builds: a short (2 KB) reasoning stream with streaming `off` sends the same two Slack messages (the `/reasoning` acknowledgement and the final reply). With `streaming.mode: "partial"` and tool-progress preview on, the same short stream still shows reasoning in the draft (`Working` / `• consider the …`) and finishes with the same `chat.update` text. Every Slack write had the same text hash on main and on this PR.
- Both builds ran side by side on a loaded host, so the absolute times are high; the comparison is between runs under the same load.
- The regression test and its test-line allocation were dropped to keep test lines flat; the Docker runs above cover the path.
```
