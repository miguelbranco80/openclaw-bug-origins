## Fix PR #156431 description (by steipete, opened 2026-09-23T10:17:33Z)

```text
Fixes #156218. Thanks @s93101179 for the report.

## What Problem This Solves

Session SQLite recovery could generate an empty support issue without explaining the original failure. The later zero-issue guard also hid recorded failures when recovery validated cleanly.

## User Impact

Recovery reports retain the original run ID, target, failure code/error, and recorded failure timestamp alongside the recovery outcome. Empty recovery prints `nothing to recover; no report filed` and generates no issue body. Prepared-transcript changes still reject the import batch; the existing rejection test is unchanged.

## Why This Change Was Made

The [2026.9.5 recovery owner](https://github.com/openclaw/openclaw/blob/v2026.9.5/src/commands/doctor-session-sqlite-recover-report.ts#L103) unconditionally generated a report. The journal already supports target issues and `failedAt`, but importer exceptions escaped before those facts were recorded, and rendering omitted the timestamp.

The [import owner](https://github.com/openclaw/openclaw/blob/eaf063e627e2d98208e0d2b8e866baee055038a9/src/commands/doctor-session-sqlite-import.ts#L69) now records the failure before rethrowing. A journal-write failure retains both causes in an aggregate error. The existing import implementation moves into a focused sibling to satisfy the line-cap gate; the orchestration module shrinks by 196 lines. The [recovery owner](https://github.com/openclaw/openclaw/blob/eaf063e627e2d98208e0d2b8e866baee055038a9/src/commands/doctor-session-sqlite-recover-report.ts#L138) reads those facts and preserves reports for actual restoration or import work; the [renderer](https://github.com/openclaw/openclaw/blob/eaf063e627e2d98208e0d2b8e866baee055038a9/src/commands/doctor-session-sqlite-failure.ts#L266) carries the recorded timestamp.

No database/manifest schema, options, dependencies, archive retention, or rollback semantics change. Existing operator journals remain the input; missing historical timestamps say `not recorded`.

The `<!-- openclaw-report:… -->` hash covers the exact generated body. New reports include the timestamp; reports with an existing issue-handoff receipt remain byte-for-byte unchanged for duplicate reconciliation.
