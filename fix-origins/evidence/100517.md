## Fix PR #143341 description (by anyech, opened 2026-09-09T19:09:14Z)

```text
Related: #115367

## What Problem This Solves

An agent in one conversation can need messages, pins, or reactions from another conversation that its configured Discord or Slack account is allowed to read. The same provider implementation could serve that request when bundled, but installing the official plugin through npm or ClawHub caused the host to reject it before the provider's destination checks could run.

The existing provider-owned read gate admitted bundled registrations only. Extending admission also requires keeping the operation attached to the caller and plugin instance that authorized it: target lookup, queued requests, retries, and result delivery must not continue with authority that has expired or been replaced.

## User Impact

With matching updated core and plugin versions, verified official installations can perform the following provider-permitted context reads:

| Plugin | Actions covered |
| --- | --- |
| Discord | `read`, `search`, `reactions`, `list-pins`, `thread-list`, `channel-info` |
| Slack | `read`, `reactions`, `list-pins` |

Account matching, current-provider context, requester context, and the provider's destination policy still apply. Bundled plugins retain their existing admission rules and receive the same lifetime checks for these opted-in reads. Other actions, unverified installations, and older adapters keep their existing authorization behavior.

Delegated Discord reaction reads also stop using the resolver that can create a DM. A user alias in the current trusted DM resolves to its existing native channel; an unmatched or unattested user target fails before provider traffic. Direct operator reads and reaction writes retain their existing resolution path.

## Why This Change Was Made

The host now combines the existing loader-verified official installation record with an explicit `readAuthorityActions` list and the adapter's `providerOwnedReadGates` declaration. The host intersects that list with the six actions above. This keeps lifetime participation and provider admission explicit, and prevents a later host action addition from silently expanding an existing adapter's opt-in. Plugin-supplied fields cannot substitute for the selected registration's authority.

Local message tools capture the existing operational caller assertion before asynchronous preparation and retain the original turn capability. That assertion is carried through routing and dispatch; Gateway requests retain their server-owned caller assertion as well. Opted-in delegated execution needs a live registered instance, including for bundled plugins. A bundled artifact fallback or an omitted scoped registration cannot supply that lifecycle.

The shared `captureChannelReadAuthority()` SDK callback is captured when each transport request is submitted, retained through queues and retries, and checked immediately before provider I/O after asynchronous request preparation. Host and installed SDK copies share the invocation scope. The host also checks completion, covering stale results and errors, and closes captured callbacks when the action finishes. These checks stop subsequent requests and stale delivery; they cannot undo a request already sent.

The complete target-alias owner repair in [#147492](https://github.com/openclaw/openclaw/pull/147492) is included in the integrated proof and remains a separate change.

The new SDK export is absent from the published 2026.9.3 and 2026.9.4 cores. Core and plugin releases therefore need coordinated version and plugin-API alignment. Package proof uses the canonical release tools in a disposable 2026.9.5 fixture, with matching build metadata and no version change in this PR.
```
