## Fix message body

```text
## Problem

A session that changes models drops its own server compaction checkpoint, resends the full raw history, and falls back to client summarization. Model changes happen through fallbacks, per-turn overrides and model alternation within one session.

The provider replay check compared the model id. After #200063 removed the credential-path check, the model check was the other common cause. On the host that reported the original incident, model changes accounted for 357 of 800 dropped-checkpoint turns, mostly a session alternating between `gpt-6-astra` and `gpt-6.1-sol`.

## Fix

- The replay check is now provider API, endpoint and session. The model id stays in the stored record but is no longer compared.
- Providers accept their own replay items across models. I checked this with raw API calls before changing anything:
  - **OpenAI compaction items:** `gpt-6-astra` ↔ `gpt-6.1-sol` and `gpt-5.4-mini` → `gpt-5.4` are accepted, and the model recalls a fact that is only in the compacted history.
  - **OpenAI encrypted reasoning:** the same pairs are accepted.
  - **Anthropic compaction blocks:** `claude-sonnet-4-6` → `claude-opus-4-8` is accepted and recalls the compacted fact. These blocks are plaintext summaries.
- An item a provider cannot use is still rejected server-side (`invalid_encrypted_content` / `item_conflict`), and the existing replay recovery handles it.

The production change is one comparison removed. The tests that asserted the model check are replaced with positive cases.

## Evidence

**Regression test:** `openai-responses-compaction-replay.test.ts` › "replays a checkpoint written by another model in the same session". It fails on the old check and passes with the fix.

**Real-model E2E** (isolated state; each arm built from its own source):
- Three seed turns on `openai/gpt-5.4-mini` with server compaction, then a final turn on `openai/gpt-5.4` in the same session with the same key.
- Request shapes come from `OPENCLAW_DEBUG_MODEL_PAYLOAD=summary`.

| arm | final-turn request | items | text chars | answer |
| --- | --- | --- | --- | --- |
| base | messages only; `compactionItems=0` | 11 | 113,090 | correct |
| fix | `compaction, message:user, message:developer`; `compactionItems=1` | 3 | 656 | correct |

**Checks:**
- The touched replay suites pass (100 tests).
- `check:changed` passes except the dead-export scan. That scan reports unused exports in files this PR does not touch, which come from the current `main` tree.

## Scope

Encrypted reasoning from a different model is still dropped on a model switch. The generic cross-model history transforms (`transcript-transform.ts`, `transport-message-transform.ts`) and `dropStaleOpenAIReasoning` strip it before the replay check runs. That costs one turn of reasoning context, not the session's history, so it is left for a separate change.

## Follow-up

The context meter still estimates from the full transcript when a checkpoint is present. That fix is a separate PR.
```

Message (truncated):

```text
## Problem

Long OpenAI Responses sessions lost their server compaction checkpoint and fell back to client summarization, even though the provider had compacted the session.

The replay identity fence for compaction and encrypted reasoning items included the auth profile hash. One OpenAI key can reach a session two ways: through an auth profile (`openai:*`) or through `models.providers.openai.apiKey`. When runs alternate between those two sources, the fence rejects the session's own checkpoints. The next request then resends the full raw history (about 1M tokens on the affected host) and client summarization runs. In the reported incident, that summarization was refused, which left the session with no summary.

This was observed in production on one host where both sources hold the same key; four sessions were affected. The fence was added in #120457 and moved in #135727.

## Fix

- The replay identity is now session plus model route only. `authProfileHash` and `authProfileId` are removed from the replay context, the compaction and reasoning replay builders, the context-usage meter, and every provider, transport and agent call site.
- A checkpoint from a different org is still rejected by the server (`invalid_encrypted_content` / `item_conflict`). The existing recovery in `openai-responses-replay-internal.ts` already handles that.
- Checkpoints saved with a legacy `authProfileHash` still replay. No migration is needed.

Net change: 32 files, +42 −77 (tests that asserted the credential-source fence are removed).

## Evidence

**Real-model E2E** (isolated state, `openai/gpt-5.4-mini`, server compaction threshold 12k):
- Setup: three seed turns run through an auth profile only. The final turn runs with the config `apiKey` present, which takes precedence. It is the same key, so only the credential source changes.
- Request shapes come from `OPENCLAW_DEBUG_MODEL_PAYLOAD=summary`.
```
