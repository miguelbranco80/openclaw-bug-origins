```text
Related: #161007, #180304, #187346

## What Problem This Solves

Fixes: an automation's failure repair turn cannot read or change the job it was asked to repair, so it asks the user to fix it instead.

## User Impact

User impact: when an owned automation fails, the repair turn in its owner conversation can now read the job's runs and update the job when the job's requester is still an owner, so most repairs no longer need a human reply. Scheduler notices about a job follow the same rule.

Risk to note: a job whose requester is not an owner (or whose stored operator source can no longer be restored) now gets read-only automation access in its repair and notice turns, and no session-owner fallback. Jobs that record no requester keep the session owner's current access, as other system turns do since #187346.

## Why This Change Was Made

System-started turns got their authority from what kind of turn they were: a label match for notices (#180304), a caller rule for completions (#187346, which left cron out), and nothing for repairs, which went through the public `agent` RPC. Any client can send the repair's provenance label on that RPC, so it could never carry authority.

Now:
- A scheduler turn about a job acts for the job's recorded requester, the same requester and owner check its scheduled runs use (channel sender, profile, or restored operator source). Owner status is rechecked before each owner-only effect.
- Repairs run on the host session-event path, like notices and completions.
- Every host system turn gets one rule for caller-scoped automation reads; the `sourceTool === "cron"` match is gone.

## Evidence

Production repair transcripts (read-only, one Gateway, since the repair feature shipped): 57 repair turns, 3 fixed their job, 28 asked the user. No repair turn ever completed an `automations` call: before 2026-10-19 the tool was absent, then a schema check failed, and since 2026-10-22 all 18 calls were refused by the owner gate. All 3 script-payload repairs were refused.

Final-effect test `src/gateway/server-cron-failure-repair.final-effect.test.ts` runs the real repair dispatcher, real session-event admission, the turn's real tool surface and in-process Gateway dispatch into a real `CronService` and its store (model synthetic). Each case reports the tool result and the stored job afterwards:

| Job requester | `automations update` | Stored description |
|---|---|---|
| Channel owner | ok | changed |
| Channel non-owner | gated | unchanged |
| Channel owner revoked while the repair was queued | turn refused at admission, no tool ran | unchanged |
| Channel owner revoked after admission | refused: tool host retired by the config change | unchanged |
| Restored Control UI admin operator source | ok | changed |
| Restored non-admin operator source | gated | unchanged |
| Operator source with its device revoked before the repair | gated (no session fallback) | unchanged |
| Operator source device revoked while queued | turn refused at admission, no tool ran | unchanged |

Two fixes came out of this proof:
- The queued-revocation case first let the update through: the requester recheck read the config captured at capture time. It now reads the Gateway's current config, as completion turns do (`authority.isCurrent(getSessionEventRuntimeConfig())`).
- A restored operator source is an owner only when it was a Control UI administrator, matching the job's in-session runs (`session-run.ts`). The non-admin case fails without this rule.

On the base commit the file fails (the repair cannot dispatch outside the old lifecycle path); production transcripts above show the base refusal itself.

Runtime-error suppression from #162772 is kept: repair session events set a host-owned `suppressErrorDelivery`, so error payloads stay in the transcript and out of chat. The owner-topic Gateway test now has the repair return a provider-error payload and asserts no chat delivery; without the flag that test fails (`prepareSessionEventDelivery` called once).

Gateway cron suite (`server.cron.test.ts`): the owner-topic repair and NO_REPLY repair cases drive the real reply runtime; they check the owner topic's session and thread route, repair pending through retries until the turn settles (success and error), one escalation, and that a forged public `cron_failure_repair` label still gets no silence. The monotonic deadline cases in `server-cron-notifications.repair.test.ts` now run against the session-event dispatcher.
```

```diff
+/**
+ * Captures the owner conversation for a turn the scheduler starts about one job (its failure
+ * repair or a notice), acting for the job's recorded requester: the requester its scheduled

+ * requester gets none; a job with no recorded requester falls back to the session
+ * principal like other unattributed system turns.
+ */
+export async function captureCronJobTurnTarget(params: {
+  job: CronStoredJob;
+  agentId: string;
+  sessionKey: string;
+  context: GatewayRequestContext;
+}): Promise<{ target: SessionEventTarget; release: () => void }> {
+  const { job, agentId, sessionKey, context } = params;
+  const capture = (options?: Parameters<typeof captureSessionEventTargetForHost>[2]) =>
+    captureSessionEventTargetForHost(agentId, sessionKey, options);
+  const nonOwner = async () => ({
+    // A known requester that is not, or no longer, an owner: never the session principal.
+    target: await capture({ requesterOwner: {} }),
+    release: () => {},
+  });
+  let requester: ReturnType<typeof resolveScheduledRequester>;
+  try {
+    requester = resolveScheduledRequester(job);
+  } catch {
+    // An undecodable stored operator source; its scheduled runs fail the same way.
+    return await nonOwner();
+  }
+  if (requester.kind === "unknown") {
+    return { target: await capture(), release: () => {} };
+  }
+  if (requester.kind !== "operator-source") {
+    const { owner, isOwner } = await checkRequesterOwner(context.getRuntimeConfig(), requester);
+    // Recheck against the Gateway's current config before each owner-only effect, as
+    // completions do for their requester; a revocation while queued is refused.
+    const assertCurrent = () => {
+      if (!isOwner?.(context.getRuntimeConfig())) {
+        throw new Error("The requester that authorized this automation is no longer an owner.");
+      }
+    };
+    const target = await capture({ requesterOwner: owner && isOwner ? { assertCurrent } : {} });
+    return { target, release: () => {} };
+  }
+  // Operator-source jobs are owned by the conversation their source names.
+  const { source } = requester;
+  const captured = job.operatorSource;
+  let operator: Awaited<ReturnType<typeof restoreGatewayOperatorSource>> | undefined;
+  try {
+    if (source.agentId !== agentId || source.sessionKey !== sessionKey) {
+      throw new Error("Automation operator source names another conversation");
+    }
+    operator = await restoreGatewayOperatorSource({
+      snapshot: source.snapshot,
+      target: { agentId, sessionKey, sessionId: source.sessionId },
+      context,

+          throw new Error("Automation operator source changed");
+        }
+      },
+    });
+    // As for the job's in-session runs, a restored source is an owner only when it was a
+    // Control UI administrator; otherwise it is the job's non-owner requester.
+    const target = await capture({

+      ...(operator.controlUiAdmin ? { ownerContinuation: true as const } : {}),
+    });

+    }

+  } catch {
+    operator?.release();
+    return await nonOwner();
+  }
```
