## Fix PR #123159 description (by vincentkoc, opened 2026-08-13T11:35:06Z)

## What Problem This Solves

Fixes an issue where an iMessage conversation with a valid runtime binding fails ordinary multi-agent selection before its bound agent can be selected.

## Why This Change Was Made

Inspect the conversation binding first through the existing binding-owner API. For an authoritative bound agent, derive only its session scope before projecting the captured binding facts. Ordinary and configured routing remain the fallback for unbound conversations.

The inbound caller awaits resolution and preserves the current `ConfiguredBindingRouteResult`, including configured-binding readiness. Activity persistence cannot silently replace the captured owner: the existing final reply-admission boundary rejects revoked, reassigned or unavailable bindings before reply generation or delivery.

This reconstruction changes only four iMessage files. It does not restore the historical shared helper or add an SDK surface, configuration, schema, or sibling-channel change.

## User Impact

Bound conversations reach their selected agent even with an ambiguous roster or conflicting ordinary route. Unbound and configured conversations retain their existing behavior; an unavailable binding owner fails closed.

## Maintainer Disposition: Adapter Outage

Retain fail-closed routing for both bound and unbound conversations while the adapter owner is unavailable. An unavailable owner is not authoritative evidence that a conversation is unbound; falling through to another agent would violate the [existing binding contract](https://github.com/openclaw/openclaw/blob/af1877ff0e31e11142d1156e0ee30ff8346e54af/docs/plugins/sdk-channel-plugins/sessions-and-bindings.md#L72). This accepts delayed delivery during that outage, including for conversations with no saved binding, and selects the accept-and-document option in the [completed ClawSweeper review](https://github.com/openclaw/openclaw/pull/123159#issuecomment-5288626594).

The unchanged [monitor catch](https://github.com/openclaw/openclaw/blob/af1877ff0e31e11142d1156e0ee30ff8346e54af/extensions/imessage/src/monitor/monitor-provider.ts#L583) abandons the pre-adoption claim and logs the original dispatch error. The [queue owner](https://github.com/openclaw/openclaw/blob/af1877ff0e31e11142d1156e0ee30ff8346e54af/src/channels/message/ingress-queue.ts#L1145) retains the payload as pending, increments attempts and records turn-abandoned; existing draining/backoff makes it eligible for another attempt. This is source-backed recovery eligibility, not a demonstrated outage-to-recovery Apple delivery trace.

Important inherited limitation: this catch calls errorless abandon, so it does not enter the generic onFailed dead-letter classifier. No bounded retry-exhaustion outcome or eventual sender-facing failure notification is claimed. Existing message-age fences still apply. Improving error-aware abandonment and adding complete bound/unbound outage-to-reply coverage belong to a separate ingress-owner follow-up; this four-file routing repair does not change queue schemas, retention or retry policy. The outage behavior and that limitation are accepted for this landing; the review's optional recovery expansion is not represented as completed proof.
