## Fix message body

```text
fix(workers): mount workspace paths that contain a comma

Container node workers failed to start when the workspace, HOME or bundle path contained a comma. The docker create --mount value was built unquoted, so Docker split it at the comma ("invalid field ... must be a key=value pair"). A mount field is now quoted only when its path contains a comma. Paths without a comma produce exactly the same arguments as before, and mounts, the read-only flag and isolation are unchanged.

Evidence: a built Gateway and node session host on node:24.22.1 using the real Docker engine (29.8.2), container isolation on, with workspace, HOME and bundle paths containing commas. On main, docker create exited 125 with "invalid field ... must be a key=value pair" and the turn failed (both runs). With this change the worker started and the turn completed (both runs). Inside the container, the comma paths were the working directory and HOME, a host marker was readable, the worker's output file appeared on the host, and a write to the bundle failed with "Read-only file system". A path without a comma gives identical arguments on both, and a path with a quote but no comma fails the same way on both. Details: https://github.com/openclaw/openclaw/pull/195304#issuecomment-6735711131.

Thanks @shuisadev and @SunnyShu0925.
```

## Fix PR #195304 description (by shuisadev, opened 2026-11-08T16:29:25Z)

```text
## What Problem This Solves

Fixes: node workers fail to start when their workspace, HOME, or bundle path contains a comma (for example `/home/ana/Projects/acme, inc/api`), because `docker create` rejects the bind mount argument with `invalid field '...' must be a key=value pair`.

## User Impact

User impact: machines whose project paths contain a comma can use `nodeHost.workerRuns.isolation = "container"` again instead of failing at worker admission. Every path that mounts today produces the same arguments as before, byte for byte.

## Why This Change Was Made

`--mount` is not a plain `key=value` flag: the engine parses it with the CSV field grammar, so an unquoted comma inside `source=` ends the field early. The three bind mounts in `createNodeWorkerContainer` interpolated the path verbatim, so a comma in a directory name split one field into two unparsable ones.

The change quotes a whole `key=value` field only when its path holds a comma, doubling interior quotes, which is the form that parser reads. Commas are the only trigger on purpose: every path that triggers quoting already fails on both supported engines today, so no launch that works can change shape. A path with a quote but no comma is left alone, because Docker rejects it and Podman accepts it today; quoting it here would trade one engine's bug for the other's, so that conflict is not settled in this change.

`--workdir` and the `HOME` environment value take the path as a single argument and parse commas fine (checked against the same daemon), so they stay untouched.

## Evidence
```

```text
Related: #136048 (non-Git directory semantics) and #142521 (non-Git worker workspace context; this PR does not implement ephemeral cloud workspaces).

## What Problem This Solves

Device-hosted sessions required a Git repository or managed worktree, a constraint inherited from ephemeral cloud sessions, even when a paired personal machine should simply work in an existing non-Git folder.

## User Impact

Users can choose **Existing folder on device** in New Session and run a session directly in an existing folder on a paired session-host device. OpenClaw does not create Git metadata, copy the folder to the Gateway, or sync, reconcile, reset, or delete it.

- `nodeHost.workerRuns.folders` is node-local consent: unset allows existing directories, a non-empty list restricts selection to those roots and their descendants, and `[]` disables the feature and its capability advertisement.
- The session stays pinned to that device: Auto/cloud dispatch, Move, and Continue on Gateway are refused. Attachment staging and the Gateway Files panel are unavailable for these sessions.
- Worker HOME stays in private node storage. Files are not locked against external changes.

## Why This Change Was Made

- `sessions.create` accepts `deviceFolder: { deviceId, path }` (requires `operator.write`); the binding is stored on the existing session entry and the `device-folder` workspace kind reuses the worker execution and lifecycle owners.
- The node owns folder policy and re-validates on every use: absolute or `~` paths only, realpath resolution (symlinks cannot escape a root), no filesystem root, no overlap with private worker storage, and a dev/ino fence between acquisition and execution. One shared rule in `node-workspace-protocol.ts` forbids preparing, resetting, transferring, seeding, or quiescing a device folder, for both ingress parsing and direct node execution.
- Gateway shutdown reads the teardown scope from the durable placement, so stopping an attachment with no in-memory tunnel no longer reaches closed worktree admission.
- A restored existing-folder create retry is owned by its frozen request; current device capacity or runtime no longer blocks it.
- Attachments are refused for device-folder sessions before anything is persisted: `chat.send` rejects them with a clear message, New Session blocks Send while attachments are attached, and worker media preparation never restages historical attachments into a device folder, so one refused file cannot make later turns fail.
- Security tradeoff: a session-host node already runs operator-directed agents with exec, so the allow-all default does not widen that boundary. The folder list is a selection guardrail, not an exec sandbox or a boundary against a compromised Gateway. Deployments that contain `operator.write` with `tools.fs.workspaceOnly` should also set a root list; the docs say so.
- Control UI selection/path input, plus docs for node configuration, session hosting, operator scopes, and workspace behavior.
```
