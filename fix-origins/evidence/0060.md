## What Problem This Solves

- Fixes an issue where users who send a photo through the ACP bridge (for example a Rabbit R1
  camera shot relayed by Rabbit Agent) see the assistant answer about the photo, but the Control UI
  chat history shows only the prompt text. The photo is missing from the original user turn and
  stays missing after reloading the conversation, while a JPEG uploaded from the Control UI into the
  same session displays correctly.
- **Related:** #51324 introduced inbound-image persistence for `chat.send` and carried an
  ACP-bridge exclusion plus a test locking that omission in; this PR removes the exclusion.
  Issue carries `clawsweeper:queueable-fix`, `clawsweeper:fix-shape-clear` and
  `clawsweeper:source-repro`.

## Why This Change Was Made

- **Intended outcome:** An ACP bridge photo is claimed by the same canonical user-turn media owner
  as a Control UI upload, so the stored turn keeps a `media://inbound/…` reference and the Control UI
  renders the photo inline in the original user message, including after a reload.
- `prepareChatSendUserTurn()` short-circuited `persistInboundImagesForTranscript()` whenever
  `isAcpBridgeClient(client)` matched, so no inbound buffer was saved and the resolved user turn
  carried neither `media` nor `mediaImageLayout`. The image still reached the model because
  `replyOptionImages` is wired independently from `attachments.parsedImages` — which is exactly the
  reported "the assistant can read it, the transcript cannot show it" split. The bridge identity
  gates ACP-only `systemInputProvenance` fields; it does not own media persistence.
- **Out of scope:** No change to how the bridge defers its commit to the agent runtime
  (`requiresRuntimeApprovedChatInput`), no new storage owner, no Control UI change, and no change to
  what the model receives.
- **Highest-risk area:** Sending the same photo to the model twice on the first turn — the concern
  raised during the review of #51324.
- **How is that risk mitigated?** The existing generic suppression is reused, not reimplemented:
  every persisted inline/offloaded fact is marked `hydrationSuppressed: true`, and
  `collectCurrentImageAttachments()` drops every suppressed `ctx.media` index, so the persisted path
  is never re-hydrated into the prompt. The model still receives the photo exactly once, from the
  inline prompt image. The retained end-to-end regression test asserts this explicitly
  (`lastDispatchImages` still holds exactly one entry).
- **Owner decision — the recorded rationale, re-checked on this head:** The review asks for an owner
  decision because the exclusion was intentional and test-protected. Provenance from public history:
  - The gate came from a **contributor-authored** commit inside #51324
    ([`6b709d734b`](https://github.com/openclaw/openclaw/pull/51324/commits/6b709d734b), "gate image
    persistence to webchat callers"), landed as `c9449d77b40a`. Its whole recorded rationale is one
    comment line added by that commit:
    `// Gated to non-ACP callers: ACP/IDE screenshots are transient and handled upstream.`
    Later refactors dropped that comment, so on main only the bare `|| isAcpBridgeClient(client)`
    survives (`src/gateway/server-methods/chat-send-user-turn.ts:180-185`) plus the test name this PR
    replaces. The Greptile **bot** summary restated the same premise ("ACP/IDE screenshot flows …
    handle persistence upstream",
    [comment](https://github.com/openclaw/openclaw/pull/51324#issuecomment-4101468041)); none of the
    five human review comments there mention ACP. The maintainer-side concern was double-submission,
    and @obviyus solved it **generically** (`602c0d1e22`: dispatch drops the persisted `MediaPath`s
    on the current turn, the canonical turn is rewritten after dispatch).
  - **"handled upstream" is not implemented anywhere in the tree** (audit at `origin/main`
    `abed61f6400`): `git grep -l -E "saveMediaBuffer|media/store|persistInboundImages" -- src/acp
    extensions/acpx` → **0 matches**, and "screenshot" does not occur in `src/acp`, `extensions/acpx`
    or `docs/cli/acp.md`. The bridge only converts image blocks into Gateway attachments
    (`src/acp/event-mapper.ts:233`), which is what `docs/cli/acp.md:36` documents. There is no
    "upstream" ACP media owner to defer to.
  - **"transient" is not true either** — ACP photos are already persisted today, just not where the
    Control UI can render them: `recordUserPrompt()` clones every prompt content block, image `data`
    included, into the SQLite replay ledger (`src/acp/event-ledger.ts:21-24` →
    `createAcpPromptUpdates`, `src/acp/event-ledger.types.ts:48-53`; row bytes are budgeted in
    `src/acp/event-ledger-bytes.ts`). That ledger feeds ACP `loadSession` replay only. It is exactly
    the reporter's observation: `acp_replay_events` holds the image block with data while the
    transcript holds no media reference. So the bytes are already stored once; this PR adds the
    managed inbound buffer plus a claim-only fact (74 B, no base64 in the transcript) that the
    existing history/renderer path can resolve.
  - The bridge identity does not own media anywhere else either:
    `requiresRuntimeApprovedChatInput()` (`src/gateway/server-methods/chat-send-goal-admission.ts:36-40`)
    has exactly two consumers — the input-commit decision (`chat-send-input-dispatch.ts:294`) and goal
    admission (`chat-send-goal-admission.ts:128`). So the question reduces to: should the canonical
    Gateway durable-media owner cover ACP photos (this PR, +13/-16, reusing existing suppression), or
    should history rendering instead be taught to read the ACP replay ledger (a much larger change
    across history projection and the Control UI, and it would still leave non-ledger ACP sessions
    without media)? @obviyus @fuller-stack-dev — a yes/no here is the only thing this PR is waiting
    on; if the answer is "render from the ledger", I will close this and open that instead.

## User Impact

- **Success criteria:** After a `chat.send` from an ACP bridge client that carries an image
  attachment, the inbound buffer is saved once under `inbound`, and the resolved user-turn message
  carries a claim-only `media://inbound/<id>` fact (`kind: "image"`, no `path`, no `workspaceDir`,
  no base64 `data`) plus its `mediaImageLayout` inline slot, while the dispatched prompt image count
  stays at 1.
- **What should reviewers focus on?** The single condition change in
  `src/gateway/server-methods/chat-send-user-turn.ts` (`prepareChatSendUserTurn`), and the one
  regression fixture `persists ACP bridge photos as durable user-turn media` in
  `src/gateway/server-methods/chat.directive-tags.test.ts`, which replaces
  `leaves ACP bridge user persistence to the agent runtime` — the test that asserted the omission.
  The whole change is +13/-16 lines across two files; no test-lines allocation is needed.
