## Fix PR #201735 description (by fuller-stack-dev, opened 2026-11-19T08:51:34Z)

```text
## What Problem This Solves

When OpenClaw was installed with pnpm (`pnpm add -g openclaw`), a plain `openclaw update` could leave the machine with no `openclaw` command and no Gateway. This was measured in real Docker cells updating published 2026.11.4 to published 2026.11.5 with pnpm 11.28.13, 12.15.0 and 12.21.0:

- The live launcher pointed into the update's temporary stage directory, which no longer existed, so every `openclaw` command failed with `Cannot find module .../.openclaw-update-native-XXXXXX/.../openclaw.mjs`. On 12.15.0 the update even reported success.
- On pnpm 11.28.13 and 12.21.0 the Gateway restart was then refused with `managed-service-ownership (service-ownership-changed)`. The Gateway stayed down after the databases had been migrated (`state-migrated-no-rollback`).

## User Impact

User impact: pnpm-managed installs update to a working CLI and a Gateway serving the new version. If the published launcher still cannot start the new package after repair, the update fails and the transaction restores the previous launchers instead of reporting success.

Installs already updated by an older updater are repaired by the new package itself. Its Doctor (which runs during the update and on `openclaw doctor`) and its Gateway startup rewrite a launcher that provably belongs to this installation and still names a removed update stage, without a user command.

Update behavior for published updaters: the installed updater runs the launcher relocation, so 2026.11.4 and 2026.11.5 still publish a launcher that points into their stage when they update to a release with this fix. In the measured first hops (2026.11.4 and 2026.11.5, each to this fix, pnpm 12.21.0), the new package's Doctor repaired that launcher during the same update. Both updaters handed the post-core steps to the new package (`update-driver-handoff`), which restarted the Gateway on the new version. Both runs ended with exit 0, a working CLI and the Gateway serving the new version. The service-ownership refusal fired only when the new package lacked the fix (2026.11.4 to public 2026.11.5).

## Why This Change Was Made

Launcher (A): pnpm writes shims as `exec node  "$basedir_abs"/'../global/v11/<group>/node_modules/openclaw/openclaw.mjs' "$@"`, with the base and the target quoted separately. The relocation pattern only recognized `"$basedir_abs/<target>"`, so the stage-relative target was published unchanged. #170131 fixed the unquoted `$basedir_abs/` form; the quoted form was never handled. This change:
- teaches relocation and verification the quoted form;
- refuses to finalize, before the Gateway is stopped, a staged launcher that relocation still leaves pointing into the stage;
- makes the post-activation check resolve every launcher target. A launcher whose target is missing is repaired, or the update fails. An unreadable format keeps the existing warning.

Service (B): before stopping the Gateway, the updater records the service as owned by the lexical pnpm global entry (`global/v11/<group>/node_modules/openclaw`). The unit runs the real path that entry resolved to in pnpm's versioned store (`store/v11/links/@/openclaw/<old>/...`). The swap repoints the entry to the new version. Revalidation's install-root-change check then re-inspected the unchanged unit against that same lexical root, which now means the new version, and found it "foreign". This only happens while the old store directory still exists; when pnpm has pruned it, the existing "unresolved" path already passed. Revalidation now also matches the unchanged definition against its own installation root. The protection is unchanged: the definition fingerprint, service name, profile and manager UID must still be the ones admitted before the stop, so an edited definition, or a service of another installation, is still refused.

### Review rounds

Landing review on `387a694` found that the launcher rewrite missed pnpm's escaped spelling when the stage path itself contains an apostrophe. With a pnpm home under `team's base/`, pnpm writes the stage in `NODE_PATH` as `team'\''s base/...`, and the raw prefix replacement never matched it. The repair then left NODE_PATH on the removed stage but still reported success, and the pre-stop guard would have refused every update on such an install. It also found that the pattern stopped at a `"` inside a single-quoted target. Both were real and are fixed in `3df4ba4`. Relocation now parses each shell word, rewrites its value and quotes it again, so every quoting form is handled the same way. Coverage, all red on `387a694` and green now:
- the repair, with the apostrophe below and above the pnpm home and with a directory named `odd "dir" $HOME \ global`;
- the updater (finalize), with an apostrophe in the stage path. A stub `node` checks the exact entry path and NODE_PATH the shell passes.

"Repaired" is reported only when nothing in the launcher still names the stage. The two refusal cases that previously never found a launcher now present one, and each fails when its guard is removed. The private repair directory is removed when the first write fails. Docs now say exactly what the first-hop runs showed.

ClawSweeper round 2 on `3df4ba4` rated it overall D / proof C / patch D. All five findings were real and are fixed in `8db0790`:
- Base directory choice used a textual `$basedir_abs` match, which missed the braced `${basedir_abs}` the rewriter emits. A shim whose bin directory is a symlink would then resolve its target from the wrong parent. Relocation and verification now use the physical bin directory whenever the shim defines `basedir_abs`.
- On Windows, absolute paths in extensionless shell shims lost the forward-slash spelling pass. Shell words and comments now get the same native and forward-slash passes as `.cmd`/`.ps1` shims.
- The repair scan read every PATH candidate before checking its type, so a FIFO named `openclaw` blocked Doctor and Gateway maintenance. It now skips anything that is not a regular file. A new test with a FIFO on PATH times out without the check and passes with it.
- Post-activation verification parsed each launcher twice. `verifyRuntimeLauncher` now returns `unknown-format` from its single read; the swap turns that into the warning and still fails a missing target.
- Docs: automatic launcher repair is macOS and Linux only; Windows users follow the reinstall steps.

ClawSweeper round 3 on `3fdf10a` (round 2's fixes merged with main) rated it overall D / proof C / patch D. All four findings were real and are fixed in `98bad55`:
- The pre-stop guard inspected every file in the staged bin directory, so another global package's shim that still named the stage failed the OpenClaw update. It now checks only the launchers the swap publishes (`resolvePackageUpdateLauncherNames`). A new negative control (`other-cli`) finalizes; the `openclaw` case still refuses. The control fails when the filter is removed.
- Physical-base detection matched any text containing `basedir_abs`, including a directory name in a path. It now requires the shim to assign `basedir_abs`. The new verification test with a lexical shim, a symlinked bin directory and a path that names `basedir_abs` fails on the textual check.
- The repair checked ownership on one read and relocated a second read. Ownership (`cmd-shim-target` equals this installation's entry) is now checked inside the repair, on the same bytes it relocates. If the launcher changed before the rename, the repair leaves it alone. That race is not covered by a test.
- The recovery command lacked `--allow-build=openclaw`. The docs, Doctor and Gateway messages now use `pnpm add -g --allow-build=openclaw openclaw@<installed-version>`, the command the recovery cell ran.

In that layout the stage sits inside the launcher's own directory, and an in-place repair kept the target unchanged, treating it as moving with the directory. A launcher rewritten in place now applies the stage relocation. The updater relocates between different directories and is unchanged. The Gateway test fails without this fix.
