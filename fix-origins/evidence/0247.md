## Fix PR #201336 description (by steipete, opened 2026-11-18T16:18:37Z)

```text
Related: #201057

## What Problem This Solves

If an update is interrupted, for example by a reboot, and the reboot also renumbers the disk (macOS APFS and other filesystems can assign a new device number at boot), every later update fails with `update-recovery-pending`: "Package publication journal does not match its installation … device number changed only". Updates from the Control UI and from `openclaw update` stay blocked until someone runs `openclaw update repair` by hand.

## User Impact

The next update now settles the leftover interrupted operation by itself and proceeds. It uses the same verified remount settlement that `openclaw update repair` already performs, so a user whose machine rebooted mid-update no longer has to find and run a repair command first. Ordinary update admission stays strict: nothing is admitted unless the remount checks (same inodes under one consistent device mapping, recorded package and launcher fingerprints) pass. Unfinished rollback and live original updaters still refuse as before.

Already-released updaters (including 2026.11.2, 2026.11.4 and 2026.11.5) still refuse. Their recovery, verified below: run `openclaw update repair --yes`, then update again.

## Why This Change Was Made

`settlePendingPackageActivation` runs automatically before update admission. Its first automatic gate compared the operation's recorded previous/candidate identities (`device:inode`, recorded before the reboot) with the live installation's identity. After a device renumbering, those never match, so automatic settlement declined, and the strict admission check that follows refused the update. The rest of the same function already compares through the verified remount mapping (`inspectRemount` → `currentIdentity`), which is why `openclaw update repair` succeeds on the same state. The gate dates from #169038, which predates remount settlement (#170046), and was never moved onto the mapped identities.

The fix computes the remount-mapped previous/candidate identities once, before that gate, and uses them there. Production change: 9 lines moved/changed in one function, no new state, no schema or config change. Docs: the remount recovery section of `docs/install/updating.md` now says the next update settles this automatically, and gives older updaters the repair-then-update step.

Alternatives considered: relaxing admission itself to accept device-only drift, rejected because admission must keep refusing unsettled foreign or unfinished operations; and leaving the repair-only path in place, rejected because it leaves Control UI updates blocked with no in-product way forward.

## Evidence

- Regression tests in `src/infra/package-update-activation-remount.test.ts` (`the next update settles a remounted publication with the previous|candidate installed`) run real prepared journals with recorded devices shifted. Both **fail on base** (automatic settlement returns `undefined`; admission then throws `device number changed only`) and **pass with the fix**.
- Consumer suites (remount, repair command, recovery helper, legacy recovery, lease recovery, retirement, publication boundary, publication kill process, plugin cohort settlement): 4 Vitest shards passed. `pnpm tsgo:core`, oxlint and oxfmt are clean.
- **Real remount on Linux (Crabbox AWS, main 7eb33ccb25f).** The npm prefix sits on a loop-mounted ext4 image. `openclaw update` is SIGKILLed after its package activation reached `prepared`. The image is then remounted on a different loop device, giving the same inodes and st_dev 1795 → 1796. Then `openclaw update` runs again:

| Installed updater | Next update | Recovery |
|---|---|---|
| main without fix | rc=1 `update-recovery-pending`, `device number changed only` | `openclaw update repair --yes` rc=0 (`publication-not-started`), then update rc=0 |
| published 2026.11.5 | same refusal | repair rc=0, then update rc=0 |
| published 2026.11.2 (the reporter's version) | same refusal | repair rc=0, then update rc=0 |
| main with fix (×2) | rc=0, `Settled previous package update … (publication-not-started)`, updated | not needed |

  Gap: the kill always landed in `prepared`, so the candidate-installed (`publishing`) remount case is covered by the regression test, not by the live run.
- Reviews: autoreview scoped-clean at P2; an independent Codex review found no findings.
```
