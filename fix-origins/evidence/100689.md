```text
## What Problem This Solves

Addresses #186676.

A PR update can reach GitHub while its confirmation is interrupted. If the original PR then closes, recovering the same request with its original requester still authorized can create a replacement PR. Recovery can also fail after the remote branch is deleted, after the update merges, or when later local work no longer matches the accepted commit.

## User Impact

Recovery records the verified accepted update against the original PR without another push or PR creation. The receipt describes the accepted update; it does not reopen the PR or claim it remains open. Later local commits, staged changes, unstaged changes and untracked files remain intact.

An explicitly new publication request after closure retains its existing behavior. Publisher identity, requester authority, repository and branch checks remain in force. This contribution adds no configuration, protocol, schema or migration requirement.

## Why This Change Was Made

A continued PR keeps its original body marker, while each update has its own request marker in the accepted commit. Ordinary retry checks evaluated the current branch, base and workspace before reconciling that accepted update. A closed PR, deleted remote branch or merged base could therefore send an already accepted request through fresh-publication eligibility.

Both shared-worktree and repository publication now use their existing observation-only recovery owners before retrying. The shared worktree first finishes any request-owned local Git/index recovery. Reconciliation then verifies the recorded commit, tree, parent, publisher and PR identity using retained receipts. A successful observation settles the original request; a genuinely new request still follows the existing publication path. The former executor-specific shortcut is removed.
```
