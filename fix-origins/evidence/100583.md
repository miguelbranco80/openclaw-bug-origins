## Fix PR #165319 description (by steipete, opened 2026-10-05T03:56:56Z)

```text
## What Problem This Solves

Fixes duplicate **Sessions board · …** entries under **OTHER** when Workboard creates its Board agent conversation. Workboard already owns that conversation through its Board agent dock.

## User Impact

Open the conversation from **Board agent** beside its board. Dock conversations stay out of ordinary session lists, Involving me views, Workboard rosters, and people counts. Exact reads and deliberate deep links keep working with the same human creator, sharing, and sandbox rules.

On the next Board agent opening, a legacy ordinary conversation is replaced with a fresh dock conversation. Its old history remains an ordinary session the operator can archive. The new conversation uses the existing reusable `displayName` field so the old unique label remains untouched.

**Agent schema remains 24.** The marker lives only in the session creation stamp in `entry_json`; there is no new column, index, or migration. The schema SQL and Doctor/transcript baseline hashes are byte-identical to main.

## Why This Change Was Made

`sessions.create` and the Control UI SDK accept `surface: "plugin-dock"`. The creation owner persists immutable `createdSurface` metadata while leaving `createdVia` and creator attribution unchanged. Existing sessions cannot gain or lose the marker through adoption, merges, replacement, or transcript rollover. The core field is reserved against plugin extension-slot collisions.

Rows derive `isDock` from that stamp. `excludeDock` filters before facets and pagination, and UI query defaults and event reconciliation maintain that discovery rule. The existing provenance, FTS, and search projections remain unchanged. The Gateway protocol version and public SDK export surface are unchanged.

**Chat empty-state follow-up:** `chat-thread.ts` renders the welcome panel, including Recent chats, for a loaded empty transcript even with an explicit session selected. The composer remains mounted. That separate chat-owner behavior is deferred under the work order.
