## Fix PR #203156 description (by steipete, opened 2026-11-21T16:00:26Z)

```text
Related: #203132

## What Problem This Solves

A completed child result queued behind a private requester continuation can be permanently discarded when a Gateway restart aborts that continuation. The private delivery branch treats the restart as an intentional cancellation and marks the undelivered result failed.

## User Impact

Completed results that have not reached their requester remain pending across restart and are delivered by startup recovery. Results already committed to the requester stay in its saved context without duplicate delivery. No migration, configuration change, or operator action is required.

## Why This Change Was Made

The private completion owner now excludes the existing `stopReason=restart` from intentional non-delivery, leaving its existing retryable outcome in charge. Ordinary cancellation retains its suppression behavior. This is one changed production line, net zero production LOC, with no new persistent states or recovery policy.

Already-consumed private results do not need re-admission: consumption is recorded after transcript commitment. Eligible root requesters resume through existing restart recovery; spawned requesters are not independently resumed, but their next turn sees the saved completion. This does not claim that an aborted private turn already produced a user-visible reply, or that a replacement session inherits another session's context.

## Evidence

A real isolated Gateway regression finishes two children, holds a private continuation consuming the first result, queues the second result, sends SIGTERM, and starts a fresh Gateway on the same isolated state and port. Before the fix, the second result becomes `failed`; after the fix, it remains pending with zero committed inputs, then delivers once. Another restart leaves exactly one committed input and one completion model response.

The consumed-result controls also pass: a top-level private continuation resumes, and an actual spawned requester has no independent restart marker but receives exactly one saved completion in its next model request and produces one reply. All three process cases pass with the current built runtime. The synthetic loopback model observes actual provider requests; no live deployment or production data is used.
