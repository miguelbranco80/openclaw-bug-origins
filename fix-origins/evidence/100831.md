## Fix PR #151165 description (by shakkernerd, opened 2026-09-17T21:34:20Z)

```text
## What Problem This Solves

Broadcast sends destinations sequentially. If a three-destination broadcast sends A, then its caller is canceled while B is in flight, the current runner throws the cancellation and erases A's completed result. Callers cannot tell that A already received the message and can duplicate that delivery by retrying the broadcast.

## User Impact

For targets A, B, and C, an interrupted broadcast now records A as succeeded, keeps B's actual failed or possibly-delivered result, and marks C as `attempted: false`. The overall result remains incomplete. A wholly unsent first or only target still returns the existing strict error.

## Why This Change Was Made

The runner checks cancellation between targets and settles any target whose adapter or Gateway operation was already in flight. Only an exact rejection at the final host handoff proves that the current target never reached provider I/O, so only that result is marked unattempted. Provider and policy failures remain attached to the current target, while explicit partial-send evidence is preserved across core normal, core best-effort, plugin, and Gateway delivery paths.

## Evidence

- Reproduced the rejection and lost prior result against the unchanged broadcast producer on Ubuntu 24.04.
- Blacksmith Testbox: 53 affected tests passed across `message-action-runner.broadcast.test.ts`, `message-action-gateway-reconciliation.test.ts`, and `message.test.ts`. The final test-only head also passed four focused broadcast → `sendMessage` cancellation cases covering ordinary and best-effort delivery, exact pre-I/O rejection, and an identityless first chunk before rejection. Production and relevant test typechecks, extension compatibility checks, formatting, lint, and runtime guards passed; the final head repeated the affected test typecheck.

Fixes #151149
```
