```text
prepareSqliteReadOnlyLocation for strict cleanup explicitly (requireCleanup),
```

## Fix PR #169572 description (by steipete, opened 2026-10-12T03:23:01Z)

```text
Related: #169337, #169482

## What Problem This Solves

Fixes: the Gateway on native Windows with stock Bun (1.4.2, 1.4.3) fails to start at `state.schema-preflight` with `SQLite read-only worker snapshot cleanup failed: ... EBUSY: resource busy or locked, rm '...database.sqlite'`, and `openclaw gateway status --deep` fails with `SQLite snapshot lease cleanup did not complete`.

## User Impact

User impact: Windows users running OpenClaw on Bun can start the Gateway (foreground or as the scheduled-task service) and run `gateway status --deep`. Gateway startup on Windows Bun also needs #169482, which fixes an earlier crash while loading plugin SDK facades. Busy private snapshot copies are logged with a `SQLite snapshot cleanup deferred` warning and removed at exit or by the next Gateway's abandoned-snapshot cleanup. Node and runtimes with qualified native SQLite close are unchanged.

## Why This Change Was Made

Bun builds without qualified native close (stock Bun, every Windows Bun) keep a private SQLite snapshot open after logical close, so Windows refuses to delete it even though the read succeeded. #169337 tolerated that only inside discovery. This moves the policy into the snapshot cleanup owner as one function that callers use only after a successful read. Discovery now uses it, and schema preflight (state and agent snapshots) and state-ownership inspection adopt it. It defers only EBUSY on runtimes without qualified native close. Failed reads, native-close failures, other removal errors, and capable runtimes stay fatal.

`gateway status --deep` runs schema preflight without an abort signal, which made its snapshot cleanup best-effort; the single-flight lease then reported the failure without its cause. Preflight already treats any cleanup failure as fatal, so it now requests strict cleanup explicitly (`requireCleanup`, still implied by a signal) and the EBUSY cause stays visible.

Accepted edge case: on these runtimes a busy snapshot copy (here ~3 MiB) can stay on disk until process exit or the next startup's reclamation. Other best-effort snapshot readers still log non-fatal EBUSY cleanup warnings on Windows Bun. The lease's handling of best-effort failures is left for a separate follow-up because it may be a custody requirement from #160946.

## Evidence

- **Native Windows, stock Bun 1.4.2 (Crabbox AWS, Windows Server, large):** Node 24.18.0, pnpm 12.9.0, Bun from npm. Built from the codeload tarball of `f284985` with #169482 and this diff applied, via `pnpm install --frozen-lockfile && pnpm build`. Result: PASS.
```
