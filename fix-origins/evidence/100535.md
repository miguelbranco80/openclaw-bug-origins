fix(commands): keep plain prose that starts with "queue" from being parsed as /queue

Fixes #188570.

A message that started with the word "queue" as ordinary prose was parsed as the /queue command. The text was dropped and the user got a false command error instead of an agent reply. Only the real /queue command form is now treated as the command. Strict native /queue behavior (see #116688) is unchanged. No system prompts, tool descriptions or agent instructions are touched.

Evidence: built Gateway runs. Main dropped the prose and returned false errors (twice); with this change both inputs reached the provider, as the captured HTTP requests show, with no false error (twice). The strict-native /queue controls were identical in all four runs, with no provider calls. Details: https://github.com/openclaw/openclaw/pull/188571#issuecomment-6530891298.

Thanks @masatohoshino.

Co-authored-by: Ayaan Zaidi <hi@obviy.us>

## Fix PR #188571 description (by masatohoshino, opened 2026-10-30T17:35:31Z)

```text
Closes #188570

## What Problem This Solves

Ordinary user prose mentioning `/queue`, such as `Can you explain how /queue works with followup messages?` or `How does /queue work?`, loses its next word before reaching the agent and generates a false invalid-mode reply.

## User Impact

Ambiguous prose reaches the agent unchanged, without a false queue error. Explicit `/queue:` syntax, an invalid bare mode, option-bearing directives and native slash commands retain validation. A token starting with a recognized mode, such as `/queue collect.`, still reports the invalid mode. Only the first `/queue` occurrence is examined, as before.

## Why This Change Was Made

The existing queue extractor now consumes the strict context already passed by the shared directive parser, paralleling the established inline `/model` prose behavior from #187416. It preserves ordinary unknown-word prose only in non-strict parsing. No configuration, prompt instruction, SDK or persistent-state contract changes.

Behavioral boundary: `/queue foo bar` typed as ordinary chat now remains prose; the same input invoked as a native command remains invalid. `/queue backlog` still reports an invalid mode. Native strictness from #116688 is unchanged.

## Evidence

[Independent built-Gateway before/after captures and strict-native controls](https://github.com/openclaw/openclaw/pull/188571#issuecomment-6530891298).

- Main `b65482ef56e96d512584fc378c73c874c05b22ba`: two fresh Gateway runs both dropped `/queue works` / `/queue work?` and emitted false invalid-mode replies.
- Candidate production revision `be84357306a6e420af3c44843d80a999ae6521d0`: two fresh Gateway runs both preserved each original input in actual HTTP provider requests and delivered only the expected marker reply.
- All four runs retained identical strict-native replies for `/queue Can you diagnose this?`, `/queue collect please help`, `/queue backlog` and `/queue collect.`, with zero provider requests for these commands.
- Secretless Linux arm64 Docker, Node 24.22.1, independently built private QA artifacts, real Gateway children and QA-channel ingress. Model responses were deterministic local HTTP fixtures, not live-provider evidence. No live Telegram claim.
- **81 existing tests passed across four consumer files**. Scoped formatting passed. All existing tests remain; no new test cases or test-budget allocation.

The final head adds only user documentation and removes the contributor's new parser cases; production behavior is unchanged from the measured candidate. Final delta against the merge base: production +20/-1, docs +3/-0, tests +0/-0. Simplification kept one existing extractor and strict-command owner, with no new helper, cache or parser path.

## Merge Danger

**Two-way door:** reverting restores the former parser behavior; no migration, new configuration or stored-state format is introduced. Blast radius is messages interpreted by the shared queue directive parser: an incorrect qualification could consume ordinary prose or fail to validate malformed commands. Native, explicit-syntax, valid-mode and mixed-directive controls remain covered.
```
