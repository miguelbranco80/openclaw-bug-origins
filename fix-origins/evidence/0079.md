## What Problem This Solves

Fixes: Claude CLI models stay "Sign-in needed" in `/models` and the Discord model picker, and `/model` rejects them, after you sign in to Claude Code, if the Gateway started while Claude Code was not signed in (or its first login check failed). Real turns through `claude-cli` worked, but these chat surfaces did not recover until a Gateway restart. The Control UI recovered or not depending on timing.

## User Impact

User impact: signing in to Claude Code on the Gateway host now shows the Claude CLI models as available, and lets `/model` and the Discord picker select them, without restarting the Gateway. The first model list read after sign-in may still show the old state; the next read (or a direct `/model`) uses the new login.

## Why This Change Was Made

- The Gateway records Claude Code's login once at startup and is designed to recheck it after a minute while model lists are read (#166305, #172471). That background recheck was started inside the plugin invocation scope of the request that triggered it. The `claude auth status` probe finishes after that request has replied and closed its scope, so publishing the result threw `Plugin invocation scope is closed`. The error was swallowed, so the stale "signed out" state stayed until restart. The recheck now runs in a detached async context (the same pattern the prepared-model-runtime refresh uses), and an unexpected failure is logged instead of hidden.
- Only Gateway `models.list` (the Control UI) triggered that recheck. `/models`, the `/model` menu and the Discord picker read the same prepared data and never triggered it, so channel-only users could not recover even with a working recheck. They now trigger the same throttled recheck. `/model` selection awaits it, so a direct `/model anthropic/...` after sign-in works on the first try.
- On main, recovery through the Control UI depended on timing: a `models.list` recheck published only if the probe finished before that request closed its scope. In my `models.list`-only base run it won that race and recovered. The failure shows up reliably when `/models` or `/model` triggers the recheck.
- The probe cost limit is unchanged: at most one `claude auth status` per prepared catalog owner per minute, and only while pickers or selections are read.

Not changed: #196694 also suggests passing config into `resolveCliRuntimeModelBackendBinding`. On real Gateways the CLI backend binding was always present (instrumented `binding={"provider":"anthropic","runtime":"claude-cli"}` on every evaluation, including hot plugin enable and `plugins.allow` edits). That issue's failure is the same stale login state shown below, and it went away for the reporter after the Gateway restart. This PR leaves that binding call alone.
