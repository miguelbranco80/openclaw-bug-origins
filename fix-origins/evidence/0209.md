* fix(cli): connect through gateway.remote.edgeAuth without a Gateway token

A CLI behind an identity-aware proxy (Cloudflare Access) has no Gateway
token or password: the proxy authenticates the WebSocket upgrade and the
Gateway uses trusted-proxy auth. `openclaw tui`, `openclaw tui --url` and
`openclaw gateway call` refused to dial in that setup, so the device could
never send the pairing request the Cloudflare Access guide describes.

When edge-auth headers are configured for the target's origin, skip the
local shared-credential prechecks and let the Gateway's device pairing
decide. Targets without edgeAuth, and other origins, keep requiring
credentials as before.

* docs(cli): limit tokenless edgeAuth pairing to trusted-proxy Gateways

* fix(cli): tell an unpaired edgeAuth device to pair through the TUI

* fix(cli): keep an explicit --url in the edgeAuth pairing hint

* fix(cli): request scopes a session-only device grant covers

A device paired with only operator.sessions.write, as the multiplayer
guide recommends for guests, could not use `openclaw gateway call` or
`openclaw tui`: the CLI asked for operator.read (and the TUI for admin,
read, write and approvals), so every connect became a scope-upgrade
request for the administrator.

`gateway call` now projects its least-privilege scopes through the
stored device grant with projectOperatorScopesForMethod, but only when
the method's session-scoped alternative still authorizes the call. The
TUI connects within a stored grant that holds operator.sessions.* and
none of its default scopes, unless a shared token or password is given.

A device approved before it ever connected has no stored grant, so its
first request can still exceed it. The Gateway's scope-upgrade refusal
reports the approved scopes: the gateway client gains an opt-in
fitScopesToApprovedGrant hook that reconnects once within them, which
the TUI uses, and `gateway call` retries once with the session grant.
Both retries store the device token they receive, so later CLI and TUI
connections fit the grant without another upgrade request.

Any other gap keeps the current request, so real upgrades still reach
the administrator. Session-only devices see the session methods; the
TUI's command list and pending approvals stay unavailable.

The CLI scope selection, including the sessions.create cwd escalation
retry it already owned, moves to call-scopes.ts; the gateway client's
host dependency defaults move to client-host-deps.ts.

A caller without operator.read has its own profile published as the
activity viewer in hello. With Cloudflare Access identity deferred until
after hello, hello published null and the later attach changed the
viewer, closing the connection with 4001 "gateway policy changed" when
no named role was configured. Resolve that identity before hello so the
published viewer is already correct.

* fix(gateway-client): document the host-deps assertions moved out of client.ts

the assertion-safety baseline grandfathered them, into client-host-deps.ts.

Related: #199692

Depends on #199693. This branch is stacked on it, so until #199693 merges the diff also shows its commits.

## What Problem This Solves

Fixes: a device paired with only `operator.sessions.write`, as the multiplayer guide recommends for guests, can't use `openclaw gateway call` or `openclaw tui`. The CLI asks for `operator.read` and the TUI for admin, read, write and approvals, so every connect becomes a scope-upgrade request for the admin.

## User Impact

User impact: a session-only guest can list, read and create its sessions from the CLI and use the TUI within its grant. Once the TUI has stored the grant with a device token, its connections and `gateway call` file no upgrade request. Behind trusted-proxy auth the Gateway issues the TUI no device token and `gateway call` stores none, so there each connection is refused once with a scope-upgrade request and then works within the grant. #199699 removes that refusal as a Gateway opt-in.

Devices whose grant holds the general scope are unchanged, and a device that needs a real upgrade (for example `operator.read` to `operator.admin`) still files one.

In the TUI, a session-only device gets no command list or pending approvals, because those need `operator.read` and `operator.approvals`.

## Why This Change Was Made

**Where the client learns its grant:**
- `gateway call` projects its least-privilege scopes through the stored device grant with the existing `projectOperatorScopesForMethod`. It narrows only when the method's session-scoped alternative still authorizes the call.
- The TUI connects within a stored grant that holds `operator.sessions.*` and none of its default scopes, unless `--token` or `--password` is given.

**A device approved before it ever connected:** it has no stored grant, so its first request can exceed it. The Gateway's scope-upgrade refusal already reports `approvedScopes`, and the client uses that:
- The gateway client gains an opt-in `fitScopesToApprovedGrant` hook that reconnects once within the reported grant, which the TUI uses.
- `gateway call` retries once with the session grant.
- The TUI stores the device token it receives with the grant, so its later connections, and `gateway call` reading that stored grant, fit it. `gateway call` keeps its read-only storage mode on the retry and stores nothing.

Until a grant is stored, each connection still files that request first, because nothing tells the client its grant before it asks. Behind trusted-proxy auth nothing is stored, so that holds for every connection. The opt-in Gateway change in #199699 removes it.

**Moves:** two moves keep the touched files within the line-cap ratchet without changing behaviour:
- CLI scope selection, including the existing `sessions.create` cwd escalation retry, moves to `src/gateway/call-scopes.ts`.
- The gateway client's host-dependency defaults move to `packages/gateway-client/src/client-host-deps.ts`. `client.ts` re-exports their types, so the package API is unchanged.

**Docs:** `docs/start/multiplayer.md` and `docs/cli/tui.md` describe the guest behaviour and when the first-connect request remains.
