* fix(worker): carry resolved exec authority across the launch boundary

An isolated worker rebuilt its exec tool at host=gateway/security=full/ask=off
regardless of the policy the Gateway resolved for the turn. Tool names crossed
the boundary on toolAuthority.allowedToolNames; exec mode did not cross it at
all, so a turn whose exec was present but mode-restricted ran at full authority
inside the worker.

Carry the resolved policy on WorkerToolAuthority, validate it in the descriptor
parser against the closed value sets, and consume it in the worker instead of
re-deriving it. Absent authority denies rather than defaulting open, so a legacy
descriptor fails closed. The field is additive and optional; no protocol version
bump.

host=sandbox maps to gateway inside the worker while security and ask are
preserved: createExecTool requires a SandboxContext that an isolated worker does
not have, and the worker is itself the isolation boundary.

instead so the descriptor cannot drift from the resolver that populates it.

## What Problem This Solves

Worker execution must retain the effective policy resolved by the Gateway. Carrying tool names and the host/security/ask tuple alone left three restrictive inputs unenforced: full-permission bypass survived a tightened allowlist, scheduled approval requirements were omitted, and empty safe-bin configuration became broader defaults.

## Why This Change Was Made

- R1: The worker requires final `security === "full"` before bypassing host approval floors. Local construction, authority production, and the worker's additional permission intersection use the pure `projectEffectiveExecPolicy` owner. Its session intersection reuses the existing restrict-only resolver. The full/off positive control remains executable.
- R2: The producer applies the captured scheduled approval requirement through that shared projection. Ask-always clears a conflicting mode and disables full-permission bypass in the local projection. Because worker approval transport is unavailable, the producer withholds exec/process for ask-always or an unsupported captured target and records local-execution guidance. Node/sandbox authority is preserved, never rewritten into usable authority.
- R3: The producer emits the bounded `safeBins: []` restriction. The strict parser accepts only an empty array, rejects malformed/nonempty representations as a whole-descriptor error, and the worker preserves the empty cap. Legacy omission also disables safe bins. Configured safe-bin profiles and explicit command approvals remain local; absolute executable identities are never copied between hosts.

The existing descriptor contract, whole-descriptor rejection, `worker-execution-authority-v1` feature fence, exec-session forwarding, and node binding remain intact. No protocol-version or persistent-state change is introduced.

## User Impact

Tightened allowlist turns deny unapproved commands even under full permission. Scheduled ask-always turns cannot execute headlessly. Empty safe bins stay empty through the worker handoff. Deny remains enforced; absent, sandbox-host, and node-host authority keep exec/process unavailable. The node binding and matching default directory remain represented for a future supported transport.

Retained workers without worker-execution-authority-v1 are reclaimed for reprovisioning. The conservative safe-bin policy can deny commands that previously succeeded remotely through default safe bins or host-local approvals. Run those commands locally with the configured approval policy. Explicit full/off worker execution remains supported.

Execution proof uses the real worker runtime, real exec enforcement, and loopback protocol with scripted inference. The scheduled placement proof exercises the production admission/launch producer against an active placement; no deployed cron job or external node RPC was exercised. The separate Codex remote-exec path is outside this change.
