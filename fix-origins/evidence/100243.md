## What Problem This Solves

`openclaw doctor --fix` can reject its required pre-migration SQLite snapshot on Linux hosts without `statx`. Thanks @StevenKrebs for reporting this and @jayzhou2309 for the original fix and Linux reproduction.

## User Impact

Doctor can publish unchanged rollback backups on these hosts. Changed file identities, sizes, or database bytes still fail verification.

## Why This Change Was Made

Node/libuv can substitute ctime when the filesystem cannot report birth time. Removing the original hard-link name changes ctime, so comparing the publication receipt's birth time to a later stat can reject the same unchanged inode.

The intermediate transfer fingerprint now compares only device/inode identity and size on every platform. The snapshot owner retains its content hashes before and after publication. Coverage uses real hard-link publication with zero and ctime-derived birth times, checks database contents and cleanup, and rejects actual same-size byte changes instead of treating an mtime-only change as rewritten data.

### Real behavior proof

Doctor's pre-migration backup runs on real Linux from source, on upstream/main d41a61f9b80 (before) and on this branch 946d8607516 (after). The script calls the same code `openclaw doctor --fix` uses for its rollback backup: it takes the real Doctor maintenance lock (`withDoctorSqliteMaintenanceLock`) and runs the Doctor backup owner (`backupDoctorSqliteDatabases`) on a fresh shared state database created by `openOpenClawStateDatabase`. That reaches `createVerifiedSqliteSnapshot` and the hard-link publication. Nothing is mocked: no `process.platform` override and no stat stubs. It does not run the full `openclaw doctor --fix` CLI, and the database is a new one rather than an upgrade from 2026.9.4 with a pending schema migration.

Setup: Docker on an arm64 Mac (Linux kernel 7.0.12-linuxkit, the `node:24-bookworm-slim` image, Node v24.21.0, the version in the issue). Both revisions are bundled with esbuild from the repo source, along with their `infra/*` worker entrypoints. This kernel has `statx`, so the "no statx" condition from the issue is made with a seccomp profile. It returns `ENOSYS` for `statx` calls that use libuv's mask (`0xFFF`, basic stats plus btime), and for `io_uring_setup`. That is the result libuv gets on Linux 4.4. libuv then falls back to plain `stat` and fills birthtime from ctime (`deps/uv/src/unix/fs.c`, the `uv__fs_statx` fallback). The filter matches only that mask because runc itself calls `statx` with `STATX_MNT_ID` during container start.

The stat probe line comes before the backup. It writes a file, hard-links it, unlinks the original name, and stats the link. With `statx` blocked, birthtime equals ctime and moves when the unlink changes ctime. That is the field main's fingerprint compares.

The full matrix ran twice, with the same results both times:

| Node `statx` | State dir filesystem | birthtime moves on link+unlink | main d41a61f9b80 | branch 946d8607516 |
|---|---|---|---|---|
| blocked (`ENOSYS`) | container filesystem (overlayfs) | yes | **fails**: `staging file changed during transfer` | backup saved |
| blocked (`ENOSYS`) | bind mount from the macOS host (virtiofs) | yes | backup saved | backup saved |
| available | container filesystem (overlayfs) | no | backup saved | backup saved |
| available | bind mount from the macOS host (virtiofs) | no | backup saved | backup saved |

What this shows:

- The failure needs Node to fall back from `statx`. With `statx` available, Linux reports a real birthtime that does not move, and main publishes the backup. So the Linux 4.4 `statx` gap in the issue is the trigger.
- On the bind mount from the macOS host, main did not fail even with `statx` blocked. The cause is not traced. A guess is virtiofs attribute caching hiding the ctime change during the transfer window. The issue's bind mount came from a Linux host, which this setup does not reproduce.
- The branch saved the backup in every case.
