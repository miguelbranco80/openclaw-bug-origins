```text
When an automatic compaction summary actually times out while the caller is live, the session commits a deterministic reduction (recent suffix verbatim, previous summary carried forward, loss notice, split-turn ask) so the turn answers and the next turn does not re-run the same timed-out summary. Manual /compact, Stop, run timeouts and non-timeout errors are unchanged.
```

## Fix PR #164246 description (by obviyus, opened 2026-10-03T10:23:40Z)

```text
Refs #164220

## What Problem This Solves
An automatic compaction whose summary request times out ends the turn with "⚠️ This conversation is too long, and shortening it took too long…". The session stays above the threshold, so every following message runs the same summary again, waits out the same 180 s window, and fails again. The conversation stays dead until someone runs `/compact` or `/new`.

## Root cause (provenance)
`executePreparedCompactionSession` (`src/agents/embedded-agent-runner/compaction-session-execution.ts`, client-summary block) turned every summary-stage failure into `fail()` without committing anything. The next turn's preflight (`runSessionCompactionIfNeeded` in `agent-runner-memory.ts`, "Preflight compaction required but failed") or overflow recovery (`overflow-context-recovery.ts`, `kind=compaction_failure`) then ran the same compaction again. The per-request host watchdog from #130993 (a93a015a5695) and #163636 (02ec714206d) is kept. Nothing used the cut that compaction had already prepared once that watchdog fired.

## Fix
- **Reduction.** `compactWithoutSummary(preparation)` in agent-core `compaction.ts` builds the commit-ready artifact without a model call. It shares `finalizeCompaction` with `compact()`.
  - It uses the cut `prepareCompaction` already chose, so the recent suffix stays verbatim and tool-call/result pairs stay intact.
  - It carries the previous summary forward, keeps file operations and the unresolved request, and names how many messages were dropped.
  - The loss notice and a split turn's raw source ask are required content during fitting; only the carried summary shrinks. This keeps the #130993 split-turn source-ask invariant. The source ask uses safeguard's existing 2,000-character bound: `formatRequiredAskContext` moved from `compaction-safeguard.ts` into agent-core, and both now share it.
- **Commit path.** `AgentSessionCompaction` has a new `"deterministic"` summary policy. It skips auth, summary hooks, and the model, and commits through the existing `appendCompactionAsync`. Transcript rows are untouched, so a later model compaction stacks on top normally (covered by a test).
- **Trigger: an actual summary timeout only.** Either the summary watchdog fired (its composed signal aborted while the caller's `params.abortSignal` did not), or the provider answered HTTP 408 or 504. The status comes from structured provider identity: `runSummarizationCompletion` now returns `SummaryProviderError`, which carries the failed provider response. The delegate finds it through the error's cause chain (safeguard wraps it) instead of parsing wrapped text. Failover's broader "timeout" class, which also covers fast 5xx, 410, DNS failures, and text-only "request timed out", keeps its existing outcomes, including the model fallback chain. The compaction must also be automatic (not manual), and the caller must still be live: no Stop, run timeout, or outer host deadline. The delegate re-arms the delegated watchdog synchronously before committing.
- **Persistence-stage timeout.** A new `onSummaryReady` signal marks the end of generation. A timeout during persistence keeps the existing failure, so a real summary is never discarded.
- **Backoff:** the committed reduction brings the session under the threshold, so the next turn does not compact. No new state, store, or config.
- **Diagnostics:** `[compaction-diag] fallback … reason=timeout summary=deterministic` (warn), and the debug `end` line reads `reason=timeout summary=deterministic`.
- **No model fallback after a timeout (deliberate).** A timed-out summary commits the reduction instead of trying the next model. Each extra candidate could add another full window to the user's wait; with two configured fallbacks that is about 9 minutes. On main the chain never ran after a watchdog timeout anyway, because the outer watchdog fired at the same moment. Rate limits and other failover errors still use the chain. A test documents this.

### Safeguard timeout exception (accepted by the maintainer)
In safeguard mode, a summary timeout now commits this reduction, so safeguard gives up its identifier-retention guarantee for that compaction:
- Older facts that were never summarized leave the model context.
- Later compactions do not bring them back, because each one starts from the previous compaction boundary. Transcript rows stay for history and explicit retrieval.
- The recent suffix, tool pairs, the pending request, and a split turn's original request are kept verbatim.

Why: the alternative dead-ends the session, with every turn waiting out the same timeout. The exception covers only summary-generation timeouts while the caller is still live. Quality rejections and all other errors keep the preserve-history outcome. Documented in `docs/concepts/compaction.md`.

### Decisions kept
- Stop and run timeout are unchanged (#133260 fa6b02a14d6e, #159105 374f893b896c).
- A custom engine is still bounded once at the host (#130993).
- Manual `/compact` still reports failures.
- Non-timeout summarizer errors keep their owners' outcomes: safeguard cancellation, overflow tool-result truncation, the rate-limit and generic-timeout fallback chain, the existing failure text, and the `gateway-compaction-abort` QA `active-failure` contract.
- Safeguard corrective-generation cancellations stay terminal, as on main. **Not changed (deferred, maintainer-approved):** a provider-returned 408 during a safeguard corrective attempt does not recover. A corrective attempt that stalls into the summary watchdog does.

### User-visible
No new notice. The answer arrives as usual. `notifyUser` users see the same start/end notices as for any successful compaction. NO_REPLY, quiet mode, and `delivery: none` paths are untouched.

### Bounded cost
- One wasted summary window per timed-out compaction (the configured `timeoutSeconds`, default 180 s).
- Then local work only: no model call, one transcript append.
- No later turn pays the window again until the transcript grows back to the threshold.
- No extra model candidates are tried after a timeout.
```

```text
prepareCompaction short-circuited to undefined whenever the last session
entry was a compaction record, treating it as a no-op signal. That proxy
does not hold: the retained context (prior summary + kept recent turns +
system prompt + injected files) can still exceed the compaction threshold,

reports nothing to do. It only becomes eligible once enough new turns
append that the compaction record is no longer last.

re-compaction path stays reachable: prepareCompaction continues to walk
```
