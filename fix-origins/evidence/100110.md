## Fix PR #153789 description (by steipete, opened 2026-09-20T15:25:55Z)

```text
Related: #153704 (comment 6). Thanks @britrik for reporting the macOS shutdown and repair-admission failure.

## What Problem This Solves

Fixes macOS Gateway stop reporting success before it has proved that the LaunchAgent is unloaded and its process has exited, followed by repair refusals that do not name the stop command.

## User Impact

`openclaw gateway stop` and `openclaw gateway stop --disable` now unload the LaunchAgent through launchd and verify shutdown before reporting success. `--disable` still preserves the disabled policy across logins. Failed shutdown reports the exact native command and required macOS session; update/repair admission names the profile-aware managed-service stop command and explains an incomplete shutdown when stop already returned successfully.

## Why This Change Was Made

The default stop owner accepted bootout and checked only the Gateway port. The separate disable-plus-stop path could deliberately leave the job loaded, which fails the update publication precondition even with no current process. Both modes now share bootout and verification of the unloaded label plus the original and subsequently observed service PIDs. Running states without a verifiable PID fail explicitly. Delegated update authority is rechecked after awaited work and before native writes or stale-process cleanup. The redundant stopped-state poll, fallback branches, and retired mutation mode are removed.

The service lifecycle owner remains `src/daemon/launchd-stop.ts`. Candidate Doctor diagnostics use the existing refusal-formatting owner and the activation markers already set by released update drivers. Standalone repair retains its existing stop/restore custody. Detached update handoffs retain their separate parent-exit contract and existing unload verification; this change does not alter update backups, rollback, or schemas.
```
