## Fix PR #170086 description (by steipete, opened 2026-10-12T18:23:25Z)

```text
## What Problem This Solves

This repair keeps update confirmation bound to the Gateway and profile that opened it, including while the confirmation UI loads and while a native update decline is pending. A stale confirmation closes without dispatching to the replacement target. Ordinary reconnects and legitimate offline acknowledgement of the same target remain supported.

## User Impact

Update confirmation keeps the original Gateway/profile target and visibly refuses revoked administrator access before either native or Gateway dispatch.

## Why This Change Was Made

Target identity and live administrator authority now have separate responsibilities. Changing Gateway/profile retires the intent; losing administrator access on the same target preserves the existing visible refusal. Both native-capable entry points, Inbox and Custodian, provide a live authority check immediately before host dispatch, and the shared confirmation refuses native dispatch if that check is absent. Gateway updates still pass through the existing current-client authority and config-write-drain owner. UpdatesPage remains deliberately Gateway-only. No installed updater, native protocol, stored format, or actual installation/restart changes are involved.

The first CI run found two real integration defects: ConfigPage's fixture omitted the new target-capture method (job114950163086), and three original native-authority browser cases lost their administrator-access alert (job114950163440). Both failures were reproduced locally with the original assertions. Independent review then caught the missed Custodian authority callback; its rendered real-owner negative test reproduced a native post after revocation, and the final repair closes that path. The sidebar native fixture was aligned with the same explicit callback contract. Earlier green focused tests did not cover those missed callers; this follow-up supersedes that incomplete evidence.

The final pinned-CI Bun selection passes 103 tests across ConfigPage, UpdatesPage confirmation, the confirmation runtime, native routing, Custodian, and SidebarUpdateCard in 9.295s wall. The full Chromium native-authority file passes all six cases in 29.834s wall: the four original cases retain their assertions, and the two added real-bootstrap cases prove posted → profile reassignment/admin revocation → declined sends zero update.run requests. Replaying that declined event after authority restoration still sends zero; a fresh current-target intent sends exactly one request and duplicate decline does not repeat it. The two browser cases measured 1.695s and 3.680s; rendered Custodian allowed/revoked cases measured 22ms/16ms and the missing-callback runtime case 133ms in the combined run. Hosted UI checks measured the Custodian allowed/revoked cases at 104ms/37ms and missing-callback case at 65ms. Native browser case costs remain to be extracted from the owning CI shard. Tests use mocked native/Gateway transports, not a real macOS updater.

The original wrong-target screenshots remain applicable. Same-target refusal before/after captures are in [the inspected screenshot proof](https://github.com/openclaw/openclaw/pull/170086#issuecomment-6130435398). They show the previously missing administrator-access outcome and its restored visible refusal. All captures are synthetic.

The owning UI app, pages, components and E2E type graphs, scoped typed lint, formatting, documentation sanity and diff checks pass. Fresh independent P2 review is scoped-clean. The existing original wrong-target screenshots and their links remain part of the proof.
```
