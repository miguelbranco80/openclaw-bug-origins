Fixes #188067.

## What Problem This Solves

Attaching an open file from **Files → More file actions → Attach to session** could silently produce no draft attachment if the pane refreshed during its download. Resizing the browser is one reproducible trigger, even when the selected file, destination session and access remain unchanged. An immediate-download control worked; the failure was in retaining the accepted action across refresh.

## User Impact

The selected file can finish attaching to the existing message draft while the pane refreshes. Existing message text and attachments remain intact, and the action still sends nothing automatically. Actual source, session, read-owner, connection or authority replacement keeps the existing cancellation behavior. Original file bytes, unsaved-editor text, upload permissions and attachment size limits continue through their existing owners.

## Why This Change Was Made

The attachment operation compares callback identities before the next UI frame commits. Both composer destination callbacks and the artifact-download resolver were recreated during every pane render, so equivalent frames looked like different owners.

Keep the composer callbacks for their captured state, read lifecycle and read signal, and keep the artifact resolver for its captured state. Changing those owners replaces the callbacks; changing attachment membership, limits or availability still produces current values. This preserves the operation's cancellation checks instead of removing them. The two existing producers retain one current binding each, with no new global cache or lifecycle service.

## Evidence

The complete browser flow failed on the base when a file-download response was held through a real pane resize: the selected file and authority fields stayed equal, all four callback identities changed, and no attachment appeared. A separate live saved-file reproduction held delivery of the actual HTTP 200 response, resized, then released the same 786 bytes; it produced the same missing attachment while preserving existing unsent work.

The regression extends the existing Files → Attach → Send scenario with that held read and resize, plus assertions for unchanged draft text and no automatic send. Existing original-byte, unsaved-editor, cancellation and composer-handoff checks remain in scope. The implementation adds 34 production lines and 9 regression lines; the allocation record covers only those 9 test lines.
