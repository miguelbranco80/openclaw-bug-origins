## What Problem This Solves

Fixes scheduled script message actions receiving a missing creator origin at core admission even when the job retains a matching recorded origin.

## User Impact

**This fixes the core admission handoff, not end-to-end account-bound Telegram deletion.** The bundled Telegram adapter separately requires authenticated current-conversation binding. A recorded channel/account origin alone does not supply it, so those scheduled mutations remain denied before provider HTTP.

No creator origin or conversation authority is inferred from routing, no account-bound job is upgraded to operator authority, and provider target checks remain unchanged. Supporting account-bound scheduled Telegram mutations needs a separately agreed authority-capture and revocation contract; this PR does not introduce one.

## Why This Change Was Made

Script preparation already resolves the recorded origin into the scheduled policy context. Admission now consumes that same prepared context instead of the bare persisted policy. This completes the core handoff left outside the preparation/cache fix in #176158.

```text
## What Problem This Solves

Scheduled condition triggers and script payloads cannot call configured MCP servers, so an automation whose "is there anything new?" check needs an MCP tool (Wispr, Plaud, Composio, GBrain…) has to start a full model turn every fire, even when nothing changed.

## User Impact

A trigger or script payload can now call `MCP.<server>.<tool>(...)` for servers the job's `toolsAllow` names explicitly (`<server>__<tool>` or `<server>__*`, matched against the full configured safe server name, which may itself contain `__`), so an MCP-backed job can return `fire: false` on quiet fires without any model call.

Existing jobs are unchanged: a script whose source never mentions `MCP` starts no server (even when `toolsAllow` names one for an agent-turn payload), and `*`, absent, or unprefixed caps expose no `MCP` at all. A named server that fails to start is simply absent from `MCP`, so an outage of a server the script does not call cannot block it; if the script then fails, the run error ends with `MCP server "<name>" is unavailable: <reason>`.

## Why This Change Was Made

The exclusion was not a policy decision: the v1 trigger PR (#101195) never acquired the session MCP runtime, and a comment described the bridge incorrectly. Each evaluation now gets its own MCP runtime through the same acquisition, `toolsAllow`, final tool policy, `before_tool_call` hooks and approvals as embedded runs, and retires it when the evaluation ends. Teardown holds a finished evaluation for at most a fixed 1 s grace (success, failure, timeout or abort alike) through the existing agent cleanup owner; a hung connect or slow shutdown keeps retiring as tracked background work instead of holding the result or a trigger slot. Trigger (30 s / 5 calls) and payload budgets are unchanged; connect time counts against them.

LOC vs `origin/main`: production +224, tests +257 (one new file), docs +19.
```
