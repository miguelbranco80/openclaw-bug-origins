## Fix PR #195351 description (by saariuslystoned, opened 2026-11-08T18:52:31Z)

```text
## What Problem This Solves

Fixes: on iOS nodes, `calendar.add` fails with `CALENDAR_INVALID: startISO required` and `reminders.add` fails with `REMINDERS_INVALID: dueISO must be ISO-8601` when the timestamp has fractional seconds, for example `2026-11-08T10:00:00.000Z`, which is what JavaScript's `toISOString()` produces. `calendar.events` and `motion.activity` / `motion.pedometer` are also affected: they silently ignore such a `startISO`/`endISO` and query their default range instead. Android accepts the same values (`Instant.parse`).

## User Impact

User impact: calendar, reminder and motion commands on iOS accept ISO 8601 instants with or without fractional seconds, matching Android. Output timestamps are unchanged.

## Why This Change Was Made

Each service parsed with `ISO8601DateFormatter()` using its default options, which reject fractional seconds. A new `OpenClawISO8601.date(from:)` in OpenClawKit tries `[.withInternetDateTime, .withFractionalSeconds]` first, then the default form. Calendar (`add` and `resolveRange`), reminders (`applyDueISO`) and motion (`resolveRange`) now parse through it.

## Evidence

Standalone run of the helper file from this branch against the default formatter used on `main`:

+import Foundation
+
+/// Parses ISO 8601 instants sent in node command params.
+///
+/// `ISO8601DateFormatter()` with default options rejects fractional seconds, but
+/// JavaScript's `Date.prototype.toISOString()` always emits them
+/// (`2026-11-08T10:00:00.000Z`), and Android's `Instant.parse` accepts both forms.
+public enum OpenClawISO8601 {
+    public static func date(from string: String) -> Date? {
+        let fractional = ISO8601DateFormatter()
+        fractional.formatOptions = [.withInternetDateTime, .withFractionalSeconds]
+        return fractional.date(from: string) ?? ISO8601DateFormatter().date(from: string)
+    }
+}
