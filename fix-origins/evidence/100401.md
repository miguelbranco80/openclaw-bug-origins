## Fix PR #163090 description (by steipete, opened 2026-10-01T23:29:05Z)

```text
## What Problem This Solves

Fixes: an already-open Control UI tab from the previous build gets 404s for its lazy `assets/*` chunks for several seconds after the Gateway restarts (for example right after `openclaw update`), so opening a not-yet-loaded view fails even though that generation is retained on disk.

## User Impact

User impact: right after a Gateway restart, an old tab's lazy chunk request waits for the retained-generation check to finish, then gets the retained bytes, instead of failing with "Importing a module script failed". Chunks of the current build and cached responses never wait.

## Why This Change Was Made

Retained generations (#129922, #131930) are invisible until `prepare()` finishes re-verifying every retained generation's bytes. On a loaded host that took 5–17 s after ready, and until then `resolveAsset()` returned null and the HTTP path 404'd immediately.

The retention owner now makes `resolveAsset` async. On a miss while a preparation's inventory phase is running, it joins that phase (success, failure, or abort all release it) and looks up once more. It waits only for inventory, not for the later publication and prune. The wait needs no new timer: preparation is already bounded by the retained-cache limits and aborts on lifecycle stop, disable, and Gateway restart drain, which releases waiters with a miss. Verification checks, limits, publication, and prune behavior are unchanged. There is no new config and no new persisted state.

The optional "let inventory yield to foreground work" idea is not part of this PR. Stale-tab requests now wait on the inventory, so slowing it would lengthen that wait, and no interleaved A/B shows a first-visible win.

Known separate limitation, not changed here: today's Control UI build is ~53 MB per generation (1,434 manifest assets: ~33.5 MB JS plus ~18 MB `.br`/`.gz` sidecars). That means the 96 MiB budget cannot keep the current generation plus a full prior one, and the post-update prune removes the prior generation. Chunks served before the prune keep coming from the per-root in-memory cache; chunks first requested after the prune still miss. This is being handled in a separate follow-up.
```
