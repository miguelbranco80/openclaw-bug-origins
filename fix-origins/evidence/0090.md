## Fix PR #200172 description (by steipete, opened 2026-11-16T16:38:48Z)

```text
Related: #197083
Related: #200022

## What Problem This Solves

Fixes: a managed update from 2026.11.3 or 2026.11.4 can leave the Gateway stopped and report "data at risk" when an `openclaw update status` call, or another reader, is running while the updater snapshots the databases.

## User Impact

User impact: such updates now finish on the new version instead of stopping the Gateway. Automatic database restoration is still unavailable for that update, and Doctor now says so in a warning.

## Why This Change Was Made

Published updaters record database fingerprints that include SQLite's WAL-index change counter. If readers keep the WAL index alive past the updater's last ledger commit, the next native open after they exit rebuilds that index. The counter resets, even though no data changed. The target Doctor then refused its first attributed write with "SQLite migration source changed after update capture". The parent refused rollback because its own comparison failed the same way. The parent's forward recovery then migrated with the target Doctor, could not read the migrated data, and kept the Gateway stopped.

Doctor now recognizes that one shape at its first admission. A database that differs from the parent's capture is adopted only if its WAL index was rebuilt over retained frames: the WAL is non-empty, iChange is zero and the last frame checksum is non-zero. Any commit after the rebuild would raise iChange again. In that case Doctor:

- keeps reporting `unchanged: false`, so the parent still refuses restore;
- warns that SQLite rebuilt the index and restoration is unavailable;
- attributes its own writes from the admitted state, so the update finishes forward.

Any other change before admission, such as a foreign shared write, still refuses at the first attributed write, as before. Writes after admission also still refuse.

Old updaters (11.3 and 11.4) take this target-side path, so this fixes 11.x → next-release hops. A 2026.11.4 *target* (#200022, 11.3 → 11.4) is not changed by this PR.

## Safety and Scope

**What is adopted.** Only databases whose difference matches the rebuilt-index shape are adopted. A real write before admission reaches that shape only if it commits frames and then every connection leaves without a checkpoint, so that the next open rebuilds the index. In practice this needs the last writer to crash, or a read-only connection to close last. Even then no data is lost: every parent's restore gate re-compares the live generations to its capture and refuses, because a restore would discard that write. The pre-fix flow also migrated the same bytes forward, through the parent's forward recovery. The existing foreign-shared-write refusal (`client-credential-update.test.ts`) and the 2026.9.34 changed-data cases still refuse unchanged. Content identity cannot be compared directly: the fingerprint a published parent sends is sha256 over [dev, ino, birthtime, content digest, iChange, frame checksum], and the rebuild has already erased the old iChange.

**Main as the parent.** Main's own generation reader is just as sensitive to rebuilds. In a local check, a capture taken while a reader holds the index, then a reader exit and a non-writing reopen, changed the committed generation both with and without a TRUNCATE checkpoint. With this PR, a main → future hop that loses that race completes forward, but automatic restore is unavailable for it. Making the fingerprint survive rebuilds is planned as a follow-up: compare against the generation with iChange normalized, since the frame checksum and content digest already record the writes. That follow-up changes how parents and targets interpret the same value across versions, so it is kept out of this fix.

**What this does not fix.** A later Doctor failure under an 11.3 or 11.4 parent still ends in "rollback refused → forward recovery → that parent's own settlement cannot open the migrated data → Gateway stopped". That code ships in the parent and hands off to the new driver only after Doctor succeeds, so the target cannot change it. On the installed new version, `openclaw update repair` recovers, as confirmed in #200022. A fix for the parent would need an 11.4.x patch release, which is a maintainer decision.

## Evidence

- Crabbox AWS reproduction, 11.4 → main `f6d0c3ea69a` (1 GB state DB, two `openclaw update status` pollers), monitored with auditd and a 100 ms watcher on the SQLite family. The run stranded: `openclaw doctor` failed with "migration source changed", rollback was refused, settlement failed with "cannot open your existing data", and the Gateway was left inactive. At the end of capture the readers exited, and the 11.4 driver's next native open rebuilt the WAL index. `-shm` went from iChange `0x7d` to `0`, while the frame checksum, WAL bytes and DB bytes were unchanged.
- New regression test `migrates after a no-write WAL index rebuild while the parent's restore stays refused`. It fails on base with the same error and passes with the fix.
- Existing refusals are unchanged: the 2026.9.34 changed-data cases, the outside-commit tests, the after-admission predecessor-stop case and the client-credential foreign-shared-write test all still pass.
- `tsgo:core` and `oxlint` pass on the touched files.
- autoreview at P2: one finding, declined and named in a code comment. A commit after capture that only read-only connections outlive, followed by a rebuild, matches the adopted shape (see Safety and Scope). A re-review with that context came back scoped-clean. An independent `codex exec` review of the narrowed diff found nothing.
```
