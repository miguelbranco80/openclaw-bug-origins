## Fix PR #199525 description (by obviyus, opened 2026-11-15T08:31:09Z)

```text
## What Problem This Solves

Fixes duplicate pull requests when an agent publishes a local checkout, commits a follow-up such as a CI fix, and calls `github_publish(workspacePath)` again.

Related: #196168.

## User Impact

Later publications from the same conversation and canonical checkout update the existing task branch and PR. Follow-up commits, amends, and rebases—including rebases with identical file contents—retain the right PR diff. The requesting conversation keeps its original workspace, and the source checkout is unchanged.

An existing publication task from an earlier version is reused when exactly one matches. If several match, the error identifies their session keys and readiness command instead of guessing or creating another PR. Existing accepted requests retain their original task and snapshot, even when the source has newer committed or uncommitted changes.

No configuration, schema migration, or administrative binding repair is required. Existing project, requester, filesystem, and publication authorization remains; a reused task is authorized before its checkout is synchronized.

## Why This Change Was Made

#196168 separated publication custody from the initiating conversation, but keyed each task by the tool invocation's idempotency key. A fresh call therefore selected a new task, branch, and PR. This change keys new tasks by conversation and canonical checkout, gives exact accepted receipts precedence, and discovers older tasks through their recorded source checkout.

Before a fresh publication, the existing task advances with an exact-tree merge retaining the source commit's ancestry. Checking both the tree and ancestry matters: a same-tree rebase still needs the new upstream history so upstream changes disappear from the PR diff. The coordinator, receipt schema, credential owner, and GitHub publisher remain unchanged.

Accepted edge case: if a newer publication advances this task while an earlier request is queued, the earlier request can fail with the existing workspace-changed error; the newer request publishes the current work. Ambiguous historical tasks require deliberate selection because automatically choosing one could update the wrong PR.
```
