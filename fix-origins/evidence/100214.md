## Fix PR #164477 description (by PollyBot13, opened 2026-10-03T19:11:00Z)

Related: #162497

## What Problem This Solves

Fixes new SQLite work being refused when cached, idle shared-state client handles occupy all 64 broker reservations.

## User Impact

New work can reclaim owner-confirmed idle shared-state capacity without raising the cap or interrupting accepted work. Retired clients reopen on their next use; no configuration, schema, data-retention, or migration change is required. The coordinator's decision is that pressure-triggered idle-handle retirement is in scope for this bug fix.

This is a partial fix for the linked issue. Cached per-agent memory-publication workers can still retain executor borrowers, and busy or non-reclaimable clients can still exhaust capacity. The separate provider-overload classification repair is already merged in #162624.

## Why This Change Was Made

The broker previously rejected a new store as soon as 64 client handles were retained. The shared-state owner already knows how to retire idle clients and reopen them safely. Admission now asks that owner for capacity, waits for retirement, rechecks opening authority and cancellation, and reserves the freed slot synchronously. Accepted scopes, pending commands, maintenance clients, and other runtime generations remain protected. Shutdown and failed-worker cleanup remain joined.

Original fix by @PollyBot13; maintainer cleanup simplifies the context and reclamation lifetime, adds cancellation and post-retirement authority coverage, and replaces repeated native-worker test setup with in-memory contract fixtures. The shared-owner integration regression still exercises the actual 64-client limit and persisted readback.
