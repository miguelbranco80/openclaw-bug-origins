Fixes #176057

## What Problem This Solves

A managed PR can receive a descriptive title during review but still land with its original generic commit subject. This happens for a one-commit PR when GitHub uses its commit title as the default squash subject. Metadata editing succeeds, yet that useful review title is missing from permanent history.

## User Impact

Managed squash landing uses the current PR title read by the merge action, for both local and repository-backed publication. The existing expected-head guard, contributor trailers, repository checks, and recovery after an uncertain response continue to apply. Merge and rebase methods retain their existing commit-message behavior; this does not rewrite published history or change repository settings.

## Why This Change Was Made

The action already retrieves and validates the title while inspecting the PR. It now supplies that value through GitHub's existing `commit_title` field for squash requests. The correction stays in the current merge owner and adds no state, configuration, or public API input. The canonical managed GitHub documentation describes the title behavior.

## Evidence

The regression exercises the actual agent tool and registered Gateway method with real local publication Git operations and synthetic GitHub responses. It verifies a one-commit publication with a generic subject, edits the PR title through the tool, and checks the resulting merge request alongside its pinned head and contributor trailers. Both local and repository cases failed on the base because the title field was missing. The repository case also covers an accepted merge with a lost response and repeated request, while merge/rebase controls check that those methods receive no title override.

`pnpm test src/gateway/github-publication-actions.test.ts --maxWorkers=1` passed all 32 cases in 57.13 seconds wall time (55.44 seconds in Vitest, including preparation). The two title cases took 826 ms and 713 ms. This existing integration file also verifies real publication, authorization, and recovery; its longer workspace-refresh scenario remains unchanged.
