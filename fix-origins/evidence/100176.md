## Fix PR #150851 description (by kybrcore, opened 2026-09-17T11:39:48Z)

```text
Closes #150850

## What Problem This Solves

Fixes: the Z.AI built-in catalog is empty when the provider is configured with a China endpoint (`https://open.bigmodel.cn/...`), because the plugin's `providerEndpoints` declares only `api.z.ai`.

## User Impact

User impact: deployments using China endpoints (bigmodel.cn keys, GLM Coding Plan CN) get the six built-in GLM rows in `openclaw models list --all --provider zai` and in model pickers, instead of hand-authoring `models.providers.zai.models` and keeping that list current.

## Why This Change Was Made

`isProviderCatalogSourceAllowed()` only trusts a plugin's catalog when the configured provider-level baseUrl matches a declared endpoint (`docs/plugins/manifest/providers.md`). The plugin itself ships and recommends the China endpoints: the `zai-coding-cn` / `zai-cn` auth choices write `https://open.bigmodel.cn/...`, and `extensions/zai/onboard.test.ts` asserts `ZAI_CODING_CN_BASE_URL`. The declared endpoint list was therefore incomplete. Declaring `open.bigmodel.cn` makes the documented "Built-in catalog" behavior apply on those endpoints.

`scripts/lib/official-external-provider-catalog.json` is updated in the same commit because `src/plugins/official-external-provider-endpoints.test.ts` requires the mirror to match the manifest.

## Evidence

Predicate check with the installed `@openclaw/zai-provider@2026.9.4` manifest and the reported config (`models.providers.zai.baseUrl = "https://open.bigmodel.cn/api/coding/paas/v4"`):

```
as shipped (hosts ["api.z.ai"])   -> false
with hosts + "open.bigmodel.cn"   -> true
```

The same install shows this is an eligibility problem rather than missing catalog data: the identical onboarding path (`openclaw onboard --auth-choice zai-coding-cn`) writes all six catalog rows when `models.mode` is `replace`, and `[]` in the default `merge` mode.

```
merge (default):  models.providers.zai.models = []
replace:          models.providers.zai.models = [glm-5.3, glm-5.3-flash, glm-5.2, glm-5-turbo, glm-5v-turbo, glm-5.1]
```

End-to-end check with the plugin installed from a local build, in an isolated HOME, identical China config (`baseUrl = https://open.bigmodel.cn/api/coding/paas/v4`, `models: []`). Only the declared hosts differ between the two runs:

```
stock plugin (hosts ["api.z.ai"])        -> 0 rows
patched plugin (hosts + bigmodel.cn)     -> 6 rows: glm-5.3, glm-5.3-flash, glm-5.2, glm-5-turbo, glm-5v-turbo, glm-5.1
```

The same result holds in the default picker view and with a running gateway plus `models list --all --refresh`.

`extensions/zai/onboard.test.ts` gains a regression test: every endpoint the onboarding can select (`ZAI_GLOBAL_BASE_URL`, `ZAI_CODING_GLOBAL_BASE_URL`, `ZAI_CN_BASE_URL`, `ZAI_CODING_CN_BASE_URL`) must stay declared in `providerEndpoints`. It fails against the unpatched manifest (missing `open.bigmodel.cn`) and passes with this change, so a future onboarding endpoint cannot be added without its declaration.

After the edit, the two `providerEndpoints` structures compared in `src/plugins/official-external-provider-endpoints.test.ts` are equal (verified directly against the edited file contents).

Environment: Debian 12 container, `openclaw 2026.9.4 (3a9d69d)`, `@openclaw/zai-provider@2026.9.4`, direct route to `open.bigmodel.cn`, no proxy or gateway in the path.

Not run locally: monorepo Vitest suite — no source checkout/pnpm install for this data-only change; CI covers it.
```
